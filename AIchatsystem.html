MODULE 01

Scope & Scale: agree on the game before playing it

requirements questions · in/out scope · 800M WAU → 1B design target

Every strong system design starts before the first box is drawn. The walkthrough opens with a volley of clarifying questions, because "design an AI chat system like ChatGPT" could mean a hundred different scopes. First: are we building the LLM itself, or integrating an existing one? Almost always integrating. Second: do responses stream word-by-word or arrive whole? We choose streaming — it's what every major product does, and it transforms perceived speed. Third: what scale? OpenAI's January 2026 announcement put ChatGPT at 700M weekly actives by July 2025, already past 800M today; we round to 1 billion for headroom and clean math, which collapses to ~200M daily actives, 2.5B prompts a day, and 20M concurrent conversations at peak (10% concurrency).

Then come the feature cuts: accounts and full conversation history — yes; shareable links and web publishing — no; English only; text only; tiered rate limits on both requests and tokens — yes; basic content moderation — required. Even the front end gets scoped by staring at the real UI: the input box and the history sidebar are in; projects, custom GPTs, code tools and image generation are out. Stating these trade-offs out loud — and being ready to defend pros and cons if the interviewer pushes back — is precisely the behavior that separates senior candidates from mid-level ones.

Step by step — opening an ambiguous design prompt

  1. Ask what you're building vs. integrating.Model training is out; LLM integration is in for nearly every interview and most startups.
  2. Set the UX contract.Streaming or wait-for-complete? Decide now — it reshapes the transport layer later.
  3. Pin the scale numbers.WAU → DAU → prompts/day → concurrency. Cite the source and round for headroom.
  4. Cut features explicitly.History yes, sharing no, text only, English only — and say why each cut is safe.
  5. Mirror the scope back.One paragraph the interviewer can veto. Silence means consent.

Three examples

Obvious

The streaming question, asked in minute two

"Do responses stream or arrive complete?" is a single question that restructures the entire transport and client design. The walkthrough answers it before any architecture exists — that ordering is the lesson.

Counter-intuitive

Cutting features makes the answer stronger

Declining shareable links, images and multilingual support isn't laziness — it buys depth on the core. Interviewers grade defended cuts, not feature counts; a shallow "everything" design loses to a deep scoped one.

Edge case

The interviewer forces image support anyway

Don't restart the design. Note it as an extension: uploads go to object storage, generation becomes an async job with a completion callback, and the chat core stays untouched. Scope pressure handled without panic.

Visual analogy

The concept

A scope board: two columns, decided in the first five minutes, referenced for the rest of the hour.

The analogy

A menu lists everything a kitchen can do; an order is what it will do tonight.

Scope questions turn the product's menu into your design's order ticket. Nobody grades the menu.
What People Get Wrong

Myth
"I should design everything the real product has — projects, GPTs, images — to show range."

Truth
Real products accreted features over years. A 60-minute design that covers everything covers nothing deeply. Seniors cut loudly and defend the cuts.

Why it happens
Range feels like competence. But depth on a bounded scope — with explicit trade-offs — is what staff-level interviews actually measure.

Why this matters: a design graded on scope discipline beats one graded on box count — in interviews and in production.

MODULE 02

Streaming UX: SSE beats WebSocket here — and it's not close

wait vs stream · WebSocket vs SSE · EventSource · stop/cancel semantics

There are two universes for delivering an LLM's answer, and the choice defines how the product feels. Option one: a plain HTTP POST that returns only when the full response exists. The user stares at a spinner for 10–30 seconds — longer with thinking models — and you can't even render an honest skeleton, because you don't know the shape of what's coming. It feels slow because it is slow to first paint. Option two: open a persistent connection and stream tokens the moment the model produces them. The first word appears almost immediately; the rest type themselves out while the user reads. Streaming doesn't make generation faster — it makes waiting invisible.

Perceived latency is dominated by time-to-first-byte of content, not total completion time. A response whose first token lands in 800ms but finishes in 20s reads as "instant and thorough"; a perfect answer that arrives whole after 20s reads as a hang. Streaming converts one long silence into continuous progress.

For the transport, the instinct is WebSocket — but WebSocket upgrades the protocol to full bidirectional communication, which is exactly what collaborative editors and typing indicators need, and exactly what token streaming doesn't. A user who sends a prompt and switches tabs still holds a live WebSocket open, burning server resources for silence. Server-Sent Events stay on plain HTTP: one-way server-to-client, a built-in EventSource API in every major browser, automatic reconnection, far less overhead, far easier debugging. That's why the major AI chat products standardized on it. While a stream is live, the send button is disabled and a Stop button lets the user cut the answer short and open a new query.

Step by step — one streamed answer

  1. User submits "explain react hooks".A POST opens the request; the response becomes a stream instead of a payload.
  2. First token arrives at the server."React" is pushed to the browser immediately — nothing waits for the full sentence.
  3. Tokens flow one by one."hooks", "are", "functions", "that"… each event appends to the visible bubble.
  4. Send is disabled; Stop is offered.The user can cancel mid-stream and start a fresh query.
  5. Completion signal.The stream closes, the full response is finalized, the send button re-enables.

Three examples

Obvious

ChatGPT's typing effect

The words appearing as if someone is typing them are SSE events being appended token by token — the exact mechanic this module teaches.

Counter-intuitive

Streaming changes nothing about generation speed

A 20-second answer still takes 20 seconds end to end. Streaming only moves the first word from second 20 to second 1. The win is perceptual — and perception is the product.

Edge case

Stop pressed at token 47

The client aborts the stream, the server stops generation, the partial answer can still be persisted, and the send button re-enables immediately. Cancellation is a first-class state, not an error.

Visual analogy

The concept — SSE

One-way token stream over ordinary HTTP. The client listens; the server talks.

The analogy — radio broadcast

You don't call the radio station back. One transmitter, many listeners, no return channel.

WebSocket is a phone call — perfect when both sides talk, wasteful when only one does. Token streaming is a broadcast.
What People Get Wrong

Myth
"Real-time means WebSocket, always. It's the modern choice."

Truth
Match the transport to the traffic shape. One-way streams over HTTP (SSE) give you auto-reconnect, simpler debugging and no idle-connection tax — which is why the major AI chat products actually ship it.

Why it happens
WebSocket is more famous, so it springs to mind first. Fame ≠ fit.

Why this matters: perceived speed is a product feature, and streaming is how you ship it.

MODULE 03

Requirements & Capacity: do the arithmetic before the architecture

functional + non-functional reqs · 70K msgs/s · 550 TB/yr · 6 Gbps

Functional requirements say what the system does; non-functional requirements say how well it must perform — and both must be committed to before any architecture. Functionally: users register and authenticate; they create and manage conversations; they send messages and receive streamed answers over SSE; every exchange — prompt and reply — is stored with full history and retrievable later in the sidebar; rate limits apply per tier on both requests and tokens; and basic content moderation screens harmful content.

Non-functionally we pin numbers we will later prove the design meets: 99.9% availability (≈43 minutes of downtime a month, ~500 a year), first token in under 2 seconds for mini models, zero message loss, end-to-end encryption for private conversations, cost efficiency, and scale to 200M daily actives. Then the arithmetic. 1B weekly actives ≈ 200M daily. 2.5B prompts a day ≈ 12–13 per user. With ~20% extra at peak, that's ~70,000 messages per second — doubled once you count the AI's replies being written too. Storage: a 100-byte prompt plus a 500-byte answer is 600 bytes per exchange; ×12.5 exchanges is 7.5KB per user per day; ×200M users is 1.5TB daily, ~550TB a year. Metadata is a rounding error — 1TB of profiles, 5TB of conversation headers. Twenty million connections lasting 10–30 seconds each, and ~750 bytes streamed per response over ~20 seconds, works out to ~750MB/s, or 6Gbps of sustained throughput. Conclusion: no single machine survives anywhere near this; distribution and multiple regions are mandatory.

The requirement ledger

  1. Functional — accounts & auth.Register, log in, per-user private storage.
  2. Functional — conversations & history.Create, list, load full message threads; prompts and replies both persisted.
  3. Functional — streaming + limits + moderation.SSE responses; two-axis rate limits by tier; safety screening.
  4. Non-functional — availability & latency.99.9% uptime; first token <2s for mini models (thinking models exempt).
  5. Non-functional — consistency, cost, security.Zero message loss; cost efficiency; E2E encryption for private chats.
  • 99.9% → ≤ ~43 min downtime/month, ~500 min/year — and each minute must later be budgeted against failover design.
  • <2s first token applies to mini models; thinking models legitimately need longer to reason.
  • Zero message loss → every write must be all-or-nothing (ACID), never partially persisted.
  • 20M concurrent conversations = 10% of DAU chatting at peak.
  • Cost efficiency is an NFR here, not an afterthought — Module 8 prices it.

Three examples

Obvious

The storage multiplication

7.5KB per user per day × 200M users = 1.5TB/day. Every storage decision in Module 6 inherits this number.

Counter-intuitive

Metadata is 1% of the problem

All the "scary" auxiliary data — 1B user profiles, every conversation header — totals ~6TB against ~550TB of chat content. Spend your design energy on the content.

Edge case

Thinking models break the latency NFR

A reasoning model can't emit a first token in under 2 seconds. That's exactly why the requirement is scoped to mini models — precise NFRs survive contact with reality.

🎯 Lock the numbers infill in the blank

At peak the system absorbs about msgs/s, stores ≈ TB/yr, and streams at ≈ Gbps.

Visual analogy

The concept

A capacity pipeline: each stage narrows raw user counts into infrastructure quantities.

The analogy

Count the boxes before renting the truck — not after the movers arrive.

Estimating messages, terabytes and gigabits before choosing servers is how you avoid paying for a moving convoy to ship three suitcases.
What People Get Wrong

Myth
"2.5 billion prompts a day means this is a write-heavy system."

Truth
Prompts are writes, yes — but each one triggers a pile of reads (account, quota, limits, history, memory). The system runs ~90% reads, 10% writes. Module 5 proves it.

Why it happens
The headline number (2.5B) is a write, so it anchors intuition. Ratios live one layer deeper.

Why this matters: estimates don't need to be exact — they need to be decision-sized, big enough to rule out single-server architectures.

MODULE 04

High-level architecture: three layers, seven services, one open connection

client / edge / service / data layers · LB vs gateway · multi-cloud · hotspots

The architecture settles into three layers. The client layer is web and mobile apps, and crucially it holds the long-lived SSE connections. The edge layer serves static assets from a CDN and fronts everything with a load balancer. The service layer begins at the API gateway — SSL termination and URL-path routing (/auth here, /messages there) — and behind it sits the cast: the message service, the orchestrator that shepherds a prompt through its whole journey and writes tokens back into the response stream; the auth service that validates JWTs; the rate limiter tracking request and token usage in Redis; a moderation service that screens the prompt; the conversation service owning all CRUD for chats and history; and an LLM gateway that routes requests to GPU clusters and handles model streaming, so the message service never talks to models directly.

Because they do different jobs at different layers. The load balancer is deliberately dumb: it spreads raw TCP/HTTP connections across gateway instances without understanding them. The gateway is smart: it terminates SSL, reads the URL path, and routes to the right service. Putting intelligence behind dumb distribution keeps each component replaceable and independently scalable.

The data layer holds a SQL primary with read replicas, the Redis cluster for limits, cold blob storage for the long tail of old conversations — a user with 1,000 chats only needs the recent 10–20 hot — and the GPU clusters themselves. And the streaming response rides the same open HTTP connection all the way back — message service → gateway → LB → browser — which is why every hop must keep the connection alive and unbuffered. Cloud-wise, the real-world pattern is multi-cloud with Azure as the lead (the Microsoft partnership), AWS second for GPU workloads, plus GCP and Oracle.

A prompt's path through the layers

  1. Client → edge.Static assets from CDN; the POST hits the load balancer, which picks a gateway instance.
  2. Gateway terminates and routes.SSL ends here; the URL path selects the message service.
  3. Message service orchestrates.Auth → rate limit → moderation → conversation context, in that order.
  4. LLM gateway generates.Prompt goes to a GPU cluster; tokens stream back to the message service.
  5. Tokens ride home.Each token is written into the open response stream: service → gateway → LB → browser.

Three examples

Obvious

Path-based routing 101

POST /auth/login → LB → gateway reads "/auth" → auth service. No service ever sees traffic that isn't addressed to it.

Counter-intuitive

The dumb box guards the smart box

Placing the "dumb" load balancer in front of the "smart" gateway is intentional layering, not redundancy — connection spreading and meaning-making are separate concerns.

Edge case

One buffering timeout kills the stream

SSE only works if every hop — LB, gateway, service — disables response buffering and raises idle timeouts. A single 60-second default somewhere silently murders long answers.

Visual analogy

The concept

The gateway reads the request path and walks it to the service that owns that job.

The analogy

A hotel concierge doesn't cook dinner or fix showers — they know exactly who does.

The front desk routes; the departments do. A gateway that tries to do the work itself has become a monolith with extra steps.
What People Get Wrong

Myth
"Load balancer and API gateway are the same box — pick one."

Truth
The LB spreads connections without understanding them; the gateway terminates SSL and routes by path with full application awareness. Both exist because the jobs are different.

Why it happens
Both sit "at the front," so they blur together. Ask what each one knows about the request and the blur disappears.

Why this matters: every component earns its place by owning one job; the moment a box does two jobs, the incident begins.

MODULE 05

The 90/10 rule: a "write monster" that's actually read-heavy

read vs write trace · schema · the three indexes that do the heavy lifting

Here's the number that rewires most engineers' intuition: a system absorbing 2.5B writes a day is still ~90% reads. Trace one prompt. It lands at the gateway and the message service, which immediately starts reading — the user's account and tier from the auth service, subscription quota and tokens consumed, the rate limiter's request and token counters, the moderation verdict, then the conversation service loading recent messages for context — or, even for a brand-new chat, the user's stored preferences and memory. Only after this pile of reads does the prompt reach the LLM gateway. When generation finishes, the SSE connection closes and exactly two writes land: the AI's message, plus an updated quota counter (the user's own message was written at the start). Reads: account, quota, limits, metadata, history, memory, feature flags. Writes: two, maybe three.

Because reads and writes scale differently. Reads scale almost freely — add another replica and another slice of traffic disappears. Writes on a strongly-consistent relational system all funnel through one primary. A 90/10 system therefore scales by replicating the cheap side, which is precisely why an unsharded primary can survive 800M weekly users.

That asymmetry is the whole ballgame, because reads scale trivially by adding replicas while writes all funnel into one primary. The schema mirrors the product's natural hierarchy: users (email, password hash, tier) own conversations (AI-generated title, pinned/archived flags, timestamps) which own messages (role — user or assistant — content, token count, created_at). Three indexes do the heavy lifting: users(email) for login lookups; conversations(user_id, created_at DESC) so the sidebar pulls just the 10–20 newest of a thousand chats in one seek; messages(conversation_id, created_at ASC) so a conversation's messages load in perfect order. Storing token_count per message looks optional today and pays off the moment you need billing or per-message usage views.

One prompt, counted honestly

  • 01POST /conversations/:id/messages — user prompt writtenW
  • 02Auth: account, tier, subscription quota, tokens consumed — four reads before a single GPU spinsR ×4
  • 03Rate limiter: request counter + token counter vs tier limitsR ×2
  • 04Moderation: rule check on the promptR
  • 05Conversation service: recent messages for context — or preferences/memory for a new chatR ×2
  • 06LLM gateway streams tokens back over SSE — no database involvement mid-stream—
  • 07Stream closes: AI response persisted, quota counter updatedW ×2

Three examples

Obvious

The sidebar loads 20 of 1,000 chats

(user_id, created_at DESC) turns "show my recent conversations" into a single index seek instead of a scan of a thousand rows.

Counter-intuitive

A brand-new chat still reads the database

No history to load? There's still the user's preferences and memory to fetch before the first token. "New chat" ≠ "no reads."

Edge case

token_count looks like clutter — until billing day

Per-message token counts seem bureaucratic right up until the moment an invoice, a usage dashboard or a Cursor-style cost view needs them. Cheap to write now, brutal to backfill later.

Visual analogy

The concept

One primary takes every write; any number of replicas serve the reads.

The analogy

One author writes every word once; readers everywhere hold printed copies.

Writes funnel to a single source of truth; reads scale by printing more copies. That's replication — and it's why 90/10 systems don't need sharding to survive.
What People Get Wrong

Myth
"Billions of writes a day means a write-heavy system that must be sharded."

Truth
Count operations, not headlines. Each prompt triggers ~8 reads and ~2–3 writes → ~90/10 read-heavy. Replicas absorb the reads; one primary comfortably absorbs the writes.

Why it happens
"2.5B prompts" is a write-shaped number, so people stop counting there.

Why this matters: design for the ratio you actually have, not the ratio you assume — 90/10 changes everything downstream.

MODULE 06

The database decision: why OpenAI didn't shard — and when you would

PostgreSQL vs MongoDB vs Neon vs sharding · the four-stage roadmap

Four candidates, one decision. MongoDB brings built-in sharding and schema flexibility, but its eventual-consistency default and weak multi-document transactions risk the unforgivable sin in chat — message five appearing before message four — and its query planner is decades behind SQL for joins. Sharded PostgreSQL dissolves the write bottleneck by hashing user_id across primaries, but OpenAI itself says it would touch hundreds of application endpoints, take months or years, add routing overhead to every query, and make distributed transactions routine. Neon, a serverless Postgres, keeps the exact single-primary-plus-replicas architecture but makes it managed: no replication, backup or failover plumbing; real Postgres semantics; autoscaling compute; storage that grows independently of compute; and instant branches — git for your database, with TTL branches that self-destruct after the test. Its honest cons: scale-to-zero is meaningless at 200M DAU, a learning curve (compute–storage separation, branch lifecycles), and today's compute ceiling (~56 vCPUs / 224GB RAM vs Azure's 128 / 512 — though ceilings move).

Because a risky migration against production data is the scariest operation in backend engineering. With branches, you copy the entire production database in seconds, run the migration on the copy, verify, then merge — and a TTL branch can expire itself after 24 hours so nobody pays for forgotten staging environments. Traditional Postgres staging copies can take ~20 minutes and live forever.

And then the actual OpenAI answer: one unsharded PostgreSQL primary with read replicas — around 50 of them. It works because ACID gives zero message loss, strong consistency guarantees ordering, the relational model fits users→conversations→messages perfectly, and the 90% read load scales by adding replicas. The write bottleneck (~30K writes/s) is real but deferred: offload write-heavy workloads to something like Cosmos DB and keep a dedicated team tuning the primary — timeouts, indexes, write batching. The staged playbook: 0–5M DAU start on Neon and ship 10× faster; 5–100M stay put and offload write-heavy paths; 100–200M either go self-managed with 20–50 replicas or stay until you hit the compute ceiling; beyond 200M sharding finally enters the chat — though OpenAI at 800M weekly users still hasn't needed it. The meta-lesson: don't over-engineer early.

The four options, weighed

  1. PostgreSQL, single primary + replicas (OpenAI's choice).ACID, ordering, proven at 200M DAU in production; writes bottleneck at ~30K/s → offload to Cosmos DB, dedicate a team.
  2. MongoDB.Sharding and flexibility for free — paid for in eventual consistency, painful multi-doc transactions, and out-of-order message risk.
  3. Neon serverless Postgres.Same architecture, fully managed, autoscaling, branching; ceilings and learning curve are the trade.
  4. Sharded PostgreSQL.Right tool — wrong decade of your company. Hundreds of endpoint changes, per-query routing, distributed transactions.

Three examples

Obvious

Three engineers, zero users → Neon

Managed infrastructure, instant branches, scale-to-zero. The team ships product instead of configuring replication and backup schedules.

Counter-intuitive

The "obviously scalable" answer is the one OpenAI refused

Sharding sounds like the senior answer in the abstract. At 800M weekly users, the team that would know best calls it months-to-years of endpoint surgery they'd rather not perform.

Edge case

When sharding IS right

A telemetry ingest system where writes equal or exceed reads? There, a single primary drowns and sharding is the correct first choice. The rule depends on the read/write ratio, not on company size.

Visual analogy

The concept

A staged roadmap: the right database for the traffic you have, with a clear trigger for the next step.

The analogy

You buy shoes for today's feet with room to grow — not adult boots for a toddler.

Neon at zero users, replicas at millions, sharding only when the writes truly demand it. Oversized infrastructure chafes exactly like oversized shoes.
What People Get Wrong

Myth
"MongoDB is the default for chat-scale systems — it was literally built for web scale."

Truth
Chat has two properties MongoDB handles poorly: strict message ordering and multi-row consistency. SQL's ACID gives both for free, and its read scaling (replicas) matches the 90/10 profile.

Why it happens
"Web scale" marketing from a decade ago outlived the trade-off analysis. Scale alone never picks a database; access patterns do.

Why this matters: the best database decision is often the one you don't make yet.

MODULE 07

API design & two-axis rate limiting: where subscriptions go to die

REST endpoints · SSE event shape · EventSource client · requests + tokens

The API stays deliberately boring REST — nothing here demands GraphQL. Auth exposes POST /auth/register and POST /auth/login (email/password or a Google-style provider) returning a JWT plus tier, and a logout route. The conversation service fronts GET /conversations — the sidebar list of titles, previews and timestamps — GET /conversations/:id with the full message array (role plus content), POST to create, DELETE to remove. Those two GETs are the physical embodiment of the 90% read stat. Messaging lives at POST /conversations/:id/messages: the request carries the prompt, the response becomes an SSE stream, and events arrive token by token — "React", "hooks", "are" — until the completion signal. On the client, the native EventSource API (or the eventsource library) attaches a listener that appends each token to the bubble; the send button stays disabled until the stream completes or the user hits Stop.

Rate limiting is where naïve designs leak money, so we limit on two axes. A single request can carry a pasted codebase — one request, tens of thousands of tokens, enormous compute — and a request-only limit waves it through while your $20-per-user subscription burns. Conversely, a bot firing 100 tiny "explain react hooks" prompts costs little per token but hammers the system, which only a request limit catches. So tiers get both dials: free might be 25 requests and 50,000 tokens a day; paid $20 around 500 requests and 2M tokens — whichever exhausts first triggers the "come back after the reset, or upgrade" message, exactly the pattern Claude's Free / Pro / Max ladder uses (heavy Max users can run $200–300). Implementation is a checkRateLimit(userId, tier) call: build a request key and a token key, read both counters from Redis, compare against the tier's limits, and gate the prompt.

Because limit checks sit on the hot path of every single request — 70K/s at peak. Counters need sub-millisecond reads, atomic increments, and natural expiry (TTLs reset daily quotas for free). A relational row update per request would add latency and write load to the very primary you're trying to protect.

The endpoint surface

  1. Auth.POST /auth/register, POST /auth/login → JWT + tier · logout.
  2. Conversations.GET /conversations (sidebar) · GET /conversations/:id (full thread) · POST · DELETE.
  3. Messaging.POST /conversations/:id/messages → response upgrades to an SSE stream.
  4. Stream events.event: token with each fragment, then a completion event; client appends and re-enables send.
  5. Limits.checkRateLimit(userId, tier) against Redis counters before the LLM is ever invoked.

Three examples

Obvious

Message #26 on the free tier

The request counter trips at 25/day. The user gets a clear message: resets tomorrow, or upgrade. Simple, predictable, enforceable.

Counter-intuitive

One message can out-cost a hundred

A single prompt with a 40K-token codebase is one request — invisible to a request limit — yet incinerates the token budget and the GPU time behind it. The token axis is the one that protects the business.

Edge case

Tokens gone at 3 p.m.

The correct UX isn't a bare 429: tell the user exactly when the quota resets ("back in 9 hours") and offer the upgrade path. Limit enforcement is a retention surface, not just a guardrail.

Visual analogy

The concept

Two independent budgets per tier; exhaustion of either one pauses the user.

The analogy

A buffet limits both how many trips you make and how much you carry per trip.

One trip with a tower of plates costs the kitchen more than ten modest trips. Two axes catch two different kinds of appetite.
What People Get Wrong

Myth
"A request rate limit is enough — one request, one unit of cost."

Truth
LLM cost scales with tokens, not requests. One prompt can carry a whole codebase. Limit requests to stop spam; limit tokens to stop bankruptcy.

Why it happens
Traditional APIs really do cost roughly the same per request. LLM APIs broke that assumption.

Why this matters: one unbounded axis is enough to bankrupt a subscription business.

MODULE 08

The $58M/month machine: costs, availability, and closing the NFR loop

GPU economics · 6 regions · 99.9% · scaling to 1B WAU

Time to price the machine. If you're a wrapper startup calling an LLM API at this volume, the bill is brutal — roughly $5M a day for mini models — which is precisely why OpenAI and friends run their own GPU clusters: you pay for compute per token instead of API markup. The monthly stack at 200M DAU: GPU infrastructure dominates at ~$52M (with smart batching improving utilization). API servers come next — 20M concurrent sessions ÷ 2,500 per server = 8,000 machines, spread across six regions at ~1,300 each, ≈ $4.6M. Bandwidth, the 6Gbps we computed in Module 3, ≈ $1M. Monitoring and logging $150K; the entire PostgreSQL estate — one primary, 20+ replicas, ~600TB — just $138K; Redis $130K; load balancers and CDN $75K each; moderation $15K. Total ≈ $58M a month, and the database everyone debates is 0.2% of it.

API pricing bundles the provider's margin, redundancy and demand-smoothing into every token. At 2.5B prompts a day you are the demand. Owning the clusters means each token costs raw compute — and techniques like smart batching (packing many users' prompts onto one GPU pass) push utilization up and per-token cost down. The fixed cost is enormous; the marginal cost collapses.

Finally, close the loop on the non-functional requirements, because interviews and production reviews both demand you trace each number back to a decision. 99.9% availability comes from six regions, read replicas and failover — with a 43-minute monthly budget. Sub-2-second first tokens come from streaming plus regionally-placed GPU capacity and mini-model routing. Zero message loss comes from ACID writes committed after generation completes. Cost efficiency comes from owned GPUs, cold storage tiering and scale-to-zero where traffic allows. Security comes from end-to-end encryption of private conversations. And scaling to 1B weekly users — the rounding we did back in Module 3 — is mostly adding replicas, regions and offloaded write paths while the single primary holds the line. That's the whole craft: every requirement has an owner, and every component can explain why it exists.

Closing the loop — NFR → decision

FAQ

Why not WebSocket if it's "more modern"?
Because modernity isn't a requirement — fit is. Token streaming is strictly one-way: server talks, browser listens. SSE delivers that over plain HTTP with a built-in browser API, automatic reconnection and trivial debugging, while WebSocket adds a protocol upgrade, bidirectional machinery you'll never use, and idle connections that linger when users tab away. Every major AI chat product landed on SSE for exactly this reason.
How does OpenAI get away without sharding at 800M weekly users?
Three reasons stack up. First, the workload is ~90% reads, and reads scale almost freely with replicas — they run around 50. Second, ~30K writes per second, while large, fits a single beefy primary (Azure-class: up to 128 vCPUs / 512GB RAM) with careful tuning: timeouts, index management, write batching. Third, genuinely write-heavy operations were offloaded to Cosmos DB rather than forced through the primary. Sharding would "work" too — at the price of rewriting hundreds of endpoints, which they've publicly said they'd rather not do.
What if my interviewer insists I design sharding anyway?
Give them the trade-off, not the surrender: sharding earns its complexity when writes rival or exceed reads, or when a single primary demonstrably saturates. Show the shard key choice (hash user_id → each shard owns a user range), mention resharding and cross-shard transaction pain, then cite the counterexample — the company with the most incentive to shard hasn't needed to at 800M WAU. That answer reads as senior judgment, not resistance.
Is 550TB/year supposed to be precise?
No — it's decision-sized. Within a factor of two it still yields the same conclusions: you need distributed storage, a cold tier for the long tail, and a replication strategy; a single instance is off the table. Interviewers grade the reasoning chain (assumptions stated → arithmetic shown → decision follows), not the fourth significant digit.
Why store token_count per message?
Because three future features depend on it and all are expensive to backfill: per-user billing and invoices, usage dashboards (the Cursor-style "this message cost N tokens" view), and per-tier analytics. One integer column written at insert time buys all of them.
Where does the "complete" signal come from?
The LLM gateway emits a completion event when the model finishes generating. The message service then closes the SSE stream, persists the full response as one ACID write, updates the token quota in Redis, and the client re-enables the send button. Nothing is marked complete until the write lands — that's the zero-message-loss contract in action.
