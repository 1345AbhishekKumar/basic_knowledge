    AI Engineering, end to end.

    AI engineering is the discipline of building applications on top of foundation models — adapting, evaluating, and serving models you didn't train. This lesson walks the full stack: how models actually work, how you measure them, how you choose and adapt them, and how you keep them fast, safe, and learning from users.

    What you'll learn

    • Why foundation models only know their training data, and how attention (Q·K·V) lets Transformers read "any page of the book".
    • How SFT and RLHF turn an autocomplete engine into an assistant — and how temperature, top-k, and top-p reshape its voice.
    • Why evaluation is the hardest engineering problem here: perplexity, similarity metrics, AI judges and their biases.
    • How to select models on a cost–performance axis, and when to prompt, retrieve, or fine-tune.
    • Context engineering: prompt structure, RAG pipelines, and the agentic pattern with tools, planning, and memory.
    • Fine-tuning that fits in memory (LoRA, quantization), data-centric quality, and the inference stack: TTFT, TPOT, batching, caching.
    • How mature architectures evolve — guardrails, routing, observability — and why user feedback is your only real moat.

    Module 01

    Foundation Models & the Attention Engine

    AI engineering exists because of a perfect storm: models got dramatically better at solving real problems while the barrier to building with them collapsed. Unlike traditional machine-learning engineers who train models from scratch, AI engineers build applications on top of foundation models — massive systems trained by companies like OpenAI or Google — focusing on adaptation rather than training.

    The breakthrough that made this possible is self-supervision. Instead of humans labeling millions of examples, the model learns by predicting parts of its own input: show it "the cat sat on the ___" and it learns to predict "mat". That solved the data-labeling bottleneck that had held AI back for years — and once you can learn from raw text, you can learn from essentially the entire internet. Scale that up and a language model becomes a large language model; add images, video, and audio and it becomes a large multimodal model.

    But here's the catch every AI engineer must internalize: a model can only know what it was trained on. Training data is web-crawled, which means clickbait, misinformation, and toxic content sneak in — teams fight back with filtering; OpenAI famously kept only Reddit links with at least three upvotes when training GPT-2. Roughly half of all crawled data is English, so languages with millions of speakers are underrepresented, and the domain mix skews toward business, tech, news, and art.

    Architecturally, nearly all foundation models are Transformers, invented to fix two fatal flaws of older sequence-to-sequence models: a decoder that only saw a compressed summary of the input (imagine answering detailed questions about a book from a one-paragraph synopsis), and token-by-token sequential processing that was painfully slow. Transformers introduced attention — the ability to weigh the importance of every input token when producing each output token, like being able to flip to any page of the book — plus parallel processing of the input.

    Attention stores a key and a value vector for every token in context, and every new token must compare against all of them. Double the context and you roughly double the K/V storage and comparison work — which is why long context windows are computationally expensive, and why so much of the capstone is about shaving that cost.

    How a Transformer generates, step by step

    1. Tokens are converted into vectors by an embedding module, which also encodes position.
    2. Pre-fill: all input tokens are processed in parallel, building the intermediate state.
    3. Inside each attention module, the current token's query is compared against every key to compute similarity scores.
    4. Those scores weight the value vectors — a high score means that token's content heavily influences the output.
    5. The weighted result passes through a feed-forward network; steps 3–5 repeat across all blocks (the "layers").
    6. An unembedding layer maps the final vectors to a probability for every token in the vocabulary.
    7. Decode: one token is sampled, appended to the input, and the loop repeats.

    Three examples

    Obvious

    GitHub Copilot-style coding help. The model predicts the next tokens given your code as context; attention focuses on the relevant function definitions above your cursor. It's self-supervised next-token prediction, productized.

    Counter-intuitive

    Data curation beats raw volume. OpenAI filtered Reddit links to those with ≥3 upvotes for GPT-2, and roughly half the crawled web is English. A "smarter" model trained on worse data loses — quality filtering is a model-quality decision, not a janitorial one.

    Edge case

    RWKV and sparse models. RWKV blends RNN-style recurrence with Transformer-style parallelism, proving attention isn't the only game in town. And a huge sparse model (mostly zero parameters) can need less compute than a smaller dense one — parameter counts alone mislead.

    The concept — attention

    Every token can flip back to any page of the input and weigh it while writing each new token.

    The analogy — seq2seq before attention

    Older models squeezed the whole book into a single index card, then answered from memory alone.

    The bridge: answering detailed questions from a one-page summary is exactly the failure mode attention fixed. An open-book exam isn't easier because the student is smarter — it's easier because any page is reachable at any moment. That reachability, per token, is attention.

    ❌ What people get wrong

    Myth — "Bigger model = always better."

    Truth — The Chinchilla scaling law says training tokens should be roughly 20× the parameter count: a 3B-parameter model needs about 60B training tokens. An undertrained giant loses to a well-trained smaller model, and sparse models make raw parameter counts misleading.

    Why — Compute is the limiting factor. Capacity without matching data never crystallizes into knowledge, and every extra parameter still costs you at inference time.

    Why this matters: every headache you'll meet later — hallucinations, context costs, weak minority-language performance — traces back to what these models were fed and how attention makes them read.

    Module 02

    Post-Training & the Probability of Words

    A freshly pre-trained model is a savant with no social skills: it's optimized for text completion, not conversation, and it will happily continue your question with more questions — or complete your sentence with confident nonsense. Post-training is the two-step process that turns raw capability into an assistant.

    First, supervised fine-tuning (SFT): you show the model thousands of high-quality instruction-and-response pairs — "here's a request, here's what a good response looks like" — and it learns the shape of helpful conversation. Second, preference fine-tuning: because humans agree on which of two responses is better far more easily than they can write perfect responses, you train a reward model to score outputs the way humans would, then optimize the base model to maximize those scores. The classic recipe is RLHF (reinforcement learning from human feedback); newer approaches like DPO (direct preference optimization) skip the separate reward model, and some companies skip reinforcement learning entirely — generating N candidates and simply picking the highest-scoring one, a strategy called best-of-N.

    Then comes generation, and here's the key idea: the model never gives you "the answer". It produces a probability distribution over every possible next token, and how you sample from it dramatically changes what users experience. Greedy sampling — always taking the most likely token — is deterministic but drifts into repetitive loops. Temperature reshapes the distribution: high values (0.7–1.0) flatten it for creative, surprising output; values near zero sharpen it for focused, repeatable answers. Top-k restricts sampling to the k most likely tokens (typically 50–500); top-p restricts it to the smallest set whose probabilities add up to a threshold like 0.9. This inherent randomness explains two behaviors that confuse almost everyone: small input changes producing inconsistent outputs, and hallucinations — the model stating incorrect information with total confidence.

    Temperature divides every logit by T before the softmax. Divide by a big number and the differences between tokens shrink, so the distribution flattens and "unlikely" words get a real chance. Divide by a tiny number and the differences are amplified until one token dominates. Nothing about the model's knowledge changed — only the shape of the dice roll did.

    The pipeline, step by step

    1. Pre-train a base model on raw text (objective: predict the next token).
    2. Curate high-quality instruction–response pairs.
    3. Run SFT so the model learns conversation shape.
    4. Collect human preference rankings ("response A beats response B").
    5. Train a reward model on those rankings.
    6. Optimize with RLHF / DPO — or use best-of-N at inference time.
    7. Choose a sampling strategy per feature: temperature, top-k, top-p.

    Three examples

    Obvious

    A customer-support chatbot at temperature ≈ 0. Same question, same answer, every time — auditable, consistent, boring in exactly the way you want.

    Counter-intuitive

    Better assistants can be worse predictors. After heavy SFT/RLHF, a model's perplexity on raw web text can rise even as it gets more useful — alignment reshapes the distribution away from statistical web-ness. Perplexity is a training proxy, not a quality verdict.

    Edge case

    Best-of-N without any RL. Some companies never run reinforcement learning: they generate N candidate responses and let a reward model pick the winner — trading inference compute for alignment quality.

    The concept — a distribution over words

    Every candidate word carries a probability; generation is a weighted dice roll, not a lookup.

    The analogy — a creativity dial

    Temperature is the dial: same musician, same knowledge — how far outside the melody they dare to play.

    The bridge: SFT teaches the song's structure; the reward model is the bandleader's taste; temperature decides how adventurous tonight's solo is. None of them change what the musician knows — they change what gets expressed.

    ❌ What people get wrong

    Myth — "Hallucinations mean the model is broken or lying."

    Truth — The model samples from a distribution learned from web data; confidence is a probability, not a verification. A hallucination is a high-probability sentence that happens to be false.

    Why — Nothing in the training objective rewards "being right when unsure". Which is why Module 3 (evaluation) and Module 5 (RAG) exist — you engineer truthfulness; you don't get it for free.

    Why this matters: the same weights can sound like an oracle or a slot machine depending on one slider — sampling strategy is a product decision, not a footnote.

    Module 03

    Evaluation — the Hardest Engineering Problem

    Here's an uncomfortable truth: for some AI applications, figuring out how to evaluate the system consumes more effort than building it. Evaluation is how you mitigate risk, uncover opportunities, and see where your system is actually failing — and it's dramatically harder than evaluating traditional ML for five reasons. The problems are complex (judging a book summary may require reading the book). Tasks are open-ended — "write me a poem about resilience" has countless valid answers. Foundation models are black boxes; you can observe outputs, never internals. Public benchmarks saturate: yesterday's hard test becomes today's perfect score. And for general-purpose models you must discover capabilities nobody thought to test. All of it is worsened by chronic underinvestment in evaluation relative to model development.

    Start with the training signals. Cross-entropy measures how surprised the model is by each token; a perfect model would achieve cross-entropy equal to the entropy of the data itself, with KL divergence of zero. Perplexity — the exponential of cross-entropy — measures next-token uncertainty, and behaves intuitively: structured data lowers it, bigger vocabularies raise it, longer context lowers it. But it's a proxy, not a verdict: after heavy post-training it can rise even as the model gets more useful. It doubles as a forensics tool — suspiciously low perplexity on evaluation data hints the model trained on it, while absurdly high perplexity flags nonsense text.

    For real tasks, prefer functional correctness where you can get it: did the system book the right reservation? Does the code run and pass tests? When reference answers exist, compare with exact match (binary, for definitive questions), lexical similarity (token overlap via edit distance or BLEU/ROUGE — brittle, since one idea has many phrasings), or semantic similarity (embedding cosine — reference-free, but only as good as your embedder). In production, the workhorse is the AI judge: a model that scores other models' outputs. Judges are fast, cheap, work without references, and correlate with human ratings — sometimes more strongly than humans agree with each other. But they're probabilistic, non-standardized, and biased: self-bias (favoring their own outputs), position bias (favoring the first answer), verbosity bias (favoring longer answers). Mitigate with randomized order, classification over numeric scoring, and few-shot rubrics — and remember a smaller model can often judge just fine.

    Building an evaluation pipeline

    1. Define criteria and tie each to a business metric (80% factual consistency → 30% of tickets automated; 90% → 50%).
    2. Pick a method per criterion — mix and match: a cheap classifier on 100% of traffic plus an AI judge on 1% for high-quality signal.
    3. Write an unambiguous rubric with worked examples, so any evaluator scores the same way.
    4. Evaluate slices, not just aggregates — a model can be better overall yet worse on every segment (Simpson's paradox).
    5. Bootstrap multiple samples of your eval set; if scores swing wildly, the pipeline isn't trustworthy.
    6. Validate the pipeline itself: right signals? reproducible? correlated metrics? what cost and latency does it add?

    Three examples

    Obvious

    Multiple-choice benchmarks with exact match. One definitive answer, binary scoring, zero ambiguity — the easy case that made early leaderboards possible.

    Counter-intuitive

    AI judges can out-agree humans. Studies show model judges sometimes correlate with human ratings more strongly than human annotators agree with each other — and they can explain their decisions, which most humans won't do for free.

    Edge case

    Perplexity as a contamination detector. If a model's perplexity on your test set is suspiciously low, it may have memorized those exact tokens during training — your "evaluation" is actually a recitation.

    The concept — exact & lexical metrics

    A health inspector's checklist: binary, repeatable, and blind to whether the meal was actually delightful.

    The analogy — AI judges

    A restaurant critic: nuanced, fast, opinionated — occasionally biased toward their own kitchen.

    The bridge: checklists (exact match, BLEU) are rigorous but can't taste; critics (AI judges) can taste but need their biases managed. Real evaluation systems employ both, plus the ultimate question — did the customer actually get fed? (functional correctness).

    ❌ What people get wrong

    Myth — "One good metric — or a leaderboard rank — tells you the whole story."

    Truth — Benchmarks saturate and get contaminated; aggregate scores hide per-segment failures (Simpson's paradox); and metrics only matter when tied to business outcomes — e.g., a usefulness threshold like "90% factual consistency before production".

    Why — A metric is a proxy for a goal. Optimize the proxy hard enough and it stops being a proxy — which is why the pipeline itself must be evaluated, repeatedly.

    Why this matters: without trustworthy evaluation, every other decision in this lesson — model choice, prompts, fine-tuning — is a coin flip you can't even see land.

    Module 04

    Model Selection & the Adaptation Ladder

    With new foundation models arriving weekly, the hard problem is no longer developing models — it's selecting the right one, and you'll do it repeatedly as your application matures. The process has two steps: first, find the best achievable performance on your task; second, map candidate models along a cost–performance axis and pick the one that delivers what you need within budget.

    Organize criteria into four buckets: domain-specific capability (does it understand legal terminology?), general capability (coherence, faithfulness, factual consistency), instruction following (does it respect your requested format?), and cost & latency. Then split attributes into hard and soft. Hard attributes — license, training-data composition, model size, privacy requirements, needed control — are essentially impossible to change, so filter on them first; they often eliminate most candidates immediately. Soft attributes — accuracy, toxicity, factual consistency — can be improved through adaptation, which is the rest of this lesson.

    A recurring fork: commercial API or self-hosted open weights? (Terminology matters: most "open source" models are actually open-weight — the training data stays closed. Truly open models publish both.) Providers typically open-source their weaker models and keep the strongest behind paywalls. APIs hand you scalability, function calling, structured outputs, and guardrails out of the box, but restrict fine-tuning and log-probability access, and expose you to pricing changes, outages, and terms-of-service shifts. Self-hosting solves data privacy, on-device needs, and control — at the cost of infrastructure. Either way, hide models behind your own internal standard API so swapping is a config change, not a rewrite.

    Public benchmarks and evaluation harnesses (tools that run many benchmarks, like OpenAI Evals) narrow your shortlist — but beware data contamination, detectable via n-gram overlap and perplexity heuristics — then run your own experiments, monitor in production, and treat selection as continuous. Finally, climb the adaptation ladder in order: extract everything you can from prompt engineering; if failures are information-based, add RAG; if they're behavior-based, fine-tune; if both, start with RAG because it's easier, then combine. Many teams skip straight to fine-tuning and pay for it.

    The selection workflow

    1. Filter out models whose hard attributes disqualify them (license, privacy, size, control).
    2. Shortlist with public benchmarks — mind aggregation weights and contamination.
    3. Run your own evaluation pipeline on your task and slices.
    4. Map survivors on the cost–performance frontier; choose for your budget.
    5. Monitor in production; re-select as models, prices, and needs change.

    Three examples

    Obvious

    Start strong, work backwards. Prototype with the most capable model to prove the task is feasible, then step down to cheaper models until quality breaks. You've now mapped your own frontier.

    Counter-intuitive

    "Open source" usually isn't. Most released models are open-weight only — training data stays closed — and providers deliberately open-source their weaker models while the strongest remain behind paywalls. Read the license; it may restrict commercial use or training other models on the outputs.

    Edge case

    The one-line provider swap. If every model call flows through your own internal standard API, a provider going bankrupt, changing terms, or getting banned in your region is a configuration change. It's also the only sane way to mix self-hosted and commercial models.

    The concept — commercial model APIs

    A rental: keys in hand in minutes, maintenance included — but mileage fees add up and you never own it.

    The analogy — self-hosted open weights

    Buying: full control, no per-mile charges — but the garage, insurance, and repairs are your problem now.

    The bridge: neither is inherently better — privacy laws, control needs, and scale decide. And whether you rent or buy, keep your own set of keys (the internal standard API) so you can change vehicles without moving house.

    ❌ What people get wrong

    Myth — "We should fine-tune from day one."

    Truth — Fine-tuning demands serious upfront investment (often more memory than a single GPU holds), can degrade other capabilities, and usually follows cheaper wins. Distillation — training a small model on a big model's outputs — often captures most of the quality at a fraction of the cost.

    Why — Teams jump to fine-tuning because it feels like "real engineering", while prompting feels trivial. The book's ladder exists precisely to stop you paying for weights changes that a better prompt would have delivered free.

    Why this matters: the right model at the wrong price kills products; the wrong model at any price kills trust.

    Module 05

    Context Engineering — Prompts, RAG & Agents

    To solve a task, a model needs two things: instructions on how to do it, and the information to do it with. Prompt engineering shapes the instructions; RAG and agents supply the information — and the ability to act.

    Prompt engineering means crafting inputs to guide outputs without touching weights — the cheapest adaptation technique, and deceptively deep. A prompt combines a task description (role and format: "you are a medical assistant; list conditions by likelihood"), examples (each one a "shot" — zero-shot, one-shot, few-shot), and the concrete task. System prompts carry standing instructions; user prompts carry the query; and the two are stitched together by a chat template that varies between models — get it wrong, even by one stray newline, and you'll suffer silent performance failures. Instructions land best at the beginning or end of a prompt, and the preferred position differs by model: GPT-4 likes instructions first, Llama 3 last. The core strategies: write clear, explicit instructions; adopt a persona; provide examples (a whimsical Tooth Fairy example drags the Santa answer from dry to playful); specify output format ("no preamble", JSON); decompose complex tasks into subtasks you can monitor, parallelize, and route to cheaper models; and give the model time to think — chain-of-thought, process instructions, self-critique — buying quality with latency and tokens. Above all, iterate like a scientist: version your prompts, track experiments, keep prompts out of code.

    Once your app faces users, expect prompt attacks: extraction (stealing your system prompt), jailbreaking and injection (subverting safety or hijacking actions), and information extraction. Defend in layers — red-team, repeat the system prompt around user input, sandbox generated code, require human approval for impactful actions, run input and output guardrails — and track violation rate against false-refusal rate, because perfect security with constant refusals is its own failure mode.

    Retrieval-augmented generation (RAG) gives the model memory it wasn't trained on: a retriever fetches relevant chunks from external sources — term-based like TF-IDF (fast, works with existing search stacks, but keyword-blind to meaning), embedding-based (semantic, but weaker on exact names and error codes, and embeddings cost latency), or hybrid, which is what production systems do — and the generator writes from the assembled context. Chunk size, overlap, reranking, and query rewriting ("what's its population?" → "what's the population of Paris?") all move quality, and there's no universal best — you experiment. RAG isn't text-only either: a multimodal system asked "what color is the house in Pixar's Up?" retrieves an image first; and text-to-SQL over a database is already a simple agent.

    The agentic pattern goes further: the model perceives, plans, validates, and acts through tools — knowledge tools (search, SQL, retrievers), capability tools (calculators, code interpreters), and write tools that change the world and demand serious safeguards. Keep planning decoupled from execution — generate a plan, validate it (heuristics, an AI judge, or a human), then run it — because errors compound across steps. And split memory three ways: training (always-needed knowledge), the context window (this session), and external storage (long-term).

    Building a context pipeline

    1. Write the system prompt: role, constraints, output format.
    2. Add few-shot examples; match the model's chat template exactly.
    3. If information is missing → index and chunk the knowledge base; retrieve, rerank, assemble.
    4. If action is needed → define tools, generate a plan, validate it, execute, observe the result.
    5. Guard inputs and outputs; log violations and false refusals.
    6. Store what matters: session facts in context, durable facts externally.

    Three examples

    Obvious

    "You are a helpful medical assistant. Analyze these symptoms and list possible conditions in order of likelihood." One sentence doing double duty: persona (role) and output format (ordered list).

    Counter-intuitive

    Where you put instructions changes results — differently per model. GPT-4 performs better with the task at the beginning; Llama 3 does better with it at the end. And a mismatched chat template fails silently: no error, just quietly worse answers.

    Edge case

    Multimodal RAG. Ask "what color is the house in Pixar's Up?" and a multimodal system retrieves an image of the house before answering. Retrieval isn't a text technology — it's a context technology.

    The concept — RAG

    A reference librarian: doesn't memorize the library — knows exactly which shelf to walk to.

    The analogy — agents

    An intern with a toolbox and a walkie-talkie: can fetch, calculate, and deliver — but checks before doing anything irreversible.

    The bridge: the librarian fetches information (retrieval); the intern changes the world (actions). Both need good instructions — and the more the intern can do, the more important the "asks first" rule becomes (plan validation, human approval, sandboxing).

    ❌ What people get wrong

    Myth — "RAG eliminates hallucinations."

    Truth — Retrieval can miss, chunks can lose context, and the generator can ignore what it retrieved. RAG dramatically reduces information-based failures — it doesn't remove the need for evaluation, guardrails, or citations.

    Why — RAG changes what the model sees, not what it is. And agents multiply the stakes: with write-access and multi-step plans, each step's small error rate compounds into real-world consequences.

    Why this matters: context is the cheapest lever you'll ever pull — the same model can fail or shine based purely on what you put in front of it.

    Module 06

    Fine-Tuning & Dataset Engineering

    When prompting and retrieval aren't enough, you change the weights — and the modern toolkit makes that far cheaper than it sounds. Fine-tuning helps in two ways: domain capability (medical, legal, code) and instruction following (consistent formats). Reach for it after you've exhausted prompt-based methods, when you need consistent structured output, or when a small fine-tuned model can replace an expensive large one — often via distillation, training the small model to imitate the large one's outputs. Avoid it for general-purpose needs (it can degrade other capabilities) and for first experiments.

    The bottleneck is memory. Training needs both forward and backward passes, so your footprint scales with total parameters, trainable parameters, and their numerical precision — a 13-billion-parameter model at 32-bit floats is 52 GB; halve the bits, halve the bill. Gradient checkpointing trades compute for memory by recomputing activations instead of storing them. Quantization shrinks precision — inference happily runs at 16, 8, even 4 bits, while training stays mixed-precision — and load models in their intended format: Llama 2's bf16 weights loaded as fp16 famously degraded. The star of parameter-efficient fine-tuning (PEFT) is LoRA: freeze the original weight matrix W, train two tiny matrices A and B whose product approximates the update, and merge them back at inference — zero added latency. PEFT is also sample-efficient: hundreds to thousands of examples where full fine-tuning wants millions. For multi-task needs, merge separately fine-tuned models (simple weight summing works surprisingly well; "Frankenmerging" stacks layers) rather than fighting catastrophic forgetting.

    But the deepest lesson of the book is data-centric AI: most companies can't build better models, yet nearly all can build better datasets — and that's the real moat. Quality means relevance, task alignment, consistency, correct formatting, uniqueness, compliance, and coverage; a small set of excellent examples beats a mountain of noise. Pilot with ~50 curated examples — if nothing improves, more data rarely will. When you need more, build a data flywheel from user interactions, augment real data (derived from it — like flipping an image), or synthesize it (created from scratch — which also helps privacy). Then process ruthlessly: dedupe, fact-check, resolve annotator disagreements, strip PII and HTML artifacts, and never modify data in place. Key hyperparameters: learning rate (fluctuating loss = too high), batch size (accumulate gradients if small batches wobble), epochs (4–10 for small datasets, 1–2 for millions), and prompt loss weight (~10% default — the model should mostly learn from responses, not prompts).

    A practical fine-tuning path

    1. Get your fine-tuning code running on the cheapest, fastest model you have.
    2. Validate your data on a mid-size model — training loss should fall as data grows; if not, something's wrong.
    3. Run experiments on your target model to see how far performance goes.
    4. Map the price–performance frontier and select deliberately.
    5. Distillation alternative: small dataset + strongest affordable model → fine-tune → let it generate more data → train a cheaper model on the expanded set.

    Three examples

    Obvious

    Match method to data budget. Full fine-tuning wants thousands to millions of examples; LoRA-style PEFT can work with hundreds. With 300 labeled examples, the choice makes itself.

    Counter-intuitive

    Data abundance erases model gaps. With ~100 examples, stronger base models fine-tune noticeably better. But after ~550,000 examples, all models converge — if you have oceans of data, a cheap model gets you there.

    Edge case

    Frankenmerging. Stacking layers from separately fine-tuned models can produce a merged model that beats both parents — no GPUs required, and unlike ensembling, no extra inference cost. Model merging is a free lunch worth trying.

    The concept — LoRA / PEFT

    Sticky notes on a textbook: the book stays intact; the notes carry your updates — and peel off cleanly.

    The analogy — full fine-tuning

    Rewriting the whole textbook by hand: maximum control, maximum effort — and every other class's notes get smudged.

    The bridge: PEFT updates a trainable sliver and leaves the "book" frozen, so one base model can carry many sticky-note adapters — one per task, language, or customer — served from a single set of weights.

    The data-processing checklist

    • Filter tasks and test scripts before big runs; keep originals — never modify data in place.
    • Run exploratory analysis on distributions and outliers; inspect inter-annotator disagreement.
    • Fact-check and manually inspect samples; guidelines must define what a "4 vs 3" response is.
    • Deduplicate to prevent over-representation of common patterns.
    • Clean formatting tokens (HTML, markdown) — improves performance and shrinks inputs.
    • Remove non-compliant data: PII, toxic material, copyrighted content.
    • Filter low-quality examples flagged during verification.
    • If data exceeds your compute budget, use active learning to keep the most helpful examples.
    • Confirm tokenizer and chat template match the target model exactly.

    ❌ What people get wrong

    Myth — "More data always fixes fine-tuning."

    Truth — If 50 curated examples show no improvement, scale rarely saves you. Fix data quality, hyperparameters, or task framing first. Garbage in, garbage out — and the hard part is writing annotation guidelines humans can actually follow consistently.

    Why — Human-generated data is error-prone and inconsistent on nuanced policies; even the Llama 3 team moved to AI-assisted annotation to hold quality. Measure your AI-generated data just like human data.

    Why this matters: weights are where behavior lives, and data is where your moat lives — everyone can rent the same model, but only you own your dataset.

    Capstone

    Inference, Architecture & the Feedback Flywheel

    A model's real-world usefulness collapses to two numbers: what it costs to run and how fast it answers. Training builds the model; inference serves it — and autoregressive generation is typically memory-bandwidth-bound, not compute-bound, because the bottleneck is moving weights from memory to silicon, one token at a time. Measure honestly: latency splits into time-to-first-token (TTFT) and time-per-output-token (TPOT), and total latency ≈ TTFT + TPOT × output tokens; look at percentiles, never averages. Throughput — tokens per second across all requests — drives cost, and latency and throughput are always in tension.

    The tactics stack in three layers. Model level: quantization (the most popular win, especially weight-only), pruning, distillation, speculative decoding (a small draft model proposes tokens the big model verifies — an assistant drafting, a manager approving), prompt lookup, and attention optimization. Service level: batching — static waits for a full batch, dynamic adds a time limit, continuous returns responses the moment they finish; decouple prefill from decode since they have opposite appetites; cache prompts and KV states. Hardware level: replica parallelism (copies of the model) for latency; tensor, pipeline, context, or sequence parallelism to split one model across machines. Practitioners reach most for: quantization, tensor parallelism, replica parallelism, attention optimization.

    Around that core, mature architectures grow in five stages — context construction, guardrails, routing and gateways, caching, and complex agentic logic with write actions. Monitoring tells you something broke; observability — log everything, track MTTD, MTTR, change-failure-rate — tells you why. And the whole machine is fed by the one asset nobody else has: your users' feedback, explicit and implicit, closing the flywheel from production back into datasets and fine-tuning.

    The Whole Field on One Screen

    SELF-SUPERVISION
    Models learn by predicting parts of their input — no human labels. They can only know what they were trained on.
    ATTENTION
    Q asks, K indexes, V carries content. Prefill is parallel; decode is one token at a time. Longer context = more K/V = more cost.
    CHINCHILLA
    Training tokens ≈ 20× parameters. Undertrained giants lose to well-trained smaller models.
    POST-TRAINING
    SFT teaches conversation shape; RLHF/DPO teach human preference. Best-of-N trades compute for quality.
    SAMPLING
    Temperature reshapes the distribution (low = focused, 0.7–1 = creative). Top-k = k most likely; top-p = smallest set ≥ 90% mass. Confidence ≠ correctness.
    EVALUATION
    Perplexity guides training, not quality. Prefer functional correctness; mix exact match, lexical, semantic, AI judges. Tie every metric to a business number.
    SELECTION
    Filter hard attributes first; map cost–performance; hide models behind your own API. Most "open source" is open-weight only.
    ADAPTATION
    Prompt first. Information failure → RAG. Behavior failure → fine-tune. Both → RAG first, then combine.
    CONTEXT
    System + user prompts via the exact chat template. Chunk, retrieve, rerank, rewrite queries. Agents: plan → validate → execute; errors compound.
    FINE-TUNING
    LoRA freezes W, trains A·B, merges at inference. Pilot with 50 examples. Data quality is the moat.
    INFERENCE
    Latency = TTFT + TPOT × tokens; use percentiles. Memory-bandwidth-bound. Quantize, batch continuously, cache prompts, parallelize.
    SYSTEMS
    Guardrails in and out, route through a gateway, log everything (MTTD/MTTR/CFR), and turn user feedback into the data flywheel.

    Frequently Asked Questions

    Do I need to know how to train models from scratch?

    No — that's the whole premise of the field. AI engineering is about adapting models you didn't train. But you do need enough architectural understanding (attention, sampling, memory) to debug behavior, estimate costs, and know which adaptation lever to pull. The book goes deep precisely so your intuitions are real, not cargo-culted.

    RAG or fine-tuning — which should I choose?

    Diagnose the failure. If the model lacks information (private docs, recent events), RAG gives it access. If it has behavioral issues (right facts, wrong format or tone), fine-tuning reshapes behavior. If both, start with RAG — it's cheaper and reversible — then combine. And remember the ladder: squeeze prompting dry before either.

    Why does my model hallucinate if it is "so smart"?

    Because it is sampling probable sentences from a distribution learned on web data — nothing in training verifies truth. Confidence is a probability score, not a fact-check. Mitigations are engineering controls: RAG for grounding, evaluation to measure it, guardrails to catch it, and low temperature when consistency matters.

    How much data do I actually need to fine-tune?

    Start with about 50 well-crafted examples. If you see clear improvement, more will likely help; if you see nothing, more data rarely fixes it — suspect data quality, hyperparameters, or task framing instead. PEFT methods can work with hundreds of examples; full fine-tuning wants thousands to millions. Stronger base models need fewer examples.

    API or self-hosting — is there a default answer?

    There is a default process: filter on hard attributes first. Strict data-privacy policies or on-device requirements eliminate external APIs immediately. Otherwise, APIs win on speed-to-production and built-in capabilities; self-hosting wins on control, privacy, and cost at heavy scale. Either way, route everything through your own internal standard API so switching stays cheap.

    Is this lesson enough to call myself an AI engineer?

    No — and it says so on the tin. This is a high-level map of an 800-page technical book. Use it to know the territory, then go deep: read the book, watch Stat Quest's Transformer series for the math, and build one small end-to-end system (prompt → RAG → eval → serve). One shipped project teaches more than ten summaries.
