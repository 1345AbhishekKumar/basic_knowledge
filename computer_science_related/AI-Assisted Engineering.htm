The Premise

Your agent should be a colleague, not a tool

The starting question wasn't "how do I make AI write code faster?" It was: what would it look like if your agent was really more like a colleague? A colleague you could hand a bug report to before you go to sleep — and trust to have it fixed by morning.

"The big theme for me, as I've been using agents to write code, is how do you trust it? When you don't have much trust in your agents, you really can't get the most out of them."

🧑‍💼 The Management Analogy

If you're an engineering manager and you don't trust your team, you end up micromanaging — looking over shoulders, checking every commit, reviewing every line. You become the bottleneck. Agents work exactly the same way. The only way to scale from 1 agent to 100 is to build trust.

Module 02

Verification: The #1 Skill

If you take one thing from this lesson, take this: the most important skill in your toolbox is verification.

What "verification" actually means

The ability for an agent to actually run the code — to take CPU traces, heap snapshots, open an iOS simulator, drive a browser. However your application is exposed to users, the agent can do the same thing and test for real.

"It doesn't guarantee your agent writes good code — but it allows it to at least write correct code. That's a really big step forward for being able to trust your agents."

The bottleneck problem

Without a verification skill, you are the verifier. The loop looks like this:

1 You tell the agent what to do
2 It writes some code
3 You open your local dev build and test it manually
4 Copy-paste screenshots / console errors back to the agent
5 Repeat forever. Zero parallelism.

The fix is the "control glass" skill — teaching the agent to drive the Chrome DevTools Protocol (or Apple's simulator utilities) so it can launch the app, click around, take traces, and read its own results.

❌ Before

Agent guesses at a flame graph. "It kind of looks like this thing." You fix it. Turns out that wasn't the problem. Slow, expensive, trust-destroying.

✅ After

Agent launches the app itself, reproduces the bug, reads the trace, and confirms the fix — without you in the loop at all.

Module 03

Skills: Teaching a Brilliant Amnesiac

Imagine hiring an engineer who is a phenomenal coder but has zero business context — they onboarded five seconds ago. How do you make them effective? You teach them. With agents, that teaching is called a skill.

🧠 "Pulling the agent into a different latent space"

A skill is just markdown. But because LLMs predict the next token, feeding them high-quality tokens up front lets them pattern-match at a higher, smarter level. The fancy phrase for this is "pulling the agent into a different latent space." Practically: give it good context and it behaves better.

How skills get built: failure-driven

The speaker's plugin, Pstack (a playful nod to Gary Tan's "GStack"), wasn't designed up front. It grew one failure at a time:

→
Observe a failure mode. Agent confidently says "it has to be this thing!"
→
Inspect the tool calls. Notice it never actually read the file that mattered.
→
Write a skill for it. "Stop hallucinating. Actually search. Use sub-agents. Stop guessing."
→
Repeat for every new failure you catch.
"You don't want to just be a passive observer of your agent. You want to be very in the driver seat in the initial stages... open up all the tool calls, read the code, read the thinking blocks. That's a great way to see where they fail."
Module 04

Evals: Unit Tests for Your Agent

Skills rot. Products change. So how do you know a skill still does what you think it does? Evals. Think of an eval as a unit test for an agent.

The eval playbook

  1. A coordinator agent writes a rubric for what the skill should accomplish.
  2. It spawns many sub-agents in individual directories.
  3. Directories are cleverly named so sub-agents don't realize they're being evaluated — agents change behavior when they know.
  4. A judge agent on a different model cross-checks the first model's scoring to avoid bias.
  5. Run across many models to see how the skill performs across the matrix.

📈 Hill climbing

Because evals produce a score, you can loop on them. Use /loop and tell the agent: "keep looping until everything is 10/10." Then walk away.

🎯 Harder than it sounds

Maintaining skills requires taste and observation. It's like being a great backseat driver during pair programming — you ask the questions a good reviewer would ask.

"Every time I modify a skill, I run an eval and make sure it's actually leading to the result I want."
Module 05

Going Cloud: Where the Leverage Is

Start local, because you can observe what the agent does. But the real payoff comes when verification skills run in the cloud — because then it's not just you who gets faster. Your whole team does.

🤖 Meet "Benny"

An always-on cloud agent that takes every incoming bug report and, on its own machine running its own editor, uses the same control skills to launch the app and try to reproduce the bug.

AutoDiagnose
AutoReport

Real example: Benny reproduced a reported bug, then discovered it was already fixed on main — so the only remaining action was to cut a new release. That's an hour of investigation saved, per report, for everyone.

🖥️ Local first

  • You can watch the agent interact
  • You see how it calls APIs
  • Fast feedback on your skill design

☁️ Then cloud

  • Massive parallelism
  • Levels up the entire team/company
  • Enables automations on real signals

⚠️ Don't skip the curve

If you're still in "1 agent, watching every output" mode, do not jump to spawning thousands of cloud agents. You'll waste enormous amounts of tokens and money. There is no shortcut — the curve is about your personal level of trust, and trust is earned in stages.

Module 06

Architecture: Brownfield vs. Greenfield

Conventional wisdom says never rewrite. The speaker makes a case for reconsidering — because agents change the math.

🏢 Brownfield (existing code)

  • Often actually in a good spot
  • Big-tech style guardrails already exist
  • Frameworks, conventions, restricted credentials
  • Agents inherit the safety rails

🌱 Greenfield (vibe-coded)

  • Biggest risk — zero guardrails
  • Agents solve tasks the most convenient way
  • Codebase spirals into "organic architecture"
  • Optimized for shortcuts, not for humans
"Before AI slop, we had human slop. Big tech infra is actually designed for the least capable engineer on your team — you build frameworks, conventions, and guardrails so your intern doesn't wipe the production database. If you already have that, your agents can do a very solid job."

The Dune Philosophy

"Dune" is the internal codename for an architecture built specifically for agents to write — think Next.js for Electron apps.

🎯 Core principle: The shortest path is the best path

Agents love shortcuts. They'll find the quickest way to solve a problem. So instead of fighting that, make the shortest path the correct path.

📁 Features in one directory

All code for a feature lives together. Agent working on onboarding? It stays in the onboarding folder. Encapsulated for ~80% of work.

🚫 Banned useEffect

React's biggest footgun is banned outright. CI fails and yells at you if it appears.

💬 Banned comments

Agents write comments describing irrelevant history ("Lauren said never do this"). 99% of the time they're noise.

🔒 Process isolation, enforced by CI

Electron apps have a renderer thread (UI, 16ms per frame budget) and a main thread. Accidentally pulling heavy work or IO into the renderer causes jank — dropped frames, long tasks, choppy UI. So Grokbot has separate electron-main and electron-renderer directories, with a CI check that inspects the dependency graph to block illegal cross-imports.

"It's actually very annoying to write code in Grokbot. But agents absorb all of that annoyance."
Module 07

Layers of Enforcement

Not all constraints are equal. Some are hard — the agent literally cannot merge bad code. Others are soft — the agent can forget. Click each layer to expand.

🚨 The worst place to be: "Code Review Land"

If the only thing enforcing your invariants is a human reading the PR and commenting "you shouldn't do this" — that's a code smell. Every time it happens, ask: How do I turn this into a lint rule? A CI failure? How do I eliminate this category of problem entirely?

🦀 Why tech stack choice matters

Rust is getting popular again in the agent era because the compiler is brutal. The borrow checker forces correctness. If you keep agents away from unsafe blocks, then "it compiles" becomes a meaningful proxy for "it probably works." You offload trust to the compiler instead of to your own eyes.

Module 08

The ROI Question

"Not everyone has unlimited tokens." Fair. So is this whole approach realistic? The answer is a trade-off analysis.

💸 Hire more engineers

  • High salary cost, ongoing
  • Coordination overhead grows
  • Planning meetings, process, politics
  • Becomes a 10,000-person org

🪙 Spend tokens up front

  • Expensive initially
  • Refactoring + constraints cost tokens
  • Pays dividends forever after
  • Even "non-frontier" models do excellent work
"The thing I couldn't do before is enforce this level of constraint in a codebase by myself. It would have taken me years to build this framework and do all the refactoring and verify it. My salary is pretty high."

🔄 The real payoff isn't just you

Once the codebase is agent-friendly, PMs and designers can ship features directly. They fix a bug, open a PR, and the engineer just reviews and stamps it. The architecture holds up under contributors who aren't engineers — because the constraints do the guarding.

🧑‍🍳 The chef analogy

You're no longer cooking every dish. You're the head chef. You have line cooks, a sous chef, different stations. Your job is to design the environment — set up the kitchen, define the stations, assign the tasks. That's what engineering becomes.
