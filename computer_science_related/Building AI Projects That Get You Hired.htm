Part I

Choosing the Problem

Before any code, you need a reason. This part is about picking something worth building — and knowing which bar you're trying to clear.

Lesson 01

Know why you're building before you build

A project can do three very different things, and each one sets a different bar for what "good" means. Confusing them is the single most common reason a portfolio project fails to do its job.

  • Teach you a skill. The bar is low. Calling a vision model once and printing the output is a perfectly good learning project. Nobody needs to see it.
  • Demonstrate skills to employers. The bar is much higher. You need robustness, evidence of judgment, and a story you can defend under questioning.
  • Become real experience. If real people use it — and especially if they pay for it — it stops being a project and starts being a job you gave yourself.

These are not the same artifact. A project that is excellent for learning can be embarrassing on a resume, because the learning version is allowed to be fragile, undocumented, and full of decisions made by someone else.

The same project can be fine for learning and disqualifying on a resume. Decide which goal you're chasing before you write a line of code.
Watch out

The classic failure: a project built purely to learn gets pasted into a portfolio and expected to convince someone you can build production systems. The gap between those two things is where rejections come from.

One practical note: if your project is meant to demonstrate skill, you will be asked why you made the choices you made. You cannot answer that question if the choices were made for you. Keep that in mind as you decide how much to delegate.

Key idea

Write down which of the three goals this project serves. If it serves all three, be honest that the bar is set by the highest one.

Lesson 02

Start from a problem, not from a technology

The most common way people get stuck is working in the wrong direction. They learn about RAG, or agents, or some new model that just dropped — and then they go looking for a problem to use it on. This produces projects that are technically current but personally hollow.

Technology-first
  • "I want to use agents somewhere."
  • "Where can I shove RAG?"
  • A solution hunting for a problem
  • Motivation dies when the novelty does
  • You can't tell when you're done
Problem-first
  • "This thing in my life is annoying."
  • "What's the simplest fix?"
  • A problem that demands a solution
  • Motivation survives the hard parts
  • Success is obvious when it arrives

Working backwards from a problem has a second benefit that isn't obvious at first: it automatically scopes the project. When you start from a technology, you have no natural stopping point — every feature seems equally justified. When you start from a problem, you know what "solved" looks like, and you can stop when you get there.

The best portfolio projects aren't always the most technically impressive. They're often the ones you have a personal connection with — and that enthusiasm comes across in interviews.
From the source

Nearly every hiring manager interviewed for the source material said the same thing: they value enthusiasm and decision-making — and you can only really demonstrate those if the idea was yours.

Don't do this

Do not copy the example app from the source video — a bookshelf-scanning book recommender. Following along defeats the entire point. Copy the process, not the project.

Key idea

Work backwards from a problem you understand. The technology choice comes last, and only if it earns its place.

Lesson 03

Find problems worth solving

If you're staring at a blank page, there are three reliable places to look. They're ordered by how easy they are to work with, not by how impressive they sound.

Your own life

The easiest place to start, and usually the best. You already understand what's annoying about the situation, which means you already know what a good solution looks like. You'll also know when you're done — a property that sounds trivial until you've spent three weeks building something with no finish line.

People around you

Friends, family, coworkers. The advantage here is that you can ask questions and get answers. The disadvantage is that you may not understand the domain deeply enough to judge whether a solution is actually good.

Communities you belong to

A subreddit, a Discord, a hobby group, a professional forum. These are gold mines because the problems are already written down — people complain in public. You can read a year of frustration in an afternoon.

What makes a problem good

Signal Why it matters
You can describe the current workaround People are already paying a cost, which means they'd value relief
The input is something you can actually get A brilliant idea that needs proprietary data is not a portfolio project
You can tell good output from bad output Without this, you can't evaluate anything you build
It's small enough to finish Unfinished projects teach you less and demonstrate nothing
Note

Personal connection isn't just a motivational trick. It's what lets you write a scoping document that reflects reality instead of guesswork, and it's what keeps you going when the third model provider in a row gives you garbage output.

Key idea

Start with your own life. You already understand the problem, you'll recognize a good solution, and you'll know when to stop.

Lesson 04

Turn a vague idea into a scoped problem statement

"An app that recommends books from a photo" is not a specification. It's a wish. Before you build anything, you need a problem statement specific enough that you can make decisions around it.

Starting from a raw note

A real first draft might look like this:

"When I go to the bookstore, I can't figure out what to buy unless I recognize a title. I want to take a picture of the books in front of me, give it info about what I like, and have it tell me which one to buy."

That's a good starting point, but it leaves too many unanswered questions to build from:

  • Who is this for, exactly?
  • What kind of photo — a shelf, a stack, a single cover?
  • Can it recommend anything it thinks I'd like, or only books it can actually see?
  • What happens if it can only read part of the shelf?
  • What does "tell me which one to buy" mean — a ranked list, a single pick, a reason?

What the scoping document covers

Fill in an initial scoping document with the areas below. Keep it short. The point is not completeness — it's having a record of what you believed before you started building.

Area What to decide early
User Who exactly is this for? You? A specific kind of reader?
Constraints Budget, time available, technical limits you're working within
Input What data goes in — format, quality, source
Output What comes out, in what shape, for what purpose
Success metrics How you'll know it works — accuracy, usefulness, satisfaction
Latency goals e.g. "no one waits 30 seconds for a recommendation"
Cost budget Even for a personal project — a number, not a feeling
Privacy What data you'll store, and what you refuse to store
Watch out

Leave most of the template blank at this stage. You don't have evidence yet for model choice, architecture, RAG, agents, or fine-tuning. Filling those in now is guessing dressed up as planning.

Why bother

For a personal project this step can feel ridiculous — it's just you. But the record matters later. When you're in an interview and someone asks why you built it a certain way, "here's what I believed before I started, and here's what changed" is a much stronger answer than reconstructing it from memory.

Key idea

The scoping document isn't a plan. It's a snapshot of your assumptions, so you can see later which ones were wrong.

Part II

Deciding What to Build

Once you have a problem, you have to justify the tooling, set up a working method, and lay foundations that won't need to be ripped out later.

Lesson 05

Ask whether AI belongs here at all

Adding a language model does not automatically make a project better or more impressive. It adds four things, and they are all costs:

  • Cost — per-call pricing that scales with usage
  • Unpredictability — the same input can produce different outputs
  • Latency — network round trips measured in seconds, not milliseconds
  • Security surface — prompt injection, data leakage, privacy exposure
"If normal software can solve the problem just as well, the model mostly gives me extra cost and unpredictability and security issues — and it just makes me look like a noob."

The honest question to ask is: what does the model do that deterministic code cannot? There are only a few legitimate answers. Handling unstructured input. Producing natural language. Making fuzzy judgments. Generalizing across categories you didn't enumerate.

If your problem doesn't require any of those, a regular program will be faster, cheaper, more reliable, and easier to test. And if you use a model anyway, an interviewer will probably notice.

Note

This question is a filter, not a formality. If the answer is "regular code is fine," you've saved yourself weeks — and you've demonstrated judgment, which is exactly what interviewers probe for.

Key idea

Justify the model. If you can't articulate why AI is required, it probably isn't.

Lesson 06

Use spec-driven development with your AI assistant

You don't have to hand-write every line. But if you outsource the thinking, you didn't learn anything — and you won't be able to defend your decisions in an interview.

"If you've outsourced your thinking to Claude Code, you did not learn. And when you're asked in an interview, you will not be able to defend the decisions that you made, because you did not make them."

The fix is a simple workflow: the assistant proposes, you review, then it implements. The proposal step is where the thinking happens, and it's the step most people skip.

Minimal repository setup

project/
├── docs/
│   ├── scoping.md          # initial problem definition
│   ├── proposals/          # one file per feature proposal
│   └── decisions/          # what changed and why
├── .claude/
│   └── steering.md         # coding standards + working rules
└── src/

The workflow, step by step

  1. You ask for a feature — "add photo uploads."
  2. The assistant drafts a proposal: what it thinks needs to change, what assumptions it's making, and a recommended task list. No implementation code yet.
  3. You review the proposal with a critical eye:
    • Did it make a decision you didn't make? Stop and question it.
    • Did it suggest something you don't understand? Ask why.
    • Did it assume something about the user that isn't true? Fix it now.
  4. Once the plan is right, implementation moves fast.
  5. Decisions get written to files, not left in chat history.
Note

Files beat chat history. Chat scrolls away and gets truncated. A decision document is still there in six months when someone asks "why did you do it this way?"

Sanity check

Before you start coding, verify that the assistant actually understands the workflow you're using. A quick test run on a trivial change will tell you whether the proposal step is going to happen or whether it's going to jump straight to code.

Key idea

Spec-driven development keeps you as the decision-maker while still getting the speed of an AI assistant. The proposal step is non-negotiable.

Lesson 07

Set up technical foundations before building features

This isn't a complete software engineering tutorial — the exact tools depend on what you're building. But one thing is nearly certain: you'll be working with data, and you'll need somewhere to put it.

What to set up first

  • A data layer. A database and file storage, ideally in one place. For this kind of project, a hosted Postgres with a generous free tier is usually enough.
  • API keys in a file, ignored properly. A .env file plus a .gitignore entry. This takes thirty seconds and prevents the worst day of your project.
  • A virtual environment. Managed with something like uv or poetry, so your dependencies are reproducible.
  • CLI tooling for your provider. Installed and authenticated, so you can work from the terminal instead of clicking through a dashboard.
Watch out

If you use AI agent skills for your database provider, use them to catch setup mistakes early. A schema error is cheap to fix on day one and expensive to fix after you've collected real data.

Key idea

Boring foundations are what make the interesting parts possible. Set them up before you have a feature to distract you.

Part III

Building Evidence

The prototype is not a small app. It's an instrument for converting your scariest assumptions into data.

Lesson 08

Design the MVP as an experiment, not a crappy app

People often read "MVP" as "build a bad version of the whole product." That's the wrong interpretation. The MVP is the smallest thing you can build that answers your biggest open questions about whether the project is viable at all.

Step one — find the questions that could kill the project

For the bookshelf example, two unknowns mattered more than everything else combined:

  1. Can a cheap vision model read book spines from a normal photo — sideways text, tiny fonts, bad lighting, dozens of titles in a single frame?
  2. Can an affordable language model take those titles plus minimal taste information and produce recommendations that are actually good?
Watch out

If off-the-shelf models are terrible at this, or only the expensive ones work, the project changes a lot. Maybe you need a custom vision system. Maybe you need a different input entirely. Maybe the idea isn't viable. Find that out before spending two weeks on a beautiful UI.

Step two — build the smallest thing that answers them

In this case: a command-line script. Give it a photo. One model reads the titles. Another model takes those titles plus your preferences and returns recommendations. That's it. No UI, no accounts, no database schema for users, no deployment.

Step three — run it like a real experiment

  • Save the result of every model call.
  • Log the model name, the prompt, the raw output, the cost, and the latency.
  • Compare results on data, not on vibes.

The temptation to skip this and "just try stuff" is strong. Resist it. If you don't log what you tried, you'll end up re-running the same experiments three weeks later because you can't remember which model performed best.

Key idea

An MVP is a research instrument. Its job is to convert your scariest assumptions into evidence you can act on.

Lesson 09

Log every model call from the very first one

One of the first things to set up is a schema for logging model calls. It feels premature. It isn't. These records become the foundation for evaluation, monitoring, debugging, and cost tracking — and building them once means you don't rebuild them three times.

Field Why you need it
modelCompare providers, versions, and price tiers
prompt_versionAttribute behavior changes to specific edits
raw_outputRe-grade later without re-running anything
cost_usdKnow whether you're inside your budget
latency_msDetermine whether the UX is feasible
errorTrack reliability over time
created_atSee trends and correlate with changes
 
-- a minimal call-log table
create table model_calls (
  id             bigserial primary key,
  stage          text not null,        -- 'vision' | 'recommend'
  model          text not null,
  prompt_version text,
  input_ref      text,                -- pointer to image or shelf
  raw_output     jsonb,
  cost_usd       numeric,
  latency_ms     integer,
  error          text,
  created_at     timestamptz default now()
);
Note

These same records power your model comparison and your production dashboard later. Build once, use twice.

Key idea

Instrument before you optimize. You can't compare what you didn't record, and you can't debug what you didn't save.

Lesson 10

Evaluate pipeline stages independently

Keep the vision stage separate from the recommendation stage. There's no reason to assume the model that's best at reading tiny text in an image is also best at recommending books. Treating them as one bundled "provider" makes it impossible to tell which part failed.

Separated
  • Compare each problem on its own merits
  • Swap one model without touching the other
  • Errors don't compound invisibly
  • Optimization has a clear target
Bundled
  • "Provider X is good" hides which part worked
  • Recommendation errors get blamed on vision
  • Impossible to optimize either stage
  • You can't explain your results

When testing the recommendation stage, give every model the same fixed list of books. Otherwise vision mistakes contaminate the comparison and you learn nothing about which recommender is better.

What the experiment actually revealed

  • Frontier models found essentially all readable books on the tiny test set, with no hallucinations. Smaller models missed titles and invented books that weren't on the shelf at all.
  • Cost was less interesting than expected. The models that performed well were already inside the scoping budget. Shaving fractions of a cent here was not where the time should go.
  • Latency was the real problem. Some calls took ten to twenty seconds just to read the shelf — before recommending anything — against a roughly fifteen-second target for the whole experience.
  • A cheaper model matched personal taste better than the expensive ones on the recommendation step. Price is not a proxy for quality on your specific task.
Watch out

The MVP also surfaced a privacy issue: source images had GPS coordinates in their file metadata that shouldn't be stored. That's the kind of thing you only find by actually running the pipeline on real files.

Key idea

Decompose the pipeline into stages and evaluate them separately. Then optimize the stage that's actually failing your requirements — not the one that's easiest to measure.

Lesson 11

Write labeling rules before you grade anything

You need test data with labels. Five photos isn't enough to claim the system works — but it is enough to answer a smaller, more urgent question: "Is this idea promising enough to keep going?"

What matters more than volume is consistency. Your rubric doesn't need to be perfect. It needs to exist, and it needs to be applied the same way every time.

Rules worth writing down

  • What counts as a "found" book versus a hallucination?
  • If a title is partially readable, does it count as found?
  • What counts as a "good" recommendation — matching your taste, or being defensible?
  • How do you score a recommendation that's good but wasn't on the shelf?
"Your labeling rules don't need to be perfect, but you must have rules that you apply consistently. Otherwise your grading is going to be some completely random thing that doesn't help you."
Watch out

Inconsistent labeling is worse than no labeling. It produces numbers that look scientific and mean nothing — and you'll make real decisions based on them.

Key idea

Boring upfront work on rubrics saves you from garbage evaluation results later. Write the rules once, then never argue with yourself again.

Lesson 12

Update the scoping document with what you learned

This is the step most people skip, and it's the one that turns a prototype into a plan. Now that you have evidence, go back to the scoping document and revise it.

  • Which assumptions turned out to be true?
  • Which ones were wrong, and what replaced them?
  • What new constraints appeared that you didn't anticipate?
  • What's now settled that you can stop worrying about?

You won't have answers to every question that will come up during the build. But after one MVP experiment, you know enough to fill in most of the rest of the document — and you know which decisions are now grounded in data rather than guesswork.

Note

This revision is itself a portfolio artifact. "Here's what I believed, here's what I tested, here's what I changed" is a much stronger interview story than "here's the final architecture."

Key idea

The scoping document is a living record. Updating it with real evidence is what separates a plan from a guess.

Part IV

Discipline and Testing

This is the part that separates a portfolio project from a hobby. It's also the part most people skip, which is why most portfolios look the same.

Lesson 13

Decide what you will not build

There's real temptation to shove every technique you've learned into one project so it looks impressive. Don't. You don't get extra points for techniques that didn't make sense — and a reviewer who knows what they're looking at will notice.

Techniques deliberately left out, and why

Technique Reason to skip
RAG No retrieval problem exists. Books come from the current shelf; extra information comes from a normal catalog lookup.
Agents Nothing to decide. The workflow is known ahead of time: read shelf, verify books, recommend. Letting a model choose would make it slower, pricier, and less predictable.
Fine-tuning Off-the-shelf models already work. No demonstrated need, and no data to train on.

Features deliberately deferred

  • Login and user accounts
  • Purchase links or affiliate integration
  • Social features, sharing, or history
  • Everything else on the "neat ideas" list

None of these are bad ideas. They're just not this version. Writing them down as explicitly out of scope is what keeps you from adding them at 2 a.m. and then never finishing.

"If the problem doesn't need those things, leaving them out is a better decision."
Note

In an interview, "I chose not to use agents, and here's why" is a stronger answer than "I used agents." Scope discipline reads as seniority.

Key idea

Advanced techniques are tools for problems you actually have — not boxes to check on a resume.

Lesson 14

Sequence phases by risk, not by convenience

Break the work into phases. Each phase should leave you with something that still works end to end, plus exactly one new addition. That way you always have a working system to fall back to.

The order matters more than the phases. Deal with risky parts early enough that they can still change the design. Anything you build after a risky assumption is confirmed is built on solid ground. Anything you build before is built on sand.

An example phase order

  1. Model router and automated quality check. So models can be swapped confidently and cheaply.
  2. Smallest useful app. Take a photo, see the titles it read. No recommendations yet. Still local.
  3. Preferences. Obviously you need to know what people like before you can recommend anything.
  4. …and so on, one capability at a time.

Components you might pull from

  • Prompt engineering — versioned, not scattered strings
  • Model selection — revisited as the product develops
  • Retrieval — if the model needs information it doesn't have
  • Agent workflows — if the system genuinely needs to decide
  • Product surface — API, UI, auth, uploads, database
  • Reliability layer — logging, errors, cost, latency tracking
Watch out

Put rough deadlines on each phase to fight scope creep — the tendency to keep adding fun stuff and never finishing anything.

Key idea

Front-load the unknowns. Anything that could invalidate the design should be built first, while changing course is still cheap.

Lesson 15

Keep a traceable line from spec to commit

Every change should have a spec and a task list. Every commit should connect to a specific task within that spec. This sounds like process overhead. It's actually the thing that makes everything else possible.

What traceability buys you

  • You can see whether things are actually being completed as intended
  • You can see where your progress is, at a glance
  • You can look back at decisions that were made and why
  • You can revert cleanly when something goes wrong
  • You can explain any part of the system to someone else

Without this, three weeks in you have a codebase full of changes you can't explain, and a bug you can't trace to its origin. With it, you have a narrative.

Key idea

A traceable project is a defensible project. If you can't explain why a line of code exists, you don't own it.

Lesson 16

Test software and AI behavior differently

There are two kinds of correctness in an AI product, and they need different tools. Mixing them up is why people either over-test (and waste time) or under-test (and ship garbage).

Deterministic software AI behavior
Example Stripping GPS data from uploads Vision model missing books on a tricky shelf
Tool Unit, integration, end-to-end tests Evaluation set with labels and a rubric
Failure mode Test fails, you notice immediately Code is valid, behavior silently degrades
When to run Every commit Whenever models, prompts, or preprocessing change

Software tests worth writing

  • Can a user upload a valid image and complete the flow?
  • Do saved books stay attached to the right person?
  • Does the metadata stripping actually remove what it claims to?
  • End-to-end browser tests — individual pieces can all pass while the product as a whole is broken.

Automate it with CI

Simple YAML files that define what runs when something happens in the repository. On every push or pull request, the pipeline installs dependencies and runs the tests automatically.

name: tests
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v3
      - run: uv sync
      - run: uv run pytest
"AI systems are weird and kind of annoying because the code can be perfectly valid while the behavior gets worse. Nothing will crash if you change the prompt — but it might miss books or hallucinate."
Key idea

Wrap the model in normal software tests, and wrap the model's output in evaluations. You need both, and they are not interchangeable.

Lesson 17

Build an evaluation set that grows with the project

An evaluation set is only useful if it covers the range of real inputs. Start small, then harden it deliberately.

How to expand it

  • Take your original test inputs and generate deliberately worse versions: blur, glare, rotation, lower resolution.
  • Add more inputs covering a wider range of real-world cases.
  • Keep the labels and rubric consistent across every version.
  • Add failures from production once you're live.

How to use it

  • Any change touching models, prompts, or preprocessing triggers a re-run.
  • Results are compared against the currently trusted version.
  • A regression shows up as a failure — exactly as intended.
  • Prompt variants can be compared systematically, side by side.
Note

This only works because prompts are versioned. Systematic prompt comparison is impossible when prompts are scattered strings across the codebase.

Key idea

A good eval set is a regression test for behavior. Most of the work becomes boring once it's automated — that's the point.

Lesson 18

Version your prompts like real code

Prompts shouldn't be random strings sprinkled through the codebase. They should be versioned parts of the system, with a repeatable way to check whether a change actually helped.

# prompts/recommend/v3.md
---
version: 3
stage: recommend
notes: "tighter output schema, no title invention"
---

You are given a list of books physically present on a shelf
and a short description of the reader's taste.

Only recommend books from the provided list.
Never invent titles.

Return JSON: [{ "title": ..., "reason": ... }]

Then any prompt change becomes an experiment:

  1. Bump the version.
  2. Run the evaluation set.
  3. Compare against the trusted baseline.
  4. Keep it, or revert it.
Note

Versioned prompts are one of the most commonly overlooked practices among beginners — and one of the cheapest to adopt. It takes ten minutes to set up and saves you from a dozen arguments with yourself.

Key idea

Even "just prompt engineering" should be approached like an experiment with a control group.

Lesson 19

Define "done" for every change

Before a change makes it back into the main project, it needs to pass a short list of checks. These aren't bureaucracy — they're what let you move fast later without breaking things.

Definition of done
  • You know what the change was supposed to do
  • Normal software tests pass
  • AI evaluation still looks good, if model behavior could be affected
  • Documentation still describes the system you actually have
  • The coding assistant reviews the change against the spec as a second set of eyes
  • If the spec needs updating, that happens too

In practice, most of this becomes fairly boring once it's automated — which is the point. The value isn't in the ceremony. It's in catching problems before they ship, so that the next change is still safe to make.

Key idea

A definition of done is what lets you move fast without accumulating hidden debt.

Part V

Shipping and Career

A working app on your laptop is worth almost nothing. The last part is about getting it in front of people — and turning that into a career asset.

Lesson 20

Monitor production and close the feedback loop

Production finds different problems than your labeled eval set. People upload weird photos. A provider gets slower. You get rate limited at the worst possible moment.

Not only do you want to know whether a change you made broke something — you also need to know whether something you didn't do broke production.

What you need to be able to answer

  • Which model handled this request?
  • How long did it take?
  • What did it cost?
  • Which prompt version was used?
  • Did the call fail, and how?
Note

You already built this in Lesson 09. The same call-log records that powered model comparison become your production dashboard. No enterprise observability stack required for a small app — a simple view over the logs is enough.

Turn failures into improvements

  1. A certain kind of input keeps failing in the same way → add it to the eval set.
  2. Reproduce the failure in a controlled way.
  3. Fix it.
  4. Keep checking that it doesn't come back.

Collect cheap feedback signals

  • User saved a recommendation → strong positive signal
  • User said "not for me" → strong negative signal
  • User abandoned mid-flow → somewhere the experience broke down

These help improve the product and inform prioritization.

Why this matters for interviews

If latency is trending up, you might prioritize caching. That gives you a real answer to "why did you add a cache?" — instead of "I don't know, caches are cool, production apps have caches."

Key idea

Monitoring isn't just for detecting breakage. It's how you generate the evidence that justifies your next engineering decision.

Lesson 21

Deploy — then present the work you actually did

Once the spec is implemented, evaluations pass, and monitoring is in place, get it off your laptop. Connect the repository to a hosting platform and let it deploy automatically whenever pre-deployment checks pass. Move your domain over from any previous version and retire the old app.

The presentation problem

Here's the uncomfortable truth about portfolio projects: all the thinking and engineering work you did is invisible in the running app. Someone clicking a link sees a simple interface and has no idea whether it took you two days or two months.

"When you just look at the app, you can't tell that I did all of this thinking and engineering work. All of that is obviously hidden."

If you just send a link, you lose most of the benefit. Fix it with the README:

  • What you built and why
  • The trade-offs you made, and what you gave up
  • Functionality overview
  • Architecture diagrams
  • What you deliberately left out, and why
  • What you'd do differently next time
Watch out

The default AI-generated README that accumulates as you build does not do this well. It describes what the code does, not what you decided. Rewrite it by hand.

Key idea

The engineering is invisible by default. The README is where you make the judgment visible.

Lesson 22

Get real users — then rewrite your resume

Everything up to this point was learned from your own testing. Real users teach you more in a week than you'll learn in a month alone.

  • A couple dozen users → great interview stories, a roadmap of real bugs, and the beginning of genuine product intuition.
  • A couple hundred or thousand → this starts looking like professional experience, because it is.
  • Paying users and a legitimate customer base → it belongs in the Experience section of your resume, not Projects.
"This is how a portfolio project can help you overcome that catch-22 where you need experience to get experience. If you create a legitimate product, you can put it on your experience section and get that first job without anyone having to take a chance on you."
Note

You can make your own opportunities. That's the whole point of building something real instead of something that only exists to be shown.

And it's still completely fine for a project to exist purely so you can learn something. Not every project needs users, revenue, or a resume line. But in order to learn something, you have to make your own project — not follow someone else's.

Reminder

Don't copy the example app. Copy the process.

Appendix

The Full Process, as a Checklist

Every step from the twenty-two lessons, in order, as a single list you can work through.

  1. Name which goal(s) the project serves: learn, demonstrate, or experience
  2. Find a problem in your own life, not a technology you want to use
  3. Check the problem is small enough to finish and you can judge good output
  4. Write a scoping doc — user, constraints, input, output, metrics, latency, budget, privacy
  5. Justify why AI is needed at all, or use regular software instead
  6. Set up spec-driven development: docs directories, steering files, proposal-before-code
  7. Verify the assistant actually follows the proposal workflow
  8. Set up the data layer, env files, gitignore, and virtual environment
  9. Identify the one or two questions that could kill the project
  10. Build the smallest experiment that answers them — a CLI is fine
  11. Log every model call: model, prompt version, output, cost, latency, errors
  12. Separate pipeline stages and evaluate them independently
  13. Give every model the same fixed input when comparing a stage
  14. Write consistent labeling rules before grading anything
  15. Update the scoping doc with what you actually learned
  16. Explicitly decide what you will NOT build — RAG, agents, fine-tuning, features
  17. Sequence phases by risk; each phase ends with a working end-to-end system
  18. Keep a traceable line from spec to task to commit
  19. Write normal tests for deterministic software plus an eval set for AI behavior
  20. Set up CI to run tests on every push and pull request
  21. Harden the eval set: blur, glare, rotation, low resolution, more variety
  22. Version prompts and treat every change as an experiment
  23. Define what "done" means for a change, and enforce it
  24. Monitor production and feed real failures back into the eval set
  25. Collect in-product feedback signals: saved, not for me, abandoned
  26. Deploy with automated pre-deployment checks
  27. Rewrite the README: trade-offs, architecture diagrams, what you left out
  28. Get real users, learn from them, then move the project to your Experience section

Lesson notes derived from a walkthrough of building an AI portfolio project end to end. The example app is illustrative — build your own problem, not this one.
