01 / SELECTIVITY
Start here · the one principle

Post less, but matter more.

A senior with 20 PRs fades by the 20th. Fatigue brings missed bugs and uneven tone. The agent exists to reclaim that attention, not to automate comments.

Core explanation. Without help, every pull request (a proposed code change) waits for a scarce senior. Queues grow to hours or days, and review 10 is weaker than review 1. The fix is not maximal output. It is selectivity (= choose only what deserves a senior's eyes). The L0 rule from the transcript: optimize for findings worth senior attention and defer the rest. A wrong style note is annoying. A missed SQL injection (database attack via crafted input) is dangerous. So the whole architecture filters noise and escalates doubt.

  • Feel the pain: remove the agent, watch queues, fatigue, inconsistency.
  • Reframe: reclaim senior attention, automate the mechanical part.
  • Filter: post high-value, high-confidence notes; escalate the rest.
  • Learn: use disputes to get sharper next time.
  • Sort failures: engineering vs model, known vs unknown (2x2).
What: You open a PR Friday, senior is on PR 19 and tired. → So what: Agent posts 2 solid notes, holds 1 unsure case for human.
What: Bot posts 30 nits on spacing. → So what: Team mutes it; real bug hides in noise.
Analogy: a good sous-chef plates only dishes ready to serve; the rest stays back for the head chef to taste.

❌ What People Get Wrong: more comments means a better reviewer.

Why This Matters: selectivity decides trust; noise kills adoption.

🔗 Leads to Module 2: selectivity needs a strict output shape to enforce it.

02 / TRIGGER AND TEAM
Bench step · precise in, structured out

One trigger in, four minds at work.

A vague trigger fires on everything. A precise trigger fires on one event. One prompt cannot hold four expert mindsets, so the work fans out and back in.

Core explanation. The trigger (= what starts the run) is exact: GitHub sends a pull_request webhook when a PR opens. The output is also exact: one structured review, a list of findings each with agent_type (security, quality, testing, docs), severity plus category, file and line location, and confidence plus rationale (= why plus how sure). Linters catch style but cannot judge intent. Static analysis finds some bugs but cries wolf and cannot read docs. One big prompt judging a whole diff has one mindset for four jobs and invents facts. So four specialists run in parallel and an aggregator merges, dedups, and scores.

  • Trigger: PR opened → webhook → verify → queue.
  • Fan-out: security, quality, testing, docs run parallel.
  • Shape: every claim carries where + why + how-sure.
  • Fan-in: aggregator merges and dedups to one review.
What: Teammate stars the repo; no PR opens. → So what: Nothing fires — trigger is PR only, not any event.
What: Security says injection risk at line 40 with reason. → So what: Developer can check, dispute, or fix fast.
What: Two agents flag the same line. → So what: Aggregator keeps one copy with higher score.
Analogy: four doctors read the same scan for bones, lungs, heart, skin; one head doctor writes the single report.

❌ What People Get Wrong: one giant prompt can cover all four concerns well.

Why This Matters: shape makes findings testable and disputable.

03 / GROUNDING
Bench step · give the stranger context

Turn the stranger into a colleague.

A model that sees only the diff invents the rest. Retrieval fetches the few repo slices that matter and puts only those in the prompt.

Core explanation. You cannot paste a whole repo into a prompt; it overflows and quality drops. Context engineering (= pick the smallest useful context) solves it. For each diff, embed it (turn code into searchable numbers), fetch nearest code plus keyword matches, merge top results, and hand them to every specialist. Three memories feed this: semantic (code, classes, conventions, past design records — vector search), episodic (past reviews: what was flagged or disputed, with time — ordered rows), procedural (how this team likes things — small rules). The transcript keeps one Tiger Cloud Postgres with pgvector, fast scale index plus disk search, and time tables, instead of three separate stores.

  • Embed diff: turn changed lines into a query vector.
  • Search: nearest code + exact names + past reviews.
  • Merge top-k: keep few best slices, drop the rest.
  • Ground: each specialist reasons with citations; keep embedding dims in sync.
What: Diff touches charge(). → So what: Fetch charge() callers + past refund bug to judge impact.
What: Team bans raw SQL strings. → So what: Procedural rule lets security flag it with reason.
Analogy: like pulling only the two recipe cards you need, not the whole cookbook shelf.

❌ What People Get Wrong: bigger context always means better reviews.

Why This Matters: grounding is the main cure for confident invention.

🔗 Feeds Module 4: even grounded claims need a confidence check.

04 / PROOF AND GATE
Bench step · trust but verify

Confidence decides; events prove.

A finding without proof cannot be defended or fixed. Every run leaves a trail, and a gate decides what the user ever sees.

Core explanation. Proof (= records that let you replay a decision) sits beside reasoning and grounding. Every span, model call, tool call, cost, latency, and choice is appended to an event spine (a time-ordered log you can replay). It powers three views: trace (rebuild any review), audit (defend or drop a disputed note), and cost (tokens, latency, per-PR spend with budget caps). The gate is simple: if a finding is critical, escalate at once; else if confidence is below threshold (say 0.6, rising as the system matures), send to the human approval queue; else post. Disputes are stored as feedback so future reviews improve and old, unused feedback fades.

  • Log all: input, retrieval, prompt version, output, cost.
  • Gate: critical → escalate; unsure → human; sure → post.
  • Dispute: developer flags wrong note → record + learn; decay unused feedback.
  • Watch spend + queue: block over-budget runs; rank queues so humans never face thousands unranked.
What: Note says injection at 55% confidence. → So what: Goes to human queue, not public PR.
What: Developer proves a note wrong. → So what: Trail shows bad retrieval; fix it once.
Analogy: like a lab notebook with receipts — claim, method, and price on every page.

❌ What People Get Wrong: a confidence number alone guarantees safety.

Why This Matters: without proof you cannot debug, bill, or earn trust.

🔗 Needs Module 5: gates fail if delivery and retries are sloppy.

05 / SHIP IT
Bench step · fast ack, safe retry

Acknowledge fast, reason slowly.

GitHub waits about 10 seconds. Reasoning needs 30 to 90. The queue between them is what makes the system real. The bench below shows the complete wiring, every box and wire from webhook to posted review.

Core explanation. The ingress (= entry handler) verifies the webhook signature (proves it came from GitHub), checks the idempotency key (= once-only marker using delivery ID) to drop retries, enqueues the job in Redis with ARQ, and answers GitHub at once. A separate worker pool then runs the LangGraph orchestrator: fan-out, aggregate, gate, post. Timeouts on every node stop a hung agent from freezing the merge. Retries with backoff plus circuit breakers survive dead tools. A WorkflowEngine interface (run, resume, get_state) keeps LangGraph swappable for Temporal later. The Genesis harness builds it in milestones, each with a demo command, token budget, and a fresh verifier plus quiz so you prove you grasp each step.

  • Verify then process: signature first, fixed 400 on bad body.
  • Enqueue: Redis holds jobs; receiver stays stateless.
  • Run: LangGraph fans out, merges, gates, posts.
  • Harden: dedup, timeouts, retries, eval set, RBAC, assumption log, dashboard.
What: GitHub resends the same delivery twice. → So what: Second copy is dropped; one review posts.
What: One specialist hangs. → So what: Node times out; merger posts partial + flags gap.
Analogy: receptionist takes the order in seconds; chefs cook in the back without blocking the door.

❌ What People Get Wrong: the model call is the system; queue and gates are extras.

Why This Matters: speed of ack plus safety of retry is what ships.

🔗 Returns to Module 1: every hardening serves selectivity.

GitHub times out in seconds; full review takes much longer, so queue it.

FAQ

Why not just prompt the diff?
One mindset cannot do four jobs, has no repo facts, and leaves no trail.

Why one database, not three?
One store means one backup, one query for retrieve + review + cost, fewer failure seams.

When does a human step in?
Any critical, any low-confidence note, any dispute — the queue, not the thread.

What if the model invents a bug?
Citation rule plus confidence plus trail expose it; dispute teaches the next run.

What needs extra care?
Precise triggers only (a claim at one inbox with the keyword claims, not any email); big vulns in public PRs go via a private channel; money, legal, and health always keep a human; log assumptions so a 9-hour surprise never repeats.
