Building a Software Factory

How a developer-experience engineer at Cursor thinks about turning an AI coding assistant into something closer to a production line — the primitives, the guardrails, and the mindset shift from writer to manager.

Speaker: Eric, Engineer — Developer Experience & Product, Cursor Format: Conference talk + Q&A Core claim: "We're not there yet — but here's the shape of it"

01 Levels of Autonomy

Eric frames the whole talk around a ladder of AI-assisted coding, borrowed loosely from Dan Shapiro's stage model. Most teams today sit around the middle rungs — the interesting question is what the top rung actually requires.

Spicy Autocomplete

In-editor, single-line suggestions

Where Cursor itself started back in 2022–23. The model completes the line you're already writing — it doesn't hold a plan.

Pair Programmer

Back-and-forth with the agent

You ask questions, get suggestions, hand off small tasks, and finish the work together. Most people adopting AI tools today sit between this rung and the next.

AI Writes the Majority

Human stays in the loop, reviewing

The agent produces most of the code. You follow traces and review diffs rather than typing — but you're still reading closely.

Delegator

You review outcomes, not code

As much work as possible goes to agents. You review what came out before you review how it was written — Eric places himself here for most projects today.

The Dark Factory

A black box that plans, ships, and tests itself

Agents plan, write, test, and ship on their own. You no longer supply instructions — only intent and a goal. Nobody is fully here yet.

02 Why a Factory

Three reasons Eric gives for wanting one at all — each borrowed, deliberately, from how physical factories work.

Throughput

More output, fewer humans

Agents can run 24/7 — no sleep, no food, no burnout. You scale by adding agents, not headcount.

Consistency

Assembly lines produce assembly-line output

A well-built factory is deterministic. Feeling like agents are getting "more probabilistic" over time is usually a signal you need more guardrails, not better luck.

Leverage

Your taste, multiplied

The factory gets more of your creativity out into the world instead of bottlenecking it on how fast you personally can type.

03 Building It — Three Pillars

Eric organizes the actual construction work into primitives and patterns, guardrails, and enablers. Each answers a different question about what the agent can find, what it can't touch, and what it's allowed to use.

Primitives & Patterns

Structure the codebase can be discovered in

  • Modularized, co-located code — an agent that can ls one folder and find everything relevant beats one that greps the whole repo.
  • Established usage patterns for auth, startup scripts, and tests, so an agent can be pointed at an existing reference and asked to reproduce it.
Guardrails

What agents can't do, and how you know when they drift

  • Hooks block agents from touching the most sensitive code — auth, encryption — where a mistake is expensive.
  • Rules should emerge from real failures, not be bulk-installed from a directory. A rule is really an SOP for the model.
  • Tests let the agent verify its own work instead of just producing plausible-looking diffs.
Enablers

What you actually let the agent use

  • Skills and MCPs give agents access to external context and capability — e.g. a skill that lets an agent ship a change behind a feature flag and report back.
  • Environment access — if the agent can start your dev environment unattended, it can scale across separate VMs with no practical ceiling.
On rules specifically

Eric calls blanket rule-installation "probably the most misunderstood concept" since Cursor Rules shipped. The instinct is to install every rule for your stack up front; what actually works better is letting rules show up only once you've watched an agent go off the rails and needed to correct it.

04 How to Build It — A Practical Walkthrough

Eric demoed this live rather than describing it in the abstract. Six moves, in the order he actually made them, that turn the three pillars above into a working factory.

1

Let the agent find its own start command

No special setup — point it at the repo. A normal package.json with a start script is enough; the agent already knows to look there first, because that pattern is heavily in-distribution.

2

Write the constitution file

An AGENTS.md at the repo root — a rules file that works across harnesses (Cursor, Claude, others) — spelling out what this specific project's agent can and can't do.

3

Give it a way to check its own work

End-to-end tests — Eric used Playwright — that spawn a real browser and click through the actual user flow. Every change gets run against these before it's trusted.

4

Add a second, automated reviewer

Layer an automated code-review pass — Cursor's own Bugbot, in Eric's case — on top of tests. It catches the things a passing test suite doesn't: style, risk, forgotten edge cases.

5

Isolate each agent's environment

For real parallel work, give each agent its own VM with a full reproducible environment — database, cache, services included — rather than one shared workspace. Git worktrees are fine for shallow tasks, but any stateful service still needs to be branched to keep agents from stepping on each other.

6

Let it prove UI work, not just claim it

For frontend changes, computer-use agents can click through the interface themselves and hand back a recording or screenshots — the fastest way Eric found to trust a visual change without reading every line of the diff.

05 The Build Checklist

Three questions Eric runs through before calling a piece of the factory done.

Runnable

Can it start itself?

Can the agent boot the project — dev server, database, dependencies — with zero human in the loop?

Accessible

Can it reach the context?

Does it have a way into Linear, Notion, Datadog, or Slack, so it understands the broader intent behind the task, not just the diff?

Verifiable

Can it check its own work?

Unit and integration tests cover this well for backend systems with clean contracts. UI work needs the agent to actually click around and confirm buttons, spinners, and flows behave.

06 Running It — Worker to Manager

Once the factory exists, Eric says the job changes more than the code does. Two shifts happen at once.

From
Worker
To
Manager
From
Sync
To
Async

You look at less code and spend more time overseeing agents. Most of the work now happens in the background, so the harder problem becomes aggregating what's changing across every agent you've spawned — not reviewing any single one of them line by line.

Scope & Parallelize

One unit of work per agent. Two agents touching the same part of the codebase at once just means merge conflicts later — scoping is still a human job.

Preserve Tribal Knowledge

Still know how data flows and which parts are critical, so you're directing agents deliberately instead of outsourcing understanding along with the typing.

Frontload Trust

Longer async tasks need more context up front — a plan or a spec — given before you send the agent off, not corrections fed in afterward.

07 Live Automations at Cursor

Four things Eric's team actually automated once they noticed themselves doing the same task by hand, repeatedly.

01 · Daily Review

A standing agent, not a habit

Reads Slack and GitHub each morning and sends a personal summary of the day before — replacing the manual note-taking Eric used to do himself.

02 · PR Comment Mining

Turning review comments into signal

After every merge, an agent reads the human comments left during review — high-signal feedback — and stores the pattern so future agents can learn from it.

03 · Agentic Code Owner

Fixing the 20% that blocked everyone

Human code owners were right ~80% of the time but caused real bottlenecks the rest — wrong time zone, blocked merges. Now an agent scores each PR's risk: low-risk changes self-approve, high-risk ones automatically pull in the right reviewer's prior feedback.

04 · Continual Learning

Rules you were too lazy to write

Instead of manually writing a rule every time he corrects an agent, a plugin scans past transcripts for repeated corrections and turns them into rules on his behalf.

08 Scaling It

The last stretch — from a handful of agents to a fleet.

Observe outcomes

Keep watching where agents go off the rails and what they produce, then feed that back in as a new rule or a piece of design-system context.

Automate the repetitive

Anything you catch yourself doing by hand more than once — copy-pasting logs, exporting a spec from Notion — is a candidate for an automation.

Climb another level

You go from managing 5–10 agents directly to, eventually, an agent that manages other agents underneath you — the same way human orgs grow managers of managers.

No shortcut

Eric is direct about this: there's no clever trick that skips the work. You run a large number of agents, watch what they actually do, and use that observation to keep tightening the guardrails — as long as the safety rails are solid, that trial-and-error is the process, not a failure of it.

09 Key Takeaways
  1. Be explicit about intent.Think hard about the actual problem before you delegate it — vague intent produces vague output at scale.
  2. Don't outsource the decisions that matter.Safety, security, databases, auth, and payments stay human-reviewed, whatever else you automate.
  3. Build the tools before you chase the output.Flywheels and systems are what actually constrain quality over time — not any single prompt.
  4. Store context for later.Transcripts and "this looked good" artifacts teach the agent — and the team — what good actually looks like.
  5. Let the agents be free where it's safe to.Give them the access they're missing, and pay attention when they start complaining about what they can't do.
10 From the Q&A

A few exchanges from the audience that sharpen the talk's edges — expand any of these.

Won't code quality and architecture rot if nobody's reviewing line by line?

Agents share the same "finish the task now" completion bias humans have, without a mental picture of how the code should evolve. Pointing them at good existing references helps, since they tend to continue whatever pattern they see. Eric expects the human role to shift toward more architectural review and periodic refactoring passes, and less line-by-line code review.

How do you keep a team's rules from splintering into one silo per engineer?

Rules tend to start as one person's preference and stay local because nobody wants to force their style on everyone else. Eric compares it to how PR review became a shared team ritual for code — he thinks rules and guardrails need the same kind of forum and consensus-building, and admits the team hasn't fully solved this yet.

What changes for mission-critical, brownfield systems that can't fail?

Spend compute and human attention up front rather than after the fact: hand-write tests for the truly critical paths and run agents against them repeatedly. Cursor's own security team built a narrow "sentinel" automation that checks specific invariants whenever a PR touches sensitive files — closer to red-teaming than to a normal review.

How do you verify a UI actually looks right, not just that it functions?

Cloud agents with computer use can navigate a live site, click through flows, and hand back screenshots or a recording — closer to instructing a QA contractor than to writing a deterministic test. For broader consistency checks, Eric has had an agent open every page referencing a recent change and return screenshots for a human to skim before merging.

Who's accountable when an autonomous change causes an outage?

Shipping more agent-written code doesn't change who's responsible for it — humans remain accountable, so observability and monitoring have to scale alongside the automation. Eric suggests the most sensitive parts of a system may still warrant fully human-written, human-reviewed code rather than agent output at all.
