Storage and Retrieval

How data structures dictate database performance: unraveling the fundamental divergence between write-optimized Log-Structured engines (LSM-trees) and read-optimized In-Place Page engines (B-trees), through to columnar analytical warehouses.

Core Paradigm

Append-Only vs In-Place

Primary Structures

SSTables, LSM-Trees, B+Trees

Workload Profiles

OLTP (Point) vs OLAP (Scan)

Hardware Alignment

Sequential I/O vs 4KB Page I/O

Executive Architecture Summary

At its foundational core, a storage engine must resolve a zero-sum mechanical dilemma: writing is fastest when appending naively to the end of a log, but retrieval is fastest when data is strictly sorted, partitioned, and pre-indexed. Every production database engine represents a specialized compromise between write throughput, read latency, storage amplification, and hardware alignment. Relational workloads (MySQL InnoDB, PostgreSQL) historically optimized for random point queries and updates in-place using 4KB/8KB B-tree pages, whereas modern high-throughput stream systems (Cassandra, RocksDB, ClickHouse) buffer writes in memory (MemTables) and flush sequential, immutable sorted runs (SSTables) compacted in the background. Meanwhile, analytical data warehouses discard row boundaries altogether, organizing data by column to maximize compression ratios and vectorize aggregations over billions of historical records.

Module 01 • The Minimalist Baseline

The World's Simplest Database & Indexing Overhead

Crucial Terms & Mathematical Definitions
Storage Engine
The internal low-level software component of a database management system responsible for storing, reading, and updating raw bytes on non-volatile media (HDD/SSD) and memory buffers.
Index
An auxiliary data structure derived entirely from the primary table data, maintained specifically to accelerate read operations (queries) at the explicit expense of write throughput and storage space.
Append-Only Log
An append-only sequence of immutable records written sequentially to disk. Inserts and updates simply append a newer entry to the tail; deletes append a deletion marker.
Write Amplification
The structural ratio of physical bytes written to underlying storage media divided by the logical bytes submitted in the database write request. Critical for SSD wear and disk saturation.

To understand modern database engines spanning millions of lines of C++, Martin Kleppmann begins with the simplest possible functional database implemented in just two lines of Bash: 

db_set () { echo "$1,$2" >> database.txt; }
db_get () { grep "^$1," database.txt | sed -e "s/^$1,//" | tail -n 1; }

db_set achieves the maximum theoretical write performance possible on any storage medium: an append-only write of $O(1)$ complexity. Appending to a file sequentially avoids costly random disk head movement on HDDs and avoids block erase cycles on SSDs. However, the penalty paid on retrieval is catastrophic: db_get has an algorithmic complexity of $O(N)$. To find a single key among one billion records, the operating system must stream every single byte from disk through CPU memory to parse the comma separator.

This illustrates the iron rule of database storage architecture: an index is a pure trade-off. Any index you add inevitably slows down write operations because every insertion, update, or deletion must update not only the primary data records, but also every secondary index structure. Yet without indexes, ad-hoc point queries on large datasets become computationally intractable.

Why can't we run a production enterprise on this 6-line Bash script? Because it completely ignores transactional atomicity (concurrency conflicts when two processes append simultaneously corrupting lines), crash safety, log size bounding (files grow to infinity), binary data serialization, and page-aligned memory caching.

Appending Sensor Telemetry
A solar panel inverter logging power output every 100ms. An append-only log ingests 10,000 writes/sec without disk seek overhead.
Counter-Intuitive
Updates Are Just Writes
Updating a customer address does not overwrite bytes in-place; it appends the new record. Compaction purges obsolete versions asynchronously.
Edge Case
Disk Full on Unbounded Log
Without background segment compaction or file rollover, high-speed append-only logs fill storage volumes in hours, crashing OS processes.
Analogy • Physical Ledger
An accountant never erases a line in a paper journal with an eraser; they append a compensating entry on the next clean row. Erasing damages the physical paper (SSD flash cell degradation); appending maintains an audit trail.
Misconception • Free Indexes
Junior engineers often add secondary indexes to every column in an ORM migration. In high-write workloads, secondary index maintenance frequently accounts for over 70% of total CPU and I/O write stalls.
Production Reality • Bitcask Hash Index
Riak's Bitcask engine stores an in-memory hash map pointing to byte offsets in append-only files. It delivers blazing fast read/write speeds, but requires every single key to fit entirely in RAM. If your key set exceeds memory, pure hash indexing breaks down.
Memory Pill "Well-chosen indexes speed up reads, but every single index slows down writes."
Module 02 • Log-Structured Storage

SSTables, MemTables & Log-Structured Merge-Trees (LSM-Trees)

Crucial Terms & Architectural Definitions
SSTable (Sorted String Table)
A file format where key-value pairs are strictly sorted by key. Once written to disk, an SSTable file is completely immutable, allowing concurrent reads without locking.
MemTable
An in-memory write buffer backed by a balanced binary tree structure (such as a Red-Black tree, AVL tree, or SkipList). It maintains newly inserted and updated keys in sorted order in RAM.
Write-Ahead Log (WAL)
An append-only sequential log on disk where every incoming mutation is immediately synced before acknowledging the client, ensuring durability if the server crashes before MemTable is flushed.
Compaction
A background merge process that continuously reads multiple sorted SSTable files, merges them using an $O(N)$ multi-way merge sort, preserves the newest version of each key, and discards superseded duplicates or tombstones.
Bloom Filter
A space-efficient probabilistic data structure that tests whether an element is definitely not in a set or possibly in a set. Prevents expensive disk reads for keys that do not exist in an SSTable.
Tombstone
A special deletion marker appended to the MemTable and flushed to an SSTable indicating that a key has been deleted. It prevents an older version in a deeper SSTable layer from resurfacing.

While an append-only log provides unmatched write speeds, a pure hash index fails when datasets outgrow memory or when queries require ranges (e.g. WHERE timestamp BETWEEN x AND y). The breakthrough solution is the SSTable (Sorted String Table), where key-value pairs are stored strictly ordered by key within each segment file.

Maintaining sorted order on disk during random incoming writes would normally require costly random rewrites. The LSM-Tree (Log-Structured Merge-Tree), formalized by Patrick O'Neil et al. in 1996 and popularized by Google Bigtable, LevelDB, RocksDB, and Apache Cassandra, solves this elegantly:

1. In-Memory Buffering (MemTable): When a write arrives, it is appended to an on-disk Write-Ahead Log (WAL) for crash durability, and simultaneously inserted into an in-memory balanced tree (the MemTable, typically a Red-Black tree or SkipList). Because insertions occur in RAM, sorting is fast and cheap.

2. Flushing Immutable SSTables: When the MemTable exceeds a configured size threshold (typically 4MB to 64MB), it is frozen into a read-only state, and a fresh active MemTable is spawned for incoming traffic. A background worker flushes the frozen MemTable sequentially to disk as a brand new SSTable file. Because the keys are already sorted in RAM, the disk write is 100% sequential streaming.

3. Multi-Way Merge Compaction: As SSTable files accumulate across disk storage levels, a background compaction worker runs an algorithm identical to mergesort: it reads multiple sorted files concurrently, iterates through keys in parallel, emits the most recent value, and writes out a single consolidated, tightly packed new SSTable file, deleting the old obsolete files.

For read operations, the database searches the active MemTable first, then any frozen MemTables, and finally searches the SSTables on disk from newest to oldest. To prevent severe read degradation when searching for non-existent keys (which would force scanning every SSTable down to disk), engines attach an in-memory Bloom filter to each SSTable.

High-Velocity Click Events

Counter-Intuitive
Deletes Are Actually Writes
Calling DELETE in Cassandra does not free disk space immediately. It writes a tombstone record to disk, which consumes storage until compaction runs.
Edge Case
Compaction Latency Spikes
If incoming write bandwidth saturates disk bandwidth, background compaction falls behind. Uncompacted SSTables multiply, causing read latency to spike at the 99.9th percentile.
Analogy • Kitchen Ticket Rail
A line cook slaps orders onto an order rail in arrival order (MemTable). Every 15 minutes, the chef stacks them, sorts them by table number, and clips them into historical batch binders (SSTables).
Misconception • Log-Structured Engines Lack Durability
Developers assume that buffering writes in an in-memory MemTable risks losing uncommitted data during power loss. In reality, the Write-Ahead Log (WAL) synchronously guarantees zero data loss via sequential disk flushes.
Production Reality • Size-Tiered vs Leveled Compaction
Cassandra uses Size-Tiered Compaction (combines SSTables of similar sizes), which is faster for heavy write throughput but requires up to 50% temporary disk headroom. RocksDB defaults to Leveled Compaction (splits data into key ranges across discrete levels L0, L1, L2), which minimizes read amplification and uses significantly less transient storage space.

Module 03 • The In-Place Page Standard

B-Trees & Hardware-Aligned Page Storage

Crucial Terms & Mathematical Definitions
B-Tree
A self-balancing search tree structure introduced by Rudolf Bayer and Edward McCreight in 1970 that breaks databases down into fixed-size blocks or pages (traditionally 4KB to 8KB), matching underlying physical hardware sector boundaries.
Branching Factor (Fanout)
The number of child page references held in a single internal B-tree node. A high branching factor (e.g. 500) allows a four-level tree to index billions of records with minimal depth: $\text{Depth} = O(\log_{\text{fanout}} N)$.
Page Split
When an insertion exceeds a page's fixed capacity, the page is split into two half-full pages (typically 50/50), and the parent routing page is updated. Cascading splits can propagate up to the root.
B+Tree Variant
The ubiquitous production variant where interior nodes store only routing boundary keys and page pointers, while all user data records are strictly confined to leaf nodes, linked sequentially via a doubly-linked list for fast range scanning.

Introduced in 1970, the B-tree remains the uncontested default indexing standard across virtually every relational database, including MySQL InnoDB, PostgreSQL, SQLite, Oracle, and Microsoft SQL Server. While LSM-trees divide data into variable-sized sequential segment runs, B-trees structure data into fixed-size blocks or pages (traditionally 4KB to 16KB), mirroring the physical block geometry of spinning disk sectors and SSD flash blocks.

One page is designated as the root. The interior pages contain an ordered array of keys and child page memory/disk references. When looking up a key, the query engine performs a binary search within the root page, identifies the pointer whose range bounds the target key, reads that child page from disk or the buffer pool, and traverses down the tree until reaching the designated leaf page.

The profound strength of the B-tree is its branching factor. With a typical 8KB page size and modest key sizes, an internal page can easily store 500 child pointers. A 4-level tree with a branching factor of 500 can index up to $500^4 = 62.5 \text{ billion records}$, meaning any arbitrary record in a multi-terabyte table can be pinpointed within at most 4 page fetches!

However, updating a B-tree requires in-place mutation. To update an existing record, the database must seek to the exact physical page on disk, read it into the buffer cache, mutate the bytes, and write the entire 4KB or 8KB page back over the exact same disk sectors. If an insertion overflows a page, it triggers an expensive page split. Furthermore, to prevent catastrophic file corruption if power cuts during a multi-page split, B-tree engines must write an independent Write-Ahead Log (or Redo Log) before mutating disk pages, introducing significant write amplification.

Production Reality • SSD Write Amplification in B-Trees
When updating a 20-byte user status field, a B-tree must write the entire 16KB InnoDB page to the SSD. If the flash drive's physical block size is 2MB, updating 20 bytes can trigger 16KB-2MB of NAND write wear.
Memory Pill "Fixed 4KB/8KB hardware pages, high branching factor, in-place updates guarded by WAL."
Module 04 • Physical Record Placement

Clustered Indexes vs Heap Files & The Covering Index Advantage

Crucial Terms & Storage Formats
Heap File
An unordered storage collection where rows are appended to data pages in arbitrary order. Secondary and primary indexes both store direct pointers (Tuple ID: Page Number + Line Offset) to heap locations.
Clustered Index (Index-Organized Table)
A storage architecture where table rows are physically ordered and stored directly inside the leaf pages of the primary key index (as in MySQL InnoDB).
Secondary Index
An auxiliary index built on non-primary columns. In clustered systems (InnoDB), secondary index leaves store the Primary Key value; in heap systems (PostgreSQL), they store the Heap Tuple Pointer.
Covering Index (Index-Only Scan)
An index that contains every column requested by a query in its key list or included payload, allowing the database to satisfy the query entirely from the index structure without jumping to leaf rows or heap files.

When an index pinpoints a matching key, how does the engine actually retrieve the full tuple (the user's name, email, address, and timestamps)? The answer divides database engines into two contrasting architectural philosophies: Clustered Indexes versus Heap Files.

In PostgreSQL, tables are stored in Heap Files. Tuples are placed wherever free space is found across unordered heap pages. Every index on the table—whether primary key or secondary—is identical in structure: its leaf nodes store a Tuple ID (TID) consisting of [Block Number, Offset Index]. Looking up a row via an index requires one tree descent followed by a single direct jump into the heap page. If a row is updated without changing its size, it can be updated in-place inside the heap block without touching any index pointers (PostgreSQL's HOT optimization).

In MySQL InnoDB, tables are strictly Clustered. The primary key index is the table. The leaf pages of the primary B-tree contain the complete columns of the row. This makes primary key lookups extraordinarily fast: descending the primary tree immediately yields the data bytes with zero secondary I/O jumps.

However, this introduces a severe penalty for secondary indexes in InnoDB: secondary index leaf pages cannot store direct physical disk pointers (because if a primary key page splits or rows move, every secondary index would have to be rewritten). Instead, InnoDB secondary indexes store the Primary Key value as their pointer. Thus, a query like SELECT email FROM users WHERE signup_date = '2026-01-01' must traverse the secondary B-tree to find the Primary Key, and then traverse the entire Primary Key B-tree from the root a second time (a "double lookup")!

This explains the profound superpower of a Covering Index. If you create an index on (signup_date, email), the secondary index leaf node already contains the requested email column. The query engine reads the answer directly out of the secondary index page and immediately returns, bypassing the primary key lookup completely.

Analogy • Book Index vs Library Shelf
A Heap File is a warehouse where books are shelved on any open rack; the catalog card gives exact shelf coordinates. A Clustered Index sorts the physical books themselves chronologically on the main shelf.
Misconception • Secondary Indexes Always Point to Disk Rows Directly
In clustered databases like MySQL InnoDB, secondary indexes never point to physical disk addresses; they point to the primary key, requiring a double B-tree descent unless covered.
Production Reality • PostgreSQL HOT (Heap-Only Tuples)
When updating a record in PostgreSQL, if none of the indexed columns were modified and the updated row fits in the same heap page, Postgres creates a Heap-Only Tuple. The index pointers remain untouched, preventing massive index write amplification across all secondary indexes!
Memory Pill "Clustered inlines data in the primary leaf; heap separates indexes from unordered tuple blocks."
Module 05 • Workload Divergence

OLTP vs OLAP Workloads & The Data Warehousing Architecture

Crucial Terms & Workload Archetypes
OLTP (Online Transaction Processing)
Workload pattern characterized by high-concurrency, low-latency queries operating on small numbers of records per request, indexed by primary/secondary keys. Typically user-facing applications (carts, orders, profiles).
OLAP (Online Analytical Processing)
Workload pattern characterized by complex queries scanning millions or billions of rows across a handful of columns to aggregate business metrics (e.g. SUM, AVG, GROUP BY). Typically used by analysts and executives.
Data Warehouse
A dedicated, centralized analytical database (e.g., Snowflake, BigQuery, ClickHouse, Redshift) separated entirely from operational OLTP databases to allow heavy analytical scans without starving production transactional traffic.
ETL (Extract, Transform, Load)
The data engineering process of periodically extracting raw transactional data from operational OLTP systems, transforming and cleaning it into an analytical schema, and loading it into a data warehouse.
Star Schema / Snowflake Schema
A dimensional data modeling pattern consisting of a massive central Fact Table (representing business events: purchases, clicks) surrounded by Dimension Tables (representing who, what, where: products, stores, customers).

In the early days of computing, databases were expected to execute both transactional operations (inserting orders into an e-commerce cart) and reporting queries (calculating total corporate revenue for the past five years). By the late 1990s, this dual-use pattern collapsed under enterprise scale.

Transactional applications demand high concurrency and strict low latency. A user loading their checkout page expects response times under 20 milliseconds. If an executive simultaneously fires an analytical SQL query that scans 50 million historical purchase records with full table scans, the database locks disk pages, evicts active user session buffers from RAM, and brings production customer traffic to a screeching halt.

This fundamental tension led to the architectural separation of OLTP and OLAP. Operational systems remain purely OLTP, running on relational engines (MySQL, Postgres). In the background, an ETL pipeline extracts data (via continuous Change Data Capture or batch export), transforms it into optimized denormalized schemas (Star Schemas), and loads it into a specialized Data Warehouse.

The physical storage mechanics required for OLAP are the polar opposite of OLTP. An OLTP query reads and writes all columns of a single row (e.g. SELECT * FROM users WHERE id = ?). An OLAP query reads one or two columns across hundreds of millions of rows (e.g. SELECT category, SUM(price) FROM sales GROUP BY category). Running such an analytical query on a row-oriented database wastes up to 98% of disk bandwidth loading unused columns into RAM!

ATM Cash Withdrawal

Counter-Intuitive
Redundant Dimension Tables
OLAP star schemas deliberately denormalize dimension tables, sacrificing relational purity to eliminate costly multi-table joins during multi-gigabyte scans.
Edge Case
HTAP (Hybrid Engines)
Modern hybrid engines (TiDB, SingleStore) maintain both a row-store for OLTP writes and an asynchronous replicated columnar store for real-time analytics.
Analogy • Cashier vs Tax Auditor
An OLTP cashier rings up individual items into paper receipts one customer at a time. An OLAP tax auditor arrives at year's end with a team of accountants to compute total quarterly tax across 500,000 receipts.
Misconception • Big Data Means You Need Hadoop/Spark
Modern columnar analytic engines (ClickHouse, DuckDB) running on a single 64-core NVMe server can scan and aggregate 1 billion rows in under 2 seconds, outperforming multi-node distributed clusters by eliminating network serialization.
Production Reality • Protecting Production OLTP from Read Stalls
Running heavy analytical queries directly against an operational OLTP database triggers shared read locks and memory thrashing. Production teams enforce read-only replica routing or streaming CDC into Snowflake/ClickHouse to isolate analytical queries from customer transactions.
Memory Pill "OLTP writes individual rows at low latency; OLAP scans wide columns over decades of history."
Module 06 • Analytical Physics

Column-Oriented Storage, Run-Length Encoding & Bitmap Indexing

Crucial Terms & Compression Fundamentals
Column-Oriented Storage
A physical storage architecture that stores all the values of a single column together contiguously in separate files on disk, rather than grouping all columns of a row together.
Bitmap Index
An indexing technique where each distinct value in a column has a bit vector (array of 1s and 0s) indicating which row numbers contain that value. Ideal for low-cardinality attributes (e.g. status, country, gender).
Run-Length Encoding (RLE)
A lossless compression algorithm that replaces repeated contiguous sequences of the same value with a count and value pair (e.g., [0, 0, 0, 0, 0] becomes 5 × 0), drastically reducing storage footprint.
Vectorized Execution / SIMD
A CPU execution model where single instruction stream operates on multiple data points simultaneously (Single Instruction, Multiple Data), evaluating bitwise AND/OR operations over compressed column bitmaps directly in L1 CPU registers.

In a traditional Row-Oriented database (MySQL, PostgreSQL), row bytes are laid out contiguously: [Row 1: col1, col2, col3...], followed by [Row 2: col1, col2, col3...]. If a fact table has 60 columns and 100 million rows, executing: 

SELECT product_id, SUM(quantity) FROM sales GROUP BY product_id;

forces the storage engine to read every single page containing all 60 columns off disk into memory, discarding 58 unneeded columns (customer addresses, payment tokens, delivery notes) in CPU registers. If the table is 200 Gigabytes, the query must physically pull 200 GB across the PCIe/SATA bus.

In Column-Oriented Storage (Parquet, ClickHouse, Amazon Redshift, DuckDB), each column is stored in its own dedicated, contiguous file: product_id.col, quantity.col, customer_id.col. To execute the query above, the database opens only the files for product_id and quantity. If those two columns consume only 3 GB out of the 200 GB table, disk I/O is reduced by 98.5%!

Even more dramatically, storing column values contiguously enables extreme data compression. In a row store, adjacent bytes have differing types (an integer, followed by a string, followed by a timestamp). In a column store, millions of identical types sit next to each other. If you have 500,000 rows with country = 'US', a Bitmap Index with Run-Length Encoding (RLE) compresses these sequences into a tiny handful of bytes. Queries with multiple filter conditions (e.g., WHERE country = 'US' AND device = 'Mobile') can be resolved by loading the two compressed bitmaps and computing bitwise AND instructions directly inside CPU SIMD registers without ever unpacking the raw data!

Misconception • Column Stores Are Slower Because They Need Stitching
Engineers worry that reconstructing rows slows down queries. But analytical queries rarely reconstruct rows—they compute aggregations (sums, counts) and return only small summarized result sets!
Production Reality • Sort Keys in Columnar Formats
In ClickHouse and Amazon Redshift, all columns are sorted by the table's primary sort key (e.g., timestamp). The first column achieves mind-boggling Run-Length Encoding compression because identical values are physically adjacent, accelerating time-range filtering.
Memory Pill "Store columns together, compress adjacent identical data types, filter with SIMD bitwise math."

Module 08 • Master Reference

Master Definitions Glossary

Exhaustive reference of every core data storage, indexing, and hardware alignment term established in Chapter 3 of Designing Data-Intensive Applications.

Append-Only Log
An immutable file structure where new mutations are simply appended to the end of the file. Maximizes write throughput ($O(1)$) by utilizing sequential disk I/O.
B-Tree / B+Tree
A balanced tree indexing structure that partitions data into fixed-size pages (4KB-8KB). In B+trees, internal nodes route searches and leaves contain data/pointers linked for range queries.
SSTable (Sorted String Table)
An immutable disk file containing key-value pairs sorted strictly by key. Serves as the persistent storage unit of Log-Structured Merge-Trees.
MemTable
An in-memory write buffer backed by a balanced binary search tree (SkipList or Red-Black Tree) that accumulates incoming mutations in sorted order before flushing to an SSTable.
Write-Ahead Log (WAL)
A sequential log on disk where every mutation is durably recorded before updating in-memory data structures or mutating disk pages, enabling complete crash recovery.
Bloom Filter
A probabilistic, memory-efficient bit-array data structure that instantly determines if a key definitely does not exist in an SSTable, preventing unnecessary disk seeks.
Compaction
The background maintenance process in LSM engines that reads multiple sorted SSTable files, merges them using mergesort, discards superseded values, and writes a single compacted run.
Clustered Index
An index structure where row data is physically stored directly inside the leaf pages of the primary key tree (e.g. MySQL InnoDB). Eliminates secondary lookups for primary key queries.
Heap File
An unordered collection of disk pages where table rows are placed arbitrarily wherever free space exists. Indexes store Tuple IDs (TIDs) pointing into the heap (e.g. PostgreSQL).
Covering Index
An index that includes all columns required by a query, allowing the database engine to resolve the request purely from index pages without fetching the underlying table rows.
OLTP (Online Transaction Processing)
Operational database workloads featuring high concurrency, low latency, and single-record point updates and reads (e.g., user checkouts, banking transfers).
OLAP (Online Analytical Processing)
Analytical workloads scanning millions of records across a few columns to aggregate business intelligence metrics (e.g., total quarterly revenue).
Column-Oriented Storage
Storing the values of each database column together contiguously on disk, drastically reducing I/O requirements for analytical queries on wide tables.
Bitmap Index
An index representing distinct column values as arrays of bits (1 for presence, 0 for absence). Enables ultra-fast boolean logic (AND, OR) directly inside CPU SIMD registers.
Run-Length Encoding (RLE)
A compression technique that condenses repeated sequences of the same value into a single count and value descriptor, achieving immense compression ratios on sorted columns.
Tombstone
A special deletion record appended to a log-structured engine to mark a key as deleted, ensuring older versions in deeper SSTable levels are suppressed during compaction.
