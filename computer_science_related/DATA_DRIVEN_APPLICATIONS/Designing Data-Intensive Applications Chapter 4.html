How applications translate in-memory objects into persistent bytes and network packets without breaking compatibility across rolling deployments, schema changes, and distributed microservices.

Executive Systems Summary

In modern distributed architectures, data formats are perpetual contracts. Application code is deployed continuously in rolling phases, meaning older versions of code and newer versions of code run concurrently across server fleets. Consequently, storage and network protocols must guarantee both backward compatibility (newer code parsing older data) and forward compatibility (older code parsing newer data without crashing or dropping unknown fields). While text formats (JSON, XML) prioritize human debuggability, they suffer from type ambiguity and high network bandwidth overhead. Schema-driven binary formats (Protocol Buffers, Thrift, Avro) eliminate string field names from the wire, compress integers using variable-length encodings (Varints), and enforce mathematical schema evolution rules, halving network transit bills and CPU serialization latencies.

Module 01 • Memory to Wire Mechanics

In-Memory Representations vs Wire Byte Sequences

Crucial Terms & Systems Definitions
Encoding (Serialization / Marshalling)
The deterministic translation of in-memory data structures (objects, structs, hash maps, memory pointers) into a self-contained sequence of contiguous bytes suitable for transmission over a network or persistence to disk.
Decoding (Deserialization / Unmarshalling)
The inverse process of taking raw serialized byte streams from a network socket or disk file and reconstituting them into native, language-specific memory objects.
Data Outlives Code
The architectural reality that while code is rewritten, refactored, or redeployed within minutes, data written to disk or databases five years ago must still be faithfully read and decoded by today's software.
Language-Specific Serialization
Built-in language encoders (Java `Serializable`, Python `pickle`, Ruby `Marshal`) that serialize raw memory layouts. Highly discouraged in production due to arbitrary remote code execution (RCE) vulnerabilities and zero cross-language interoperability.

Every software application operates over two fundamentally distinct representations of data. In memory, data is kept in structures optimized for fast CPU instruction access: objects, structs, dynamic arrays, balanced trees, and hash tables with memory pointers linking memory addresses directly. However, memory pointers have meaning only inside a single running operating system process; you cannot send a 64-bit RAM pointer over an Ethernet cable or write it to an SSD block, because another machine (or a restarted process) has an entirely different virtual memory space.

Thus, to transmit data across a network or save it durably to disk, the process must convert its memory structures into a self-contained sequence of bytes. This transition is known interchangeably as encoding, serialization, or marshalling.

Many programming languages provide built-in serialization libraries (such as Java's java.io.Serializable, Python's pickle, or Ruby's Marshal). While convenient for quick prototypes, Martin Kleppmann warns that using language-specific serialization in production is a catastrophic antipattern:

1. Security Vulnerabilities (RCE): Deserializers in these frameworks instantiate arbitrary classes based on byte instructions, enabling attackers to inject payload byte streams that execute arbitrary shell commands inside your server.

2. Language Lock-in: A Python process cannot natively decode a Java Serializable stream without complex proxy layers, preventing your architecture from evolving into modern polyglot microservices.

3. Zero Compatibility Governance: Language-specific formats tightly couple the serialization stream to private class fields, causing instant deserialization crashes when a developer refactors a class name or changes a field type.

Obvious Case
Language-Neutral JSON
A Go backend serializing a user profile to JSON; an iOS Swift app and a React browser client decode the payload seamlessly.
Counter-Intuitive
Pickle Security Exploits
Accepting a Python pickle file from an untrusted client allows execution of os.system('rm -rf /') during the simple pickle.loads() invocation!
Edge Case
Java Serialization UID Mismatch
Adding a private debug field to a Java entity invalidates its serialVersionUID, causing cached session objects in Redis to fail with InvalidClassException.
Analogy • Flat-Pack Furniture
An assembled wooden desk in your office (in-memory object with joints and legs) cannot fit through a narrow postal slot. You must disassemble it into a flat cardboard box with bolts and screws (serialized byte stream), ship it across town, and reassemble it in the destination room.
Misconception • Built-in Encoders Are Production-Grade
Engineers assume built-in language tools are optimized. In reality, Python's pickle and Java's Serializable are notoriously slow, consume excessive memory buffers, and introduce severe CVE security vulnerabilities.
Production Reality • Standardized Binary Schemas
Enterprise architectures strictly mandate standardized, language-agnostic serialization formats (Protocol Buffers, Avro, Thrift, or JSON Schema) across all network RPC boundaries, database caches, and message queues to ensure 100% interoperability and security isolation.
Memory Pill "Never use language-specific serializers; data always outlives the running application code."
Module 02 • Human-Readable Text

Textual Formats (JSON, XML, CSV) & The 64-Bit Float Precision Trap

Crucial Terms & Numerical Standards
JSON (JavaScript Object Notation)
A lightweight, text-based, language-independent data interchange format based on a subset of JavaScript object literals. Uses key-value maps and arrays.
IEEE 754 Double Precision (64-Bit Float)
The standard floating-point format used by JavaScript for all numbers. Has 53 bits of precision, meaning integers greater than $2^{53} - 1$ ($9,007,199,254,740,991$) cannot be represented exactly and suffer silent bit rounding.
Base64 Encoding
A scheme that converts raw binary byte sequences into ASCII characters to safely travel over text protocols (like JSON or XML), introducing an unavoidable 33% data bloat.
Field Name Verbosity
The overhead caused by text formats explicitly printing field strings (e.g. "transaction_timestamp_utc") in every single record, consuming up to 80% of the byte payload.

Textual formats—predominantly JSON, XML, and CSV—are the undisputed lingua franca of the public web and HTTP REST APIs. Their overwhelming popularity stems from being human-readable, easily debuggable in curl/browser consoles, and natively supported in every language without compilation steps.

However, textual formats have severe structural flaws that become crippling at production scale:

1. Ambiguous Number Types & The JavaScript Float Trap: In XML and CSV, numbers and digit strings are indistinguishable without external schemas. In JSON, there is no distinction between integers and floating-point numbers. Furthermore, JavaScript engines parse all JSON numbers as IEEE 754 double-precision 64-bit floats, which only provide 53 bits of integer mantissa ($2^{53} - 1 = 9,007,199,254,740,991$). If a database sends an unsigned 64-bit integer ID (e.g., a Twitter tweet ID or Snowflake ID like 9007199254740993), JavaScript quietly rounds it down to 9007199254740992, corrupting primary keys!

2. Inefficient Binary Data Handling: JSON and XML cannot directly embed raw binary bytes (such as JPEG thumbnails or encrypted byte blobs). Applications must encode them into Base64 strings, increasing payload size by 33% and wasting CPU cycles encoding and decoding.

3. Extreme Text Verbosity: When sending a collection of 50,000 JSON records, the field name strings ("user_identification_number", "shipping_address_line_1") are printed 50,000 separate times! In high-volume internal microservices, up to 75% of network bandwidth is wasted transmitting repeated string keys.

JSON is a full English invoice written out by hand with descriptions. A binary schema is a standardized 2D barcode: compact, error-checked, and read by machine scanners in microseconds.
Misconception • JSON is Compact Enough for Microservices
Parsing and stringifying JSON in high-throughput microservices consumes up to 30% of total CPU cycles in Node.js, Go, and Java services just converting strings to memory objects.
Production Reality • The id_str Workaround in Enterprise APIs
Because JavaScript frontend clients run in millions of browsers, backend APIs dealing with 64-bit integer keys (Snowflakes, UUID ints) must always serialize IDs as strings ("id": "184920491029301923") to prevent silent browser rounding.
Memory Pill "JSON numbers larger than $2^{53}$ silently round in JavaScript; always send large IDs as strings."
Module 03 • Schema-less Binary Encoding

Binary Encoding without Predefined Schemas (MessagePack & BSON)

Crucial Terms & Format Profiles
MessagePack
A binary serialization format for JSON-like objects that replaces textual punctuation (curly braces, commas, colons) with single-byte type and length headers, while preserving field names as literal strings.
BSON (Binary JSON)
The primary storage and wire format used by MongoDB. Extends JSON with explicit data types (Date, Raw Binary, Int64, Decimal128) and prepends byte-length headers for fast field traversal.
Schema-less Binary Overhead
The limitation that because no external schema file exists, the binary byte stream must carry every field name string inside every single encoded record, yielding only modest (10-25%) compression over raw text.

Recognizing the CPU and size inefficiency of text JSON, early binary efforts sought to create drop-in binary replacements that required no changes to application code and no schema definitions. The prominent results are MessagePack, BSON (MongoDB), and CBOR.

How does MessagePack encode a JSON object like {"userName": "Martin", "favoriteNumber": 1337, "interests": ["daydreaming", "hacking"]}?

1. It replaces the outer curly brace { with a single byte 0x83 (indicating a map with 3 key-value entries).

2. It encodes the first key as 0xa8 (string of length 8), followed by the 8 ASCII bytes u s e r N a m e.

3. It encodes the integer 1337 as a 2-byte uint16 (0xcd 0x05 0x39), saving bytes compared to the 4-byte string "1337".

When you tally the entire MessagePack byte sequence for this record, it comes out to 66 bytes, compared to 81 bytes for minified JSON. While shaving off 15 bytes is an improvement, it is fundamentally disappointing. Why did a binary format only achieve a modest 18% size reduction?

Because all field names are still stored explicitly as ASCII strings inside the byte stream! The bytes for "userName", "favoriteNumber", and "interests" account for 32 out of the 66 bytes—nearly 50% of the entire payload! To achieve true compaction, a format must eliminate field names from the wire entirely.

Obvious Case
MongoDB BSON Storage
MongoDB stores documents in BSON, enabling native Date objects and raw binary fields without string parsing overhead.
Counter-Intuitive
BSON Can Be Larger Than JSON
BSON includes explicit document length prefixes and type markers, frequently making a BSON document larger than gzip-compressed JSON!
Edge Case
Redis Caching with MessagePack
Using MessagePack for Redis cache values speeds up serialization by 2.5x over JSON without needing schema compilers.
Analogy • Shorthand vs Removing Names
MessagePack is like an office clerk using abbreviations for punctuation ("obj:3" instead of "{ }"), but still writing out full employee job titles on every single index card.
Misconception • Binary Automatically Means Ultra-Small
Binary encoding without an agreed-upon schema cannot eliminate string keys. If your schema has 20 long field names, a schema-less binary payload remains mostly ASCII text.
Production Reality • When to Choose MessagePack
MessagePack is ideal when you need a fast, zero-configuration 2x serialization speedup for dynamic payloads where schema definition is impossible (such as arbitrary user JSON logs in Elasticsearch/Fluentd).
Memory Pill "Schema-less binary formats save punctuation bytes, but still waste bandwidth transmitting string field names."
Module 04 • Schema-Driven Compaction

Protocol Buffers (Protobuf), Apache Thrift & Variable-Length Integers

Crucial Terms & Binary Encoding Mechanics
Protocol Buffers (Protobuf)
Google's open-source, language-neutral, schema-driven binary serialization mechanism. Replaces field name strings on the wire with compact integer field tags and wire types.
Field Tag (Field Number)
A unique integer identifier assigned to each field in a .proto schema (e.g. string user_name = 1;). The field tag is what actually travels in the binary wire format.
Varint (Variable-Length Integer)
An integer encoding method where the Most Significant Bit (MSB) of each byte serves as a continuation flag. Small integers (0–127) take 1 byte; larger integers expand dynamically to multiple bytes.
ZigZag Encoding
A bit-manipulation algorithm that maps signed integers to positive unsigned integers ($0 \to 0, -1 \to 1, 1 \to 2, -2 \to 3$), preventing negative numbers from consuming 10 bytes in standard two's-complement varint encoding.

The breakthrough in efficient binary serialization came when Google developed Protocol Buffers (Protobuf) and Facebook created Apache Thrift. Both frameworks operate on a fundamental insight: if the sender and receiver both possess a pre-compiled schema, the wire format does not need to contain field name strings at all!

In Protobuf, a schema is defined in a .proto file: 

message Person {
  required string user_name       = 1;
  optional int64  favorite_number = 2;
  repeated string interests       = 3;
}

When Protobuf serializes this record, it represents each field as a 1-byte Tag Header combining the Field Number and the Wire Type (encoded as (field_number << 3) | wire_type). For field 1 (user_name, wire type 2 for length-delimited string), the tag byte is simply 0x0A. It then writes a 1-byte string length (0x06), followed by the 6 raw ASCII bytes M a r t i n. The string "user_name" is never transmitted.

For numeric fields, Protobuf employs Variable-Length Integers (Varints). In standard fixed 64-bit integer encoding, the number 1337 consumes 8 full bytes on disk. In a Varint, each byte uses 7 bits for data and 1 bit (the MSB) as a continuation marker:

  • If the integer fits in 7 bits ($0 \le x \le 127$), the MSB is 0, and the number consumes precisely 1 single byte!
  • For 1337, it splits into two 7-bit chunks: 0x39 and 0x0A, resulting in the 2-byte sequence 0xb9 0x0a (the MSB of the first byte is 1 indicating more bytes follow).

Thanks to field tags and varints, the exact same record that took 81 bytes in JSON and 66 bytes in MessagePack compresses down to just 33 bytes in Protobuf—a massive 60% bandwidth reduction!

Analogy • Numbered Form Fields
A paper tax return asks you to fill boxes labeled [1], [2], [3]. When submitting by mail, you only write "1: John, 2: 45000", leaving out the printed legal questions.
Misconception • Field Tags 1–15 and 16+ Are Identical
Field tags 1 through 15 encode the tag number and wire type in a single byte. Field tags 16 and above require 2 or more bytes. Reserve tags 1–15 for your most frequently used fields!
Production Reality • gRPC Microservice Standards
Modern high-throughput internal microservices at Google, Netflix, and Uber use gRPC (HTTP/2 + Protobuf) exclusively for inter-service RPCs, slashing network egress costs and eliminating JSON serialization CPU bottlenecks.
Memory Pill "Protobuf transmits integer field tags instead of string names; varints shrink small numbers to 1 byte."
Module 05 • Dynamic Schema Resolution

Apache Avro & Dynamic Schema Resolution

Crucial Terms & Big Data Serialization
Apache Avro
A schema-driven binary data serialization system developed within the Apache Hadoop project. Uniquely, Avro binary streams contain neither field names nor tag numbers nor data types.
Writer's Schema
The precise schema definition that the producing application used when it serialized and wrote the record to disk or the Kafka topic.
Reader's Schema
The schema definition that the consuming application expects and compiles against when decoding incoming records into memory.
Schema Registry
A centralized network service (e.g. Confluent Schema Registry) that stores all versioned Avro schemas. Messages on Kafka include only a 4-to-8 byte Schema ID prefix rather than the full schema string.

While Protobuf and Thrift rely on static integer field tags, Apache Avro takes binary compaction to its theoretical limit. In Avro, the binary encoding of a record is simply the raw values concatenated together: a length prefix followed by string characters, followed by a varint integer, followed by repeated array items.

There are no field tags, no field names, and no wire type markers anywhere in the record byte stream. For our sample record, Avro produces a binary payload of just 32 bytes.

How can an Avro decoder parse a stream of raw concatenated bytes without any delimiters or tags?

The secret is Dynamic Schema Resolution:

1. The decoder reads the bytes by walking through the fields in the exact order specified by the Writer's Schema (the schema used when the file or message was generated).

2. The decoder compares the Writer's Schema against the application's Reader's Schema by matching field names. If the field order differs between the two schemas, the Avro library dynamically rearranges the fields in memory.

3. If the Writer's Schema contains a field that the Reader's Schema does not recognize, Avro reads the bytes using the writer schema's type and silently skips over them. If the Reader's Schema expects a field that was not present in the Writer's Schema, Avro automatically populates the missing field using the default value declared in the Reader's Schema.

Where does the Writer's Schema come from? In large analytics files (like Apache Parquet / Hadoop container files), the full Writer's Schema is written once at the beginning of the multi-gigabyte file. In streaming message queues like Apache Kafka, producers register schemas in a Schema Registry and prepend a tiny 4-byte Schema ID to each message, enabling high-throughput validation without sending schema text.

Misconception • Avro Requires Embedding Schema in Every Packet
Beginners fear Avro schemas waste network bandwidth. In real-time message streams, only a 4-byte Schema ID is sent; the consumer fetches the full schema once from the Schema Registry and caches it.
Production Reality • Schema Evolution in Data Lakes
In petabyte data lakes (Parquet/ORC/Avro on S3), Hive and Spark query tables spanning 5 years of evolving schemas. Avro's dynamic resolution allows modern queries to scan legacy 2021 files alongside 2026 partitions seamlessly.
Memory Pill "Avro transmits zero tags or field names; decoders dynamically resolve Writer Schema against Reader Schema."
Module 06 • Compatibility Engineering

Schema Evolution: Backward, Forward & Full Compatibility

Crucial Terms & Compatibility Axioms
Backward Compatibility
Newer code can read and decode data that was written by older code. (Essential when deploying new backend code that must read existing historical database records or cache entries).
Forward Compatibility
Older code can read and decode data that was written by newer code. (Essential during rolling deployments where un-upgraded servers or older mobile app versions receive messages from upgraded servers).
Full Compatibility
A schema evolution guarantee that is simultaneously backward compatible AND forward compatible across all versions.
Rolling Upgrade (Phased Deployment)
Deploying a new software version across a 100-node server cluster gradually (e.g. 5 nodes at a time) to avoid downtime. For hours, v1 and v2 software run simultaneously and exchange data.

In large-scale production environments, instantaneous global upgrades are impossible. When deploying a new release across 500 microservice nodes, the deployment proceeds as a rolling upgrade. For a window of minutes to days, 50% of your fleet runs Version 2 while the remaining 50% runs Version 1. Furthermore, mobile clients (iOS/Android) may not update for months.

This operational reality establishes the twin pillars of schema evolution:

1. Backward Compatibility Rules: To ensure newer code can read older data:

  • Every newly added field must be optional or declare a sensible default value. If new code reads an old record where the field does not exist, it falls back to the default.
  • You must never add a required field in a newer schema version!

2. Forward Compatibility Rules: To ensure older code can read newer data:

  • When older code encounters a field tag or column it does not recognize, it must gracefully ignore and skip it rather than crashing.
  • You can only remove a field that was optional (or had a default), and you must never reuse its tag number in future schemas.

A critical subtle bug occurs when data flows through an intermediary node: if Version 1 of a service reads a Version 2 record, modifies an unrelated field, and writes the record back to the database, will it preserve or discard the unknown Version 2 fields? In Protobuf and Thrift, newer libraries preserve unknown fields in memory to prevent silent data corruption during round-trips!

Schema Modification Action Backward Compatible? Forward Compatible? Safety Verdict & Rule
Add an Optional field with Default YES YES 100% Safe (Fully Compatible)
Add a Required field NO (Old data lacks it) YES DANGEROUS: Breaks reading old data
Remove an Optional field YES NO (Old code expects it) CAUTION: Must reserve tag number
Change Field Tag Number (Protobuf) NO NO FATAL: Corrupts all decoders
Change 32-bit int to 64-bit int YES (in Protobuf varint) NO (64-bit truncated to 32) PARTIAL: Safe only if values fit 32-bit
Obvious Case
Adding an Optional Avatar URL
Adding optional string avatar_url = 4; allows v2 code to render images while v1 code safely skips tag 4.
Counter-Intuitive
Removing Required Fields
You can never safely remove a required field. Old code will reject every single new record as invalid and throw exceptions.
Edge Case
Reusing Tag Numbers
Deleting phone_number = 3 and later defining email = 3 causes old clients to parse email strings as phone numbers!
Analogy • Electrical Plugs
A modern 3-prong grounded wall outlet is backward compatible (accepts old 2-prong plugs) and forward compatible (old 2-prong extension cords can still plug into modern wall circuits).
Misconception • Schema Validation Should Reject Unknown Fields
Strict schema validators that throw errors on encountering unknown fields completely destroy forward compatibility, making rolling deployments impossible without full downtime.
Production Reality • Protobuf 3 Removed the `required` Keyword
Google learned from painful production outages that required fields prevent safe schema evolution. As a result, Protobuf version 3 completely removed the required keyword, making all fields optional by default!
Memory Pill "Only add optional fields with defaults; never change tag numbers; preserve unknown fields."
Module 07 • Data in Motion

Modes of Dataflow: Databases, RPC (REST/gRPC) & Asynchronous Message Queues

Crucial Terms & Communication Topologies
Dataflow Through Databases
Communication where a process writes bytes to a database and another process reads them later. The writer and reader may be separated by milliseconds or by decades ("data outlives code").
Remote Procedure Call (RPC)
A synchronous client-server communication paradigm that attempts to make a network request look syntactically like calling a local function in the programming language (e.g. gRPC, Thrift, REST).
Asynchronous Message Broker
An intermediary service (such as Apache Kafka, RabbitMQ, or AWS SQS) where producers publish messages to named topics/queues, and consumers process them asynchronously with decoupled lifecycles.
Backpressure & Load Buffering
The capability of a message queue to absorb sudden traffic spikes (e.g., 50,000 requests/sec during Black Friday) and buffer them safely on disk, preventing backend database crashes.

Whenever data leaves an in-memory process, it must flow through one of three primary communication channels:

1. Dataflow Through Databases: In database storage, the process that wrote the data may have executed 5 minutes ago or 5 years ago. A single table often contains rows written by ten different historical versions of application code. Unless all migrations preserve backward and forward compatibility, legacy rows will crash new services.

2. Dataflow Through Service Calls (REST & RPC): In web architectures, clients (browsers, mobile apps) talk to servers via REST over HTTP, while internal microservices communicate via RPC (Remote Procedure Calls) such as gRPC. However, Martin Kleppmann emphasizes that network RPC is fundamentally flawed when treated like a local function call: local function calls are deterministic and fast, whereas network requests are vulnerable to packet drops, variable network latency, server timeouts, and partial failure states where a server executes an action but the network drops the acknowledgement.

3. Dataflow Through Asynchronous Message Passing (Kafka, RabbitMQ): In high-scale systems, sending requests directly between synchronous services leads to catastrophic cascading failure: if downstream Service B slows down, upstream Service A exhausts its connection thread pool and crashes.

An asynchronous message broker decouples the producer from the consumer:

  • Load Leveling (Buffering): If 100,000 checkout requests spike during a flash sale, Kafka buffers them safely on disk; backend payment workers consume at their maximum stable rate (e.g., 5,000/sec) without crashing.
  • Fault Isolation: If the downstream inventory service crashes, messages accumulate safely in the broker until the service restarts, with zero lost transactions.
  • Fan-out (Pub/Sub): A single order event published to Kafka can be consumed simultaneously by the payment service, notification service, analytics pipeline, and fraud detection engine.

Analogy • Phone Call vs Voice Message
An RPC call is a telephone call: both parties must be available simultaneously, and if one drops out, the conversation fails. A message queue is voicemail: you leave a recorded message and the recipient listens when they are free.
Misconception • Message Brokers Eliminate Failure
Message queues decouple availability, but introduce new failure modes: out-of-order message delivery, duplicate delivery requiring idempotency, and consumer lag accumulation.
Production Reality • Idempotent Consumer Design
Because distributed message queues guarantee at-least-once delivery, network acknowledgements can drop, causing consumers to receive duplicate messages. Production consumers must be strictly idempotent (e.g. using unique transaction IDs or database upserts) to prevent charging customer credit cards twice!
Memory Pill "RPC tightly couples availability and latency; message brokers buffer spikes and isolate service failures."
Module 08 • Master Reference

Master Definitions Glossary

Exhaustive reference of every core data encoding, serialization format, schema evolution rule, and network communication term established in Chapter 4 of Designing Data-Intensive Applications.

Encoding (Serialization)
The deterministic translation of in-memory data structures (objects, structs, hash maps) into a self-contained sequence of contiguous bytes suitable for transmission over a network or persistence to disk.
Decoding (Deserialization)
The inverse process of parsing a serialized byte stream from a network socket or disk file and reconstituting it into native, language-specific memory objects.
Backward Compatibility
Newer code can read and decode data that was written by older code. Essential for reading historical database records or cache entries.
Forward Compatibility
Older code can read and decode data that was written by newer code. Essential during rolling phased deployments across microservice clusters.
Full Compatibility
A schema evolution state that is simultaneously backward compatible AND forward compatible across all versions.
Protocol Buffers (Protobuf)
Google's open-source, language-neutral, schema-driven binary serialization mechanism that replaces string field names on the wire with compact integer field tags and wire types.
Field Tag (Field Number)
A unique integer identifier assigned to each field in a .proto or Thrift schema. Serves as the key identifier in the binary wire format.
Varint (Variable-Length Integer)
An integer encoding method where the Most Significant Bit (MSB) of each byte indicates continuation. Allows small integers (0–127) to consume just 1 byte.
ZigZag Encoding
A bitwise mapping that interleaves negative and positive integers ($0 \to 0, -1 \to 1, 1 \to 2$), preventing negative numbers from ballooning to 10 bytes in varints.
Apache Avro
A schema-driven binary data serialization format for Hadoop and Kafka that transmits pure concatenated values with neither field tags nor field names in the byte stream.
Writer's Schema vs Reader's Schema
The schema used when data was written versus the schema expected by the consumer. Avro dynamically matches field names between the two during deserialization.
Schema Registry
A centralized service (e.g. Confluent Schema Registry) that stores versioned Avro/Protobuf schemas. Messages include only a 4-byte Schema ID prefix.
MessagePack
A schema-less binary encoding for JSON that removes punctuation syntax (braces, colons), but still retains full field name strings in every encoded record.
Remote Procedure Call (RPC)
A synchronous network communication abstraction that attempts to make a remote network request look like calling a local function in application code (e.g. gRPC).
Asynchronous Message Broker
An intermediary service (such as Apache Kafka, RabbitMQ, or AWS SQS) where producers publish messages to named topics/queues for asynchronous processing.
IEEE 754 64-Bit Float Trap
The limitation where JavaScript parses all numbers as 64-bit floats with 53-bit integer precision, silently corrupting numeric IDs exceeding $9,007,199,254,740,991$.
