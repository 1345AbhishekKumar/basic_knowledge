Transactions, ACID & Isolation Levels

In distributed systems and relational engines, hardware crashes, network partitions, race conditions, and out-of-order writes are unavoidable realities. Transactions are an abstraction mechanism designed to simplify application development by grouping multiple reads and writes into a single logical execution unit with strict safety guarantees.

Module 01

The Foundations of ACID: Deconstructing the Myth

In database theory and software engineering folklore, ACID (Atomicity, Consistency, Isolation, Durability) is frequently invoked as a golden stamp of absolute transactional safety. Coined in 1983 by Theo Härder and Andreas Reuter building on Jim Gray’s seminal 1970s transaction research, ACID was designed to establish a precise vocabulary for fault-tolerance in data management systems.

However, in commercial database marketing, ACID has degraded into a vague catch-all buzzword. Different vendors define and implement ACID properties in wildly divergent ways. To build resilient applications, engineers must deconstruct each letter of ACID and understand what the database engine guarantees versus what remains the software developer’s responsibility:

Atomicity (Abortability): Atomicity does not mean concurrency safety (which is the job of Isolation). Atomicity means all-or-nothing execution with clean abortability. If a transaction consists of multiple writes (e.g., updating a user’s balance, deducting inventory, and inserting an audit log), and a failure occurs halfway through—such as a network drop, a power loss, a disk quota exhaustion, or a unique constraint violation—the database discards or rolls back all modifications made by that transaction. The database never leaves the data in a half-finished state.

Consistency (Application Invariants): Unlike Atomicity, Isolation, and Durability—which are pure properties of the database engine—Consistency is fundamentally an application-level invariant. If your business rule states that "credits must equal debits" or "a bank balance cannot drop below zero", the database cannot inherently understand your application logic. The database provides tools (such as foreign key constraints and UNIQUE checks), but if the application writes malformed or illogical data, the database will faithfully store that bad data. Therefore, Consistency belongs to the application.

Isolation (Concurrency Control): Concurrently executing transactions must not interfere with or corrupt each other. The ultimate ideal of isolation is Serializability: the guarantee that even if thousands of transactions run concurrently on multi-core CPUs, the final database state is identical to what would have occurred if they ran one after the other in serial sequence.

Durability (Crash Resilience): Once a transaction successfully commits, its written data will never be lost, even if the database process crashes or hardware powers down immediately afterward. In a single-node database, durability is achieved via a Write-Ahead Log (WAL) flushed to non-volatile storage with fsync. In modern cloud databases, durability relies on cross-datacenter quorum replication.

Core Architectural Definitions
🛑 Abortability (Atomicity)
The ability of the database to discard all partial writes of a failed transaction, allowing the client to safely retry without leaving corrupt state.
⚖️ Application Invariant (Consistency)
A business truth about the data (e.g. accounting balances) that must always hold true before and after a transaction commits.
💾 Write-Ahead Log / WAL (Durability)
An append-only log on disk where modifications are written and fsynced before pages are altered in the buffer pool.
1

Transaction Initiation & WAL Buffering

The client issues BEGIN. As SQL statements execute, modifications are buffered in memory and recorded to the Write-Ahead Log buffer with the allocated transaction identifier (TxID).

2

Constraint Validation & Fault Detection

Before committing, the engine validates unique indexes, foreign keys, and column nullability. If any statement triggers an error, the database enters an error state and rejects further commands until rollback.

3

Synchronous Fsync on Commit vs. Instant Undo

On COMMIT, the WAL buffer is flushed to disk via fsync(). On failure or ROLLBACK, the engine rolls back in-flight changes using Undo logs (MySQL) or marks tuples as dead (Postgres).

Obvious Case

Bank Transfer Debit & Credit

Deducting $100 from Alice and adding $100 to Bob must execute in one atomic transaction. If the server crashes after deducting Alice, atomicity ensures Alice’s $100 is refunded on restart.

Counter-Intuitive

Consistency Is Not a Database Guarantee

If your software accidentally transfers funds to the wrong user account number, the database will happily commit the transaction. The database guarantees ACID atomicity and isolation, not your business logic.

Edge Case

Multi-Datacenter Durability Mirage

A single-node database that completes fsync is durable against OS crashes, but if a fire destroys the datacenter, data is lost. True durability in 2026 requires multi-region synchronous replication.

💡 Real-World Analogy

Atomicity is like a contract signing ceremony: either both parties sign every page and exchange keys, or someone tears up the paperwork and no property changes hands.

❌ What People Get Wrong

Confusing Atomicity with Thread Isolation. Atomicity only protects against crashes and partial write failures; it does NOT prevent two concurrent threads from reading and overwriting each other’s data.

📌 Production Reality

Databases that promise "ACID" without specifying their isolation level often default to weak isolation (Read Committed), leaving systems vulnerable to subtle concurrency anomalies.

🔗 Inter-Module Link

Because atomicity only solves partial crash failures, we must explore Isolation levels (Module 2) to control how concurrent transactions see each other’s writes.

🧠 Memory Anchor: Atomicity = Abortability (clean rollback on crash); Consistency = Invariant preservation (your code); Isolation = Concurrency control; Durability = Non-volatile persistence.
Module 02

Weak Isolation Levels & The Concurrency Anomaly Hierarchy

If transactions could only be executed one after another in strict serial order, database concurrency bugs would not exist. However, true serial execution destroys performance: throughput plummets and latency skyrockets on multi-core database servers handling thousands of simultaneous connections.

To maintain high transaction throughput, relational databases implement Weak (Non-Serializable) Isolation Levels. Instead of guaranteeing absolute isolation, weak isolation levels trade specific concurrency safety guarantees for raw speed. Unfortunately, weak isolation introduces subtle, notoriously difficult-to-debug concurrency phenomena (race conditions):

1. Dirty Reads: A transaction reads data written by another concurrent transaction that has not yet committed. If Transaction A updates a row from $100 to $200, and Transaction B reads $200 before Transaction A aborts and rolls back to $100, Transaction B made decisions based on data that technically never existed.

2. Dirty Writes: A transaction overwrites uncommitted data that was written by another concurrent transaction that has not yet committed. If Transaction A updates the buyer of a car and Transaction B concurrently updates the recipient of the invoice on the same car, dirty writes can cause the invoice to go to Transaction B’s user while the car is transferred to Transaction A’s user.

3. Non-Repeatable Read (Read Skew): A client reads the same record twice during a single transaction and sees different values because another transaction committed an update in between. The classic example is a bank transfer: Alice has two accounts with $500 each ($1000 total). She checks Account 1 (sees $500). Concurrently, Bob transfers $100 from Account 2 to Account 1 and commits. Alice then checks Account 2 (sees $400). In Alice’s view, her total balance is $900—a temporary illusion of lost money called Read Skew.

Read Committed is the industry’s most widely used baseline isolation level (the default in PostgreSQL, Oracle, and SQL Server). It completely eliminates Dirty Reads (by only returning committed data) and Dirty Writes (by acquiring row-level write locks until commit). However, Read Committed does not prevent Read Skew, Lost Updates, or Write Skew.

Core Concurrency Anomalies
👻 Dirty Read
Reading uncommitted modifications made by another in-flight transaction that might later be aborted.
✍️ Dirty Write
Overwriting uncommitted data written by another active transaction, corrupting multi-table integrity.
📉 Read Skew (Non-Repeatable Read)
Seeing different snapshots of the database at different points in time during a single transaction.

Module 03

Snapshot Isolation & MVCC Internals: PostgreSQL vs. MySQL InnoDB

The definitive solution to Read Skew without sacrificing read throughput is Snapshot Isolation (commonly called Repeatable Read). Under snapshot isolation, each transaction reads from a consistent point-in-time snapshot of the database taken at the exact moment the transaction began.

The core design principle of snapshot isolation is: Readers never block writers, and writers never block readers. A long-running analytics query or database backup can execute for hours without taking read locks, while concurrent write transactions continue modifying the database at full speed.

To implement snapshot isolation, storage engines use Multi-Version Concurrency Control (MVCC). Instead of overwriting existing table rows in-place, the database maintains multiple physical versions of each row simultaneously. Each version is stamped with metadata identifying the creating transaction ID and the deleting/updating transaction ID:

PostgreSQL MVCC (Append-Only Tuples & Heap Vacuuming): In PostgreSQL, every row (tuple) in the heap table contains hidden header columns: xmin (the transaction ID of the transaction that inserted the row) and xmax (the transaction ID of the transaction that deleted or updated the row; 0 if still active). When an UPDATE runs, PostgreSQL does not modify the old row; it writes a brand-new tuple into the heap and sets xmax on the old tuple.

The visibility rule is straightforward: A transaction with ID $T$ can see a tuple if $T \ge \text{xmin}$, the creating transaction was committed, and either $\text{xmax} = 0$ or $\text{xmax} > T$ (meaning the row was deleted after $T$ began). Over time, old row versions that are no longer visible to any running transaction become "dead tuples". PostgreSQL uses a background Auto-Vacuum daemon to scan pages, mark dead tuple slots as reusable, and prevent severe Table Bloat.

MySQL InnoDB MVCC (In-Place Clustered Index & Undo Logs): MySQL InnoDB takes a radically different architectural approach. InnoDB stores table data directly inside a clustered B-Tree index organized by primary key. When an UPDATE occurs, InnoDB modifies the row in-place inside the B-Tree page to maximize cache locality and eliminate heap bloat.

To provide snapshot views for older running transactions, InnoDB records the before-image of the modified row into an Undo Log segment on disk and attaches a 7-byte rollback pointer (DB_ROLL_PTR) to the row. When an older transaction queries the row, InnoDB follows the rollback pointer chain back through the Undo Log to reconstruct the historical row snapshot on the fly in memory. Once all older transactions commit, a background purge thread truncates and reclaims the undo log.

Core MVCC Storage Primitives
🏷️ xmin / xmax (Postgres)
Header fields on heap tuples tracking creating (xmin) and deleting (xmax) transaction IDs for snapshot visibility calculations.
📜 Undo Log (InnoDB)
A rollback data structure storing delta chains of historical row values, enabling in-place updates in clustered B-Trees.
🧹 Vacuum vs. Purge Thread
Postgres Auto-Vacuum reclaims heap dead tuple slots; MySQL InnoDB Purge thread trims completed Undo Log segments.

Module 04

Preventing Lost Updates, Write Skew & The Phantom Menace

While Snapshot Isolation provides clean, repeatable reads, it does not solve all concurrency conflicts when multiple transactions write to the database concurrently. The two most infamous write concurrency hazards are Lost Updates and Write Skew.

The Lost Update Hazard: A lost update occurs during a read-modify-write cycle. If two transactions concurrently read value $V = 42$, compute $V + 1$, and write $43$ back to the database, the second write silently overwrites the first. One increment is permanently lost.

Modern applications prevent lost updates using several battle-tested patterns:

  • Atomic Update Operations: UPDATE counters SET value = value + 1 WHERE id = 42; (eliminates the client-side read-modify-write cycle by acquiring a row lock in the engine).
  • Explicit Locking: SELECT * FROM accounts WHERE id = 42 FOR UPDATE; (forces concurrent transactions to queue until the first transaction commits).
  • Optimistic Compare-and-Set: UPDATE wiki SET text = 'new' WHERE id = 1 AND version = 5; (if another editor bumped version to 6, the update matches 0 rows and the app retries).

Write Skew & Phantoms: Write skew is a generalized, subtle manifestation of race conditions that occurs when two transactions read overlapping rows, verify a business rule, and then update disjoint rows. Because they modify different records, raw row-level write locks do not conflict, allowing both transactions to commit and violate the global invariant!

The classic example is the Doctor On-Call Shift System. The hospital policy mandates that at least one doctor must remain on call at all times. Currently, Alice and Bob are both on call. Alice feels sick and requests leave; her transaction checks SELECT count(*) FROM doctors WHERE on_call = true (sees 2), and updates Alice to on_call = false. Concurrently, Bob also feels sick; his transaction checks SELECT count(*) (sees 2), and updates Bob to on_call = false. Both transactions commit. Now zero doctors are on call!

Write skew occurs because a write in one transaction changes the premise of a search query in another transaction. This phenomenon is known as a Phantom (a write in one transaction changes the search result set of another transaction). Mitigating phantoms requires either Materializing Conflicts (creating lock rows), Index-Range Locks, or true Serializable Isolation.

Write Concurrency Primitives
🔄 Lost Update
Two concurrent read-modify-write cycles where the second write clobbers the first without incorporating its changes.
🩺 Write Skew
Concurrent transactions reading common state and updating disjoint rows, breaking a multi-record invariant.
👻 Phantom Read
A write in one transaction inserting or altering rows that match the predicate query of a concurrent transaction.

Module 05

True Serializability: Actual Serial Execution & Two-Phase Locking (2PL)

Serializable Isolation is universally recognized as the strongest possible isolation level. It guarantees that even if transactions execute concurrently, the end result is mathematically indistinguishable from having executed them one at a time in some serial order. Under serializability, dirty reads, dirty writes, read skew, lost updates, write skew, and phantoms are completely eliminated.

Historically, database engines implemented Serializability through two classical techniques:

1. Actual Serial Execution (Single-Threaded Engines): If multi-threaded locking causes overhead and deadlocks, why not run every transaction sequentially on a single CPU core? Made viable in the mid-2000s by RAM affordability (keeping entire working datasets in memory) and OLTP workload profiles, systems like VoltDB, Redis, and Datomic execute transactions strictly one by one on a single thread.

However, actual serial execution requires that every transaction is packaged as an in-memory Stored Procedure. If a transaction waited for interactive network round-trips from a client web server, the entire database throughput would drop to single-digit queries per second.

2. Two-Phase Locking (2PL): For over 30 years, Two-Phase Locking was the dominant implementation of serializability in relational databases (such as MySQL InnoDB's SERIALIZABLE mode). 2PL enforces a strict rule: Readers block writers, and writers block readers.

In 2PL, locks are categorized into Shared Mode (Read) and Exclusive Mode (Write):

  • If Transaction A has read a row (Shared lock), Transaction B must wait before writing to that row.
  • If Transaction A has written to a row (Exclusive lock), Transaction B must wait before reading or writing that row.
  • Phase 1 (Growing Phase): The transaction acquires locks as it reads and writes. Locks can only be acquired, never released.
  • Phase 2 (Shrinking Phase): At the end of the transaction (commit or abort), all locks are released simultaneously (Strict 2PL).

To prevent Phantom Writes (e.g., preventing a new booking row from being inserted into an empty time slot), 2PL uses Predicate Locking or practical Index-Range Locking (Next-Key Locking), which locks all index records in the search range, plus the gap before the next record.

The severe downside of 2PL is performance degradation. Lock contention causes throughput collapse, high p99 tail latencies, and frequent Deadlocks (e.g., Transaction 1 holds Lock A and waits for Lock B, while Transaction 2 holds Lock B and waits for Lock A). The database must run background deadlock detection graphs and forcefully abort one transaction.

Serializability Primitives
🔒 Two-Phase Locking (2PL)
Pessimistic concurrency where readers block writers and writers block readers, holding all locks until final commit.
📐 Index-Range / Next-Key Lock
Locking existing index keys plus the empty gaps between them to prevent phantom inserts from concurrent transactions.
💀 Deadlock Cycle
A cyclic dependency where two or more transactions are blocked waiting for locks held by each other, requiring an engine abort.
1

Growing Phase (Acquiring Locks)

As each SQL statement in the transaction executes, the engine requests Shared (S) locks for reads and Exclusive (X) locks for writes. If another transaction holds a conflicting lock, this transaction is placed into a wait queue.

2

Deadlock Graph Traversal

The database engine periodically constructs a directed Wait-For graph. If a closed directed cycle is discovered (A waits for B, B waits for A), the engine picks a victim transaction, forcibly aborts it, and releases its locks.

3

Shrinking Phase (Atomic Release on Commit)

Under Strict 2PL, locks are never released during execution. Only after the WAL log is completely flushed on COMMIT or rolled back on ROLLBACK are all held locks released to unblock queued transactions.

Obvious Case

Strict 2PL in Financial Ledgers

Core banking engines running in MySQL SERIALIZABLE mode acquire exclusive row locks on accounts during high-value transfers, mathematically preventing concurrent overdrafts.

Counter-Intuitive

Single-Threaded Speed in VoltDB & Redis

Running transactions on a single CPU core without locks is often 10x faster than running multi-threaded 2PL with locks, because lock manager synchronization overhead and cache line bouncing are eliminated.

Edge Case

Next-Key Lock Escalation in MySQL

In MySQL InnoDB, querying WHERE age > 30 FOR UPDATE locks not just matching records, but all gap intervals up to infinity, accidentally blocking concurrent inserts for age = 35.

💡 Real-World Analogy

2PL is like reserving individual tools in a workshop: you borrow tools as you need them and hold onto every single tool until your entire carpentry project is finished.

❌ What People Get Wrong

Confusing 2PL (Two-Phase Locking) with 2PC (Two-Phase Commit). 2PL is a single-node concurrency control mechanism; 2PC is a distributed consensus protocol for committing across multiple nodes.

📌 Production Reality

Very few modern high-scale web systems use 2PL because the latency penalty of lock queues under high concurrency is catastrophic. Modern systems prefer SSI (Module 6).

🔗 Inter-Module Link

To achieve the gold standard of Serializability without the crippling lock overhead of 2PL, researchers created Serializable Snapshot Isolation (Module 6).

🧠 Memory Anchor: Two-Phase Locking: Readers block writers, writers block readers. Hold all locks until commit. High safety, terrible concurrency throughput under write contention.
Module 06

Modern Serializable Snapshot Isolation (SSI) & Distributed ACID

For decades, software engineers were forced to make a painful compromise: either accept the severe performance bottlenecks and deadlocks of Two-Phase Locking (2PL), or settle for weak isolation (Snapshot Isolation) and manually defend against write skew and phantoms with custom application locks.

In 2008, researchers Michael Cahill, Uwe Röhm, and Alan Fekete invented Serializable Snapshot Isolation (SSI). Formally integrated into PostgreSQL 9.1 and modern distributed engines like CockroachDB, SSI provides true mathematical serializability with the raw performance and non-blocking reads of snapshot isolation.

SSI is an Optimistic Concurrency Control (OCC) algorithm. Instead of blocking transactions with pessimistic read/write locks, SSI lets transactions execute concurrently without delay. Transactions read from multi-version snapshots and perform local writes.

While transactions execute, the SSI engine tracks dangerous dependency structures in background memory. Specifically, SSI detects anti-dependencies (also called rw-antidependencies or SIREAD locks), which occur when Transaction 1 reads a version of data, and concurrent Transaction 2 subsequently writes a newer version of that same data.

Mathematical graph theory proves that a serializability violation can only occur if there is a cycle of two consecutive anti-dependency edges in the dependency graph (i.e., $T_1 \xrightarrow{rw} T_2 \xrightarrow{rw} T_1$). When a transaction attempts to commit, the SSI engine inspects the graph: if a dangerous cycle is detected, the engine safely aborts one of the conflicting transactions with a retry error (SQLSTATE 40001: serialization_failure).

If contention is low to moderate (the standard reality for 99% of web applications), almost no cycles occur, and SSI achieves near 100% of the throughput of raw Snapshot Isolation while mathematically guaranteeing complete immunity to Lost Updates, Write Skew, and Phantoms.

Modern SSI Primitives
⚡ Optimistic Concurrency Control
Executing transactions without locking and validating conflicts only at commit time, assuming conflicts are rare.
👁️ SIREAD Lock
A non-blocking ephemeral in-memory marker recording that a transaction read a specific tuple or index gap.
🔄 rw-Antidependency
A directed conflict edge created when a transaction reads an older version of data that is subsequently updated by another.

Frequently Asked Questions

Why isn't true Serializable isolation the default in all relational databases? +
Historical databases used Two-Phase Locking (2PL) for serializability, which introduced crippling lock wait queues, deadlocks, and severe latency spikes. While modern Serializable Snapshot Isolation (SSI) has dramatically reduced overhead, Read Committed and Repeatable Read remain the defaults in PostgreSQL and MySQL to ensure backwards compatibility and maximum throughput for non-conflicting workloads.
How does PostgreSQL handle transaction ID (TxID) wraparound? +
PostgreSQL transaction IDs are 32-bit integers, wrapping around every 4 billion transactions ($2^{32}$). To prevent ancient committed tuples from suddenly becoming invisible, PostgreSQL uses modular arithmetic (modulo $2^{31}$) and runs an aggressive "Vacuum Freeze" process. Vacuum Freeze sets a special FrozenXID flag on old tuples, treating them as permanently older than all existing transaction IDs.
Why is MySQL InnoDB less susceptible to table bloat than PostgreSQL? +
InnoDB stores primary data directly inside clustered B-Tree pages and updates records in-place. Historical row snapshots are stored separately in Undo Log segments. When updates occur, only the undo log expands, keeping clustered B-Tree index pages tightly packed. Once older transactions commit, the background purge thread reclaims undo log space without rewriting table pages.
What is Next-Key Locking and why does MySQL use it? +
Next-Key Locking combines an index-record lock with a gap lock on the gap immediately preceding the index record. MySQL InnoDB uses next-key locking in Repeatable Read isolation to lock both matching records and empty gap ranges (e.g. locking the gap between ID 10 and 20), preventing phantom inserts from other transactions.
Can optimistic concurrency control (like SSI) cause transaction starvation? +
Yes. Under intense write contention on a single shared key, long-running transactions will repeatedly detect conflicts and abort. In high-contention write hotspots (such as ticketing flash sales), combining SSI with exponential backoff retries or switching to explicit pessimistic row locking (SELECT ... FOR UPDATE) is necessary to ensure forward progress.
What is the difference between single-node ACID and distributed ACID? +
Single-node ACID relies on local OS memory locks and local disk fsync calls on a single server. Distributed ACID (e.g., across CockroachDB, Spanner, or Vitess) requires distributed consensus protocols (Raft/Paxos) for durability and Two-Phase Commit (2PC) or TrueTime synchronized clocks for cross-shard atomicity and isolation, introducing network round-trip overhead.
