The Trouble with Distributed Systems

On a single computer, operations are fundamentally deterministic: if hardware functions, instructions execute faithfully; if hardware fails, the entire machine crashes cleanly. In distributed systems, computing enters the realm of partial failures: networks delay, drop, or duplicate packets, quartz clocks drift unpredictably, and garbage collection pauses turn healthy leaders into phantom split-brain nodes.

Module 01

Faults, Partial Failures & The Scale Paradox

Writing software for a single computer is fundamentally deterministic. When code executes on a single operating system, instructions run predictably according to CPU architecture. If a physical hardware fault occurs—such as a power failure or a fried memory controller—the entire system halts completely (a total failure).

In distributed systems, computing enters an entirely different paradigm governed by Partial Failures. A partial failure is a condition where some components of the distributed system are operating perfectly, while other components are failing, delayed, or partitioned in unpredictable ways. Because the working parts of the cluster cannot reliably know whether a remote machine has crashed or is simply experiencing network congestion, the system behaves nondeterministically.

This leads directly to The Scale Paradox: When managing a single database server with a mean time between failures (MTBF) of 3 years, hardware crashes appear as rare anomalies. However, when an enterprise scales horizontally to a cluster of 10,000 servers, hardware faults cease to be exceptional events. With 10,000 machines, on average 9 to 10 servers fail, reboot, or lose connectivity every single day.

Therefore, building distributed systems requires a philosophical shift: Fault tolerance is not an operational afterthought; it must be an inherent mathematical property of the software architecture. Systems cannot assume that remote machines or network cables are reliable.

📌 Production Reality

Module 02

Unreliable Networks & The Two Generals Impossibility

The internet and datacenter networks are asynchronous packet networks. In an asynchronous network, when a node sends a packet to another node, the network provides no guarantees regarding when the packet will arrive—or whether it will arrive at all.

When Node 1 sends a request to Node 2 and does not receive a response within a given timeframe, Node 1 cannot distinguish between five fundamentally different failure scenarios:

  • 1. The request was lost in the network (e.g., dropped by a congested router buffer).
  • 2. The request is waiting in a queue and will be delivered after a severe delay.
  • 3. Node 2 crashed or powered down before processing the request.
  • 4. Node 2 processed the request successfully, but its response was lost on the return path.
  • 5. Node 2 processed the request, but its response was delayed and will arrive later.

This uncertainty is formalized by The Two Generals Problem: Two allied generals (General 1 and General 2) have surrounded an enemy city. They can only win if they attack at the exact same time. The only way to communicate is by sending foot messengers through enemy territory, where messengers risk capture.

If General 1 sends a message: "Attack tomorrow at 8:00 AM", General 1 cannot attack unless he knows General 2 received it. General 2 sends an acknowledgment: "Received, 8:00 AM confirmed". But General 2 cannot attack unless he is certain General 1 received the confirmation (otherwise General 1 will stay behind). General 1 must send an acknowledgment of the acknowledgment... ad infinitum.

Computer science proofs establish that it is mathematically impossible to guarantee mutual certainty over an unreliable communication channel with a finite number of messages. Distributed databases circumvent this impossibility not through infinite acknowledgments, but through Quorums and Majority Voting (accepting that absolute unanimity is unachievable).

Assuming that TCP guarantees message delivery. TCP guarantees in-order retransmission if the network connection holds, but cannot deliver packets if the physical cable is cut or the receiver crashes.

Module 03

Unreliable Clocks: Time-of-Day vs. Monotonic Clocks & Clock Drift

In distributed systems, ordering events is fundamental. If Client A updates a user profile and Client B subsequently updates the same profile, the database must know which update occurred later. In our daily lives, we rely on clocks to order events. In distributed computing, physical clocks are fundamentally unreliable.

Every computer server possesses two fundamentally different types of hardware clocks:

1. Time-of-Day Clocks (Wall Clocks): In POSIX systems, clock_gettime(CLOCK_REALTIME) returns the number of seconds since the Unix epoch (January 1, 1970). Time-of-day clocks are periodically synchronized across networks using the Network Time Protocol (NTP). However, because network latency to NTP servers is variable, NTP can jump backward or forward (a "step") by tens or hundreds of milliseconds. A time-of-day clock can literally report that 12:00:01 occurred before 12:00:00!

2. Monotonic Clocks: clock_gettime(CLOCK_MONOTONIC) returns elapsed time from an arbitrary reference point (such as server boot time). Monotonic clocks are guaranteed to never jump backward and strictly move forward at a steady rate. They are ideal for measuring intervals (e.g. request timeouts), but have zero meaning across multiple servers (Node A's monotonic clock cannot be compared with Node B's monotonic clock).

The Last-Write-Wins (LWW) Catastrophe: Many multi-leader and leaderless databases (such as Apache Cassandra and Riak) use wall-clock timestamps to resolve write conflicts under the Last-Write-Wins (LWW) strategy. If two writes conflict, the engine keeps the write with the higher timestamp and discards the other.

If Node 1's quartz clock drifts just 50ms ahead of Node 2's clock due to ambient server heat:

  • Client 1 writes value $X = 1$ to Node 1 at real time $t_1$. Node 1 timestamps it as $t_1 + 50\text{ms}$.
  • Client 2 writes value $X = 2$ to Node 2 at real time $t_2$ (where $t_2 > t_1$, a causally later write). Node 2 timestamps it as $t_2$.
  • Because $(t_1 + 50\text{ms}) > t_2$, the database concludes that Client 1 wrote after Client 2.
  • Disaster: The older write permanently clobbers the newer write! Causality is inverted, and valid user data is silently destroyed.
Clock & Timestamp Primitives
⏰ Time-of-Day Clock

📈 Monotonic Clock
Guaranteed to strictly move forward (CLOCK_MONOTONIC); perfect for measuring timeouts on a single node, but incomparable across nodes.
💥 Last-Write-Wins (LWW)
A conflict resolution heuristic that keeps the write with the highest wall-clock timestamp, prone to silent data destruction from clock skew.

Module 04

Synchronized Clocks & Google Spanner TrueTime

Given the severe hazards of clock skew, can physical clocks ever be trusted to order distributed transactions? In 2012, Google published their landmark paper on Google Cloud Spanner, introducing a breakthrough API known as TrueTime.

Instead of pretending that all servers have identical clock times, TrueTime explicitly exposes clock uncertainty. When an application queries TrueTime via TT.now(), it does not return a single scalar timestamp. Instead, it returns a confidence interval:

TT.now() → [ tearliest, tlatest ]  where  tlatest - tearliest = 2ε

Here, $\epsilon$ represents the maximum clock error bound. To keep $\epsilon$ exceptionally small ($\le 7\text{ms}$ in Google datacenters), Google equips every datacenter with dedicated hardware: GPS satellite receivers paired with independent Atomic Rubidium Clocks.

The Commit-Wait Rule: How does Spanner achieve global serializable transactions without distributed lock contention across continents? Spanner uses the Commit-Wait Rule:

  • 1. Transaction $T_1$ executes and requests commit timestamp $s = \text{TT.now().latest}$.
  • 2. The transaction engine deliberately pauses and waits for $2\epsilon$ (e.g. 14ms) before releasing its locks and exposing the write to clients.
  • 3. Because $T_1$ waited $2\epsilon$, by the time any subsequent transaction $T_2$ begins, $T_2$'s earliest possible timestamp is guaranteed to be strictly greater than $s$ ($t_{2,\text{earliest}} > s$).

By waiting out the clock uncertainty interval, Spanner mathematically guarantees that causality matches timestamp order globally without requiring cross-region consensus on every read.

TrueTime Primitives
🛰️ TrueTime API (TT.now)
An API returning time as a bounded range [t_earliest, t_latest] based on GPS and atomic rubidium clocks.
⏳ Clock Uncertainty Bound (ε)
The maximum possible deviation between any two clocks in the infrastructure (typically ±7ms in Google Spanner).
🛑 Commit-Wait Rule
Intentionally pausing a write transaction for 2ε before commit to ensure subsequent transactions receive strictly higher timestamps.

Module 05

Process Pauses, Garbage Collection & The Fencing Token Defense

Assume a distributed database where networks are fast and clocks are calibrated. A catastrophic distributed failure mode can still occur due to Process Pauses.

In modern operating systems and managed runtimes, a running thread or database process can be completely suspended for seconds or minutes without its knowledge due to:

  • Garbage Collection (GC) Stop-The-World Pauses: Java/Go runtimes pausing all execution threads to sweep heaps.
  • Virtual Machine Live Migration: Hypervisors (AWS EC2, VMware) suspending a VM to copy memory pages to another physical host.
  • Operating System Page Swapping: Thrashing memory pages to SSD or spinning disk.
  • Unix Signals: An admin issuing SIGSTOP or thread context switching delays.

The Zombie Leader Hazard: Consider a leader lease pattern using ZooKeeper or etcd. Node 1 acquires a 10-second leader lock lease to write to shared cloud storage (e.g. S3 or an HBase file).

Immediately after checking that its lease is valid, Node 1 encounters a 15-second GC Stop-The-World pause. While Node 1 is frozen:

  1. Its 10-second lease in ZooKeeper expires.
  2. The cluster declares Node 1 dead and elects Node 2 as the new leader.
  3. Node 2 acquires a new lease and writes updated data to storage.
  4. Node 1 finishes its GC pause, wakes up, and resumes execution at the very next line of code: "Write to storage"!
  5. Node 1 still believes it is the valid leader and writes stale data, silently corrupting the file written by Node 2!

The Solution: Monotonic Fencing Tokens: Software cannot assume a process knows how much time passed while it was asleep. To protect storage against zombie leaders, the lock service must issue a monotonically increasing fencing token (a number that strictly increments with every lease, e.g. 33, 34, 35).

Every write request to the storage service must include the client’s fencing token. The storage node maintains a record of the highest token it has processed so far:

Storage Rule: If incoming_token < max_token_seen → REJECT WRITE (Stale Zombie Leader!)

When Node 2 writes with token 34, storage updates its threshold to 34. When Node 1 wakes up and attempts to write with token 33, the storage service rejects the write ($33 < 34$). Storage integrity is preserved.

Process Pause & Fencing Primitives
⏸️ Stop-The-World (STW) Pause
A runtime condition where all application execution threads are suspended by the garbage collector or hypervisor.
🧟 Zombie / Split-Brain Leader
A node whose lease expired during a pause, but resumes execution incorrectly believing it is still the authoritative leader.
🛡️ Fencing Token
A monotonically increasing integer attached to write requests that storage nodes use to reject writes from superseded leaders.

Module 06

System Models, Quorum Truth & Byzantine Realities

To formally reason about distributed systems and prove that an algorithm (such as Raft, Paxos, or Two-Phase Commit) will never corrupt data, computer scientists define formal System Models.

System models categorize timing assumptions and node failure behaviors into precise mathematical constraints:

Timing Models:

  • Synchronous Model: Network delays, message transmission times, and process execution pauses have known, strictly bounded upper limits. (Unrealistic for general internet/datacenter computing).
  • Partially Synchronous Model: The system behaves synchronously most of the time, but occasionally experiences unbounded network delays, GC pauses, or clock drift (the realistic model for modern cloud engineering).
  • Asynchronous Model: An algorithm can make zero timing assumptions (no clocks, no timeouts). Algorithms like FLP impossibility prove consensus is impossible in pure asynchronous networks with even 1 faulty node.

Node Failure Models:

  • Crash-Stop: A node fails only by crashing completely. Once a node crashes, it never recovers or speaks again.
  • Crash-Recovery: Nodes can crash at any time and resume execution later. Non-volatile storage (WAL) persists state across reboots, but in-memory state is lost (the standard model for databases).
  • Byzantine Faults: Nodes may lie, forge messages, collude maliciously, or suffer silent hardware bit flips. Defending against Byzantine faults requires cryptographic signatures and $3f + 1$ node quorums (Blockchains, aerospace fly-by-wire).

The Definition of Truth in Distributed Systems: In a distributed system, truth is not determined by any single node. Truth is defined strictly by Quorums (Majority Voting). A decision is valid if and only if a strict majority of nodes ($\lfloor N/2 \rfloor + 1$) agree. Because any two majorities must share at least one overlapping node, a split cluster can never make two contradictory decisions.

System Model Primitives
🌐 Partially Synchronous Model
The standard cloud model: operates synchronously with predictable latency under normal conditions, but allows temporary unbounded delays.
🗳️ Majority Quorum (N/2 + 1)
A quorum threshold ensuring that any two surviving voting groups must overlap by at least one node, preventing split-brain consensus.
🎭 Byzantine Fault
Arbitrary failure behavior where nodes send conflicting, corrupted, or malicious messages to different peers.
1

Select Realistic System Models

Acknowledge that cloud databases operate under the Partially Synchronous, Crash-Recovery model without assuming synchronous network upper bounds.

2

Enforce Majority Quorum Elections

Require strictly $\lfloor N/2 \rfloor + 1$ votes for leader election and write commitments. If a network partition isolates 2 nodes from a 5-node cluster, the 2 nodes must refuse writes.

3

Persist State across Crash Reboots

Flush election terms, votes, and log commitments to non-volatile disk using WAL logs so recovering nodes do not vote twice in the same term.

Obvious Case

Raft 3-of-5 Quorum Commit

In an etcd cluster of 5 nodes, a client write is committed as soon as 3 nodes append it to their WAL logs. The 2 slower or partitioned nodes catch up later.

Counter-Intuitive

Why Byzantine Fault Tolerance Is Unused in Datacenters

BFT protocols add massive compute and message complexity. Inside a private company VPC, all machines run authorized binaries, making non-Byzantine Crash-Recovery models optimal.

Edge Case

Silent Memory Bit Flips (Cosmic Rays)

While non-Byzantine models assume honest software, hardware bit flips in non-ECC RAM can alter memory values. Storage engines use CRC32/SHA256 checksums to detect corruption.

💡 Real-World Analogy

Quorum truth is like a democratic parliament: no single member can declare a law alone; a bill only passes if a strict majority votes in favor.

❌ What People Get Wrong

Believing an even number of nodes (e.g. 4 nodes) is better than an odd number (3 nodes). A 4-node cluster requires 3 votes for a majority and can still only tolerate 1 node failure—the exact same tolerance as a 3-node cluster!

📌 Production Reality

Production consensus clusters (etcd, ZooKeeper, Consul) are always deployed with 3, 5, or 7 nodes to maximize fault tolerance while avoiding split-vote ties.

Frequently Asked Questions

Why is calling an external API inside a database transaction dangerous? +
Calling an external HTTP API (such as Stripe or OpenAI) inside an open database transaction holds row locks and connection pool slots open during external network delays. If the external service slows down or suffers a network partition, transaction queues build up, database connections exhaust, and the entire primary database collapses.
What is the difference between CLOCK_REALTIME and CLOCK_MONOTONIC? +
CLOCK_REALTIME measures calendar time against the Unix epoch and can jump backward or forward when synchronized via NTP. CLOCK_MONOTONIC measures time elapsed since server boot and is guaranteed to strictly move forward, making it the only safe clock for calculating timeouts and request latencies.
Why can't we use Lamport timestamps instead of TrueTime in all databases? +
Lamport timestamps provide a total causal ordering, but they cannot enforce real-time physical ordering without communication. If Client A writes to Shard 1, tells Client B over the phone, and Client B writes to Shard 2, Lamport timestamps cannot prove Client B's write occurred after Client A's write without cross-shard messaging. TrueTime solves this using physical time bounds.
How does a Phi Accrual Failure Detector improve upon static timeouts? +
Instead of using an arbitrary binary threshold (e.g. "declare dead after 5 seconds"), a Phi Accrual Failure Detector measures historical heartbeat inter-arrival times. It outputs a continuous scale of suspicion ($\Phi$). If the network is experiencing temporary congestion, $\Phi$ rises gracefully, allowing systems to wait longer before triggering disruptive failovers.
What happens during an asymmetric network partition? +
In an asymmetric partition, Node A can transmit packets to Node B, but Node B's replies are blocked. Node B believes Node A is dead, while Node A believes Node B is refusing to respond. To prevent split-brain chaos, consensus protocols require two-way quorum voting where only nodes with bidirectional communication can participate in elections.
