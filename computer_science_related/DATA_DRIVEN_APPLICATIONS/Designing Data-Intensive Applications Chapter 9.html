Module 01

Linearizability: The Illusion of a Single System Image

When building applications atop distributed databases, software engineers naturally desire the system to behave as if it were a single, instantaneous computer. In distributed systems literature, this ultimate guarantee is formalized as Linearizability (also known as atomic consistency, strong consistency, or immediate consistency). Under linearizability, the system provides a strict recency guarantee: as soon as any client finishes a write or reads a new value, all subsequent reads by any client across any node in the cluster must return that value or an even newer one.

It is paramount to distinguish Linearizability from Serializability. Serializability is an isolation property of multi-operation transactions (ACID), ensuring that transactions execute equivalent to some serial schedule, even if that schedule operates over stale snapshots. Linearizability is a freshness and timing guarantee on individual objects (registers). A system can be Serializable but not Linearizable (e.g., Snapshot Isolation reading from an hour-old replica), or Linearizable but not Serializable (e.g., single-key atomic compare-and-set operations without multi-row transactional atomicity). When a system satisfies both, it achieves Strict Serializability (External Consistency), as implemented in Google Spanner.

The canonical violation of linearizability is the Alice and Bob World Cup Score Anomaly. Imagine Alice and Bob sitting on a sofa watching the World Cup final. The referee blows the final whistle: Germany wins. The score updates on the leader database. Alice refreshes her phone app; her query hits Follower 1, which has already received the replication stream. Alice shouts, "Germany won!" Bob, sitting right next to her, immediately taps refresh on his phone. Bob's query hits Follower 2, which is experiencing 50 milliseconds of network lag. Bob stares at his screen and sees "Game in progress: 0–0." To Bob, time has traveled backwards. This causal inversion violates the human intuition of absolute time and is the fundamental bug linearizability eliminates.

Core Definition: Linearizability
A system is linearizable if all concurrent operations appear to take effect atomically at a specific point in time between their invocation and response on a global timeline, ensuring no client ever observes a stale value once a newer value has been acknowledged or read.
Figure 9.1: The Alice & Bob read skew anomaly. When cross-channel communication exists (Alice speaking to Bob), replication lag violates linearizability.
1

Global Real-Time Register Invariant

In a linearizable datastore, there exists a single logical time continuum. As soon as write operation $W(x=v)$ returns SUCCESS to the calling client, all subsequent read operations $R(x)$ invoked anywhere in the universe must return $v$ or a subsequent write's value.

2

Causal Channels Outside the Database

If Alice and Bob never interacted, Bob seeing stale data might be classified as simple eventual consistency. But because Alice communicated with Bob via an external side-channel (voice, instant messenger), Bob has causal knowledge of the future state. The database fails linearizability because its read path ignores real-world causal ordering.

3

Compare-and-Set (CAS) and Lock Pre-requisite

Linearizability is strictly required whenever a system needs atomic Compare-and-Set primitives (e.g., leader election, single-username reservation, or distributed lock acquisition). Without linearizability, two nodes can simultaneously believe they acquired the lock.

Obvious Example

Unique Username Registration

Two users concurrently try to register `@saturn`. If the user table is linearizable, exactly one write succeeds and the second receives a unique constraint violation immediately.

Counter-Intuitive Example

Serializable Snapshot Isolation (SSI)

A database running PostgreSQL SSI prevents all isolation anomalies (dirty reads, write skew), yet a reader can legitimately read from a 10-minute-old snapshot without violating Serializability. SSI is Serializable, but not Linearizable!

Edge-Case Example

Leader Fencing via CAS

A distributed leader leases a lock in ZooKeeper with an auto-incrementing epoch token. If the lock register is non-linearizable, an old partitioned leader could renew its expired lease concurrently, creating split-brain data corruption.

💡 Visual Analogy
Think of a physical whiteboard in a classroom. If a teacher writes "Class Dismissed" on the board, anyone looking at the board sees it instantly. An asynchronous replica cluster is like having 100 assistants copying the board onto separate sheets of paper with variable walking speed—some students see "Class Dismissed" while others still see "Pop Quiz".
❌ What People Get Wrong
"Serializability is stronger than Linearizability." They are orthogonal dimensions! Serializability deals with multi-statement transaction order independence; Linearizability deals with real-time freshness of single-object operations. The strongest combined level is Strict Serializability.
🎯 Why This Matters in Production
If you implement leader election, inventory decrementing, or billing checkouts on read-replicas without linearizability, you will encounter race conditions, duplicate charges, and split-brain outages. You must know when you require linearizable primary reads vs. eventual follower reads.
Memory Rule Linearizability = Real-Time Freshness (No time travel after an ACK). Serializability = ACID Isolation (Transactions behave as if executed sequentially).

Module 02

The Cost of Linearizability & The CAP Trade-Off

If linearizability provides such an intuitive, foolproof mental model, why are the vast majority of distributed databases (including MySQL, PostgreSQL read pools, MongoDB, and Cassandra) non-linearizable by default? The answer lies in the harsh physical constraints of networks: Latency and Unavoidable Partitions.

The relationship between linearizability and fault tolerance is formalized by the CAP Theorem (and its modern, comprehensive generalization, PACELC). When network cables are cut or routers fail between two datacenters, creating a network partition ($P$), a distributed data system is forced to choose between two mutually exclusive behaviors:

  • Linearizability / Consistency (CP): The isolated node refuses to serve client writes or reads because it cannot verify whether a newer write occurred in the other partition. The system sacrifices Availability to prevent stale or conflicting data.
  • Availability (AP): The isolated node continues serving reads and writes using whatever local state it possesses. The system remains Available, but completely sacrifices Linearizability.

Crucially, even when the network is operating with 100% perfection without any partitions, linearizability exacts a brutal latency tax. In a linearizable system, every write must synchronize across nodes, and every read must verify it is not querying a deposed leader (via lease checks or quorum reads). As proved by Attiya and Welch, the response time of read and write operations in a linearizable datastore is fundamentally proportional to the network round-trip time ($RTT$) between nodes. While an asynchronous write returns in $0.5\text{ ms}$ on local NVMe, a cross-datacenter linearizable write requires $50\text{ ms}$ to $200\text{ ms}$ of speed-of-light network transit.

The PACELC Theorem Extension
If there is a Partition (P), how does the system trade off Availability (A) versus Consistency (C)? Else (E), when the network is operating normally, how does the system trade off Latency (L) versus Consistency (C)?
Figure 9.2: Replication topology across a network partition. Sync replicas in DC-1 maintain quorum; DC-2 must choose between returning stale data (AP) or throwing 503 errors (CP).

Obvious Example

Transatlantic Fiber Cut

A submarine cable between US-East and EU-West is severed. An AP system (Cassandra) allows both regions to accept writes independently (diverging branches), while a CP system (Spanner) blocks EU writes until communication restores.

Counter-Intuitive Example

Single-Leader Crash Failover

Even on a single-leader database (like standard Postgres or MySQL), asynchronous failover to an un-caught-up follower can resurrect deleted rows or violate uniqueness constraints, silently breaking linearizability.

Edge-Case Example

Garbage Collection Pauses

A leader node suffers a 2-second JVM Stop-the-World pause. During the pause, followers elect a new leader. When the old leader awakens, it serves non-linearizable writes for 200ms before discovering its lease expired.

💡 Visual Analogy
Imagine two bank branches in New York and London connected by a telephone line. If the phone wire snaps, a customer in London asks to withdraw all their money. The London teller must either: (1) Refuse service until the phone is repaired (CP - Consistent but Unavailable), or (2) Hand over the cash, risking that the customer also withdrew the money in New York (AP - Available but Non-linearizable).
❌ What People Get Wrong
"CAP means you choose any 2 of 3: Consistency, Availability, or Partition Tolerance." You cannot choose "CA"! Network partitions are physical realities of hardware and cannot be avoided. Your only architectural choice is how to behave when a partition occurs: sacrifice Availability or sacrifice Consistency.
Memory Rule CAP is a Trade-off Under Failure: Partitions are inevitable. You choose between CP (Consistency & Errors) or AP (Availability & Stale Data).

Module 03

Ordering, Sequence Numbers & Total Order Broadcast

In Chapter 8, we discovered that physical wall clocks (NTP) cannot be trusted to establish a total order of events due to clock skew and leap second smearing. If physical timestamps are unreliable, how can distributed nodes agree on the exact chronological order of transactions? The solution is to transition from physical time to Logical Ordering and Total Order Broadcast.

An initial attempt at logical ordering is Lamport Timestamps. Each node pairs an incrementing counter with its unique node ID: `(counter, node_id)`. Whenever node $A$ sends a message to node $B$, it includes its counter; node $B$ advances its internal counter to $\max(\text{counter}_A, \text{counter}_B) + 1$. This guarantees that if operation $A$ causally preceded operation $B$, then $\text{timestamp}(A) < \text{timestamp}(B)$.

However, Lamport timestamps possess a fatal limitation: they only establish ordering after the fact. Imagine a user attempting to claim the username `@alex`. A node checks its local state, sees no conflict, and issues a Lamport timestamp `(42, Node_1)`. But it cannot know if another node concurrently issued `(41, Node_2)` for the same username until it has collected all operations from every other node in the cluster. If the network is slow or partitioned, the node cannot decide whether to commit or abort in real time.

To make real-time decisions, a system requires Total Order Broadcast (also known as atomic broadcast). Total Order Broadcast is a protocol for exchanging messages between nodes that enforces two strict safety properties:

  • Reliable Delivery: If a message is delivered to one correct node, it is guaranteed to be delivered to all correct nodes (no dropped messages).
  • Totally Ordered Delivery: Messages are delivered to every node in the exact same identical sequence. If node $A$ delivers message $m_1$ before $m_2$, node $B$ can never deliver $m_2$ before $m_1$.
Equivalence Theorem: Total Order Broadcast & Linearizability
A Total Order Broadcast log is mathematically equivalent to a linearizable datastore: you can implement Total Order Broadcast atop linearizable Compare-and-Set registers, and you can implement linearizable storage atop a Total Order Broadcast log (by appending writes to the log and sequencing reads after the latest log entry).
Figure 9.3: Total Order Broadcast implementing State Machine Replication. Every replica receives log events in the identical sequence, ensuring convergence to identical database states.
Obvious Example

ZooKeeper / etcd Transaction Log

When Kubernetes writes a Pod specification to `etcd`, the write is submitted to Raft Total Order Broadcast. Every control plane node applies the update at the identical log index $i$.

Counter-Intuitive Example

Fencing Token Generation

Lock servers cannot just hand out boolean locks. They issue monotonic sequence numbers via total order broadcast. Even if an old client wakes up from GC, the storage server rejects tokens lower than the highest observed sequence number.

Edge-Case Example

Total Order Broadcast Read Stale Trap

While Total Order Broadcast makes writes linearizable, reading directly from a replica's local state without querying the log index can still return stale data! To achieve linearizable reads, the node must perform a quorum read or lease check.

💡 Visual Analogy
Total Order Broadcast is like a single numbered deli counter ticket dispenser. No matter how many customers push into the bakery simultaneously, everyone pulls a ticket with a strict integer: 101, 102, 103. The bakers serve customers strictly by integer order, completely eliminating disputes about who arrived first.
❌ What People Get Wrong
"Lamport timestamps can be used to prevent double-spending or unique constraint violations in real time." False! Lamport timestamps let you sort historical events after the fact, but they cannot tell you whether another node generated a lower timestamp 1 millisecond ago without waiting for all nodes to respond.
Memory Rule Total Order Broadcast: Reliable Delivery + Identical Order across all nodes. It is the architectural foundation of State Machine Replication.

Module 04

Atomic Commit & Two-Phase Commit (2PC)

On a single database node, transactional atomicity is straightforward: the engine writes all mutations to the Write-Ahead Log (WAL), appends a single COMMIT record to disk, and executes `fsync()`. If the machine loses power one microsecond before the commit record is flushed, the entire transaction is rolled back during crash recovery. If power fails one microsecond after, the transaction is replayed and committed. The commit record is the crisp, atomic point of no return.

In a distributed database where a transaction spans multiple nodes (e.g., deducting money from an account on Node A and crediting an account on Node B), a simple commit command is completely broken. If the network drops after Node A commits but before Node B receives the message, Node A has committed while Node B rolls back, irreparably violating ACID Atomicity.

The classic algorithm for solving this across heterogeneous or partitioned systems is Two-Phase Commit (2PC) (not to be confused with Two-Phase Locking (2PL)!). 2PC introduces an external Coordinator (or Transaction Manager) and divides the commit process into two distinct phases:

  • Phase 1 (Prepare): The coordinator generates a globally unique transaction ID and sends a `PREPARE` RPC to every participating node. Each participant acquires necessary row locks, executes the query into temporary undo/redo buffers, writes changes and a `PREPARED` record to its local disk WAL, and replies with `VOTE YES` (an irrevocable guarantee that it can commit) or `VOTE NO` (if locks failed or disk was full).
  • Phase 2 (Commit / Abort): The coordinator tallies the votes. If every single participant voted YES, the coordinator writes a `COMMIT` record to its own WAL—this is the Point of No Return! The coordinator then broadcasts `GLOBAL COMMIT` to all participants. Participants commit their local transactions, release their locks, and return an acknowledgment. If even one participant voted NO or timed out during Phase 1, the coordinator writes `ABORT` to its WAL and broadcasts `GLOBAL ABORT`.

The fatal flaw of 2PC is that it is a Blocking Protocol. If a participant votes `YES` in Phase 1, it enters the dreaded In-Doubt state: it has irrevocably surrendered its autonomy. It cannot abort (because the coordinator might decide to commit), and it cannot commit (because another node might have voted NO). If the coordinator crashes or network cables disconnect immediately after Phase 1 votes are cast, the participant must hold all row locks indefinitely until the coordinator recovers. In production, an In-Doubt lock freeze cascades across the entire database, locking up connection pools and halting all application traffic.

The In-Doubt Dilemma in 2PC
Once a participant votes "YES", it promises under oath that it will commit if told to do so. If the coordinator dies before delivering Phase 2, the participant is frozen in doubt, holding exclusive table/row locks on disk until an administrator manually intervenes or the coordinator reboots from WAL logs.
Figure 9.4: Two-Phase Commit protocol timeline. If the coordinator crashes after receiving YES votes, participants enter the blocking In-Doubt state with locks held indefinitely.
Obvious Example

XA Distributed Transactions (Java JTA)

An enterprise Java service coordinates a transfer between a PostgreSQL database and an IBM MQ message queue using the XA 2PC standard, ensuring message ack and row insert commit in lockstep.

Counter-Intuitive Example

Why 3-Phase Commit (3PC) Doesn't Save Us

Three-Phase Commit (3PC) attempts non-blocking commit by adding a "PreCommit" stage, but it assumes a synchronous network with bounded delay. Over real-world asynchronous Internet networks, 3PC can split-brain under partitions.

Edge-Case Example

Orphaned Prepared Transactions in PostgreSQL

If a client issues `PREPARE TRANSACTION 'foo'` and disconnects, PostgreSQL holds all locks and prevents table auto-vacuuming indefinitely until a DBA manually runs `ROLLBACK PREPARED 'foo'`.

💡 Visual Analogy
2PC is like a traditional marriage ceremony. The officiant (Coordinator) asks Groom (Node 1) "Do you take...?" Groom says "I do" (Vote YES). Officiant asks Bride (Node 2) "Do you take...?" Bride says "I do" (Vote YES). Both have committed their vows. If the officiant suddenly suffers a heart attack before saying "I now pronounce you husband and wife", the couple is stuck at the altar—unable to marry someone else, yet legally not married.
❌ What People Get Wrong
"2PC and 2PL (Two-Phase Locking) are the same thing." 2PL is a concurrency control mechanism for serializable isolation (holding locks until end of txn). 2PC is a distributed atomic commit protocol across multiple nodes. They solve completely distinct problems!
Memory Rule 2PC = Unanimous Vote + Point of No Return. Vulnerability: Coordinator crash leaves participants locked in the In-Doubt state.

Module 05

Distributed Transactions in Sharded Architectures

When scaling relational databases horizontally via sharding (as popularized by Vitess at YouTube, Slack, GitHub, and PlanetScale), data is partitioned across dozens or hundreds of independent MySQL or PostgreSQL instances. While queries that target a single shard run at native B-tree speed with low single-digit millisecond latency, transactions that span multiple shards introduce severe architectural headwinds.

When an application issues a transaction modifying rows across Shard 1 and Shard 2 via a routing proxy (`vtgate`), the proxy must orchestrate a distributed 2PC transaction across the corresponding tablet processes (`vttablet`). In this environment, the latency multiplier becomes catastrophic:

  • 6x Network Hop Expansion: A single single-shard insert requires 1 network round-trip. A cross-shard 2PC insert requires: Begin Shard 1 + Begin Shard 2 $\rightarrow$ Insert Shard 1 + Insert Shard 2 $\rightarrow$ Prepare Shard 1 + Prepare Shard 2 $\rightarrow$ Global Commit. This generates at least 6 distinct network round-trips across the cluster.
  • Lock Contention Amplification: Because InnoDB row locks must be held on both shards from the moment the insert executes until the final `GLOBAL COMMIT` ACK is received, lock hold times surge from $2\text{ ms}$ to $50\text{ ms}+$. Concurrent transactions attempting to touch the same rows queue up behind the locks, quickly exhausting database connection pools.
  • The Vitess Lessons: Due to these catastrophic performance degradation patterns, Vitess historically removed distributed transactions entirely, later reintroducing them only with strict timeouts and warnings. Modern distributed database architectures strongly advise designing application data models to strictly isolate transactions to a single shard key.

When cross-boundary coordination is strictly unavoidable, modern engineering teams replace synchronous 2PC with Asynchronous Sagas (compensating transactions) or Ledger Patterns using optimistic concurrency and single-row atomic increments.

The Sharded Transaction Golden Rule
Design your sharding key (e.g., `tenant_id` or `account_id`) so that 99.9% of all write transactions are strictly scoped to a single database shard. Treat cross-shard 2PC as an expensive, emergency fallback rather than standard operational flow.
Figure 9.5: Cross-shard transaction in Vitess. VTGate coordinates 2PC across independent MySQL shards, amplifying network round-trips and extending InnoDB lock hold durations.
Obvious Example

Slack Channel Sharding

Slack shards databases by `workspace_id`. All messages, channels, and member writes within a workspace occur inside a single MySQL shard, completely bypassing cross-shard 2PC.

Counter-Intuitive Example

Saga Pattern with Compensating Actions

Rather than locking Shard A and Shard B synchronously, a flight booking service commits the seat reservation immediately on Shard A. If hotel booking fails on Shard B later, an asynchronous message executes a Cancel Reservation compensating transaction.

Edge-Case Example

LSM-Tree vs B-Tree Contention

Under extreme high-contention sequential writes (like append-only ledger ledgers), B-Trees suffer lock contention on leaf pages. LSM-Tree databases (like ClickHouse or RocksDB) ingest writes sequentially in memory with near-zero locking overhead.

💡 Visual Analogy
A single-shard transaction is like paying a single cashier for groceries. A cross-shard 2PC transaction is like buying items at 4 different stores simultaneously, forcing all 4 store managers to hold the items at the register on the phone with you until everyone confirms credit card authorization.
❌ What People Get Wrong
"Modern NewSQL databases (CockroachDB, Spanner) eliminated the 2PC performance penalty." They use optimized protocols (Raft per range + 2PC across ranges), but the laws of physics remain: cross-shard transactions still require multiple network RTTs and hold locks across nodes!
Memory Rule Colocate by Shard Key: Keep transactions local to one node. Use Sagas or Ledger patterns when crossing shard boundaries.

Module 06

Fault-Tolerant Consensus & Coordination Services

The fundamental flaw of Two-Phase Commit is that it requires unanimous agreement: if even one node crashes, the system cannot make forward progress. In distributed systems, the ultimate solution to non-blocking coordination is Consensus. The consensus problem requires one or more nodes to propose values, and the algorithm guarantees that all non-faulty nodes agree on a single, irrevocable decision.

Formally, a consensus algorithm (such as Paxos, Raft, or Zab) must satisfy four core safety and liveness properties:

  • Uniform Agreement: No two nodes can ever decide differently on the same log index.
  • Integrity: No node can decide twice on the same proposal.
  • Validity: If a node decides value $v$, then $v$ must have been proposed by some participant.
  • Termination: Every non-faulty node eventually decides on a value (liveness under majority availability).

How does Consensus avoid the blocking dilemma of 2PC? Consensus algorithms rely on Majority Quorums. In a cluster of $N$ nodes (where $N = 2F + 1$), the protocol requires agreement from only a majority of $\lfloor N/2 \rfloor + 1$ nodes. A 5-node cluster requires only 3 votes to commit an entry, gracefully tolerating up to $F = 2$ dead nodes without halting or waiting!

To prevent split-brain leadership, consensus protocols employ Epoch Numbers (called Terms in Raft, Ballot Numbers in Paxos, or Zxids in Zab). If an old partitioned leader wakes up and attempts to append log entries, majority followers reject its messages because a newer leader has already been elected with a higher Epoch number.

Because running consensus on every database row is computationally expensive, distributed architectures use specialized Coordination Services like ZooKeeper, etcd, and Consul. These systems run Raft or Zab to hold small, critical cluster metadata: leader election locks, service discovery endpoints, fencing tokens, and sharding routing maps.

2PC vs. Quorum Consensus Comparison
2PC requires UNANIMOUS agreement ($N$ of $N$): If 1 node dies, the protocol blocks indefinitely. Consensus requires MAJORITY agreement ($\lfloor N/2 \rfloor + 1$): If a minority of nodes die, the system continues making progress with zero interruption.
Figure 9.6: Raft/Paxos 5-node consensus cluster. The majority quorum (Nodes 1, 2, 3) commits entries without waiting for failed Nodes 4 and 5.
Obvious Example

Kubernetes Control Plane (etcd)

A 3-node etcd cluster runs Raft. If 1 control plane VM dies, the remaining 2 nodes still form a majority quorum ($2 > 3/2$), allowing continuous pod scheduling and API server commits without pause.

Counter-Intuitive Example

Why Odd Cluster Sizes ($3, 5, 7$) are Mandatory

A 4-node cluster tolerates $F = \lfloor (4-1)/2 \rfloor = 1$ failure, requiring a majority of 3. A 3-node cluster also tolerates 1 failure (majority 2). Adding a 4th node adds cost and network traffic without increasing fault tolerance!

Edge-Case Example

ZooKeeper Ephemeral Node Heartbeats

In Kafka or Vitess, a leader registers an ephemeral node in ZooKeeper. If the leader experiences a network timeout, ZooKeeper deletes the ephemeral node, automatically triggering a consensus election for a new leader.

💡 Visual Analogy
Consensus is like the Supreme Court voting on a decision. There are 9 judges ($N=9$). If 4 judges are ill and absent, the remaining 5 judges still form a majority quorum ($5 > 4.5$) and deliver a legally binding, final judgment. No single absent judge can hold the court hostage.
❌ What People Get Wrong
"Paxos and Raft can handle Byzantine (malicious / hacked) nodes." False! Paxos and Raft operate in the Crash-Recovery Model where nodes may crash or delay, but messages are authentic. Dealing with lying or corrupted nodes requires Byzantine Fault Tolerance (BFT), requiring $3F + 1$ nodes.
Memory Rule Consensus Quorum Formula: $N = 2F + 1$. A cluster of size $N$ survives $F$ node failures with a majority vote of $\lfloor N/2 \rfloor + 1$.

Question 01

What is the fundamental difference between Serializability and Linearizability?

Click to reveal answer ↻
Answer

Serializability is an ACID isolation property for multi-operation transactions (execution matches some serial order). Linearizability is a real-time recency guarantee on single objects (reads return the latest acknowledged write).

Question 02

Why does Two-Phase Commit (2PC) cause the dreaded "In-Doubt" lock freeze?

Click to reveal answer ↻
Answer

Once a participant votes "YES" in Phase 1, it surrenders its autonomy. If the coordinator crashes before broadcasting Phase 2, the participant cannot abort or commit unilaterally, holding row locks indefinitely.

Question 03

Why are Lamport Timestamps insufficient to implement a unique username register in real time?

Click to reveal answer ↻
Answer

Lamport timestamps establish a total order only after all operations are collected. A node cannot decide immediately whether a username is unique because a concurrent write with a lower timestamp might still be in flight.

Question 04

How do consensus algorithms (Paxos/Raft) eliminate the single-point-of-failure blocking problem of 2PC?

Click to reveal answer ↻
Answer

2PC requires unanimous ($N$ of $N$) agreement. Consensus protocols require only a majority quorum ($\lfloor N/2 \rfloor + 1$). In a 5-node cluster, 3 nodes can commit log entries even if 2 nodes are completely dead.

Question 05

Why did Vitess and YouTube historically disable cross-shard 2PC?

Click to reveal answer ↻
Answer

Cross-shard 2PC amplifies network round-trips (6+ RTTs) and holds InnoDB row locks across shards for tens of milliseconds, causing connection pool exhaustion and catastrophic throughput collapse under load.

Question 06

What role do Epoch Numbers (Terms) play in consensus leader election?

Click to reveal answer ↻
Answer

Epoch numbers guarantee that there is at most one valid leader per term. If an old partitioned leader wakes up and attempts to issue commands, followers reject them because they recognize a higher epoch number.

Q1: Can we achieve Linearizability without a single leader?

Yes, leaderless systems (like Dynamo or Cassandra) can achieve linearizability by performing strict read-repair and read/write quorum overlap ($W + R > N$). However, to handle concurrent racing writes without Last-Write-Wins data loss, leaderless stores must implement a consensus-based Compare-and-Set register (like Cassandra Lightweight Transactions via Paxos).

Q2: Why does Google Spanner need atomic GPS and atomic clocks (TrueTime)?

Google Spanner uses TrueTime uncertainty bounds ($\epsilon \approx 7\text{ ms}$) to assign monotonic commit timestamps to transactions. By waiting $2\epsilon$ before releasing a commit (Commit-Wait), Spanner achieves Strict Serializability (Linearizability + Serializability) across globally distributed datacenters without requiring cross-region 2PC locks for read-only transactions!

Q3: What happens if an etcd cluster loses 2 nodes in a 3-node deployment?

In a 3-node cluster, the majority quorum requirement is $\lfloor 3/2 \rfloor + 1 = 2$. If 2 nodes die, only 1 node remains. The cluster can no longer form a quorum and transitions to read-only or error state, rejecting all writes to protect consistency until at least 1 node recovers.

Q4: How does a ledger pattern with optimistic concurrency solve the cross-shard 2PC bottleneck?

Instead of locking rows across Shards A and B simultaneously in a 2PC transaction, each shard maintains an append-only ledger log. Transactions execute a conditional atomic write (`INSERT ... WHERE sequence = expected_seq`) locally on Shard A, then publish an event to an ordered message queue to append on Shard B asynchronously.

🚀 Production Action Items
  1. Audit Shard Routing Keys: Review your database schema to verify that high-frequency write paths do not trigger cross-shard 2PC transactions. Ensure multi-row operations share a common tenant or entity ID.
  2. Check Ephemeral Locks & Fencing Tokens: If you use ZooKeeper or Redis for distributed locks, ensure downstream storage engines validate monotonic fencing tokens to prevent zombie leader corruption during GC pauses.
  3. Validate Quorum Cluster Sizing: Verify that production etcd and ZooKeeper clusters use odd numbers of nodes ($3$ or $5$) and are distributed across independent availability zones.
