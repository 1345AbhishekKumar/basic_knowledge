System design for absolute beginners

Break It on Purpose: How One Server Grows into a Real System

Load balancers, caches, replicas and shards — added one at a time, only when something actually breaks, and always with the price tag attached.

🎯 Objective

By the end, you'll be able to explain — in plain English — what each piece of a scaled-up web app does, why it gets added, and what it costs: load balancer, stateless servers, shared sessions, connection pools, read replicas, caching, queues & workers, and sharding. You'll also run and modify a small working program that implements the sharding rule.

🧰 Prerequisites

Basic computer literacy — you can use a browser, save a file, and open it. No coding knowledge is assumed; every term is defined the moment it appears.

10–15 minutes of reading, plus about 10 more if you do the code challenge at the end.

The big idea

Building Was Never the Hard Part

Anyone can build a full application these days — front end, backend, database, deployed and online — and with AI, faster than ever. So here is the uncomfortable question the source video asks: if anyone can build the app, what's left that makes you a good engineer?

The answer: building the thing was never the hard part. The hard part is what happens when the app you built gets popular — when one server isn't enough, when the database can't keep up, when it's slow and you don't know why. That subject is called system design: deciding how the pieces of an app fit together so it stays fast and alive under real traffic.

Most tutorials teach it as a pile of scary words — load balancers, replicas, sharding, caching — thrown at you all at once, on day one, for an app that has 50 users. We'll do the opposite. We start with one server and one database, then we break it on purpose, over and over. Every time it breaks, we fix exactly one thing — so by the end, you know why every piece is there, and what it costs to add.

The setup

Start Simple: One Server, One Database

This is your app — two boxes:

  • A server: a computer that runs your code and answers your visitors.
  • A database: the place where your data (users, orders, tickets) is stored.

If you've built anything and put it online, this is what you have. And here's a point worth repeating: this setup is enough for thousands of users — not dozens, thousands. Most applications alive right now look exactly like this and will never need to look like anything else. That is not a failure, and it's not something you have to grow out of.

The break

The Moment It Breaks: Everyone Shows Up at Once

Say you built an app for buying concert tickets — the real thing, like Ticketmaster, StubHub or SeatGeek. You deploy it (put it online), you test it, everything works perfectly. Then a big show goes on sale at 10:00 in the morning — or, if you're unlucky, 5 p.m. on a Friday — and tens of thousands of people open your site at the exact same moment.

Your app falls over: slow to a crawl, requests hanging, some never finishing at all. And here's the thing — nothing is wrong with your code. No bad queries, no bugs. The problem is simpler: a single server can only do so many things at once. When thousands of requests (each "hey, give me this page" message from a browser) arrive together, they pile up in a queue, waiting their turn. The queue gets so long that requests time out — they give up and die before the server ever reaches them.

Fix #1

Bigger Box vs. More Boxes

You have two ways to handle thousands of people at once — and one day you'll genuinely choose between them.

Option A — vertical scaling: one bigger box

Vertical scaling means getting a bigger server: more processing power, more memory — the same single machine, just stronger and larger. This is the right first move almost every time: you change nothing about your code, you pay for a bigger machine, and you're done for the afternoon. To put a number on it: a $20-a-month server handles hundreds of requests per second for a typical app — millions of requests a day on one cheap box.

But it runs out. There is a biggest machine you can rent, and it gets very expensive long before you reach it. A bigger box buys you time — it doesn't buy you forever.

Option B — horizontal scaling: more ordinary boxes

Horizontal scaling means running several ordinary servers and splitting the people between them. And be very clear about what those servers are, because it trips people up: they are not different parts of your app — not one server for payments, one for messaging. They are identical copies of your whole app, the same code running three times, and each copy can handle any request on its own.

You still ship your app once — you just tell your platform to run three instances of it. (If you're on something like Vercel, it's quietly already doing this for you.) And this approach keeps going: too much traffic again next year? Add more copies. There's no ceiling in the same way, because you're not depending on one machine being big enough.

✅ Best practice

If a bigger server fixes your problem, buy the bigger server and get back to work. Scaling out (adding machines) is for when scaling up (buying a bigger one) genuinely stops working — not before.

Fix #2

The Referee: Load Balancer

The moment you have more than one server, you face a question you didn't have before: a request comes in from a user — which server does it go to? Something has to stand in front of your servers and hand each incoming request to one of them, spreading the people out evenly so no single server gets overwhelmed while the others sit idle.

That thing is a load balancer. A request comes in → the load balancer picks a server → the server does the work. If one server is busy, send the next request to a different one. Add a fourth server next month? The load balancer starts using it. The users never know how many servers there are or which one they got. Nginx is a classic one — and if you deploy on Vercel or Railway, you already have a load balancer; you just never had to set it up or think about it.

But we have to talk about cost, because everything we add from here has one:

  • It's a new single point of failure. A single point of failure is any one piece whose death takes the whole system down. If the load balancer goes down, it doesn't matter that you have three healthy servers behind it — nobody can reach them. In real systems, the load balancer itself also has a backup, which is more stuff to run.
  • Quieter, and sneakier: your servers must become interchangeable. For the load balancer to send any request to any server, every server has to be able to handle every request. Right now, they aren't. The next section is where that bites.

⚠️ Common pitfall

Forgetting the load balancer itself can die. Three healthy servers behind one dead load balancer equal zero working app. Real systems keep a second load balancer waiting — which is exactly the kind of "invisible cost" this lesson keeps score of.

Fix #3

Who Am I? Sessions and Stateless Servers

The mystery of the random logout

You're now running multiple instances, and a brand-new problem appears. A user logs in on Server A, browses, picks a ticket, hits Buy — and that request goes to Server B, which immediately says "you're not logged in," even though they logged in a second ago. Nothing is broken. This happens the moment you run more than one server and don't handle sessions properly.

First: what does being logged in even mean? When you log in, the server checks your password, then needs to remember "it's you" on every request after that — so you don't retype your password on every click. So it makes a note: this person is logged in as Bob. It hands you a session ID — a random string that points at that note. Your browser sends the session ID with every request, and the server checks the note to know it's you.

The question that matters: where does the server keep that note? By default, the easy answer is: in the server's own memory. Now combine that with three servers. You log in, and the load balancer happens to send that request to Server 1 — so the note "Bob is logged in" lives in Server 1's memory. A moment later you click something — that's a new request — and the load balancer sends it to Server 2. Server 2 has never heard of you: the note is on Server 1. Server 2 looks in its own memory, finds nothing, and does the only thing it can — asks you to log in again. That's the "random logout." You're not being kicked out; you're being sent to a server that doesn't have your note. With three servers, roughly two out of every three clicks land on a server that doesn't know you.

The fix: stateless servers + one shared note

The fix is a rule: servers are not allowed to remember anything about you between requests. No server keeps a note in its own memory. Instead, the note goes somewhere all of them can reach — a separate place off to the side that every server can read from and write to. Now it doesn't matter where you land: you log in, the note is written to the shared place, and on your next click — whichever server the load balancer picks — that server reads the same shared place, finds your note, and knows it's you.

A server that keeps nothing about you in its own memory is called stateless. Every server is now interchangeable — exactly like the load balancer needed. Any server can handle any request, because none of them are keeping secrets the others can't see.

That shared place is very often Redis — an in-memory storage (it keeps data in RAM), which is extremely fast to read from. That matters because you're hitting it on every single request. Hold on to that name — Redis comes back later for two completely different jobs.

The cost: every request now does one extra thing — it reaches out to that shared store to find your note before it can do anything else. That's a little time added to every single request, and one more piece of infrastructure that has to stay up: if the shared store goes down, nobody can be logged in at all.

⚠️ Common pitfall

Users getting randomly logged out right after you added a second server? That's not a bug in your login code — it's session notes living in each server's own memory. Move them to a shared store and the "bug" disappears.

Fix #4

The Database, Part 1: Too Many Open Doors (Connection Pool)

So the front of the system is solid: load balancer, several stateless servers, everyone gets served. And all of them are talking to one database. You can probably guess where this is going.

New symptom: the app is slow again — but this time every server is healthy, none is at capacity, no bad queries, nothing seems broken. Confusing, until you notice the thing all servers have in common: they're all talking to the same single database. We scaled the servers, but we never scaled the thing behind them. Two separate problems hide here — let's take them one at a time.

Problem 1 — the database only has so many open connections

Here's a fact about databases many people don't know: a database will only hold so many open connections at the same time. Each connection — each open line from a server to the database — costs it memory and attention, so there's a hard limit on how many it'll accept at once. And that limit is lower than you'd guess: not millions — often just a few hundred on smaller hosted plans, sometimes even a few dozen.

Now count how many things are trying to connect: three servers, and each server opens several connections so it can handle several requests at once. That adds up fast. And if you're on serverless — where the platform spins up a fresh copy of your code for each request that arrives, like Vercel does — it gets worse in a way that surprises people: a big traffic spike means hundreds of fresh copies appearing at once, each grabbing its own new connections, filling every slot in seconds.

And here's the tell that makes this recognizable fast: the symptom isn't slowness — it's errors. Your ticket app was completely fine, then a popular show went on sale, traffic spiked, and suddenly: database connection errors, right at the moment things were going well. That's this.

The fix — a connection pool

The fix sits between your servers and the database, and it's almost boring how simple the idea is. Instead of every server opening and closing its own connections whenever it likes, you keep a small, fixed set of connections open at all times — and everything shares them. A request needs the database → it borrows one from the set → uses it → hands it straight back for the next request. This is a connection pool. The database only ever sees that small, fixed number of connections, no matter how many servers or requests you have. You've stopped overwhelming it with the sheer number of open lines. PgBouncer is a common one for Postgres, and most managed databases now ship a pooler you can simply switch on.

⚠️ Common pitfall

Seeing errors (not slowness) exactly when traffic spikes, then hunting for bugs in your own code? Count your database connections first — a few hundred open lines is a common ceiling, and serverless platforms multiply them fast.

Fix #5

The Database, Part 2: Genuinely Out of Capacity (Read Replicas)

That first fix handles the errors — but not the other problem, the one people usually mean when they say "the database can't keep up." Connections are under control, and the database is still maxed out: it's genuinely doing more work than one machine can do.

Before doing anything clever, do one quick free check: are your common queries actually using indexes? An index works like the index at the back of a book — it lets the database jump straight to the row you want instead of reading the whole table. If your app looks users up by email on every login and there's no index on the email column, the database is scanning every row to find one person, every single time. That one missing index looks exactly like a capacity problem — but it isn't one. Add the index, and the load can just disappear. Check that first: it's free.

But say you've checked, the indexes are there, and the database is simply out of room. Now look at what it's spending all its effort on. Think about how you actually use an app: you open any social app and scroll — you read post after post after post, and once in a while you write something. For every one thing you write, you read hundreds. That's true of almost any app — TikTok is you "reading" videos as you scroll. Reads massively outnumber writes, which means the database spends nearly all its effort answering reads. Take the reading load off it, and you fix nearly all of the problem.

The fix — make copies of the database

One database stays the original — the only one you're allowed to write to; everything you add or change goes there. Call it the primary. Then you make copies: read-only, you can't write to them, but you can read from them all day. Whenever something changes on the primary, it sends that change out to the copies so they stay up to date. These copies are read replicas.

Now the work is spread out: writes go to the primary; reads — the huge majority of your traffic — get shared across the replicas. Each machine is doing a fraction of what one machine was drowning under.

And this one has a cost that's different from the others: it doesn't just cost you money or a moving part — it quietly makes your app a little wrong. When you write something to the primary, it takes a moment — usually tiny, but not zero — for that change to reach the copies. Picture this: you post something, the write goes to the primary, and immediately your app loads your feed — that read goes to a replica that hasn't received your new post yet. You look at your own feed right after posting, and your post isn't there. You refresh, and there it is. Nothing was broken; the copy was just half a second behind. That gap has a name: replication lag, and it's the price of read replicas.

Your data is now slightly out of date on the copies for a moment, sometimes — which is usually completely fine (somebody seeing a post half a second late doesn't matter). But sometimes it does matter: you seeing your own post missing feels broken. For those specific cases, apps deliberately read from the primary instead of a replica.

And that's the real lesson, the one worth taking over everything else: you just made your app faster and slightly wrong — on purpose — and you chose which parts are allowed to be slightly wrong, and which are not.

⚠️ Common pitfall

Replication lag looks like a bug ("my post disappeared, then reappeared after refresh!"). It isn't — it's a trade-off you chose. The fix for "my own writes must be visible to me" is to read those specific queries from the primary, not to panic.

Fix #6

Stop Recomputing: Caching

The database is handled now: writes to the primary, reads spread across replicas, connections pooled. But some of those reads are still expensive. There's one particular kind of question we ask the database over and over — thousands of times — and get almost the same answer every time. Computing the same answer thousands of times is just wasteful.

Take the follower count on a profile. To get it, the database has to count every follower record for that person. If someone has 2 million followers, that's the database counting through 2 million rows to produce one number. And that number sits on their profile — meaning every single person who opens that profile makes the database count all 2 million again. Thousands of times an hour: the same expensive count, for a number that barely moves. Wasteful.

So instead of computing it every time: compute it once, and keep the answer somewhere fast. The next person who asks gets the saved answer, and the database is never touched. A saved answer, kept somewhere fast and close, is a cache.

The flow is simple. A request comes in asking for the follower count. First, check the cache: is the answer already sitting there? If yes — hand it straight back, never go near the database. If no — ask the database, and here's the important part: put it in the cache on the way back, so the next person gets it for free.

A cache is fast in a way a database can't be, because it keeps its data in memory rather than reading from disk — the answer comes back in a fraction of the time. And this is very often Redis again: the same Redis you already run for login sessions. Same piece of tech, doing a second job — worth noticing, because you didn't add a whole new system to your stack. (It gets a third job in the next section.)

cache-check.js — illustrative pseudocode 
// Pseudocode — the cache-check flow from the lesson.
// (Illustrative only: it needs a real Redis and a real database to run.)

async function getFollowerCount(userId) {
  // 1. ALWAYS check the cache first — it lives in memory, so it is fast.
  const cached = await redis.get("followers:" + userId);
  if (cached !== null) return cached;   // cache HIT: the database is never touched

  // 2. Cache MISS: ask the database (the expensive part).
  const count = await db.countFollowers(userId);

  // 3. The important step: save it on the way back,
  //    so the next person gets the answer for free.
  await redis.set("followers:" + userId, count);
  return count;
}

The cost of caching is the sharpest in the whole lesson: the moment you save a copy of an answer, that copy can go out of date. Someone gets a new follower — the real count in the database is now one higher, but the cache is still holding the old number, and everyone opening that profile sees the old count until the cache is updated or thrown away. Deciding when to throw away that saved answer, so it doesn't stay wrong for too long, is genuinely one of the harder problems in the whole field. There's an old joke among engineers: the two hardest things in computing are naming things and knowing when to clear your cache.

So here's the real skill, and it isn't really technical: caching trades correctness for speed, on purpose — and you have to decide which pieces of your app are allowed to be a little wrong for a little while, and which are not. A follower count 30 seconds out of date? Nobody will ever notice, nobody is harmed — cache it hard. The balance in somebody's bank account? That can never be even slightly out of date — you do not cache that, ever.

And it's worth stopping on that decision for a second, because it's the whole point. An AI will happily write that caching code for you, and write it well — but it will not make that call, because the call isn't about code. It's about your product, your users, and what they will and won't accept. You can outsource the typing, but not the decision-making. That's the part of the job that isn't going anywhere.

⚠️ Common pitfall

Caching by reflex — including data that must never be stale, like account balances or "is this ticket still available?" during checkout. Rule of thumb: cache hard what nobody minds being 30 seconds old; never cache anything where "slightly wrong" costs money or trust.

Fix #7

Don't Make Users Wait: Queues and Workers

The expensive reads are cached, the database is doing far less work, and the app is quick front to back. But there's one more kind of slow — and it's a strange one, because it has nothing to do with reading data at all.

Think about a typical signup flow. A user fills out the form, clicks Sign up, and expects the account to be created right away. But creating the account might not be the only thing your server has to do: you might also need to send a verification email, track the signup in your analytics, and set up some initial data. Do all of that before sending the response, and the user is just sitting there, staring at a loading spinner.

And it's more than just slow — because sending that verification email isn't something your server does itself. It hands the email to an outside service and waits for that service to say "sent." Your signup is now only as fast as that email service: if it's having a slow day, your signup is slow today; if it's down, your signup fails too. You've tied whether someone can even join your app to whether some separate email company happens to be up right now. That's a bad thing to tie together.

You've already seen this pattern — you just didn't know it. When you sign up for something and the verification email takes a few seconds to land, or you upload a video and it says "processing" and lets you carry on: that delay is not the app being slow. It's the app being built correctly.

The fix — split the work

Creating the account is the only part the user actually needs to happen before you answer them. The verification email doesn't have to happen in that same moment — it just has to happen soon. So you split the work: the instant the account is created, you answer the user — "You're signed up!" — and you don't send the email right then. Instead, you write down a note ("send a verification email to this person") and drop it onto a list. That list is a queue: just a line of jobs waiting to be done, in order. Then something separate — not the server handling the user's request, but a different process whose only job is working through that list — picks up the note and sends the email a moment later, while the user is already happily looking at their logged-in homepage. That separate process is a worker.

And it isn't just verification emails: password resets, notifications, receipts, video processing — any slow job you don't want a user waiting on goes on the same queue, and the worker quietly chews through it in the background. For a lot of apps, this is a tool called BullMQ, and it runs on Redis — the same Redis you already have for sessions and your cache. Three jobs now in a single piece of technology.

That's the whole win: the signup becomes instant, and it no longer cares whether the email service is even up. If it's down, the note just waits in the queue until it comes back — the account was already created either way.

But let's not forget the costs. First, the work now happens later — which is exactly why that verification email takes a few seconds to show up. For a verification email, nobody cares; just know that "done" now means we have promised to do this, not this is finished. Second, you have two more things to run, and you have to keep both the queue and the worker alive. Third — jobs can fail. The worker tries to send the email and the email service is down, so plan for it: try again in a minute, and if it keeps failing, put it somewhere a human can look at later.

⚠️ Common pitfall

"Fire and forget." A job you dropped on a queue and never checked on is a job you're quietly not doing. Every real queue setup needs retries and a "dead letter" pile that a human eventually reads.

Fix #8 · last resort

When the Data Itself Won't Fit: Sharding

Everything we've fixed so far was about handling more people. This last one isn't about people — it's about how much data you have. Remember the read replicas? Every one of them is a full copy of your database, which quietly assumes your whole database fits on one machine in the first place. But what if it doesn't? What if the data just keeps growing until it's too big for any single machine to hold? A copy can't save you now — there's no machine big enough to copy it onto.

So you do the one thing we've avoided all lesson: stop keeping all your data in one place. You split it across several databases, and each one holds only part of it. That immediately raises a problem: if your data is spread across, say, three databases, how does your app know which one to put a new user in — and later, which one to find them in again? You can't drop them anywhere: if you saved users randomly, you'd have to search all three databases every time, which is slower than the one database you started with.

The rule

You need a rule, built on one column — a property every record has. For users, the obvious choice is the user ID. The simplest possible rule: take the user ID, divide it by the number of databases you have, and the remainder tells you where they go. Three databases: remainder 0 → Database 1, remainder 1 → Database 2, remainder 2 → Database 3. Your users end up spread evenly, each database holding roughly a third.

Quick note: if your IDs have letters in them, like a UUID, you first run them through a hash function — which turns any value into a number, the same number every time — and then the exact same divide-by-remainder rule applies.

Each of these databases is called a shard, and the whole approach — splitting your database across shards by a rule — is called sharding.

And here's the part that makes it actually click. A request comes in for user number 5. The app runs the same exact rule: 5 ÷ 3 leaves remainder 2 → Database 3. It goes straight there. It doesn't search. It doesn't check the other two. It just knows — because the rule is consistent, the same user always lands on the same shard, and writing data and finding it again both use the same rule. You've essentially split your lookup, read, and write time by three.

The cost — cross-shard queries

As long as a question is about one user, everything's fine: one shard, fast. But some questions are not about one user. Say you want to count how many users you have in total. There is no single shard that knows the answer — no shard has all the users. You have to ask all three, get their separate counts, and add them up yourself. A question that used to be one simple query is now three queries plus some assembly — and it gets worse the more shards you have: 10 shards means asking 10 databases and combining 10 answers. Anything that has to look across all your data — counting, sorting everything by date, searching everyone — now touches every shard.

These are called cross-shard queries, and avoiding them is the whole art of sharding. It's why choosing the rule — which column you split on — is such a big decision. Pick well, and almost every query stays on one shard. Pick badly, and all your common queries have to hit every machine: you've built something slower than what you started with. Oh, and one more thing — once your data is split like this and all your code is written around it, going back is its own painful migration.

So this is the most powerful tool in the whole lesson — and still the one you reach for last, by a long way. Teams put it off for years, and they're right to: you do it only when the data simply will not fit any other way. (For a sense of real-world scale: Notion went from one database to sharded at over 200 billion rows while the whole product stayed alive.)

✅ Best practice

Shard only when the data won't fit on one machine — never "to be ready for scale." One extra consequence of the remainder rule: change the number of shards, and every user's home database changes. That's exactly why the transcript calls un-sharding (or re-sharding) a painful migration.

    // THE SHARDING RULE from the lesson:
    // divide the user ID by the number of databases.
    // The REMAINDER decides which database to use.
    function shardFor(userId, dbCount) {
      const remainder = userId % dbCount;   // e.g. 5 % 3 = 2
      return remainder + 1;                 // 0 → DB 1, 1 → DB 2, 2 → DB 3…
    }

    function route() {
      const id    = Number(document.getElementById("userId").value);
      const count = Number(document.getElementById("dbCount").value);

      if (!Number.isInteger(id) || count < 2) {
        document.getElementById("result").textContent = "Please enter valid numbers.";
        return;
      }

      const db = shardFor(id, count);
      document.getElementById("result").textContent =
        "User " + id + " → " + id + " ÷ " + count +
        " leaves remainder " + (id % count) + " → Database " + db;
    }

⚠️ Common pitfall

This is a simulator of the routing rule, not a real database. And notice what happens if you change the shard count mid-flight: every user's home database changes. In a real system that means moving data — the painful migration the lesson warns about. Real teams pick their shard count and rule very carefully, once.

  3. Task 3 — bonus, UUIDs: add a tiny hash function so that IDs with letters in them, like "f81d4fae-7dec", also route to a consistent database. The same input must always give the same shard.

Solution — what you should have done

Task 1: 7 ÷ 5 = 1 remainder 2 → Database 3. Notice you only changed the input's value — the rule itself never changes. That's the whole trick: one consistent rule, applied everywhere, forever.

Task 2: the key realization is that a total count cannot skip any shard — no single shard knows the whole answer, so the loop is forced to visit every one:

solution.js 
// Task 1 — User 7 with 5 databases:
//   7 % 5 = 2  →  Database 3. Only the input changed, not the rule.

// Task 2 — the cross-shard "count everyone" query:
function countAllUsers(shardCounts) {
  let total = 0;
  for (const count of shardCounts) {   // must visit EVERY shard — no skipping
    total += count;
  }
  return { total: total, shardsQueried: shardCounts.length };
}
// countAllUsers([4001, 3998, 4010])
//   → { total: 12009, shardsQueried: 3 }  ← the cost of a cross-shard query

// Task 3 (bonus) — a simple deterministic hash for UUID-style IDs:
// same input → same number, every single time (that is the whole point).
function simpleHash(str) {
  let h = 0;
  for (let i = 0; i < str.length; i++) {
    h = (h * 31 + str.charCodeAt(i)) % 1000000007;
  }
  return h;
}
// shard = simpleHash("f81d4fae-7dec") % dbCount + 1;

Task 3 (bonus): the hash must be deterministic — same input, same number, every time — or users would silently move between databases. Any simple loop over the characters (like simpleHash above) works; then the remainder rule applies exactly as before.
