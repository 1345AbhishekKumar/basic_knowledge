01 / FUNDAMENTALS

Why RAG Exists

LLMs know a lot — but most of the world's important data is private. RAG bridges that gap.

Large language models are trained on publicly available data. But the data that matters most — your personal files, corporate documents, internal knowledge bases — is private and never seen during training. RAG (Retrieval Augmented Generation) solves this by letting you feed external data into an LLM at query time.

Context windows have exploded: from 4K–8K tokens a year ago to over a million tokens today. That means thousands of pages of private text can now be loaded into an LLM's working memory. RAG is the structured way to do this — instead of dumping everything in, you retrieve only the relevant pieces and use them to augment the LLM's generation.

  • LLMs are trained on public data — most important data is private
  • Context windows grew from 4K to 1M+ tokens, making external data feasible
  • RAG = Retrieval Augmented Generation: fetch relevant docs, then generate grounded answers
  • This is the new operating system paradigm: LLMs + private data sources
Obvious What: You ask your company chatbot "What's our refund policy?" So what: Without RAG, it guesses from public training data. With RAG, it finds your actual policy document and quotes it.
Counter-intuitive What: A bigger model doesn't always give better answers on private data. So what: A small model with good RAG retrieval often beats a giant model that's guessing — grounding beats raw scale.
Edge case What: Context windows hit 1M tokens but retrieval still matters. So what: Even with huge windows, stuffing everything in is slow and expensive. RAG targets what's needed.
A library with millions of books (LLM training data) vs. a librarian who finds the exact page you need from your private filing cabinet (RAG).
Bigger context windows mean RAG is obsolete — no, retrieval is still cheaper, faster, and more precise than dumping everything in.
RAG unites LLM processing power with the private data where most real-world value lives.
The RAG Motivation
Private data + LLM = grounded answers

Recall Prompt

What are the two main reasons RAG exists, according to this module?
(1) Most important data is private and not in LLM training sets. (2) Context windows are now large enough to feed external data, but RAG makes this efficient by retrieving only what's relevant.

Compact Scenario

A You're building a customer support bot. Do you: (a) Fine-tune the LLM on all support tickets, or (b) Use RAG to retrieve relevant past tickets at query time?
Best choice: (b) RAG. Fine-tuning is expensive and doesn't update when new tickets arrive. RAG retrieves current, relevant tickets on the fly — always up to date, always grounded.

02 / FUNDAMENTALS

RAG Pipeline Overview

Three stages, one flow: index your documents, retrieve relevant chunks, generate grounded answers.

RAG has three core stages. Indexing processes your documents so they can be searched — typically by splitting them into chunks and storing numerical representations (embeddings) in a vector store. Retrieval takes a user question, embeds it the same way, and finds the closest document chunks. Generation stuffs those retrieved chunks into a prompt and asks the LLM to produce an answer grounded in that context.

  • Indexing: Load documents → split into chunks → embed → store in vector store
  • Retrieval: Embed question → similarity search → return K nearest chunks
  • Generation: Stuff retrieved chunks + question into prompt → LLM generates answer

The advanced RAG landscape adds techniques at each stage: query translation (improve the question before retrieval), routing (send it to the right source), query construction (convert to structured queries), and active RAG (grade and retry if results are poor).

Basic RAG Pipeline
Three stages: Index → Retrieve → Generate
Obvious What: A FAQ chatbot needs to answer from your company docs. So what: You index all FAQ articles, retrieve the matching one, and let the LLM rephrase it conversationally.
Counter-intuitive What: Retrieval quality matters more than LLM quality in RAG. So what: A great LLM with bad retrieval still gives bad answers. Fix retrieval first.
Edge case What: What if no document matches the question? So what: The LLM may hallucinate. Active RAG (Module 17–18) handles this by grading and falling back to web search.
Like a doctor consulting a medical database before diagnosing: look up relevant studies (retrieve), then reason over them (generate) rather than guessing from memory alone.
"RAG is just a vector store lookup" — no, the pipeline includes clever preprocessing, query rewriting, and quality grading at multiple stages.
Understanding the full pipeline lets you identify which stage is the bottleneck when your RAG system performs poorly.
🔗 Deep dive into the first stage: Module 3: Documents to Vectors
03 / FUNDAMENTALS

Indexing: Documents to Vectors

How documents become searchable numbers — splitting, embeddings, and sparse vs. dense representations.

To search documents, you need a numerical representation. There are two main approaches: sparse vectors (like TF-IDF) count word frequencies across a large vocabulary — most entries are zero, hence "sparse." Dense embeddings compress a document into a fixed-length vector (e.g., 1536 dimensions) using machine-learned models that capture semantic meaning.

In practice, you load documents, split them into chunks (because embedding models have limited context windows — typically 512 to 8K tokens), embed each chunk into a vector, and store those vectors in a vector database. Each vector links back to the original text.

  • Load documents from source (PDF, web, database, etc.)
  • Split into chunks that fit the embedding model's context window
  • Embed each chunk using an embedding model (e.g., OpenAI embeddings → 1536-d vector)
  • Store vectors + original text in a vector store (Chroma, Pinecone, etc.)
Obvious What: A 10-page PDF about return policies. So what: Split into ~20 chunks, embed each, store in Chroma. Now searchable by question.
Counter-intuitive What: Smaller chunks aren't always better. So what: Tiny chunks lose context. Too large chunks mix unrelated topics. Sweet spot is usually 500–1500 tokens.
Edge case What: Code documents with lots of imports and boilerplate. So what: Standard chunking may split a function mid-definition. Consider semantic chunking or AST-based splitting.
Embedding is like giving every document a GPS coordinate in "meaning space." Documents about similar topics land near each other — you don't need to read them all, just find the ones closest to your question's location.
From Document to Embedding
Split → Embed → Store

Recall Prompt

What is the difference between sparse and dense vector representations?
Sparse vectors (like TF-IDF) have one entry per word in a large vocabulary, mostly zeros — they count word frequencies. Dense embeddings compress the document into a fixed-length vector (e.g., 1536 dimensions) using machine learning to capture semantic meaning in a compact form.

04 / FUNDAMENTALS

Retrieval: Similarity Search

Finding the nearest neighbors in embedding space — the core of RAG retrieval.

When you embed both documents and questions into the same high-dimensional space, similar meanings land near each other. Retrieval is simply a neighborhood search: find the K closest document vectors to the question vector. This is K-Nearest Neighbors (KNN) search, and it's the backbone of modern vector stores.

The K parameter controls how many chunks you retrieve. K=1 gets the single best match; K=5 casts a wider net. Too low and you miss context; too high and you dilute with irrelevant chunks. The right K depends on your use case.

  • Embed the user's question using the same embedding model as the documents
  • Search the vector store for the K most similar vectors (KNN search)
  • Return those chunks with their similarity scores
  • Tune K: too low = missing info; too high = noise
Obvious What: Question: "What is task decomposition?" So what: Embedding search finds the chunk that explains task decomposition — even if it uses slightly different words.
Counter-intuitive What: "Cosine similarity" ignores vector magnitude. So what: What matters is the direction (meaning), not the size (length). A short document and a long one about the same topic score similarly.
Edge case What: K=1 misses related context from adjacent chunks. So what: Use K=3–6 for multi-faceted questions, or implement "parent document retrieval" — retrieve a small chunk, return the larger section it belongs to.
Like asking a librarian for books on "quantum physics" — they don't check every shelf, they go to the physics section and grab the closest 3 books to your topic.

🔗 Now let's generate answers from retrieved chunks — Module 5: Prompts & Chains
05 / FUNDAMENTALS

Generation: Prompts and Chains

Putting it all together — prompt templates, LCEL chains, and producing grounded answers.

Generation is the final stage: you take the retrieved document chunks, stuff them into a prompt template along with the user's question, and pass it to an LLM. The prompt has placeholders (keys) like "context" and "question" that get filled with the retrieved chunks and the original query.

In LangChain, you compose these pieces into a chain using LCEL (LangChain Expression Language). A simple chain connects: prompt → LLM → output parser. A RAG chain automatically triggers retrieval when invoked, passing the question through to the retriever and plumbing results into the prompt.

  • Define a prompt template: "Answer the following question based on this context: {context} Question: {question}"
  • Choose an LLM (e.g., GPT-3.5, Claude, Llama)
  • Build a chain: prompt | LLM | output parser
  • Invoke with {"context": retrieved_docs, "question": user_question}
Obvious What: Retrieval returns 3 chunks about refund policies. So what: The prompt assembles them into "Based on these documents: [chunks], answer: what's the refund policy?" and the LLM generates a clear answer.
Counter-intuitive What: A more detailed prompt doesn't always produce better answers. So what: Overly complex instructions can confuse the LLM. Simple, clear prompts with good context often outperform elaborate ones.
Edge case What: Context window overflow when retrieved chunks are too large. So what: Limit K or use summarization to compress retrieved content before generation.
The prompt template is a fill-in-the-blank form: the retrieved documents are your research notes, the question is the exam prompt, and the LLM is the student writing an answer using only those notes.

Recall Prompt

What are the three pieces you need to build a basic RAG chain?
(1) A retriever that fetches relevant documents, (2) A prompt template with placeholders for context and question, (3) An LLM that generates the answer from the populated prompt.

06 / QUERY TRANSLATION

Multi-Query

Fan out one question into multiple perspectives to improve retrieval coverage.

User queries are often ambiguous or poorly worded for embedding-based retrieval. Multi-query takes one question and rewrites it into several differently worded versions from different angles. Each version is embedded and searched independently, then the unique results are combined. This "shotgun approach" increases the chance of retrieving the right documents.

The intuition: a question's initial wording might not align well with how relevant documents are embedded. By rewriting from multiple perspectives, you cover more of the embedding space.

  • Take the user's original question
  • Use an LLM to generate 3–5 rephrased versions from different perspectives
  • Run retrieval independently for each version
  • Take the unique union of all retrieved documents
  • Pass combined documents to the generation step
Multi-Query Flow
One question → many perspectives → combined results
Obvious What: Question: "How do agents use memory?" So what: Rewrites might include "types of agent memory," "persistent vs. episodic memory in AI," "memory architectures for LLM agents."
Counter-intuitive What: More rewrites don't always help. So what: Too many rewrites add noise. 3–5 is usually the sweet spot — enough diversity without diluting with tangential results.
Edge case What: The original question was already perfectly worded. So what: Multi-query still helps because the LLM's rewrites may match document phrasing better than your exact words.
Like asking the same question in 5 different ways at a library — each wording might help the librarian find a different relevant book that one phrasing alone would miss.

🔗 Add smart ranking on top — Module 7: RAG Fusion
07 / QUERY TRANSLATION

RAG Fusion

Multi-query + reciprocal rank fusion = smarter ranking across multiple retrievals.

RAG Fusion is nearly identical to multi-query — you generate multiple rephrased questions and retrieve for each. The key difference: instead of just taking a union of results, you apply Reciprocal Rank Fusion (RRF), a ranking algorithm that consolidates the multiple ranked lists into one optimized order.

RRF works by looking at where each document appears across all the ranked lists and aggregating those positions. A document that appears high in multiple lists gets boosted. This is especially useful when querying across multiple vector stores or many differently-worded questions.

  • Generate multiple rephrased questions (same as multi-query)
  • Retrieve ranked document lists for each question
  • Apply reciprocal rank fusion: aggregate positions across all lists
  • Take the top-N from the fused ranking for generation
Obvious What: Doc A ranks #1 in list 1 and #3 in list 2. Doc B ranks #2 in both. So what: RRF may rank Doc A higher because it appeared at #1 in one list — consistent high placement wins.
Counter-intuitive What: RRF doesn't need actual similarity scores. So what: It works purely on rank positions, making it robust to different score scales across different vector stores or embedding models.
Edge case What: All rewrites retrieve the same documents. So what: RRF doesn't help if rewrites aren't diverse enough — diversity in the LLM-generated rewrites is critical.
Like asking 5 friends to rank their top 3 pizza places, then combining their lists: a place that appears high on everyone's list wins over one that's #1 for just one friend.

Recall Prompt

What's the key difference between multi-query and RAG fusion?
Both generate multiple rephrased questions and retrieve for each. The difference is that RAG fusion applies Reciprocal Rank Fusion to rank the combined results by position across all lists, while multi-query simply takes the unique union without re-ranking.
🔗 Break complex questions into sub-problems — Module 8: Query Decomposition
08 / QUERY TRANSLATION

Query Decomposition

Break hard questions into simpler sub-questions, solve each, then combine.

Some questions are too complex for a single retrieval. Decomposition breaks them into sub-questions that can be answered individually. There are two flavors: sequential (answer Q1, use that answer to inform Q2, and so on — from Google's "Least-to-Most" paper) and parallel (answer all sub-questions independently, then concatenate).

A related technique called IRCoT (Interleaved Retrieval + Chain of Thought) combines retrieval with reasoning at each step — each sub-question's answer feeds into the next, building up the solution progressively.

  • Use an LLM to decompose the question into sub-questions
  • For sequential: answer Q1 → use answer as context for Q2 → continue
  • For parallel: answer all sub-questions independently, concatenate
  • Combine sub-answers into a final response
Obvious What: "What are the main components of an autonomous agent?" So what: Decomposes into: "What is LLM technology?" → "What are agent components?" → "How do components interact?"
Counter-intuitive What: Parallel decomposition is simpler but weaker than sequential. So what: Sequential builds knowledge step by step. Parallel treats sub-questions as independent — loses cross-references.
Edge case What: Sub-questions that depend on each other but are run in parallel. So what: The second sub-question lacks context from the first, leading to incomplete answers. Use sequential for dependent chains.
Like solving a math problem: first find x, then use x to find y. You can't find y without x — sequential decomposition respects that dependency.

🔗 The opposite direction: going more abstract — Module 9: Step-Back Prompting
09 / QUERY TRANSLATION

Step-Back Prompting

Ask a higher-level question first, then use that background to answer the specific one.

While decomposition makes questions more specific, step-back prompting goes the opposite direction — it generates a more abstract, higher-level question that captures the general concept. You then retrieve documents for both the original and the step-back question, combining the context for a richer answer.

This works especially well for textbook-style domains where high-level concepts are in one chapter and specific implementations in another. The step-back question retrieves the conceptual foundation, and the original question retrieves the specific details.

  • Use few-shot prompting to generate a more abstract "step-back" question
  • Retrieve documents for both the original and step-back questions
  • Combine both sets of retrieved context
  • Generate the final answer using the enriched context
Obvious What: "What is task composition for LLM agents?" So what: Step-back: "What is the process of task composition in general?" — retrieves broader conceptual docs.
Counter-intuitive What: Sometimes a vaguer question retrieves better documents. So what: Specific questions may not match any document exactly. Abstract questions match general knowledge that contains the answer.
Edge case What: Step-back generates an unrelated abstract question. So what: Poor few-shot examples lead to bad abstractions. Tune the examples carefully for your domain.
Before asking "What's the exact pH of lemon juice?", first ask "What is pH?" — understanding pH gives you the framework to interpret the specific answer.
🔗 Map questions into document space — Module 10: HyDE
10 / QUERY TRANSLATION

HyDE (Hypothetical Document Embeddings)

Generate a fake answer first, then use it to find real documents.

Questions and documents are very different text objects — short and sparse vs. long and dense. HyDE bridges this gap by having the LLM generate a hypothetical document (a plausible-looking answer passage) and then using that hypothetical document for retrieval instead of the raw question.

The intuition: a hypothetical document, even if factually wrong, is closer in embedding space to the real target document than the short, potentially poorly-worded question. The LLM's "best guess" at what an answer looks like becomes a better search query.

  • Prompt the LLM: "Write a passage that would answer this question: [question]"
  • Embed the generated hypothetical document
  • Use that embedding to search the vector store
  • Pass real retrieved documents (not the hypothetical) to the LLM for generation
Obvious What: Question: "How do agents use memory?" So what: LLM generates a fake passage about agent memory systems. That passage embeds near real docs about memory architectures.
Counter-intuitive What: The hypothetical document can be factually wrong and still work. So what: What matters is the embedding location, not the content accuracy. The wrong passage is still closer to the right docs than the raw question.
Edge case What: Domain where the LLM has no knowledge. So what: The hypothetical document will be generic and may not land near the right docs. HyDE works best when the LLM has some domain familiarity.
Like describing a suspect to a sketch artist — even if the sketch isn't perfect, it's easier to match against a photo database than a verbal description alone.

Recall Prompt

Why is a hypothetical document better for retrieval than the raw question?
Questions are short and sparse; documents are long and dense. They live in different regions of embedding space. A hypothetical document — even if factually wrong — is a longer, denser text that lands closer to real documents in embedding space than the raw question does.
🔗 Send questions to the right source — Module 11: Routing
11 / ROUTING

Routing

Direct questions to the right data source — vector store, SQL, graph DB, or different prompts.

After translating a query, you need to route it to the right source. A question about code goes to Python docs; a question about physics goes to a physics knowledge base. There are two approaches:

Logical routing: Give the LLM knowledge of available data sources and let it reason about which one to use. The output is a structured object (via function calling) constrained to specific options — essentially classification with structured output.

Semantic routing: Embed the question and embed reference prompts for each data source. Choose the most similar prompt. Pure math, no LLM reasoning needed.

  • Define your available sources (vector stores, DBs, prompts)
  • Logical: Bind a data model to the LLM for structured output classification
  • Semantic: Embed question + reference prompts, pick most similar
  • Route to the appropriate retriever chain
Routing Decision
Question → classifier → right data source
Obvious What: Question mentions Python code. So what: Logical router classifies it as "python_docs" and sends to the Python documentation retriever.
Counter-intuitive What: Semantic routing can work without an LLM at all. So what: Embed the question, embed reference prompts, compute cosine similarity — pure math, no API call, very fast.
Edge case What: Question spans two domains. So what: Router picks one. Consider routing to both or using a combined retriever for multi-domain queries.
🔗 Convert natural language to structured queries — Module 12: Query Construction
12 / ROUTING & CONSTRUCTION

Query Construction

Turn natural language into structured queries — metadata filters, SQL, Cypher.

Users ask questions in natural language, but vector stores need structured filters. "Find me videos about chat LangChain published after 2024" needs to become a structured query with date filters. Query construction uses function calling to convert natural language into the domain-specific language (DSL) your data source needs.

For vector stores, this means metadata filters (date ranges, categories, view counts). For SQL databases, it's text-to-SQL. For graph databases, it's text-to-Cypher. The pattern is the same: describe your schema to the LLM via structured output, and it produces queries that match.

  • Define a schema describing your available filters and search fields
  • Bind that schema to the LLM using function calling / structured output
  • User asks in natural language → LLM outputs a structured query object
  • Parse the output and apply it to your vector store / DB
Obvious What: "Show me short videos about agents from 2024." So what: LLM outputs: {content_search: "agents", publish_date: {gte: "2024-01-01"}, length: {lte: 600}}.
Counter-intuitive What: The LLM doesn't execute the query — it just generates it. So what: The structured output is a Pydantic object. Your code applies it. The LLM is a query translator, not a database engine.
Edge case What: Ambiguous filter: "recent" could mean last week, month, or year. So what: Define sensible defaults in your schema or prompt the LLM to ask for clarification.
Like a concierge: you say "I want a quiet table for two near the window" and they translate that into the restaurant's reservation system codes.
🔗 Now let's look at smarter indexing strategies — Module 13: Multi-Representation Indexing
13 / ADVANCED INDEXING

Multi-Representation Indexing

Index summaries for retrieval, store full documents for generation — best of both worlds.

Traditional indexing embeds document chunks directly. Multi-representation indexing takes a different approach: use an LLM to create a summary (proposition) of each document, embed that summary for retrieval, but store the full raw document separately. When retrieval matches a summary, you return the full document to the LLM.

This is powerful with long-context LLMs: the summary is optimized for retrieval (keywords, big ideas), while the full document gives the LLM complete context for generation. No need to worry about chunk boundaries losing important information.

  • Load full documents
  • Use an LLM to generate a summary/proposition for each document
  • Embed and index the summaries in a vector store
  • Store full raw documents in a separate document store
  • At retrieval: match summaries → return full documents via doc IDs
Obvious What: A 50-page report on AI safety. So what: Summary captures "AI safety alignment RLHF" — retrieves well. Full 50-page report goes to the LLM for comprehensive answer.
Counter-intuitive What: Summaries can include keywords the original document doesn't emphasize. So what: LLM-generated summaries may "translate" the document into retrieval-friendly language — a feature, not a bug.
Edge case What: Full document exceeds the LLM's context window. So what: You're back to needing chunking for generation. But with 1M+ token windows, most documents fit.
Like an index at the back of a textbook: the index words (summaries) help you find the right page, but you read the full page (document), not just the index entry.
🔗 Build hierarchical indexes — Module 14: Raptor
14 / ADVANCED INDEXING

Raptor: Hierarchical Indexing

Cluster documents recursively into a tree of summaries — handle both specific and broad questions.

Some questions need a specific chunk; others need information synthesized across many documents. Raptor builds a hierarchical tree of document summaries: start with leaf documents, cluster similar ones, summarize each cluster, then cluster those summaries, and repeat recursively until you have a single top-level summary.

Index all levels together — raw chunks, mid-level summaries, and top-level summaries. Low-level questions retrieve raw chunks (specific details). High-level questions retrieve summaries (broad synthesis). This gives you semantic coverage across the entire abstraction hierarchy.

  • Start with raw documents as leaf nodes
  • Embed all documents, cluster similar ones together
  • Summarize each cluster into a parent node
  • Repeat recursively until one cluster remains
  • Index ALL levels (leaves + all summaries) together in one vector store
Raptor Hierarchical Tree
Documents cluster → summarize → recurse
Obvious What: 30 LangChain docs about different topics. So what: Raptor clusters them into groups (agents, retrieval, chains), summarizes each, then indexes all levels together.
Counter-intuitive What: You don't need to split documents at all with long-context LLMs. So what: Raptor works on whole documents — embed, cluster, summarize, recurse. No chunking needed.
Edge case What: Very heterogeneous document sets. So what: Clustering may produce poor groups. Consider domain-specific clustering or adjusting the number of clusters.
Like organizing a library: books on the same shelf (cluster), shelves grouped by section (summary), sections grouped by floor (higher summary) — you can search at any level of detail.
🔗 Token-level embedding matching — Module 15: ColBERT
15 / ADVANCED INDEXING

ColBERT: Token-Level Embeddings

Instead of one vector per document, embed every token — then match question tokens to document tokens.

Traditional embeddings compress an entire document into a single vector — potentially losing nuance. ColBERT takes a different approach: embed every token in both the document and the question. Then for each question token, find the most similar document token (max similarity), and sum those max scores. This "late interaction" captures fine-grained matching that single-vector embeddings miss.

The trade-off: ColBERT reports very strong performance, but requires more storage (many vectors per document) and has latency considerations for production use. The RAPTOR library makes it easy to experiment with.

  • Tokenize both document and question
  • Embed each token individually (positional weighting applied)
  • For each question token, compute similarity to all document tokens, take the max
  • Final score = sum of max similarities across all question tokens
Obvious What: Question: "What emotion Studio did Miyazaki found?" So what: Token-level matching finds "Miyazaki" ↔ "Miyazaki" and "emotion" ↔ "Studio Ghibli" separately, then combines.
Counter-intuitive What: ColBERT doesn't compress anything — it stores more data. So what: Quality comes from preserving token-level detail, not compressing. More storage = better matching.
Edge case What: Very long documents with ColBERT. So what: Each token gets a vector — a 10K-token document needs 10K vectors. Check max token limits and storage requirements.
Like a word-matching game: instead of comparing entire sentences at once, you highlight matching words in each and score how many individual words overlap.

Recall Prompt

How does ColBERT's scoring differ from traditional single-vector similarity?
Traditional: one vector per document, cosine similarity between document vector and question vector. ColBERT: one vector per token, each question token finds its best-matching document token (max similarity), then all max scores are summed. This captures fine-grained token-level matching that single-vector compression loses.
🔗 Now let's build active, self-reflective RAG flows — Module 16: Active RAG with LangGraph
16 / ACTIVE RAG

Active RAG with LangGraph

Flow engineering: build logical graphs where the LLM decides when to retrieve, grade, retry, or generate.

Basic RAG is a straight line: retrieve → generate. Active RAG adds decision points. With LangGraph, you define a state graph where each node modifies a shared state dictionary, and conditional edges let the LLM choose what happens next. This is "flow engineering" — you design the graph, define what each node does, and let the LLM navigate it.

A typical active RAG flow: retrieve documents → grade relevance → if irrelevant, transform query and do web search → generate. The grading nodes use structured output (binary yes/no) to make deterministic routing decisions.

  • Define state as a dict: {question, documents, generation, ...}
  • Define nodes as functions that take state and return modified state
  • Define conditional edges: if grade=yes → generate; if grade=no → transform → web search
  • Lay out the graph: entry → retrieve → grade → conditional → generate → end
Active RAG Flow
Grade → decide → retry or generate
Obvious What: Question about a very niche topic not in your index. So what: Grade says "irrelevant" → transform query → web search finds the answer → generate with web results.
Counter-intuitive What: Adding grading steps adds latency but improves quality. So what: Use fast models (GPT-3.5-turbo, Groq) for grading — these are simple yes/no decisions that don't need big models.
Edge case What: Infinite loop: grade fails → transform → grade fails again. So what: Limit iterations (e.g., one retry max) to prevent runaway flows.
Like a quality control line in a factory: every product gets inspected (graded). Defective ones get reworked (transform + re-retrieve). Only passing products ship (generate).
🔗 The specific grading technique — Module 17: Self-RAG
17 / ACTIVE RAG

Self-RAG

Grade document relevance, check for hallucinations, verify answer quality — then retry if needed.

Self-RAG moves from single-shot RAG to a cyclic flow. After retrieval, you grade whether the documents are actually relevant to the question. After generation, you check for hallucinations (is the answer faithful to the retrieved documents?) and answer relevance (does it actually answer the question?). If any grade fails, you loop back — rewrite the question, re-retrieve, or regenerate.

This is especially valuable as context windows grow: you can use fast, cheap LLMs to do the grading (it's a binary yes/no task), keeping latency low while dramatically improving quality.

  • Retrieve documents
  • Grade: Are documents relevant to the question?
  • If irrelevant → rewrite question → re-retrieve
  • Generate answer
  • Grade: Is the answer faithful to the documents? (No hallucination)
  • Grade: Does the answer actually address the question?
Obvious What: Retrieved doc is about "apple pie recipes" but question is about "Apple Inc. stock." So what: Relevance grade = no → rewrite query with "technology company" → re-retrieve.
Counter-intuitive What: Self-RAG works with small open-source models. So what: Grading is a simple binary task — even a 7B model can do it well. You don't need GPT-4 for quality checks.
Edge case What: Document is relevant but answer hallucinates details not in the document. So what: Faithfulness grade catches this. Regenerate with stricter "only use provided context" instructions.
Like a self-editing process: write a draft (generate), then ask "Did I actually answer the question?" and "Did I make anything up?" — revise until both answers are yes.

CRAG: Corrective RAG

When your index fails, fall back to web search — corrective RAG as a safety net.

What happens when a question is outside the scope of your index? Corrective RAG (CRAG) adds a web search fallback. After grading documents as irrelevant, instead of just rewriting the query, you perform a web search to find answers from the broader internet. This makes your RAG system robust to out-of-domain questions.

CRAG works well with small open-source models (like Mistral 7B running locally via Ollama), making it practical for production. The core pattern: grade → if bad → web search → use search results for generation.

  • Retrieve documents from your index
  • Grade document relevance
  • If relevant → use retrieved docs for generation
  • If irrelevant → trigger web search as fallback
  • Use web search results for generation instead
Obvious What: User asks about a news event from yesterday. So what: Your index doesn't have it → grade says irrelevant → web search finds current articles → generate from search results.
Counter-intuitive What: Web search as a "feature" not a "failure." So what: CRAG embraces that no index is complete. The fallback is intentional — broader coverage without maintaining a massive index.
Edge case What: Web search returns low-quality or biased results. So what: Consider adding a quality grade on web results too, or limiting to trusted search domains.
Like a doctor who checks their hospital's database first, but if the case is unusual, they consult external medical literature — better to find the right answer from somewhere than to guess.

Still Confused?

When should I use multi-query vs. RAG fusion?
Multi-query is simpler — just combine unique results. Use RAG fusion when you need better ranking across multiple retrievals, especially across different vector stores. RAG fusion's reciprocal rank fusion produces a consolidated ranking that's often better than a raw union. Start with multi-query; upgrade to RAG fusion if ranking quality matters.
Do I still need RAG if context windows are 1M+ tokens?
Yes. Even with huge windows, dumping everything in is slow, expensive, and can degrade LLM performance (the "lost in the middle" problem). RAG targets only relevant content, keeping costs low and answers precise. The trend is to use long context plus RAG — the LLM reads the full retrieved document, not just a chunk.
How do I choose between HyDE, step-back, and multi-query?
They solve different problems. Multi-query handles ambiguous wording. Step-back handles questions that need broad conceptual context. HyDE handles the mismatch between short questions and long documents. Try multi-query first (easiest to implement); add step-back for knowledge-heavy domains; experiment with HyDE for retrieval quality issues.
What's the latency impact of active RAG (Self-RAG, CRAG)?
Grading adds one extra LLM call per grade step. Use fast models (GPT-3.5-turbo, Groq, small open-source models) for grading — these are simple yes/no decisions. Limit cyclic retries to 1 turn. The quality improvement usually justifies the small latency cost, especially for high-stakes applications.
Should I use Raptor or multi-representation indexing?
Multi-representation indexing is simpler — summarize each doc, index summaries, retrieve full docs. Raptor adds hierarchical clustering for questions that span many documents. Start with multi-representation; add Raptor when you have many documents and need to answer both very specific and very broad questions from the same corpus.
