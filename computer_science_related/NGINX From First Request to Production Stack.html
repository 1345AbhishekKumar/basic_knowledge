Built for one outcome: putting nginx in front of your own full-stack app — React front end, Node.js API, database — so every request enters through a single, secure, fast door. One tangible win: by the last module you can deploy and secure that exact stack yourself.

Module 01

What a Web Server Is

spec: transcript 00:02:31 → 00:05:00

When you type google.com and press enter, your browser sends an HTTP request to a server, the server processes it, and a response comes back for the browser to display. That part of the story everyone knows. The interesting question is the next one: should your application — Node.js, Laravel, ASP.NET — handle every single request directly?

For a small site, it can. But the moment thousands of users arrive at once, your application is doing two jobs at the same time: running the actual application logic, and managing thousands of raw network connections. The transcript's answer to that overload is the reason this lesson exists: put a web server in front of the application. Requests go to the web server first, and it decides what to do with each one.

The decision rule is simple. A request for a static file — HTML, CSS, JavaScript, an image — is returned straight from disk, without waking the application at all. A request that needs processing is forwarded to the application. So a web server is software that receives client requests and returns the appropriate response, acting as the gatekeeper in front of your code.

NGINX (the transcript pronounces it "Engine-X") is a free, open-source web server — fast, lightweight, built to handle a very large number of connections on very little CPU and memory. And it is more than a web server: it can also work as a reverse proxy, load balancer, HTTP cache, and API gateway. Netflix, GitHub, Cisco, TikTok, LinkedIn and X all use it in their infrastructure. That versatility is exactly what the rest of this lab builds up, module by module.

Procedure — the two-path decision every request faces

  1. Browser sends an HTTP/HTTPS request to the server.
  2. The web server receives it before any application code runs.
  3. Static file (HTML, CSS, JS, image)? Return it directly from disk.
  4. Needs processing? Forward it to the application behind you.
  5. Application's response travels back through the same door.

Examples from the field

  • Obvious: A portfolio site serves its index.html and stylesheet straight from the web server — no application is ever involved.
  • Counter-intuitive: nginx was not created to replace Apache; it was created because modern apps needed performance, scalability and low resource use more than Apache-style flexibility.
  • Edge-case: On a tiny low-traffic blog, letting the application serve everything "works fine" — the web server earns its keep only when concurrency grows.
Visual analogy — toggle
❌ What people get wrongPeople assume the application must face the internet directly because "the browser talks to the server." In the transcript's architecture, the browser talks to the web server, and the application talks only to the web server.
Why this mattersEvery later module — proxy, balancing, caching, HTTPS, security headers — is this one idea stacked: nginx stands in front, and the app stands behind. Miss the front-door model and everything after it feels arbitrary.

Module 02

Installing nginx & Writing Your First Server Block

spec: transcript 00:17:05 → 00:32:04

The course installs nginx on a Linux VPS over SSH. Three commands in, and it's running: sudo apt update, then sudo apt install nginx, then verify with nginx -v. Because nginx runs as a Linux service, sudo systemctl status nginx should show it active (running) — and visiting your server's IP in a browser shows the default "Welcome to nginx" page. The config lives in /etc/nginx/ (running nginx -V prints the exact path), and the "Welcome" page itself sits in /var/www/html/.

The nginx.conf file is organized into contexts: global settings at the top (the worker user, worker_processes auto so nginx matches your CPU cores), an events block for connection handling, and the big http block where all web configuration lives. At the bottom of the http block, include lines load everything in conf.d and sites-enabled. You could define websites directly inside http, but the recommended practice is one file per site.

That per-site file is a server block: it defines which port to listen on, which domain to answer (server_name), and where files live (root plus an index). The transcript creates one in sites-available/first-site, then — because nginx only reads sites-enabled — creates a symbolic link between the two. Editing happens in sites-available; enabling happens by linking; disabling happens by removing the link — the file stays put either way.

Then the ritual that repeats in every single module of this course: check the config with sudo nginx -t, and apply it with sudo systemctl reload nginx. Note the word — reload, not restart: reload applies new configuration without dropping existing connections. That's the preferred move after every config change, and the course does it dozens of times.

Procedure — first static site on port 90

  1. sudo apt update && sudo apt install nginx · verify: nginx -v, systemctl status nginx.
  2. Create content: /var/www/first-site/index.html with one H1.
  3. Write the server block in /etc/nginx/sites-available/first-site.
  4. Enable it: sudo ln -s /etc/nginx/sites-available/first-site /etc/nginx/sites-enabled/
  5. sudo nginx -t → "syntax is ok / test is successful".
  6. sudo systemctl reload nginx → visit http://YOUR_IP:90.
server {
    listen 90;
    server_name localhost;      # your domain goes here later
    location / {                # rules for the root of the site
        root /var/www/first-site;
        index index.html;
    }
}

Examples from the field

  • Obvious: Serve a hand-written index.html from /var/www/first-site on port 90 — the transcript's exact exercise.
  • Counter-intuitive: The config file exists but nginx ignores it until it's linked into sites-enabled — creating the file alone changes nothing.
  • Edge-case: Miss one semicolon and nginx -t fails before anything breaks — the course trips on exactly this and fixes it in one line.

❌ What people get wrongTwo classics from the transcript: putting server blocks directly in nginx.conf instead of per-site files, and forgetting that sites-available alone does nothing — nginx loads sites-enabled.
Why this mattersThis is your goal's first real step: a static page served from your own VPS. The identical pattern — file in sites-available, symlink, test, reload — is how every site on that server gets added.
Quick check

Model answer: listen (port) → server_name (domain) → location / (scope) → root + index (files). L·S·L·R.

Module 03

The Reverse Proxy — One Door for the Whole Stack

spec: transcript 00:06:46 → 00:16:53 · 00:32:04 → 00:46:57

First, the distinction the transcript draws carefully. A proxy works on behalf of the client: it controls internet access and hides the client's identity. A reverse proxy sits on the server side: clients send every request to it, and it decides where each request goes. Behind nginx there might be a Node.js, Django or ASP.NET application — or several. The benefits: better security (backends are hidden) and routing each request to the right service.

The course's real stack makes this concrete: a React front end on port 3000, a Node.js/Express API on port 3001, a database, and Mongo Express on 8081 — all started with docker compose up --build -d. Each service exposed on its own port works for testing, but in production you can't ask users to remember port numbers or hit your backend directly. The fix: one entry point. A new config file /etc/nginx/sites-available/docker-demo listens on port 80 and uses three location blocks to sort traffic.

The routing keyword is proxy_pass. Requests to / go to the React app at http://localhost:3000; requests starting with /api/ go to http://localhost:3001; requests starting with /mongo/ go to http://localhost:8081. One door, three rooms behind it.

Two debugging episodes in the transcript are worth their weight. First, enabling the new block still showed the default page — the default site's symlink in sites-enabled had to be removed (sudo rm /etc/nginx/sites-enabled/default) and nginx reloaded. Second, /api/users failed until a trailing slash was added: without it, nginx forwards the entire original URI (localhost:3001/api/users), while the Node app expected localhost:3001/users. And Mongo Express needed its own accommodation — an environment variable (ME_CONFIG_SITE_BASEURL: /mongo/) telling it to generate its links under the sub-path. Reverse proxying isn't just forwarding; it's matching what each backend expects to receive.

Procedure — route three services through port 80

  1. Create /etc/nginx/sites-available/docker-demo with a server block, listen 80.
  2. location / → proxy_pass http://localhost:3000; (React).
  3. location /api/ → proxy_pass http://localhost:3001/; (Node API — trailing slash).
  4. location /mongo/ → proxy_pass http://localhost:8081/; (Mongo Express).
  5. Symlink into sites-enabled; remove the default link.
  6. sudo nginx -t → sudo systemctl reload nginx → test all three paths.
server {
    listen 80;
    server_name localhost;
    location /        { proxy_pass http://localhost:3000;  }   # React
    location /api/    { proxy_pass http://localhost:3001/; }   # Node API
    location /mongo/  { proxy_pass http://localhost:8081/; }   # Mongo Express
}

Examples from the field

  • Obvious: One domain serves the React app at / and the API at /api/ — users never see a port number.
  • Counter-intuitive: proxy_pass http://localhost:3001 (no slash) forwards /api/users as-is and breaks the route; the slash is the whole fix.
  • Edge-case: Mongo Express was never designed to live under a sub-path — it needs its ME_CONFIG_SITE_BASEURL variable to agree with the proxy.
Visual analogy — toggle
❌ What people get wrong"A proxy and a reverse proxy are the same thing." No — a proxy serves the client; a reverse proxy serves the server. The second classic: blaming nginx when /api/users 404s, when the real culprit is a missing trailing slash on proxy_pass.
Why this mattersThis is the architecture of your goal: a full-stack app with one public address. Almost everything you'll deploy as a working developer — front end, API, admin tools — sits behind exactly this pattern.
Quick check

Your React app runs in one container and your API in another. What does the reverse proxy give you?

Write the three location paths and their proxy_pass ports from memory.
Model answer: / → 3000 (React) · /api/ → 3001 (Node API) · /mongo/ → 8081 (Mongo Express).

Module 04

Load Balancing — Three Backends, One Upstream

spec: transcript 01:16:16 → 01:31:47

Popularity creates two problems the transcript states plainly: a single server has limited CPU and memory, and if that one backend dies, the whole app is unavailable. The fix is running multiple instances of the backend and letting a load balancer distribute incoming requests between them. Instead of making one server bigger (vertical scaling), you add more servers (horizontal scaling) — think of a Black Friday traffic spike that no single machine could absorb.

Three VPS servers would be the production shape, but for the tutorial the course simulates it with Docker: three containers from the same backend image — api, api2, api3 — on one machine. A small testing aid makes distribution visible: each container gets an API_NAME environment variable that the Node app echoes in every response, so you can see exactly who handled what. Before the nginx change, though, nothing improves — nginx still sends everything to one API.

The nginx mechanism is an upstream group, declared before the server blocks: an upstream backend_servers block listing each server as server api:3001;, server api2:3001;, server api3:3001;. The container service names work as hostnames because all containers share one Docker network — nginx finds them by name, no IPs needed. Then the API location changes from proxy_pass http://api:3001 to proxy_pass http://backend_servers. The default strategy is round robin — first request to api, second to api2, third to api3, then repeat.

The payoff is availability: the course stops container api2 with docker stop — and the app keeps working, requests flowing to api and api3, until api2 is started again and rejoins the rotation. The honest limitation is stated too: all three containers share one VPS, so if the VPS itself goes down, everything goes down. One honest caveat — a general proxy_cache on everything would break /api/users, which must always be fresh; caching choices come in Module 05.

Beyond round robin, three controls tune the distribution. least_conn considers how busy each server is — useful when some requests take much longer than others. weight gives stronger machines a larger share (weight=3 gets roughly three times the traffic). backup keeps a server idle until the others fail. The course doesn't demo these live — it encourages you to change the config, rebuild, and watch the behavior shift.

Procedure — from one API to a balanced trio

  1. Clone the API service twice in docker-compose: api2, api3 (same image, same port).
  2. Add API_NAME env var to each so responses identify their server.
  3. Declare the group: upstream backend_servers { server api:3001; server api2:3001; server api3:3001; }
  4. Point the API location at the group: proxy_pass http://backend_servers;
  5. Test: docker exec … nginx -t, rebuild, refresh — responses rotate api → api2 → api3.
  6. Failure drill: docker stop api2 → app still serves; docker start → rotation heals.
upstream backend_servers {
    server api:3001;      # round robin by default
    server api2:3001;     # least_conn;  → fewest active connections
    server api3:3001;     # weight=3;    → bigger share   backup; → idle reserve
}
server {
    ...
    location /api/ { proxy_pass http://backend_servers; }
}

Examples from the field

  • Obvious: Three identical API containers rotating api → api2 → api3 per request, visible in the responses.
  • Counter-intuitive: Adding a third backend container changes nothing on its own — nginx keeps using one until an upstream points at all three.
  • Edge-case: A stopped api2 doesn't error or queue requests; traffic silently flows to the survivors until it returns.
Visual analogy — toggle
❌ What people get wrong"One backend is enough if it's powerful." The transcript's second problem isn't capacity — it's availability: with one instance, any crash takes the app offline. Also: container names like api2 work in upstream because of the shared Docker network — they're not magic hostnames.
Why this mattersAvailability is the property users actually notice: they don't see which server answered, they see whether the app answered. For your full-stack app, this is the difference between a crash being an outage and a non-event. (Mnemonic: R · L · W · B — Robin, Least, Weight, Backup.)
Quick check

Three identical API containers sit behind an upstream group. One is stopped for maintenance. What happens?

✍ Recall — write before expanding
Write an upstream group for your three API containers from memory.
Model answer: upstream backend_servers { server api:3001; server api2:3001; server api3:3001; } then proxy_pass http://backend_servers; in the location.

Module 05

HTTP Caching — Serve It Once, Reuse It Many

spec: transcript 01:31:53 → 01:45:32

Without caching, every identical request walks the whole road: nginx → backend application → database query → response back through all of it. If a thousand users ask for the same product page, the application repeats the same work a thousand times. Caching means nginx stores the response the first time and serves it directly to everyone after. Fewer requests reach the backend and database — faster responses, lower load.

The demo makes the benefit visceral: a process-data API endpoint that deliberately takes 7 seconds to respond. Click it once — seven seconds. Click it again — another seven. After enabling the proxy cache, the first request still takes seven seconds; the second returns almost instantly, because nginx hands back its stored copy without asking the backend at all.

Configuration lives in three lines (mnemonic: define the zone, use the zone, time the zone). First, an proxy_cache_path at the top of the config: proxy_cache_path /data/cache/nginx keys_zone=api_cache:10m max_size=1g inactive=30m use_temp_path=off; — the path where responses are stored, a 10 MB shared-memory zone named api_cache for cache metadata, a 1 GB disk cap, a 30-minute eviction rule for untouched items, and temp files written directly into the cache directory. Second, inside the API location: proxy_cache api_cache; turns it on. Third: proxy_cache_valid 200 10m; — a successful (200) response stays valid for ten minutes. Because nginx runs in a container, a Docker volume maps the cache directory out so the cache survives container recreation.

Then the transcript shows the trap that makes caching a judgment call. A user named Sara is created; the page refreshes — and she's missing, because the user list is being served from the cache while the database has already changed. The lesson: don't cache every endpoint. Frequently-changing data should bypass the cache. The fix shown: split /api into two locations — an exact-match location = /api/process-data { proxy_cache api_cache; … } that keeps caching, and a general location /api { … } with no cache directive at all. After rebuilding: Sara appears immediately (list uncached), while process-data is still instant (cached).

Procedure — cache the slow endpoint only

  1. Top of config: proxy_cache_path /data/cache/nginx keys_zone=api_cache:10m max_size=1g inactive=30m use_temp_path=off;
  2. Exact-match location for the slow endpoint: location = /api/process-data → proxy_cache api_cache; + proxy_cache_valid 200 10m;
  3. General API location without any cache directive, so /api/users stays fresh.
  4. docker-compose: mount a volume for the cache directory so it survives rebuilds.
  5. Test: first click ~7 s, second click instant; create a user → appears immediately.
proxy_cache_path /data/cache/nginx keys_zone=api_cache:10m
                 max_size=1g inactive=30m use_temp_path=off;

location = /api/process-data {     # cache ONLY this endpoint
    proxy_pass http://backend_servers;
    proxy_cache api_cache;
    proxy_cache_valid 200 10m;
}
location /api {                    # everything else: always fresh
    proxy_pass http://backend_servers;
}

Examples from the field

  • Obvious: The 7-second process-data call becomes instant on every repeat within 10 minutes.
  • Counter-intuitive: Success can hide a bug — Sara is saved in the database yet vanishes from a cached user list.
  • Edge-case: location = /api/process-data is an exact match: it caches that one endpoint while the broader /api stays uncached.
Visual analogy — toggle
❌ What people get wrong"Turn caching on for the whole API." The Sara episode is the counterexample: cached lists show stale data. Cache responses that can be safely reused; let changing data bypass the cache.
Why this mattersCaching is the cheapest performance you'll ever buy: a few config lines turn a 7-second endpoint into a millisecond one and take load off both app and database — with a staleness trade-off you now know how to control.
Quick check

Your /api/users list is cached for 10 minutes. A new user registers. What do visitors see?

Model answer: proxy_cache_path (top of config — the zone), proxy_cache (location — use the zone), proxy_cache_valid (location — time the zone).

Module 06

Gzip Compression — Fewer Bytes, Same Data

spec: transcript 01:45:38 → 01:56:18

A browser requesting a page or an API response receives HTML, CSS, JavaScript — or a big JSON payload. The transcript's demo has a "Big Data" button returning a response over 9,000 KB that takes several seconds to arrive. The data itself is fine; the transfer is the problem. HTTP compression shrinks responses before they cross the network, and nginx can do the compressing.

The negotiation is already built into HTTP: the browser sends an Accept-Encoding header listing formats it supports (the demo shows gzip and br among others), and the server answers with a Content-Encoding header naming the format it used. Before configuration, the demo response has no Content-Encoding — uncompressed. From the application's point of view nothing changes at any point: nginx compresses, the browser decompresses automatically, and the app keeps working with the same data.

Three gzip directives matter. gzip on; enables compression. gzip_min_length 1000; skips responses under about a kilobyte — compressing tiny responses costs more than it saves. gzip_types text/css application/json application/javascript application/xml image/svg+xml; lists which content types are fair game (text formats; you don't re-compress already-compressed images). After enabling and rebuilding, the 9,000+ KB response drops to about 1,600 KB — with Content-Encoding: gzip confirming it in dev tools, and not one line of application code changed.

One more dial: gzip_comp_level, from 1 to 9. Level 1 (the default) favors speed and low CPU; level 9 squeezes hardest — the demo got down to ~1,000 KB — but spends more CPU and time on every response. Level 9 doesn't necessarily mean a faster experience; production usually picks a moderate balance. The course settles on level 5.

Procedure — compress in three lines

  1. gzip on; — enable compression in nginx.
  2. gzip_min_length 1000; — don't bother under ~1 KB.
  3. gzip_types …; — CSS, JSON, JavaScript, XML, SVG.
  4. Optional: gzip_comp_level 5; — a production-friendly balance.
  5. Verify in dev tools: Content-Encoding: gzip, and watch the size drop.
gzip on;
gzip_min_length 1000;
gzip_types text/css application/json application/javascript
           application/xml image/svg+xml;
gzip_comp_level 5;   # 1 = fastest, 9 = smallest; 5 = balanced

Examples from the field

  • Obvious: A 10 MB JSON response compressed to ~1.6 MB transfers in a fraction of the time.
  • Counter-intuitive: Pushing to level 9 made the response smaller (~1,000 KB) — but costs CPU on every request, so production often prefers a middle level.
  • Edge-case: Responses under 1,000 bytes are left alone by gzip_min_length — compressing them would add overhead without meaningful savings.
Visual analogy — toggle
❌ What people get wrong"Highest compression is fastest for users." Level 9 shrinks most but burns CPU per response; the transcript deliberately picks level 5 as the working balance. And compression belongs to text formats — not to images that are already compressed.
Why this mattersThis is the rare optimization where three lines of config deliver a ~6× reduction with zero application changes — bandwidth saved, pages faster, users happier.
Quick check

A 10 MB JSON response becomes 1.6 MB with gzip. Who unpacks it?

Module 07

Hardening — Headers, Rate Limits, and a Locked Front Door

spec: transcript 01:56:23 → 02:07:49

Security at the nginx layer follows the course's four-move pattern: Hide, Guard, Throttle, Refuse. First, hide: response headers can leak your exact nginx version in the Server header. Knowing the version doesn't mean you're in danger — but there's no reason to share it. One line, server_tokens off;, keeps the header while dropping the version.

Second, guard with security headers — nginx sitting in front of the app makes it the perfect place to add them (they complement, not replace, a firewall). X-Content-Type-Options: nosniff stops the browser from guessing file types — a .txt that actually contains JavaScript won't get executed. X-Frame-Options: DENY (or SAMEORIGIN if you embed your own pages) blocks your site being framed elsewhere — the anti-clickjacking move. Referrer-Policy: strict-origin-when-cross-origin limits how much of the previous page's URL leaks to other sites. Permissions-Policy: geolocation=(), microphone=(), camera=() — empty parentheses mean no origin may use those features; disable what a blog doesn't need, keep what your app genuinely uses. And Content-Security-Policy: default-src 'self' allows only same-origin resources — where the transcript hits a live lesson: the demo loaded Bootstrap from a CDN, the page broke, and the header had to be removed. Build CSP around what your app actually loads.

Third, throttle. A rate limit zone is defined in the http context — limit_req_zone $binary_remote_addr zone=api_limit:10m rate=5r/s; — tracking requests by client IP in 10 MB of memory at five requests per second. Applying it in the API location with limit_req zone=api_limit; means each IP gets five requests per second; beyond that, nginx blocks the excess. This curbs abuse and simple HTTP floods while shedding needless load.

Fourth, refuse direct IP access. The demo site was reachable via the raw server IP; that's not a disaster, but nginx shouldn't serve your main site to unknown hostnames. A default server block — listen 80 default_server; with server_name _; (the underscore matches nothing real) and return 444; — closes the connection without any response. And a gotcha the transcript demonstrates: the IP was still reachable over HTTPS, because a second default block on listen 443 ssl was needed too. Remember the boundary: this is nginx-level restriction — a firewall is still the tool for fully sealing the server.

Procedure — the four moves

  1. Hide: server_tokens off;
  2. Guard: add the five security headers with add_header … always;
  3. Throttle: define limit_req_zone in http context, apply limit_req in the API location.
  4. Refuse: default_server blocks on 80 and 443 returning 444.
  5. Rebuild, reload, and test each one (headers in dev tools; 6th request in a second → blocked; IP → connection closed).
server_tokens off;

add_header X-Content-Type-Options nosniff always;
add_header X-Frame-Options DENY always;                # or SAMEORIGIN
add_header Referrer-Policy strict-origin-when-cross-origin always;
add_header Permissions-Policy "geolocation=(), microphone=(), camera=()" always;
# Content-Security-Policy default-src 'self'  — only if you allow no external resources!

limit_req_zone $binary_remote_addr zone=api_limit:10m rate=5r/s;  # http context

server {                                    # catch-all: refuse unknown hosts
    listen 80 default_server;
    server_name _;
    return 444;                             # close connection, no response
}

Examples from the field

  • Obvious: After server_tokens off; the Server header reads just "nginx" — no version.
  • Counter-intuitive: The well-meant CSP header broke the demo site — its CDN-loaded Bootstrap was now forbidden, so the header came back out.
  • Edge-case: Blocking the IP on port 80 still left HTTPS access working — the same refusal needed a second block on 443.
Visual analogy — toggle
❌ What people get wrong"Adding security headers makes the site secure." The transcript is explicit: they add a layer — they don't replace a firewall. And CSP set to 'self' will break any page that loads fonts, CSS or scripts from elsewhere unless those origins are allowed.
Why this mattersYour full-stack app will be scanned by bots within hours of going live. These four moves cost a dozen config lines and remove the loudest low-hanging fruit — version disclosure, clickjacking, flooding, and IP-level prowling.

Module 08

HTTPS with Let's Encrypt — Two Environments, One Client

spec: transcript 00:15:18 → 00:16:53 · 00:59:44 → 01:16:12

Users send usernames, passwords, payment details. Unencrypted, others may see or alter that data. HTTPS uses SSL/TLS to turn the traffic into a protected format only client and server can read. When nginx is the reverse proxy, it should be the one handling HTTPS — managing certificates once, centrally, instead of on every app server. The client makes a secure connection to nginx, nginx handles the SSL/TLS work, then forwards the request onward. That pattern is called SSL termination — easier certificate management, centralized security config, less work for app servers.

Before any certificate: DNS. The course creates two A records — for sarvinstylecoding.com and www.sarvinstylecoding.com — pointing at the VPS IP through Cloudflare's nameservers, then updates server_name to the real domain. The site is now reachable by name; the browser still warns it's "not secure."

Certbot, the official Let's Encrypt client, then does the heavy lifting. Approach one — nginx installed directly on the VPS: install certbot python3-certbot-nginx, run sudo certbot --nginx, answer the prompts (email for expiry notices, accept terms, pick your domains — space- or comma-separated, choose the redirect option), and certbot detects your nginx config, issues the certificate, and rewrites the config itself. Opening the file afterward shows what it added: a second server block listening on 443 ssl, the ssl_certificate and ssl_certificate_key paths pointing into /etc/letsencrypt/, recommended SSL settings via options-ssl-nginx.conf, and an HTTP→HTTPS redirect so everyone arrives encrypted. Test with curl -I https://…, then watch the padlock appear.

Approach two — nginx in a Docker container: the host's certbot can't reach inside it, so the certificates must come to nginx. The compose service exposes 443:443, mounts /etc/letsencrypt read-only (ro) into the container, and the project's own config gains two server blocks: the port-80 block reduced to a redirect — return 301 https://$host$request_uri; where $host is the domain and $request_uri the original path — and the 443 block carrying the certificate paths and all the proxying. After docker compose down and up --build -d, verify config inside the container (docker exec … nginx -t) and confirm HTTP now redirects to HTTPS. One operational nuance the transcript demonstrates twice: when switching between the two setups, stop and disable the host nginx service first — port 80 can only have one owner.

Procedure — certbot on a VPS (approach one)

  1. DNS first: A records for your domain and www → server IP.
  2. sudo apt install certbot python3-certbot-nginx -y
  3. sudo certbot --nginx → email → terms → domains → redirect.
  4. Inspect the rewritten config: 443 ssl block + certificate paths + redirect.
  5. sudo nginx -t → reload → curl -I https://yourdomain → padlock.
# approach two: nginx inside Docker Compose
nginx:
  image: nginx:1.27-alpine
  ports:
    - "80:80"
    - "443:443"
  volumes:
    - ./nginx/default.conf:/etc/nginx/conf.d/default.conf
    - /etc/letsencrypt:/etc/letsencrypt:ro   # certs, read-only

# in default.conf:
server {
    listen 80;
    server_name yourdomain.com www.yourdomain.com;
    return 301 https://$host$request_uri;    # $host = domain, $request_uri = path
}
server {
    listen 443 ssl;
    server_name yourdomain.com www.yourdomain.com;
    ssl_certificate     /etc/letsencrypt/live/yourdomain.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/yourdomain.com/privkey.pem;
    location /       { proxy_pass http://web:3000;  }
    location /api/   { proxy_pass http://backend_servers; }
    location /mongo/ { proxy_pass http://express:8081; }
}

  • Obvious: One certbot run converts the whole site to HTTPS and sets up the redirect automatically.
  • Counter-intuitive: Certificates issued on the host are useless to a containerized nginx until the /etc/letsencrypt volume is mounted in.
  • Edge-case: Even with the 80 default_server refusing IP access, HTTPS-IP access persisted until the same refusal was added on 443.

Module 09

The Working Rhythm — Test, Reload, Verify

spec: transcript 00:31:50 → 00:32:04 · throughout

Watch the course closely and a rhythm emerges that outlasts any single directive. Edit the config. Then — always — sudo nginx -t (inside a container: docker exec <container> nginx -t): "syntax is ok / test is successful." Only then systemctl reload nginx — or docker compose up --build -d when the change includes image or compose edits. Then verify in the browser or with curl -I.

The reload choice is deliberate: reload applies new configuration without stopping the service, so existing connections are never interrupted — that's why it's the preferred move after every config change. A full restart is for service-level operations like stopping and disabling nginx when a container takes over port 80. The transcript saves this test-first habit from embarrassment repeatedly: the forgotten semicolon, the 404 until the trailing slash, the CSP-broken page, the Sara cache — every one was caught by the same short loop.

And the deeper pattern underneath: configuration belongs in version control. Moving nginx config into the project (an nginx/default.conf file mounted into the container) was called out as "a very important improvement" — nginx becomes just another service in compose, and every fix ships with the code. Combined with the stack — React, Node.js, database, Mongo Express, nginx — you have the production shape this course promised from minute one: a VPS or Docker setup, one entry point, and a calm verification loop.

That's the whole arc, assembled: the front door (M1–M2), the router (M3), the traffic cop (M4), the memory (M5), the packer (M6), the guard (M7), the vault (M8) — and this rhythm (M9) keeping all of it honest.

Procedure — the loop, every time

  1. Edit config (ideally in the project, version-controlled).
  2. nginx -t — or docker exec <container> nginx -t in Docker.
  3. Apply: systemctl reload nginx, or docker compose up --build -d.
  4. Verify in browser / curl -I — the exact path and header you changed.

Examples from the field

  • Obvious: Every course edit — proxy, cache, gzip, headers — is followed by nginx -t then reload, dozens of times.
  • Counter-intuitive: A missed semicolon doesn't corrupt a running server — nginx -t catches it before reload, which is exactly why the test comes first.
  • Edge-case: Switching nginx from host to container needs systemctl stop and disable — otherwise the old service grabs port 80 again on reboot.

FAQ — from the transcript's own confusion points

Do I still need nginx if my app already listens on a port?

Yes — that's the course's starting problem: React on 3000, API on 3001, Mongo Express on 8081 means users must remember port numbers and backends are exposed directly. nginx gives you one entry point that routes by path, hides the backends, and later adds caching, compression, security, and HTTPS in the same place.

Why did /api/users fail until I added a trailing slash?

Without the trailing slash, proxy_pass http://localhost:3001 forwards the entire original URI — localhost:3001/api/users — while the Node app expected localhost:3001/users. With the slash, nginx strips the matched prefix. One character, whole route.

Why did my site break after adding Content-Security-Policy?

default-src 'self' allows only same-origin resources — and the demo loaded Bootstrap CSS from a CDN, so the browser refused it. Either allow the external origins your app actually uses, or drop the header until you've mapped your resources.

My cached endpoint shows stale data — how do I fix it?

That's the Sara episode: the user list was cached while the database changed. Keep caching for safely-reusable endpoints (exact-match location for /api/process-data) and let frequently-changing paths (/api/users) bypass the cache in a separate location.

Reload or restart after a config change?

Reload. It applies the new configuration without stopping the service, so existing connections are never interrupted. Reserve stop/start/disable for service-level changes — like freeing port 80 when a Dockerized nginx takes over.
