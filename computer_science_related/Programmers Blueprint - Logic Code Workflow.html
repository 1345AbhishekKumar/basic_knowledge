Experiment 01 · Conceptual Foundation

Think first: computational thinking and algorithms

Objective — Solve the problem on paper before touching the keyboard: decompose it, name the patterns, hide the irrelevant detail, and write steps a literal machine could follow.

The journey starts with a mindset, not a keyboard. That mindset has a name: computational thinking, described as a pillar of computer science education and defined as the human ability to frame problems so they can be solved by computational means. Notice it is called a universal methodology, useful with or without code. Its moves are specific: break a large challenge into smaller parts (decomposition), notice what repeats (pattern recognition), throw away what does not matter (abstraction), and lay out steps (algorithm design). This mirrors the scientific method you already know — identify the problem, research what is known, hypothesize a solution, plan tests, evaluate — and Harvard’s CS50 is one well-known course built exactly this way, teaching thinking over language trivia. If you take one sentence from this module, take this: languages change, but the habit of stating a problem exactly is the durable skill.

Out of that habit comes the algorithm: a finite sequence of well-defined instructions that takes an input, produces the wanted output, and terminates. Three words there carry weight. Finite means it ends — a procedure that never stops is not a solution. Well-defined means each step is unambiguous to its executor. Terminates means you can point at the end state and check you arrived. The word itself carries history, tracing back to the ninth-century Persian mathematician al-Khwārizmī, and it comes with a working rule beginners should tape to the monitor: every instruction must earn its place by moving toward the goal, and the process of writing steps down, testing them, and refining them is itself the creative part of programming. So before any syntax, practice this bench move: given any chore (sorting books, planning a trip, checking IDs at a door), write its goal, its inputs, its end state, and its steps — then strike any step that does not serve the goal.

Procedure

  1. Write the goal in one sentence and name the end state you can check.
  2. List the inputs you are given and the output you must produce.
  3. Decompose: split the job into 3–5 sub-tasks small enough to describe in a line each.
  4. Abstract: cross out every detail that does not change the outcome.
  5. Draft steps, run them by hand on a tiny example, refine, and document each choice.

Bench figure 1: frame → split → hide → step → check the end.

ObviousDoor check: goal “admit 18+ only”; input age; output admit/deny; steps: read age → compare → decide. End state is checkable.
Counter-intuitiveThinking counts without code. You can decompose and abstract a recipe or a commute — the methodology transfers.
Edge caseA “procedure” with no end state (keep stirring forever, no stop test) fails the algorithm definition no matter how precise each step sounds.
# Python bench log: an algorithm written down BEFORE code
# Goal: admit ages 18+ . Input: age . Output: admit/deny . End: decision printed
# Steps: 1) read age  2) compare age >= 18  3) print result
age = 20
print("admit" if age >= 18 else "deny")  # admit
# Every line above maps to a step you wrote first. No step, no line.
Visual analogy — A lab protocol written before touching beakers: goal, reagents (inputs), end state (precipitate, reading), then steps. — No protocol, no experiment; no algorithm, no program.
✕ What people get wrong: “Learning to program means memorizing a language.” The opposite holds: grammar without problem-framing produces fluent nonsense.
Why this matters: Decomposition and abstraction are what let you face a 10,000-line codebase later without panic — same moves, bigger bench.

Experiment 02 · Control Structures

The universal grammar: sequence, selection, iteration

Objective — Build any logic from three constructs only, and prove each one terminates or branches exactly as drawn.

Every algorithm is assembled from three control structures, and mastering them is mastering the universal grammar present in virtually every mainstream language. First, sequence: statements run top to bottom in order, and order is load-bearing. The swap example makes the point physically — exchanging two variables takes three assignments through a temporary holder, and any reordering loses a value. Second, selection (branching): the program tests a condition and takes one path, typically spelled if / else if / else, with compound tests built from AND, OR, NOT and nested conditionals for more than two cases. The age-gate (admit above 18?) is the canonical demo. Third, iteration (looping): repeat a block instead of copying it — count-controlled for loops for a known number of repetitions, condition-controlled while loops for “until something changes,” with the classic failure mode being the infinite loop whose exit never arrives.

Two ideas elevate this from syntax lesson to worldview. One: these three plus unbounded recursion make a system Turing complete — able in principle to compute anything computable — which is why nearly all modern languages qualify and why your effort here transfers everywhere. Two: beginners should learn the constructs, not the language; CS50-style courses drill efficient problem-solving precisely because grammar outlives tools. Your bench discipline for this experiment: for every loop, write its start, its end test, and its step before running; for every branch, list which inputs take which path; for every sequence, ask what breaks if two lines trade places. Do that on paper three times and you will read most short programs at sight.

Procedure

  1. Sequence check: number your lines; swap two and predict what breaks (try the variable swap).
  2. Selection map: write each condition, then one example input per branch including nested cases.
  3. Iteration contract: state start, continuation test, and step; prove the test must eventually fail.
  4. Compound test: combine two conditions with AND/OR/NOT and enumerate the truth table.
  5. Transfer test: restate the same logic in a second language’s spelling without changing structure.

Animation: the temp holder carries the value across. Static fallback: t=a (save 3), a=b (7), b=t (3) — skip temp and 3 is lost.

Step 0: i=0, test 0<5 true → body runs
ObviousAge gate with AND: age >= 18 and has_ticket admits; either false denies. Two conditions, one decision.
Counter-intuitiveOrder is logic: a = b; b = a without temp leaves both holding one value. Correctness lives in sequence, not just statements.
Edge casewhile True with no break and no changing test is an infinite loop — the termination contract unsigned.
# Python - the whole grammar, runnable:
# SEQUENCE: order matters (classic swap demo)
a, b = 3, 7
t = a      # park 3 in temp
a = b      # a becomes 7
b = t      # b becomes parked 3
print(a, b)  # 7 3  (try skipping t and watch 3 vanish)

# SELECTION: branches, compounds, nesting
age = 20
if age >= 18:
    print("admit")
else:
    print("deny")
has_ticket = True
if age >= 18 and has_ticket:   # AND / OR / NOT
    print("enter")
if not has_ticket:
    print("no entry without ticket")

# ITERATION: count-controlled vs condition-controlled
for i in range(3):    # exactly 3 times
    print(i)          # 0 1 2
n = 3
while n > 0:          # while the condition holds
    print(n)
    n -= 1            # the step that guarantees an exit
Visual analogy — Sheet music: sequence is the bar order, selection is the repeat-with-alternate-endings sign, iteration is the “play 4×” marking. Same notes, different performance.
✕ What people get wrong: “A loop is just shorthand, so the exit barely matters.” The exit is the loop: an unwatched test is how infinite loops are born.
Why this matters: Sequence-selection-iteration appear in every language you will ever meet; time spent here pays rent in all of them.

Experiment 03 · Data, Syntax, Control Flow

Vocabulary and grammar: types, variables, syntax

Objective — Name every value’s type, store it in a well-named variable, and write lines the toolchain accepts on the first pass.

With logic in hand you need materials: data. Types are classifications that decide what a variable may hold and what operations make sense. The primitives are stable across languages — integers for whole numbers (with sized variants like byte, short, long fixing memory and range), floats and doubles approximating decimals for science and money, Booleans as the true/false atoms that power every condition and loop test, and chars and strings for single symbols and text. Variables are simply named memory slots holding such values; user_age as an int is the standard example here, and meaningful names are prescribed as readability practice, not decoration. The bench habit: before manipulating anything, say its type aloud — “this is an int, so division behaves like…” — because half of beginner bugs are type confusions wearing syntax costumes.

Then the grammar: syntax, the rules a compiler or interpreter enforces before running anything, with violations reported as syntax errors up front. Languages differ in dialect — C#’s semicolon terminators versus languages that end statements with line breaks; block delimiters as braces in C/Java/JavaScript versus begin/end keywords in Pascal; Python’s significant indentation where whitespace is law, not style; and case-sensitivity where myVar and myvar are strangers. Control flow then reappears as sentence structure: sequence by default, selection branching with if/else, iteration repeating with for/while — and justifying why a given construct fits, with its trade-offs stated, is a genuinely professional skill. Your procedure below turns that into routine: declare, name well, respect the local punctuation, and choose each construct on the record.

Procedure

  1. Classify: label each value int / float / bool / char / string before use.
  2. Contain: store it in a meaningfully named variable (user_age, not x2).
  3. Punctuate per dialect: semicolons, braces, or indentation — exactly one, consistently.
  4. Direct flow: pick sequence, selection, or iteration and note why the others fit worse.
  5. Compile mentally: reread for the four syntax traps (terminator, delimiter, indent, case).

Bench figure 3: classify → contain → punctuate → direct.

Obvioususer_age = 30 (int): arithmetic and comparisons behave as whole-number math.
Counter-intuitiveIn Python, indentation is syntax — a misaligned block is not ugly, it is illegal.
Edge casemyVar vs myvar in a case-sensitive language: two different boxes, one silent misread away from a bug.

Experiment 04 · Modularity and Organization

Build to last: modules, cohesion, clean benches

Objective — Split any program over ~50 lines into single-purpose modules behind narrow interfaces, and file them where strangers can find them.

Small scripts forgive mess; large ones collect on it. The answer, dating to the 1960s, is modular programming: separate functionality into independent, interchangeable modules, each a self-contained unit doing one task, combined into the whole. The mechanism is encapsulation — internals hidden, a well-defined interface exposed as a contract — so a developer uses a module through its promises without studying its machinery. Five payoffs are enumerated and worth memorizing: readability (small focused units), testability (isolate and probe one unit), reusability (proven modules travel between projects), maintenance (fixes stay local), and collaboration (teams meet at interfaces, not in each other’s code). If a module cannot be explained in one sentence, it is probably two modules wearing a coat.

Two meters judge the split. Cohesion — how related a module’s insides are — should be high: one purpose, ideally functional cohesion (a single discrete function), up from coincidental, logical, temporal, procedural, communicational, and sequential groupings. Coupling — how much modules lean on each other — should be loose: from worst (content: reaching into another’s internals; common: shared globals; control: flag puppeteering; stamp: hauling whole structures for one field) toward the ideal data coupling (minimal, immutable arguments). Then the bench itself: a Python project with main.py entry, /modules, /data, /tests, a .gitignore keeping junk out of version control, snake_case filenames (user_authentication.py, never hyphenated my-module.py which Python cannot import), and three named sins — one giant file, circular imports, and code-data soup. Organization is presented bluntly as the amateur-to-professional divide, so treat filing as part of the program, not after it.

Procedure

  1. Slice: carve the task so each module earns a one-sentence purpose (functional cohesion).
  2. Contract: write each interface first — inputs in, promises out, nothing else visible.
  3. Decouple: replace shared globals and control flags with minimal data arguments.
  4. File: main.py + /modules + /data + /tests + .gitignore; snake_case everywhere.
  5. Inspect: hunt the three sins (monolith, cycles, soup) and refactor one before committing.

Bench figure 4: one purpose per box, thin contracts, filed benches.

ObviousAuth module exposes login(user, pw); billing never sees password hashing — contract honored, test written against the interface.
Counter-intuitivePassing a whole record when one field suffices (stamp coupling) feels generous but welds modules together at the extra fields.
Edge caseTwo modules importing each other (cycle) can freeze or crash at load — the layout must be a one-way street.
# Python - modularity you can run: two files, one contract
# File: modules/user_authentication.py
def login(user, password):
    """Contract: (str, str) -> bool. One purpose: verify credentials."""
    stored = {"ada": "lovelace42"}
    return stored.get(user) == password

# File: main.py
# from modules.user_authentication import login
# print(login("ada", "lovelace42"))  # True
# print(login("ada", "wrong"))       # False
# Try it inline here (same contract, single file demo):
stored = {"ada": "lovelace42"}
def login(user, password):
    return stored.get(user) == password
print(login("ada", "lovelace42"), login("ada", "wrong"))  # True False
Visual analogy — A lab of single-purpose instruments with labeled ports: centrifuge, spectrometer, incubator. You read the port labels, never rewire the insides.
✕ What people get wrong: “Splitting files is bureaucracy for big teams.” Even solo scripts gain isolated tests and local fixes — the readability and maintenance wins start at file two.
Why this matters: High cohesion + loose coupling is the exam answer behind every “clean codebase” compliment you will ever receive.

Experiment 05 · Debugging and Errors

Expect bugs: reproduce, read, isolate, fix

Objective — Turn any failure into a four-move routine, pick the right lens for its error type, and shrink every fix with early testing.

Bugs are not verdicts; they are inventory. Perfect first attempts are vanishingly rare — and beginner struggle has a known cause in cognitive load theory: too much state in working memory at once. The prescribed antidote is routine. First, reproduce the bug under controlled conditions; an unreliable failure cannot be diagnosed. Second, read the error message like an instrument: modern toolchains name the line and the complaint (missing file, typo, wrong type), and stack traces walk the call history backward to the source — with the pragmatic tip of searching the trace’s last line, often landing on someone else’s solved Stack Overflow twin. Isolation comes next with four named tools: print debugging (liberal prints revealing values and reach, including surprise nulls), commenting out (disable halves binary-search-style until the fault is cornered), a real debugger (breakpoints, variable inspection, line-by-line stepping — deeper than prints), and rubber-duck debugging (explain aloud until hidden assumptions confess).

Then classify, because type dictates tactics. Syntax errors break grammar (misspelled keyword, missing parenthesis, wrong operator) and are caught before running, with the toolchain pointing at the scene. Logic errors run fine and answer wrong — an off-by-one loop, a flipped comparator — betrayed only by output, hunted with prints and hand-tracing; the unintentional infinite loop is their classic smoke. Prevention closes the loop: Debug As I Go (test each fragment immediately, run often after small edits so failures stay single and shallow) and the 20–30-minute rule (stuck that long? stand up, reset, return with fresh eyes). Debugging, framed this way, stops being punishment and becomes a core analytical skill that separates novices from practitioners.

Procedure

  1. Reproduce: script the exact inputs that trigger it, twice in a row.
  2. Read: line number, message, full stack trace — search the last line if cryptic.
  3. Isolate: prints → halve by commenting → breakpoint stepping → duck explanation.
  4. Classify: syntax (fix spelling/grammar) vs logic (fix reasoning, re-trace by hand).
  5. Prevent: DAIG after every fragment; break at 20–30 stuck minutes.

Animation: the suspect range halves each run. Static fallback: 64 → 32 → 16 → fault cornered in ~6 runs.

ObviousTypo’d keyword halts before running with a line number — fix spelling, rerun. That’s syntax.
Counter-intuitiveExplaining code to a duck works: speech forces each assumption into the open where wrong ones crack.
Edge caseLoop running once too few with zero messages — logic error; only output-vs-expectation reveals it.
# Python - the debug bench, runnable:
# 1) PRINT debugging: watch values evolve
total = 0

    total += n
    print("DEBUG n =", n, "total =", total)  # trace the accumulation
print("sum:", total)  # 12

# 2) SYNTAX vs LOGIC: meet both, on purpose
# print("hi"     # <- syntax error: uncomment to see the toolchain point at it

avg = sum(scores) / len(scores)
print(avg)  # 84.33... if you expected 84, check rounding logic, not spelling

# 3) DAIG: test the fragment NOW, not at 500 lines
def is_even(n):
    return n % 2 == 0
print(is_even(4), is_even(7))  # True False - proven before reuse

Experiment 06 · Tools and Workflow

The workbench: editors, terminal, Git, routine

Objective — Assemble a working bench (editor, terminal, repo) and run the six-step loop on every task, however small.

Code does not happen on a blank screen; it happens on a bench. The bench has three permanent fixtures. First, the writing surface: a full IDE (editor + compiler/interpreter + build tools + debugger in one GUI — IntelliJ IDEA, PyCharm) with completion, live error flags, refactoring, and visual debugging that lowers cognitive load, versus lighter source editors, with VS Code recommended as the beginner sweet spot (fast, free, extensible into IDE-like powers) and Notepad++, Vim, Emacs acknowledged for terminal-adjacent work. Choice is framed as preference-plus-project, but the default advice is explicit: start with VS Code. Second, the terminal/CLI: the text doorway to the OS for compiling (gcc), interpreting (python), installing (pip, npm), and above all driving Git — with cd / ls / mkdir movement as the first skill to learn.

Third — “not optional,” “mandatory” — Git, Torvalds’ 2005 distributed version control: every change tracked, history rewindable, branches for safe experiments, collaboration without stepping on toes, via the beginner loop of repo → commit with real messages → push to GitHub → pull others’ work. These tools then carry a workflow distilled from the SDLC (plan, design, implement, test, deploy, maintain) into six bench steps: plan/sketch, set up environment + repo, write-and-test incrementally (DAIG again), commit regularly with clear messages, debug systematically, document with a README (what it does, how to run it). Internalize that loop and every project, from homework to production, runs on the same rails.

Procedure

  1. Surface: install VS Code; open your project folder in it.
  2. Terminal: cd in, ls, mkdir myproject, run python --version.
  3. Repo: git init, first commit with a message that explains why.
  4. Loop: plan → tiny code → run → commit → debug → README, every session.
  5. Share: push to GitHub; pull before starting; branch for experiments.

Bench figure 6: three fixtures, one loop. The loop is the skill.

Counter-intuitiveA “heavy” IDE can be the lighter choice for beginners — offloading syntax memory beats proving toughness in Vim on day one.
Edge caseUntracked secrets or 2 GB data files committed once pollute history forever — hence .gitignore before the first commit.

Experiment 07 · Synthesis

The pyramid: four layers, five moves

Objective — Place every idea on the pyramid and leave with five dated, doable first moves.

Everything stacks into a pyramid, and the shape is the lesson. Base: the conceptual foundation — computational thinking and algorithm design, the transferable problem-solving discipline. Middle: the constructive elements — data types as vocabulary, variables as containers, syntax as grammar, control structures as sentence structure, translating plans into runnable code. Upper: structuring complexity through modularity — encapsulation, cohesion, coupling, filing — the professional response to growth. Cap: debugging as inevitable process plus the ecosystem of tools and workflows that make it survivable. A beginner holding this picture stops asking “which tutorial next?” and starts asking “which layer is weak?” — that picture is your roadmap.

From the pyramid fall five dated moves: think first and code later (plan and algorithm before implementation); master the primitives (variables, int/float/bool/str, the three constructs — the universal vocabulary); embrace modularity early (functions and files even in tiny projects); treat debugging as a feature (expect bugs, read messages, print liberally, stay systematic); learn the tools alongside the language (Git, VS Code, terminal now, not “later”). Run one small project through all five — plan it, type it from primitives, file it in modules, debug it by routine, commit and document it — and you will have rehearsed, at small scale, the whole profession. That is the blueprint’s final claim: not syntax memorized, but a durable, adaptable foundation for a career.

Procedure

  1. Diagnose: label your weakest pyramid layer honestly (think / build / structure / process).
  2. Think: solve the next task on paper — goal, inputs, steps, end state.
  3. Build: implement from primitives only; justify each construct choice aloud.
  4. Structure + process: modularize, DAIG-test, commit with a why-message, README it.
  5. Date it: put the five moves on a calendar — one per week, one tiny shipped project.

Bench figure 7: broad base, narrow cap. Weak base, wobbly everything.

ObviousWeek 1 move: solve FizzBuzz on paper (goal/steps/end) before opening the editor.
Counter-intuitiveThe “advanced” layer (tools) is a beginner move: committing day one beats “learning Git later.”
Edge caseA project with perfect syntax but no plan still fails the pyramid — the base, not the middle, is missing.
# Python - all five moves in one bench run:
# MOVE 1 think: goal=sum evens under 20; end: printed total
# MOVE 2 primitives: int + for + if (universal vocabulary)
total = 0
for n in range(20):
    if n % 2 == 0:
        total += n
print(total)  # 90
# MOVE 3 modularity: one purpose, narrow contract
def sum_evens(limit):
    """(int) -> int. Single discrete function."""
    return sum(n for n in range(limit) if n % 2 == 0)
print(sum_evens(20))  # 90
# MOVE 4 debug as feature: DAIG-prove it now
assert sum_evens(20) == 90 and sum_evens(0) == 0
print("proven")  # MOVE 5: commit this + a README line
Visual analogy — Masonry pyramid: thinking is the foundation course, code the walls, modules the chambers, debugging and tools the capstone that keeps rain out.
✕ What people get wrong: “Synthesis means I’m done learning.” The pyramid is a diagnostic loop — every new project re-tests every layer.
Why this matters: Five dated moves beat fifty bookmarked tutorials. The whole arc of this manual cashes out here.

intWhole numbers (…, -1, 0, 42). Sized variants (byte, short, long) fix memory use and value range.
float / doubleApproximations of real numbers with decimals, for science, money, and measurement. Doubles carry more precision.
boolA logical value, True or False. The result of every condition; steers all selection and iteration.
char / string (str)A single symbol (char) versus a sequence of characters as text (string). Python uses str for both.
VariableA named storage slot in memory holding one value. Name it for its meaning (user_age), not its position.
SyntaxThe grammatical rules of a language (terminators, delimiters, indentation, case). Violations are syntax errors, caught before running.
Control flowThe order statements actually execute in: sequence by default, redirected by selection and iteration.

Experiment 4 — Modules

TermDefinition
Modular programmingDesign technique splitting a program into independent, interchangeable modules, each doing one task, combined into the whole.
EncapsulationHiding a module’s internals while exposing only a well-defined interface — use via promises, never rewiring.
Interface (contract)The public face of a module: what it does, what goes in, what comes out. The meeting point for tests, reuse, and teams.
CohesionHow related a module’s insides are. High is good — one purpose. Ladder (worst→best): coincidental, logical, temporal, procedural, communicational, sequential, functional.
CouplingHow much modules depend on each other. Loose is good. Ladder (worst→best): content, common, control, stamp, data (minimal, immutable arguments).
Circular importTwo modules importing each other — a one-way street violated; can freeze or crash loading. Restructure instead.
snake_caselowercase_words_joined_by_underscores — the Python convention for filenames and functions. Hyphens break imports.

Experiment 5 — Debugging

TermDefinition
BugAny gap between what the program does and what it should do. Normal inventory, not a verdict on you.
DebuggingThe systematic routine — reproduce, read, isolate, fix — of finding and removing bugs. A core engineering skill.
Syntax errorBroken grammar (misspelled keyword, missing parenthesis, wrong operator). Caught pre-run, with a line number.
Logic errorFlawed reasoning that runs without crashing but answers wrong (off-by-one, flipped comparator). Found via output vs expectation.
Stack traceThe recorded history of function calls leading to a failure — read it backward to the source; searching its last line often finds a solved twin.
BreakpointA marked line where a debugger pauses execution so you can inspect live variable values and step forward line by line.
Print debuggingRevealing values and reach with liberal print statements. Fastest lens for “what does the machine actually hold?”
Rubber-duck debuggingExplaining code aloud line by line to an inanimate listener until hidden assumptions confess.
DAIG (Debug As I Go)Testing each small fragment immediately after writing it, running often so failures stay single and shallow.

Experiment 6 — Workbench

TermDefinition
IDEIntegrated Development Environment: editor + compiler/interpreter + build tools + debugger in one GUI (PyCharm, IntelliJ). Lowers syntax memory load.
Source code editorA focused writing surface for code files (VS Code — the recommended start; also Notepad++, Vim, Emacs), extendable toward IDE powers.
Terminal (CLI)The text doorway to the OS: run code (python), compile (gcc), install (pip), drive Git. First moves: cd, ls, mkdir.
GitDistributed version control (2005): tracks every change, rewinds history, branches safe experiments. Mandatory from day one.
Repository / commit / branchRepo: the tracked project. Commit: a saved snapshot with a why-message. Branch: a parallel line for experiments without touching the main.
SDLC (distilled)Software Development Life Cycle — plan, design, implement, test, deploy, maintain. Your bench loop is its pocket edition.
READMEThe project’s front page: what it does and how to run it. Required for anything you share, including with future-you.

FAQ

Do I start by memorizing Python?

No. This manual puts problem-framing first: decompose, design steps, and check the end state. Syntax is the last mile, and this manual’s Python blocks are deliberately small so logic stays visible.

Why just three control structures?

Sequence, selection, and iteration compose all algorithms — plus recursion they reach Turing completeness. Learn the grammar once and every language becomes a dialect.

When should I split code into modules?

Earlier than feels necessary: one purpose per unit, narrow interfaces, filed layout. Treat organization as the professional divide, not big-team overhead.

Print debugging or a real debugger?

Prints for quick value-and-reach checks; debugger (breakpoints, inspection, stepping) when state is tangled. The duck is for assumptions. All four are sanctioned.

Is Git really mandatory for solo beginners?

Yes — history, reverts, and messages serve future-you immediately, and branches make experiments safe. “Later” is how work gets lost.
