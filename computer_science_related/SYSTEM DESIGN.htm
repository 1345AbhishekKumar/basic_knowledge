The Single Server Setup

Every complex system starts simple. Before scaling anything, understand how one server handles one request — the web app, database, and cache all living on the same box.

How a request actually travels

A user never has your server's IP address — they have a domain, like app.demo.com. Getting from that domain to a response involves DNS resolution, then a direct HTTP round trip.

Two traffic sources, two response shapes

  • Web clients — the server handles business logic, storage, and presentation using HTML, CSS, and JavaScript.
  • Mobile clients — communication happens over HTTP as API calls; responses are typically JSON because it's lightweight and easy for mobile devices to parse.
// GET /product/{id} GET domain.com/product/8841 // 200 OK — application/json { "id": "8841", "name": "Wireless Keyboard", "description": "...", "price": 49.99 }
Where this breaksThis setup is ideal for a small user base — but a single server has a hard ceiling. The next lessons peel apart the web tier, data tier, and traffic-distribution layer that let a system grow past one box.
Key takeaways
  • Start small: a single-server setup is the clearest way to learn the essential components before adding complexity.
  • Every request follows the same shape — DNS resolution → HTTP request → server processing → response — no matter how large the system eventually becomes.
  • Web and mobile clients place different demands on the server: HTML/presentation logic versus lightweight JSON APIs.

Databases: Relational vs. Non-Relational

As the user base grows, we split the web tier (handling traffic) from the data tier (managing storage) so each can scale independently. But which database family fits your data?

Relational (SQL) tables · rows · joins

Data lives in tables — columns are fields, rows are records. Examples: PostgreSQL, MySQL, Oracle, SQLite.

  • Join operations let you combine tables — e.g. a customers table and a products table combined into an orders table holding foreign keys to both.
  • ACID transactions guarantee correctness for multi-step operations like a bank transfer:
    • Atomic — the whole transaction succeeds or fails as one unit.
    • Consistent — moves the database from one valid state to another.
    • Isolated — concurrent transactions don't interfere with each other.
    • Durable — committed data survives a crash.

Non-Relational (NoSQL) flexible · fast · unstructured

Document Store

MongoDB

JSON-like documents holding complex, nested data in a single record.

Wide-Column Store

Cassandra · Cosmos DB

Tables with dynamic columns — handles massive scale and heavy write throughput.

Graph Store

Neo4j · Amazon Neptune

Entities and relationships stored as graphs — e.g. product recommendations from order history.

Key-Value Store

Redis · Memcached

Primarily RAM-resident — simplicity and raw speed for read/write.

The same customer→order→product relationship that needed a join in SQL can live as one embedded document in MongoDB — trading relational structure for flexibility and low-latency reads.

Choosing between them

Use SQL when…Use NoSQL when…
Data is well-structured with clear relationships (e.g. e-commerce customers & orders)You need super low latency for quick responses
You need strong consistency & transactional integrity (banking, finance)Data is unstructured/semi-structured (JSON blobs) and relationships aren't critical
Complex, multi-table queries are commonYou need flexible, scalable storage for massive volumes (e.g. a recommendation engine's activity data)
Key takeaways
  • Separating the web tier from the data tier lets each scale according to its own load.
  • SQL = structure, joins, ACID guarantees. NoSQL = flexibility, scale, speed — in document, wide-column, graph, or key-value form.
  • The right choice depends on your data shape and consistency needs, not on which is "newer."

Vertical vs. Horizontal Scaling

Two ways to handle more traffic: make one server bigger, or use more servers. Almost every large-scale system eventually chooses the latter.

Vertical ScalingHorizontal Scaling
Add resources (RAM, CPU) to the existing serverAdd more servers to share the load
Simple; fine for low/moderate trafficSuited for large-scale, high-traffic applications
Resource limits — hard cap on how much a single machine can be upgradedHigher fault tolerance — one server failing still leaves others serving traffic
Lack of redundancy — if the one server goes down, the whole app goes downBetter scalability — add servers as demand grows

Horizontal scaling raises a new question immediately: with three servers instead of one, how does a client's request know which server to hit? That's the job of a load balancer — the subject of the next lesson.

Key takeaways
  • Vertical scaling is simple but hits a hard resource ceiling and creates a single point of failure.
  • Horizontal scaling trades simplicity for fault tolerance and near-unbounded scalability.
  • Horizontal scaling requires a traffic-distribution layer — a load balancer.

Load Balancing

A load balancer sits between clients and the server pool, deciding which server handles each request — and keeping traffic away from servers that are down.

Seven load-balancing strategies

01

Round Robin

+

Each server in the pool receives requests in sequential, rotating order — first request to server 1, second to server 2, third to server 3, then back to server 1.

Best for: servers with similar specifications/capacity.

02

Least Connections

+

Directs traffic to whichever server currently has the fewest active connections.

Best for: applications with variable-length sessions.

03

Least Response Time

+

Chooses the server with the lowest response time and the fewest active connections — balancing responsiveness against current load.

Best for: pools of servers with different capabilities, when fastest response is the priority.

04

IP Hash

+

Hashes the client's IP address to consistently route that client to the same server on every request.

Best for: cases where a server holds per-client state or context.

05

Weighted (Round Robin / Least Connections)

+

Servers are assigned weights based on capacity/performance (RAM, CPU). A 64GB server gets proportionally more traffic than a 16GB one.

06

Geographical

+

Routes requests to the server geographically closest to the user — e.g. a Europe-based user hits a Europe-region server instead of US-East.

Best for: global services where latency reduction matters.

07

Consistent Hashing

+

A hash function places servers on a conceptual "hash ring." A user's IP is hashed onto the same ring, and their request goes to the nearest server on that ring.

Like IP hashing, it keeps the same client on the same server — with better rebalancing behavior when servers are added or removed.

Health checks & implementations

Load balancers continuously ping servers with health check requests. A server that fails a health check is marked offline and receives no traffic until it recovers.

Software

NGINX · HAProxy

Installed on your own server; you configure the pool, algorithm, and health checks yourself.

Hardware

F5 · Citrix

Dedicated appliances known for high performance and rich feature sets.

Cloud-managed

AWS ELB · Azure LB · Google Cloud LB

Comes with automatic scaling, security, and built-in monitoring — no manual setup.

Quick check
A chat app needs every message from a given user to land on the server that holds their session cache. Which strategy fits best?
Key takeaways
  • A load balancer distributes traffic across a server pool and reroutes around failed nodes using health checks.
  • Seven common strategies: Round Robin, Least Connections, Least Response Time, IP Hash, Weighted, Geographical, Consistent Hashing — pick based on server homogeneity, session stickiness, and latency needs.
  • Load balancers ship as software (NGINX, HAProxy), hardware (F5, Citrix), or managed cloud services (AWS/Azure/GCP).

Single Points of Failure

A single point of failure (SPOF) is any component whose failure takes the whole system down with it — and a load balancer, ironically, can become one.

When the database fails, every API instance loses its data source — and the whole system fails with it, regardless of how many redundant API servers you have.

Why SPOFs matter

  • Reliability — one failure can take the entire system down, meaning real business loss (e.g. users can't reach checkout).
  • Scalability — systems with SPOFs struggle to scale, since each new component adds another point of risk.
  • Security — an attacker who identifies the SPOF (e.g. the load balancer) can target it directly and bring the whole system down with a single attack.

Removing the load balancer as a SPOF

Strategy A

Redundancy

Run more than one load balancer. If one fails, traffic shifts entirely to the other; when it recovers, traffic is rebalanced (e.g. 50/50) between them.

Strategy B

Health checks & monitoring

Continuously monitor load balancer health itself, the same way load balancers monitor servers — so failures are detected immediately.

Strategy C

Self-healing systems

Automatically spin up a fresh instance to replace a failed load balancer, minimizing interruption.

Key takeaways
  • A SPOF is any single component whose failure collapses the entire system.
  • SPOFs threaten reliability, scalability, and security simultaneously.
  • Mitigate with redundancy, health monitoring, and self-healing replacement — applied to every critical layer, including the load balancer itself.

API Design

REST, GraphQL & gRPC

An API is a contract — what requests can be made, and what responses to expect — that hides implementation details and sets clear boundaries between systems.

StyleShapeStrengthBest for
RESTResource-based endpoints, standard HTTP methods, statelessSimplicity, HTTP caching, wide tooling supportWeb & mobile applications
GraphQLSingle endpoint; client specifies exact fields via a query languageMinimal round trips — one request instead of severalComplex UIs with nested/varied data needs
gRPCRPC methods defined via Protocol Buffers; supports streamingHigh performance, bidirectional streamingMicroservice-to-microservice / internal communication

REST vs. GraphQL, side by side

// REST — 3 separate round trips GET /v1/users/123 GET /v1/users/123/posts GET /v1/users/123/followers // GraphQL — 1 request, exact shape query { user(id: "123") { name posts { title content } followers { name } } }
RESTGraphQL
EndpointsResource-based (/users, /posts)Single endpoint (/graphql)
Response shapeFixed structure per endpointClient-defined per request
VersioningExplicit (/v1, /v2)Usually schema evolution without versioning
CachingHTTP caching via headersApplication-level caching

Four principles of great API design

01

Consistency

Uniform naming, casing, and patterns across every endpoint.

02

Simplicity

Minimal complexity, intuitive design — usable without reading docs.

03

Security

Authentication, authorization, input validation, and rate limiting as defaults.

04

Performance

Caching, pagination, minimized payloads, and fewer round trips.

The litmus test"The best API is the one you can use without even reading the documentation."

Protocol shapes the API

  • HTTP — enables RESTful and GraphQL capabilities directly (status codes, caching headers).
  • WebSocket — enables real-time, bidirectional APIs (chat, live streaming).
  • gRPC / HTTP2 — used for fast microservice-to-microservice communication.

The API design lifecycle

  1. Requirements — use cases, scope/boundaries, performance needs, security constraints.
  2. Design approach — top-down (start from requirements, common in interviews), bottom-up (start from existing data models), or contract-first (define request/response shapes before implementation).
  3. Development & local testing.
  4. Deployment & monitoring on staging/production.
  5. Maintenance — the payoff for keeping designs simple.
  6. Deprecation & retirement — e.g. sunsetting v1 once v2 is adopted.
Key takeaways
  • REST, GraphQL, and gRPC solve different problems — resource simplicity, flexible querying, and internal performance, respectively.
  • Good APIs are consistent, simple, secure, and performant — in that order of daily impact.
  • API design is a full lifecycle: requirements → design → development → deployment → maintenance → deprecation.

Application Layer Protocols

Application-layer protocols define message format, request/response patterns, and connection handling — sitting atop TCP/UDP in the network stack.

HTTP

Hypertext Transfer Protocol

Foundation of web APIs. Request = method + URL + version + host + headers. Response = status code + headers + body.

HTTPS

HTTP + TLS/SSL

Encrypts data in transit, adds integrity and authentication, and carries SEO benefits. The standard for production.

WebSocket

Bidirectional, persistent

After one handshake, the server can push data to the client without being asked — unlocking real-time updates with minimal latency and bandwidth waste versus polling.

AMQP

Advanced Message Queuing Protocol

Enterprise messaging: producers publish to queues, consumers pull when they have capacity — guaranteeing delivery for async workflows like order processing.

gRPC

Google Remote Procedure Call

Runs over HTTP/2, uses Protocol Buffers, supports built-in streaming. Best for server-to-server communication (most browsers lack full HTTP/2 support).

HTTP methods & status codes

MethodPurpose
GETRetrieve data
POSTCreate data
PUT / PATCHUpdate data (full / partial)
DELETERemove data
RangeMeaning
2xxSuccess — request completed as expected
3xxRedirection
4xxClient error — the requester made a mistake
5xxServer error — something failed on the server side

Polling vs. WebSocket

Choosing a protocol

Consider: interaction pattern (request/response vs. real-time), performance needs, client compatibility (browsers vs. servers), payload size, security requirements, and developer experience (tooling & docs).

Key takeaways
  • HTTP/HTTPS underpins REST and GraphQL; WebSocket enables real-time bidirectional communication; AMQP guarantees async message delivery; gRPC maximizes server-to-server performance.
  • WebSocket removes the wasted round trips inherent to polling by letting the server push data on its own schedule.
  • Protocol choice should follow interaction pattern, performance, client compatibility, and payload characteristics — not habit.

Transport Layer: TCP vs. UDP

Below the application layer sits the transport layer — the protocols actually responsible for moving packets across the network.

TCPUDP
Connection-based (three-way handshake first)No handshake, no connection tracking
Guarantees delivery — lost/out-of-order packets are resent/reorderedNo delivery guarantee — lost packets simply aren't resent
Reliable but slower (overhead from ordering & retransmission)Fast, lightweight, less overhead
Use for: payments, authentication, banking, email — anything needing accuracyUse for: video calls, live streaming, online gaming — anything favoring speed over perfect delivery
Quick check
A live video-call feature drops a few video frames when the network hiccups, but keeps playing smoothly. Which transport protocol is it most likely using?
Key takeaways
  • TCP trades speed for reliability via handshakes, ordering, and retransmission — the right choice whenever correctness matters more than latency.
  • UDP trades reliability for speed — the right choice when occasional data loss is acceptable in exchange for low latency.
  • Application protocols (HTTP, WebSocket, gRPC) are built on top of these transport-layer choices.

API Design

Designing RESTful APIs

REST APIs model your business domain as nouns, not verbs — and lean on standard HTTP semantics for everything else.

Resource modeling

  • Business domain nouns become resource collections: products, orders, reviews.
  • GET /api/products → the collection. GET /api/products/123 → one item.
  • Nested resources: GET /api/products/123/reviews → reviews for that product.
  • Use nouns, never verbs, in the URL — GET /orders, not GET /getOrders.

Filtering, sorting & pagination

// filtering GET /api/products?category=electronics&in_stock=true // sorting GET /api/products?sort=price_asc // pagination (page/limit) GET /api/products?page=2&limit=10 // pagination (offset/limit) or cursor-based GET /api/products?offset=20&limit=10

Doing this server-side — rather than shipping every row to the client — saves bandwidth, improves performance on both ends, and gives the front end more flexibility.

CRUD via HTTP methods

MethodEndpoint shapeBehavior
GET/api/v1/productsSafe & idempotent — repeat calls return the same result
POST/api/v1/productsCreates a resource; changes server state; not idempotent
PUT/api/v1/products/123Replaces the whole resource
PATCH/api/v1/products/123Partially updates a resource
DELETE/api/v1/products/123Removes the resource

Status codes in practice

  • 200 OK — successful GET
  • 201 Created — successful POST
  • 204 No Content
  • 400 Bad Request — malformed input
  • 401 Unauthorized
  • 404 Not Found
  • 500 Internal Server Error

Best practices checklist

✓

Plural nouns

/products, not /product.

✓

Correct HTTP methods

Never overload a single verb — no /delete endpoints reached via POST.

✓

Filtering, sorting, pagination

Never return unbounded collections.

✓

Explicit versioning

/api/v1, /api/v2 — so breaking changes don't break old clients.

Key takeaways
  • Model resources as plural nouns; let HTTP methods carry the verb.
  • Always bound collection responses with filtering, sorting, and pagination.
  • Explicit versioning (/v1, /v2) protects existing clients when the API evolves.

Designing GraphQL APIs

GraphQL exists to fix REST's overfetching/underfetching problem — clients describe the exact shape of data they need, in one request.

Schema & type system

The schema is the contract between client and server. It defines types (e.g. User, Post), queries (reads — the GraphQL equivalent of GET), and mutations (writes — the equivalent of POST/PUT/PATCH/DELETE).

type User { id: ID! name: String! posts: [Post!]! } type Query { user(id: ID!): User } type Mutation { createUser(name: String!): User }

Querying & mutating

// query query { user(id: "123") { name posts { title } } } // mutation mutation { createPost(title: "Hello", body: "World") { id title } }

Error handling — a key difference from REST

GraphQL always returns 200 OK at the transport level, even on failure. Errors surface inside the response body via an errors array, alongside any partial data that was still resolvable.

{ "data": { "user": null }, "errors": [ { "status": 404, "message": "Not Found", "path": ["user"] } ] }

Best practices

  • Keep schemas small and modular.
  • Limit query depth to avoid infinitely nested queries (user → posts → comments → …).
  • Use meaningful naming for types and fields — the schema is shared with every client.
  • Use dedicated input types for mutations.
Key takeaways
  • GraphQL trades REST's multiple endpoints for one endpoint plus a client-specified response shape.
  • Errors live inside a 200 response's errors field, not in the HTTP status code.
  • Depth limits and modular schemas keep GraphQL APIs maintainable at scale.

Security

Authentication

Authentication answers one question: who is this? It's the gate that must be passed before anything else — including authorization.

Common confusionJWT is a token format, not an authentication method. OAuth2 is an authorization framework, not authentication. Single Sign-On is a UX pattern, not an authentication method. Bearer auth is a pattern — "whoever holds this token gets access" — and JWT is just the most common bearer token format.

Basic authentication methods

A

Basic Authentication

+

Credentials sent as a Base64-encoded username:password string in the Authorization header, on every request.

Weakness: Base64 is trivially reversible — insecure unless wrapped in HTTPS, and rarely used in production outside internal tools.

B

Digest Authentication

+

Same challenge/response flow as Basic, but sends an MD5 hash instead of the plain credentials.

Weakness: Better than Basic, but still outdated compared to modern token-based options.

C

API Key Authentication

+

A unique key is generated per client and sent via an Authorization or X-API-Key header. The server looks it up against a stored hash + scopes.

Weakness: Unlike JWT, keys are opaque random strings — the server must look up who owns the key. If a key leaks, anyone can use it, and there's no built-in expiration unless you implement one.

D

Session-Based Authentication

+

User logs in, server creates a session (stored in memory, Redis, or a database) and returns a session cookie. Subsequent requests look up that session ID.

Trade-off: Stateful — the server must remember every session. Works well for traditional web apps but doesn't scale as cleanly for distributed APIs. Redis is the common production choice for session storage because of its speed and built-in expiration.

Token-based authentication

Bearer + JWT

JSON Web Token

A signed JSON object holding the user ID, expiration, and claims (roles, permissions). Verified locally via signature — no database lookup needed, so it's stateless and scalable.

Access Token

Short-lived

Valid ~15 min–1hr; used on every API call.

Refresh Token

Long-lived

Valid for days/weeks; used only to mint a new access token. Store in an HTTP-only cookie — never in local storage — to prevent XSS theft.

OAuth2 & OpenID Connect

  • OAuth2 is an authorization framework — it answers "what can this app access on my behalf?" The result is an access token proving permission, not identity.
  • OpenID Connect (OIDC) layers authentication on top of OAuth2 by also returning an ID token — a JWT that carries the user's actual identity (email, user ID). This is what powers "Sign in with Google/GitHub."

Single Sign-On & identity protocols

SSO is a user-experience pattern: log in once with an identity provider, then access multiple services without re-authenticating — enabled underneath by identity protocols:

ProtocolFormatCommon use
SAML (Security Assertion Markup Language)XML-based assertionsEnterprise / legacy systems (Salesforce, corporate dashboards)
OpenID ConnectJWT ID tokenModern consumer sign-in flows (Google, GitHub)
Quick check
A colleague says "we use JWT for authentication." What's the more precise statement?
Key takeaways
  • Authentication verifies identity; it always happens before authorization.
  • Sessions are stateful (server remembers); tokens like JWT are stateless (server verifies a signature).
  • OAuth2 = delegated authorization. OpenID Connect = OAuth2 + identity (an ID token). SSO = a UX pattern built on identity protocols like SAML or OIDC.

Authorization

Once the system knows who you are, authorization decides what you're allowed to do.

Three authorization models

1

Role-Based Access Control (RBAC)

+

Users are assigned roles (e.g. Admin, Editor, Viewer), and each role has a fixed permission set. Admin: create/read/update/delete + manage users. Editor: create/read/update, no delete, no user management. Viewer: read-only.

Seen in: GitHub repo access, CMS tools, team-management dashboards — the most common model overall.

2

Attribute-Based Access Control (ABAC)

+

Access is granted based on user attributes (department, age), resource attributes (confidentiality, owner), and environment conditions (time of day, location, device) — e.g. "allow read access if user.department == HR AND resource.classification == internal."

Trade-off: More flexible than RBAC, but more complex and prone to policy conflicts.

3

Access Control Lists (ACL)

+

Each individual resource carries its own permission list — e.g. a document where Alice has read-only access, Bob has read+write, and a third user has no access at all.

Seen in: Google Docs/Drive sharing. Highly specific and user-centric, but harder to scale across millions of objects.

In practiceReal systems often combine models — e.g. RBAC for coarse-grained roles, layered with ABAC conditions for fine-grained edge cases.

How rules get enforced

  • OAuth2 (delegated authorization) — e.g. authorizing Vercel to access a specific GitHub repo. Instead of handing over your password, GitHub issues a scoped access token representing exactly the permissions you approved.
  • JWT / bearer tokens — carry the user's identity and claims (roles, scopes, expiration, issuer) on every request; the server applies its authorization model against those claims.
Key distinctionTokens are the mechanism that carries identity/claims across the wire. RBAC, ABAC, and ACL are the models that decide what those claims are allowed to do. Don't conflate the two.
Key takeaways
  • Authorization is a distinct step after authentication — it governs permitted actions, not identity.
  • RBAC (roles), ABAC (attributes/conditions), and ACL (per-resource lists) each trade simplicity for flexibility differently.
  • OAuth2 and JWT are the mechanisms that carry and enforce those permissions in real traffic.

Protecting the API Attack Surface

An unprotected API is an open door. Seven proven techniques close the most common attack vectors.

1

Rate Limiting

+

Caps how many requests a client can make in a given window — per endpoint, per user/IP, and globally (to blunt distributed/botnet attacks where each bot stays under an individual limit).

2

CORS

+

Cross-Origin Resource Sharing controls which domains a browser is allowed to call your API from — blocking malicious sites from making authenticated requests on a user's behalf.

3

SQL / NoSQL Injection

+

Occurs when raw user input is concatenated directly into a database query, letting an attacker bypass checks and read, modify, or delete data. Fix: parameterized queries or ORM safeguards — never string-concatenated SQL.

4

Firewalls & VPNs

+

Web Application Firewalls (e.g. AWS WAF) filter traffic for known attack patterns — suspicious SQL keywords, malformed methods — before it reaches the API. VPNs restrict private/internal APIs (e.g. an admin dashboard) so only requests from within the company network can reach them.

5

CSRF (Cross-Site Request Forgery)

+

Tricks a logged-in user's browser into submitting an unwanted request (e.g. a hidden money transfer) using their existing session cookie. Fix: pair session cookies with a CSRF token that must match on every state-changing request.

6

XSS (Cross-Site Scripting)

+

An attacker injects a malicious script into content that gets stored and later rendered to other users (e.g. a comment field) — the victim's browser then executes it, potentially stealing cookies or session data. Fix: sanitize/escape all user-supplied content before storage and render.

Key takeaways
  • Rate limiting and CORS control who and how often can reach your API.
  • Parameterized queries close injection attacks; CSRF tokens and content sanitization close CSRF and XSS.
  • Firewalls and VPNs add a perimeter layer, filtering malicious traffic before it ever reaches application code.
