Software Fundamentals Matter More Than Ever

A talk for anyone who believes their skill set is no longer worth anything in the AI age — and the argument for why the opposite is true.

From a teacher who built a course called Claude Code for real engineers, and had to work out a curriculum for AI coding while the ground kept moving.

The thesis

Code is not cheap. In fact, bad code is the most expensive it's ever been — because a codebase that's hard to change stops you from collecting the bounty AI can offer. AI does really, really well in a good codebase.

Which means good codebases matter more than ever. Which means software fundamentals matter more than ever.

01

Specs-to-code is vibe coding by another name

"I kept running the compiler, kept running the compiler, and I would just end up with garbage."

What the movement says

Write a specification about how an application is supposed to work. Use AI to turn it into code. If there's a problem with the application, go back to the spec — don't look at the code. Change the spec, run the compiler again, get more code.

What actually happened when he tried it

  1. Got code out.
  2. Ran it again — got worse code.
  3. Ran it again — got even worse code.
  4. Kept running it — ended up with garbage.
The verdict: "I don't think this works. The idea that we can just ignore the code and have the code manage itself is just sort of vibe coding by another name."

And the fix he reached for wasn't a better compiler. It was: explain to the LLM in English what a good codebase looks like. Which meant going back to old books.

→ Treating code as a disposable output of a spec doesn't remove the engineering problem. It just hides it until the code becomes garbage.
02

Complexity and software entropy

"Complexity is anything related to the structure of a software system that makes it hard to understand and modify the system."

Two old books gave him the vocabulary for what he was seeing.

A Philosophy of Software Design
John Ousterhout

Bad code is complex code. A bad codebase is one that's hard to change. If you can't change a codebase without causing bugs, it's a bad codebase. Good codebases are easy to change.

The Pragmatic Programmer
Hunt & Thomas

Software entropy. Things tend toward disaster and collapse. Every time you change a codebase thinking only about that change — not the design of the whole system — it gets worse and worse.

Why this explains the specs-to-code result

Everything inside the specs-to-code idea — run the compiler again and again — was producing worse code, because it was entropy in its purest form. Every regeneration is a change made without regard for the design of the whole.

The reframe: a "bad codebase" isn't an aesthetic judgment. It's a functional one. It's a codebase where change causes bugs — which is precisely the thing AI needs to be able to do reliably.
→ Design of the whole system is not optional overhead. Without it, every change makes the next one harder.
03

The AI didn't do what I wanted

Failure mode 1

"Me and the AI don't share a design concept."

The diagnosis

The Pragmatic Programmer again: no one knows exactly what they want. When you're talking to the AI, that conversation is the requirements gathering. There's a communication barrier, and it's not one-sided.

Frederick P. Brooks, The Design of Design, gives the concept a name: the design concept. When more than one person designs something together, there's an ephemeral idea floating between them — the invisible theory of what you're building.

Crucially: the design concept is not an asset. It's not something you can put in a markdown file. Which is exactly why "write a better spec" doesn't solve it.

The skill: grill me

skill · grill-me
Interview me relentlessly about every aspect of this plan
until we reach a shared understanding.

Walk down each branch of the design tree, resolving
dependencies between decisions one by one.

Two sentences. What they produce:

  • The AI asks 40, 60, sometimes 100 questions before it's satisfied a shared understanding has been reached.
  • It turns the AI into a kind of adversary — continually pinging you with ideas until the concept is shared.
  • The resulting conversation becomes a PRD for big work, or gets turned directly into issues for an AFK agent on small changes.
The repo went viral — ~13,000 stars. "People love this thing."
His opinion, stated as opinion: this is better than the default plan mode in Claude Code. "Plan mode is extremely eager to create an asset. It really wants to just create a plan and start working. Whereas I think it's a lot nicer to reach a shared design concept first."
→ You can't write the design concept into a file. You have to argue your way to it.
04

The AI is just way too verbose

Failure mode 2

"It's kind of like the AI is talking just using too many words to try to communicate what it's doing."

The diagnosis

This feels familiar to any developer who has worked with a domain expert. Someone wants you to build something on microchips. You have no idea what microchips are. You need to establish a shared language — otherwise they use terms you don't understand, you translate that into code neither of you really understands, and the gap widens.

The source: Domain-Driven Design

DDD calls it the ubiquitous language: conversations among developers, the expressions in the code, and conversations with domain experts are all derived from the same domain model.

In practice: a markdown file full of a list of terms that you and the AI have in common. You focus on those terms, make sure they actually mean what they say, and use them everywhere — in the code, when talking about the code, and when talking to the AI.

The skill: ubiquitous language

  • Scans your codebase for terminology.
  • Creates a markdown file — a set of tables with all the terminology.
  • You pass it to the AI, and you keep it open while grilling and planning.

What he observed in the thinking traces

  • Planning improves.
  • The AI thinks in a less verbose way.
  • The implementation ends up more aligned with what was planned.
"This has absolutely been a powerhouse. Unbelievably good."
→ Verbosity is often a symptom of a missing shared vocabulary, not a personality flaw in the model.
05

It built the right thing — but it doesn't work

Failure mode 3

"The rate of feedback is your speed limit."

The obvious fix: feedback loops

  • Static types. "If you're not using TypeScript, that's crazy."
  • Browser access for front-end work — the LLM needs to look around.
  • Automated tests. Obviously.

The less obvious problem

Even with feedback loops in place, the LLM doesn't use them well. It doesn't get the most out of them the way a veteran developer would. What it tends to do is way too much at once — produce huge amounts of code, and then think "oh, I should probably type check that."

The Pragmatic Programmer calls this outrunning your headlights — driving too fast for how far you can see. Because the rate of feedback is your speed limit. You should be testing as you go, taking small deliberate steps.

The skill: TDD

  1. Write the test first.
  2. Make that test pass.
  3. Refactor the code to make it nicer — and consider the design.
Why it works on an LLM: TDD forces it to take small steps. It's a structural constraint, not a suggestion.

The honest complication

Testing is really hard, and always has been, because writing a test forces a pile of interdependent decisions:

  • How big a unit do you want to test?
  • What do you mock?
  • What behaviors do you even want to test?

Test a really big unit — like an entire massive application — and it might be quite flaky. Test a smaller unit and you need to mock more. It's all interlinked.

The connection back to code quality: good codebases are easy codebases to test. The better your codebase, the better your feedback loops. The better your feedback loops, the better the code the LLM produces. It's a loop, and it goes both directions.
→ Don't just add feedback loops. Force the small steps that let the feedback actually land.
06

Deep modules vs shallow modules

"Shallow modules … a ton of different tiny little blobs that the AI has to walk through and navigate. This is really hard for the AI to explore."

So what does a testable codebase look like? Back to Ousterhout: you want deep modules, not shallow ones.

Shallow modules

not much functionality · complex interface

Deep modules

lots of functionality · simple interface

Why shallow is a trap with AI

AI is really good at creating codebases that look like the left one. And the result is:

  • The AI doesn't understand what your code is doing.
  • It attempts to explore, but because the layout is poor, it may not reach the right module in time.
  • It doesn't understand all the dependencies.
  • Net effect: it doesn't understand your code.

What deep modules buy you

  • Lots of functionality hidden behind a simple interface — complexity is hidden, not eliminated.
  • You can look inside if you want, but you don't need to. You can just use the interface.
  • Because the boundaries are so simple, you test at the interface and verify through it.
  • This is a codebase that rewards TDD.
Who designs the interface? You should probably have a lot of control over them and design them really well — otherwise AI might mess up the design. The implementation, you can leave to the AI a bit more.

The skill: improve codebase architecture

It's not trivial, but it's a set of steps you can reuse again and again:

  1. Explore the codebase.
  2. Look for opportunities where code is related.
  3. Wrap all of that in a deep module.
→ Structure is not cosmetic. It's the difference between an AI that can navigate your codebase and one that gets lost in it.
07

Your brain can't keep up

Failure mode 6

"Raise your hand if you've felt more tired than you have ever before in your development career."

The problem

The feedback loops are working. Things are kicking into gear. You're shipping more code than you ever have. And your brain can't keep up — it's knackering. A tangled codebase makes this worse, because you, as well as the AI, have to hold all of that information in your head.

The relief: treat modules as gray boxes

  • Design the interface.
  • Don't review the implementation too much.
  • As long as there's a testable boundary outside the module, and you understand its purpose and can design it from the outside, you don't need to think about the implementation.
With an honest caveat: you obviously can't do this with everything — things like finance, or anything else critical. But in many, many modules in your app, you don't need to.

The skill: design the interface, delegate the implementation

What this demands of your process

Whenever you're touching the code or planning, you need to be aware of the modules in your application. You need to know that map really well. It has to:

  • Be part of your ubiquitous language.
  • Be built into your planning skills.
  • Show up in the PRD — specific about the module changes and the interfaces inside those modules, and how they're being modified.
Kent Beck: "Invest in the design of the system every day." This is the core of it. Specs-to-code does not invest in the design of the system — it divests from it. It gets rid of that.
→ The point of good structure isn't just AI comprehension. It's that you get to stop holding everything in your head at once.
08

Code is not cheap — you are the strategist

"If we think about AI as a really great on-the-ground programmer, a kind of tactical programmer … you need someone above that. And that's you."

The idea he's rejecting

There's an idea that drives the specs-to-code movement: code is cheap. He doesn't think it's right.

Bad code is the most expensive it's ever been. If you have a codebase that's hard to change, you're not able to take all of the bounty that AI can offer — because AI in a good codebase actually does really, really well.

The division of labor

LayerWho
Tactical — making the code changes on the ground AI. A really great on-the-ground programmer. A sergeant.
Strategic — thinking at the level above that You. And that requires software fundamental skills we've been using for 20 years and longer.
The message to take away: code is important. Your fundamentals are not obsolete — they're the thing that determines whether the AI can be effective at all.
→ The AI got better at typing. It didn't get better at deciding what the system should be.

The through-line

Everything in the talk reduces to the same handful of moves.

  • 01 Don't ignore the code Specs-to-code that never looks at the output ends in garbage. It's vibe coding by another name.
  • 02 Name what bad code is Complexity: structure that makes the system hard to understand and modify. Bad code = hard to change.
  • 03 Argue your way to a shared design concept You can't write it into a file. Grill until the invisible idea floating between you matches.
  • 04 Build a shared language A ubiquitous language file of shared terms. Less verbosity, better planning, more aligned implementation.
  • 05 Force small steps with TDD The rate of feedback is your speed limit. The LLM will outrun its headlights by default.
  • 06 Design deep modules, not shallow blobs Lots of functionality behind a simple interface. Testable at the boundary. Rewards TDD.
  • 07 Design the interface, delegate the implementation Treat modules as gray boxes so your own brain can keep up. Not for finance — but for a lot of the app.
  • 08 Invest in the design of the system every day Kent Beck's rule. Specs-to-code divests from design. This invests in it.
And the message underneath all of it: code is not cheap. Bad code is the most expensive it's ever been. AI is a great tactical programmer — you're the strategic layer above it, and that requires the fundamentals we've been using for decades.
