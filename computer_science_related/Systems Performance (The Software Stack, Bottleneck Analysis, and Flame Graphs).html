Systems Performance: The Software Stack, Bottleneck Analysis, and Flame Graphs

A self-contained, interactive systems engineering manual on identifying root causes, understanding how userland code crosses the kernel boundary, diagnosing multi-node cascading latency, and reading call-stack flame graphs to optimize production software.

What You'll Learn in This Lab

  • Map any execution stall across the full vertical software stack: from userland app logic, through system libraries and syscall boundaries, into kernel scheduling/page caches, down to physical and virtualized hardware.
  • Isolate distributed cascading bottlenecks where application ORM query patterns falsely disguise themselves as database storage failures.
  • Execute systematic bottleneck analysis using empirical metrics (P99 query latency, IOPS, individual disk request latency, host process tables) without guesswork.
  • Distinguish statistical stack profiling (low-overhead periodic sampling) from event tracing (exact hooks via eBPF/ftrace), and know when each applies.
  • Interpret call-stack flame graphs accurately, navigating root-to-leaf hierarchies on the Y-axis and aggregated on-CPU sample widths on the X-axis to identify high-leverage architectural optimizations.
  • Evaluate critical systems trade-offs including non-volatile write durability (fsync) versus high-throughput async batching (io_uring), and zero-downtime online schema migrations under load.

Module 01

The Modern Software Stack: Layered Performance from Userland to Silicon

When a software application runs sluggishly, the instinctive reaction of most software engineers is to stare exclusively at their own code. We audit loops, check variable allocations, and debate algorithmic complexity. Yet in modern operating environments, your application code represents only the very top tier of a deep, multi-layered pyramid. Beneath your high-level business logic sits a hierarchy of system libraries, a strict kernel boundary, intricate OS subsystems, and physical or virtualized hardware.

As Brendan Gregg emphasizes in Systems Performance, an execution bottleneck can materialize at any layer of this stack—or within the subtle friction points where layers interact. Userland applications do not possess direct authority to access network cards, touch physical memory addresses, or command SSD storage controller chips. Whenever your program wishes to persist a state record or transmit an HTTP payload, it must cross the system call boundary (syscall), transitioning processor privilege from unprivileged User Mode (Ring 3 on x86-64) to privileged Kernel Mode (Ring 0).

Once inside the kernel, your request enters complex subsystems: the CPU process scheduler deciding when your thread receives another quantum of execution; the Virtual Memory manager translating virtual pages through page tables and maintaining the page cache; the Virtual File System (VFS) coordinating journal writes and sector blocks; and the networking stack processing TCP socket buffers. Understanding this entire hierarchy is what separates guessing from true systems performance engineering.

⚙ Step-by-Step Traversal of the Software Stack
1
Application Layer (Userland) Your custom software (e.g., Node.js backend, Chromium browser, PostgreSQL process) executing business logic in unprivileged user space. Optimization here focuses on algorithms, data structures, and avoiding needless work.
2
System Libraries (Dynamic / Static Linking) Standard shared libraries like glibc (standard C library), memory allocators (jemalloc, ptmalloc), and cryptography suites (libcrypto/OpenSSL). Application code relies on these primitives daily; poor implementations here degrade the entire runtime.
3
System Call Interface (The Privilege Boundary) The hardware gate (e.g., syscall / sysenter instructions) where CPU registers are preserved, execution switches to kernel mode, and parameters are validated. Calls include read, write, epoll_wait, mmap, and fsync.
4
The Operating System Kernel The central arbiter managing physical resources: CPU time-slicing (CFS scheduler), virtual memory page tables and page cache, file system drivers (ext4, XFS, ZFS), and network packet queues.
5
Hardware & Virtualized I/O Devices Multi-core CPUs, caches (L1/L2/L3), physical DRAM, NVMe SSDs, network interface cards (NICs), and virtualized hypervisor devices (e.g., AWS EBS volumes, Nitro cards). Latency changes by orders of magnitude across this boundary.
Interactive Stack Layer Inspector
Application Layer: Code you author. Typical stalls: quadratic algorithms, memory thrashing, synchronous locking, and inefficient ORM serialization. Diagnostic tool: Application-level logs, APM, and profilers.
Three Real-World Manifestations Across Stack Layers
Obvious Case
High CPU from Inefficient App Logic
A developer implements an in-memory deduplication algorithm using nested arrays, triggering an O(N²) CPU spike that consumes 100% of a CPU core in Userland space.
Counter-Intuitive Case
System Library String Parsing Penalty
App code is algorithmically clean, but relies on an outdated dynamic C string comparison function in a shared system library that performs excessive memory allocations on every invocation.
Edge-Case Phenomenon
Hypervisor Steal Time & Bus Contention
App and kernel telemetry look pristine, but query latency fluctuates wildly because a neighbor virtual machine on the cloud host exhausts the shared PCIe bus or CPU cache lines (L3 cache thrashing).
🏛 Visual Analogy: The High-Security Ministry
Imagine Userland as the public lobby of a government ministry where citizens (applications) draft paperwork. To file a document or retrieve records from the basement vault (hard drive), citizens cannot simply walk downstairs. They must present requests at a bulletproof teller window (the System Call boundary). A sworn officer (the Kernel) validates permissions, queues the request in the intake registry (the Scheduler), checks whether a duplicate is already sitting on the clerk's desk (the Page Cache), and only dispatches a runner to the physical basement if absolutely necessary.
❌ What People Get Wrong
Believing that performance engineering begins and ends with application source code optimization, assuming the operating system and hardware execute every instruction with constant zero-cost friction.
Why This Matters
Understanding the vertical hierarchy prevents wasting engineering cycles refactoring perfectly sound application routines when the true stall originates from filesystem journal locks or memory paging.

Module 02

Distributed Topologies: Cascading Latency & Network Amplification

Examining a single server's software stack in isolation is only half the battle. In modern web and enterprise systems, software is distributed across networks. A request from a mobile client does not execute in a vacuum: it hits a content delivery network, routes to an application gateway, fans out across microservices, enqueues work onto message brokers like Apache Kafka, issues relational transactions against PostgreSQL or MySQL, and forwards audit events to analytical warehouses.

In a distributed architecture, latency compounds multiplicatively. A client perceives high latency not because any single server crashed, but because small delays cascade through the dependency tree. Ben Dickin highlighted on stream how easily developers misattribute the location of a bottleneck. When an application server takes 800 milliseconds to respond, the engineering team frequently blames the database server: "PostgreSQL is choking."

Yet upon profiling the database node, CPU is sitting at 20% and storage queues are empty. The true culprit is often an Object-Relational Mapper (ORM) on the application server issuing the classic N+1 query anti-pattern—firing 2,000 round-trip queries sequentially over a 0.3ms internal network link. The network round-trips and TCP socket serialization amplify a 2ms database operation into an 800ms user-facing catastrophe.

Distributed Request Flow & Cascading Path
Network Flow Trace: Notice how a single inbound client request fans out. If the App Server performs synchronous blocking calls to the queue or issues unbatched queries to PostgreSQL, upstream latency skyrockets while backend CPU remains low.
Three Real-World Distributed Bottlenecks
Obvious Case
Cross-Region WAN Latency
An application server deployed in Frankfurt synchronously queries a database hosted in Northern Virginia on every user click, incurring an unavoidable 90ms speed-of-light penalty per round trip.
Counter-Intuitive Case
ORM N+1 Masquerading as DB Failure
The database admin receives a pager alert for high latency. Investigation reveals the database is executing queries in 0.05ms, but the app server is executing 4,000 round trips sequentially per web request.
Edge-Case Phenomenon
Kafka Partition Backpressure Collapse
A downstream analytics consumer slows down, filling Kafka partition leader buffers, which causes producers on the primary app servers to block on network write buffers, choking incoming HTTP traffic.
🚢 Visual Analogy: The Logistics Port
Imagine a modern container port. Even if the primary container crane (the database) can lift a shipping crate in twenty seconds, a cargo truck cannot leave the terminal if the gate security inspection (the app server) verifies each shipping invoice one sheet at a time, making hundreds of phone calls back to headquarters before releasing the truck. The crane appears backed up, but the congestion was entirely created at the distribution checkpoint.
❌ What People Get Wrong
Assuming that because a dashboard flags a database request as taking 500ms, the solution is automatically to scale up database instance sizing or rewrite database indexes.
Why This Matters
Distinguishing transport and serialization bottlenecks from true storage engine contention saves companies thousands of dollars in unnecessary database hardware upgrades.

Module 03

Bottleneck Analysis: Diagnosing the "Mysterious Slow Database"

During the live stream, Ben Dickin walked through an instructive systems incident modeled directly after real-world production outages discussed in Chapter 1 of Systems Performance. Understanding this diagnostic methodology is the core foundation of systems engineering: moving methodically through metrics, disproving false assumptions, and isolating the empirical root cause.

The Incident: A production PostgreSQL database powering an e-commerce platform has operated reliably for months. Its P99 query latency is stable at a crisp 2 milliseconds. Suddenly, two days ago, the P99 query latency rockets upward to 50ms, 200ms, and spikes above 500ms. The slow query log—configured to capture any query executing for longer than 1.0 second—begins filling with dozens of warnings every minute.

The on-call engineers run the standard triage checklist:

  • Did application workload change? No. Inbound query throughput (QPS), query shapes, and access patterns are identical.
  • Did total data volume change? No. The database table footprint is exactly 100 Gigabytes, unchanged from last week.
  • Did database configuration change? No. Buffer pool allocations, work_mem, and WAL settings are untouched.

Looking at basic server health dashboards reveals an apparent contradiction: CPU utilization is flat at 50%. CPU is clearly not the bottleneck. However, Disk IOPS (I/O operations per second) has skyrocketed tenfold—from 1,000 IOPS to 10,000 IOPS. The naive conclusion? "The hard drive is dying! The SSD must be failing!"

Yet inspecting individual disk request latency reveals that each I/O read/write operation still completes in 0.10 milliseconds. The NVMe SSD hardware is exceptionally healthy. It is not slow; it is simply being bombarded with 10x more work. Why would an identical workload on an identical table footprint suddenly require 10x more physical disk reads?

The Discovery: Inspecting the host's active process table (top / telemetry) uncovers 20 new processes. Two days ago, another developer spun up an unisolated test Docker container on the same production node to test experimental migrations. The host possesses 64 Gigabytes of physical RAM. Previously, the production PostgreSQL engine enjoyed 50GB of memory for shared buffers and the Linux kernel page cache. The rogue container seized 25GB of RAM.

With host memory sliced in half, PostgreSQL's cache hit ratio collapsed. Pages that previously resided in fast nanosecond DRAM were evicted by the kernel. PostgreSQL was forced to fetch rows from the physical NVMe storage on every query—exploding disk IOPS and driving P99 query latency through the roof!

Three Noisy Neighbor & Cache Eviction Incidents
Obvious Case
Backup Script Exhausting Page Cache
A nightly pg_dump or tar backup reads the entire disk sequentially without POSIX_FADV_DONTNEED, flushing the active database index cache out of DRAM.
Counter-Intuitive Case
Rogue Test Container on Prod Host
As demonstrated by Ben, a secondary container claiming 25GB RAM on a 64GB host cuts page cache in half, causing identical queries to generate 10x physical disk IOPS.
Edge-Case Phenomenon
Transparent Huge Pages (THP) Stall
The Linux kernel background defragmenter (khugepaged) locks memory regions to allocate contiguous 2MB hugepages, causing sporadic 1000ms latency spikes while CPU is low.
📚 Visual Analogy: The Researcher's Desk
Think of the host's 64GB RAM as a spacious library desk where a researcher (PostgreSQL) keeps 50 open reference books for instant consultation. If a graduate student sits down and dumps their own equipment across half the desk (the test container), the researcher must pack 25 books away into the basement archives (the SSD). Every time the researcher needs an excerpt, they must hike down to the basement. The researcher isn't sick, and the basement isn't broken—the desk was simply crowded out.
❌ What People Get Wrong
Equating a surge in disk IOPS with hardware degradation or demanding faster SSDs, rather than checking if host memory eviction is forcing cache misses.
Why This Matters
Saves days of downtime and costly storage migrations by resolving the issue with a single command: isolating or terminating the rogue process.

Module 04

Profiling vs. Tracing: Statistical Sampling vs. Event Instrumentation

When you need to investigate where software is spending time, you must choose your observational mechanism carefully. Engineers frequently conflate two fundamentally distinct observability techniques: Profiling and Tracing. Choosing the wrong one can either leave you blind or introduce severe observer overhead that crashes your production service.

Profiling (Statistical Sampling): Profiling inspects the system periodically at a defined sample frequency. For example, a profiler might interrupt the CPU 99 times a second (99 Hertz). At each sample tick, the profiler takes a snapshot of the CPU's current Program Counter and walks backward through the call stack frames to record: main() → PostgresMain() → PortalRun() → ExecScan() → libcrypto(). Over a 10-second window, collecting 990 samples provides an extraordinarily accurate statistical distribution of which functions occupied CPU cycles, with negligible overhead (typically less than 1–2% CPU penalty).

Tracing (Event Instrumentation): Tracing, by contrast, is deterministic and event-based. Tools like strace, ftrace, or eBPF attach hooks to specific probe points (such as function entries and exits or system call boundaries). Tracing records every single occurrence of that event along with precise timestamps and parameters. While tracing gives exact counts and catches rare outliers that periodic sampling might miss, attaching high-frequency trace points to hot function paths (like memory allocations occurring millions of times per second) can cause devastating 10x–100x execution slowdowns.

🔬 How Call Stack Sampling Operates in the Kernel
1
Non-Harmonic Sampling Timer Setup The profiler (e.g., Linux perf record -F 99 -p <PID> -g) configures hardware Performance Monitoring Counters (PMC) or a kernel timer to fire at 99Hz. The rate 99Hz is chosen deliberately over 100Hz to prevent harmonic resonance with periodic 10ms operating system timer ticks.
2
Non-Maskable Interrupt (NMI) & Register Freeze When the counter overflows, the CPU generates an interrupt. The CPU freezes execution of the current thread and records the instruction pointer (RIP register).
3
Frame Pointer Stack Unwinding The kernel unwinds the stack using frame pointers (RBP register) or DWARF unwind tables, recording the chain of caller return addresses from leaf to root.
4
Symbol Resolution & Aggregation Hexadecimal memory addresses are matched against the binary's symbol table (e.g., 0x7f4e8b → ExecScan). Identical call stacks are grouped and counted.
Three Profiling & Tracing Scenarios
Obvious Case
Continuous Production CPU Profiling
Sampling production database threads at 99Hz continuously using eBPF, outputting aggregated profile weights to Flame Graphs with undetectable 1% CPU overhead.
Counter-Intuitive Case
Production Outage Caused by Strace
An engineer runs strace -p <PID> on a heavily loaded production API server. Because ptrace context-switches on every syscall, response latency spikes from 5ms to 800ms.
Edge-Case Phenomenon
Omission of Frame Pointers (-fomit-frame-pointer)
A C++ binary compiled with -O3 -fomit-frame-pointer reuses the RBP register for general variables, preventing the kernel profiler from unwinding the stack and yielding a broken flame graph.
📸 Visual Analogy: Strobe Photography vs. CCTV Gate Log
Sampling is like setting up a strobe light flashbulb that snaps a photograph of a bustling factory floor every few seconds. You get an accurate statistical distribution of what workers are doing without slowing them down. Tracing is like stationing a security guard who stops every worker at every door to log their exact name and badge number. The guard captures every entry, but creates a massive line at the entrance.
❌ What People Get Wrong
Assuming that running strace or full event tracing in production is safe because "it's just a diagnostic tool."
Why This Matters
Choosing statistical profiling first allows continuous diagnostic visibility in live environments without risking high-overhead cascading outages.

Module 05

Flame Graphs: Mechanics, Navigation, & Deep Query Diagnosis

Before Brendan Gregg invented Flame Graphs in 2011, profiler outputs were dumped as dense tabular text reports. Engineers had to scroll through thousands of rows of call-tree statistics, trying to mentally assemble deep function call paths. For modern complex runtimes like PostgreSQL or Chromium—which frequently execute call stacks 30 to 60 frames deep—tabular profilers made identifying root bottlenecks nearly impossible.

A Flame Graph converts thousands of sampled call stacks into an intuitive, compact visual hierarchy. Understanding the two axes of a flame graph is the single most important rule of systems visualization:

  • The Vertical Y-Axis (Stack Depth): Shows the ancestry of function calls. The bottom bar is the root function (e.g., main). Above it is the function it invoked (e.g., PostgresMain), climbing upward until the top-most bar represents the leaf function actively executing on CPU when the sample occurred.
  • The Horizontal X-Axis (Sample Population, NOT Time!): Spans the entire sample population. The X-axis does NOT represent the passage of time from left to right! Stacks are sorted alphabetically to merge identical code paths. The horizontal width of any function bar is directly proportional to how frequently that function appeared on the CPU.

On stream, Ben Dickin demonstrated a custom interactive flame graph tool inspecting an actual PostgreSQL query execution profile. We can observe several distinct functional towers:

First, an ExecScan tower calls MD5_text and libcrypto. While developers might worry that cryptography hashing is slowing down their database, looking at the flame graph reveals that the entire libcrypto block occupies only ~12% of the total width. Applying Amdahl's Law, even if you optimized the cryptographic hashing library to run infinitely fast (reducing its time to zero), the overall query would only improve by 12%!

By contrast, look at the wide blocks for ExecCheckIndexConstraints (22% of runtime) and the massive block for heap_insert and pg_fsync (38% of runtime). These wider blocks expose the true leverage points: can we relax non-essential index constraints, or batch transactions to amortize synchronous disk persistence?

Three Diagnostic Interpretations of Flame Graphs
Obvious Case
The Wide Flat Plateau
A leaf function (e.g., hash_search or spin_lock) spanning 70% of the entire graph width, indicating a glaring hot loop consuming the vast majority of CPU cycles.
Counter-Intuitive Case
Narrow Cryptographic Tower (Amdahl's Trap)
Developers spend two weeks optimizing libcrypto assembly, only to realize the flame graph clearly showed it accounted for a modest 10% of total profile width.
Edge-Case Phenomenon
Off-CPU Sleeping Stalls
An on-CPU flame graph looks mostly empty while queries take seconds. Switching to an Off-CPU Flame Graph reveals threads blocked waiting on pthread_mutex_lock or disk I/O.
🏔 Visual Analogy: The Mountain Range Silhouette
A Flame Graph resembles an inverted mountain range where peak height represents call-stack depth and peak width represents CPU consumption. A towering spire that is pencil-thin is just a deeply recursive function that returns quickly. A wide plateau that stretches across half the horizon is where the real energy of the system is being burned.
❌ What People Get Wrong
Believing the X-axis of a flame graph flows chronologically in time from left to right like a timeline recording.
Why This Matters
Understanding that the X-axis is an aggregated, alphabetically sorted sample population prevents misinterpreting code execution order and focuses attention purely on cumulative resource consumption.

Module 06

Systems Trade-offs: Durability (fsync), io_uring, & Zero-Downtime Migrations

In production systems engineering, there are no solutions—only trade-offs. Two of the most profound engineering trade-offs highlighted during the stream involve the relationship between software and storage hardware: Durability versus Throughput, and Schema Governance versus Development Velocity.

The fsync Durability Trade-off: When a database executes an INSERT or UPDATE, it cannot simply declare the transaction committed by writing bytes into OS page memory. If power fails a millisecond later, those unwritten bytes in volatile DRAM vanish forever. To guarantee the Durability property of ACID transactions, the engine must issue an fsync() system call. This forces the operating system to flush all dirty buffers across the storage controller directly into non-volatile NAND flash.

However, fsync() is synchronous and expensive: the calling thread freezes until the physical drive acknowledges magnetic or flash cell commitment. Ben Dickin noted that while disabling fsync yields blindingly fast write performance, it introduces real risk of catastrophic data corruption upon power loss. This compromise is acceptable for ephemeral clickstream logging, but fatal for financial ledgers.

Modern Kernel I/O: io_uring: Traditionally, asynchronous I/O in Linux (libaio) was notoriously flawed and limited. Over recent years, the Linux kernel introduced io_uring, a zero-copy asynchronous interface based on two lockless circular ring buffers shared between Userland and the Kernel (a Submission Queue and a Completion Queue). By eliminating system call context switches and batching I/O requests, io_uring allows databases like PostgreSQL (being adopted in versions 18 and 19) to achieve massive IOPS efficiency gains on NVMe storage.

Zero-Downtime Online Schema Changes: In large-scale systems (such as GitHub, Booking.com, or DigiKala running multi-terabyte tables), running a simple ALTER TABLE ADD COLUMN will acquire exclusive table locks that block incoming queries, instantly cascading into sitewide downtime. Tools like gh-ost (GitHub Online Schema Migrations, invented by Shlomi Noach, who now works at PlanetScale) and Vitess VReplication solve this by building a shadow table, streaming changes asynchronously via binlogs, and executing an instantaneous atomic table swap with zero downtime.

🔄 How Online Zero-Downtime Schema Migrations Work (gh-ost Pattern)
1
Ghost Table Provisioning A shadow table (_users_gho) is created with the desired new schema (new columns, indexes, or altered types) on the live database.
2
Asynchronous Change Log Streaming Instead of placing triggers on the active table (which adds lock contention to production queries), the tool acts as a replication replica, tailing the database binary log (binlog) to capture live inserts, updates, and deletes.
3
Throttled Backfill Iteration Existing historical rows are copied from the original table to the shadow table in small, throttled primary key batches. If database replica lag or CPU exceeds defined thresholds, the migration automatically throttles back.
4
Atomic Table Swap (Cut-over) Once backfill matches live replication, an atomic statement: RENAME TABLE users TO _users_del, _users_gho TO users; executes in milliseconds, completing the migration with zero downtime.
Three Production Trade-off Scenarios
Obvious Case
Synchronous Commit in Banking
Every bank transfer executes a mandatory synchronous fsync to disk before acknowledging the client, ensuring funds are never phantom-lost in a power failure.
Counter-Intuitive Case
Asynchronous WAL for Click Tracking
A high-volume analytics ingest pipeline sets synchronous_commit = off. Write throughput 5x increases, accepting that a kernel crash may lose the trailing 20 milliseconds of user telemetry.
Edge-Case Phenomenon
Storage Controller Capacitor Failure
An enterprise SSD with Battery-Backed Power Loss Protection (PLP) reports immediate fsync completion from onboard volatile DRAM cache, but fails to flush during power outage because internal capacitors dried out.
❌ What People Get Wrong
Believing that modern NVMe solid-state drives are so fast that synchronous disk flushing and locking coordination are no longer significant bottlenecks.
Why This Matters
Balancing durability requirements against throughput limits enables architectures that withstand massive read/write scale without sacrificing data safety.

AMDAHL'S LAW OF OPTIMIZATION
$$S_{\text{latency}} = \frac{1}{(1 - p) + \frac{p}{s}}$$ The potential speedup of an entire system is strictly bounded by the proportion \(p\) of execution time that the optimized component actually consumes.
LITTLE'S LAW FOR QUEUING SYSTEMS
$$L = \lambda \times W$$ The average number of requests in a system \(L\) equals the long-term arrival rate \(\lambda\) multiplied by the average time \(W\) each request spends in the system.

Frequently Asked Questions from the Stream

Why does the flame graph show libcrypto taking only 12% if the query uses MD5 hashing? +
Because cryptographic hashing was only executed on individual row tokens during record projection. The remainder of the execution was occupied by index checks, heap table tuple updates, and write-ahead log synchronization. Never assume a complex function dominates runtime without viewing the measured sample width.
Why choose 99 Hz instead of an even 100 Hz for sampling call stacks? +
Operating system schedulers and periodic background routines frequently operate on round intervals (e.g., every 10ms = 100Hz). Sampling at exactly 100Hz risks phase-locking (harmonic lock-in) with these background tasks, producing skewed profiles. 99Hz or 49Hz breaks this resonance.
If disk latency was still 0.1ms, why did query P99 latency spike to 500ms? +
Because each query had to execute hundreds of disk read operations in sequence. Even when an individual NVMe read takes only 0.1ms, executing 500 sequential physical reads due to cache misses totals 50ms of blocking I/O time per query, backing up connection pools.
When should I use an Off-CPU Flame Graph instead of an On-CPU Flame Graph? +
Use an On-CPU Flame Graph when the system is CPU-bound (high %CPU usage). Use an Off-CPU Flame Graph when software is unexpectedly slow but CPU utilization is low or idle, indicating threads are blocked waiting on locks, disk I/O, or network sockets.

Recommended Next Steps

  1. Audit your production builds: Ensure all critical binaries are compiled with frame pointers enabled (-fno-omit-frame-pointer) so kernel profilers like perf can unwind stacks accurately.
  2. Inspect host memory reservations: Verify that production database nodes run with strict cgroup memory isolation or dedicated instances to prevent noisy neighbors from cannibalizing the page cache.
  3. Run sample profiles: Try running perf record -F 99 -a -g -- sleep 10 on a local Linux development box, and generate a Flame Graph using Brendan Gregg's open-source flamegraph.pl scripts.
