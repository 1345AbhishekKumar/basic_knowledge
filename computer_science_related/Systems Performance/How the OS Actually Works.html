01 / FOUNDATION
Start here

The OS is a layer of useful lies

Why every program needs abstractions over raw hardware.

JIT — abstraction: plain meaning: a simplified promise that hides messy detail. Why exists: hardware is shared and hard to use directly. Example: a process lets code act as if it owns the CPU and RAM. Precise meaning: the operating system enforces the promise in software plus hardware.
JIT — operating system: the layer between programs and hardware. It owns CPU scheduling, memory mapping, and file storage so programs do not fight over them.
JIT — primitive: a building block with fixed behavior you can trust. A process is a primitive for execution. SQLite storage is a primitive for durable data. Good infrastructure is a combination of such primitives into components that work together.

A process is an abstraction the operating system places over hardware so one running application can act as if it owns the computer. The real system runs tens, hundreds, or thousands of programs at once, yet each process gets a simple model for executing instructions, reaching memory, and opening files.

The key abstractions are process, thread, virtual memory, and filesystem. A process is a running instance of a program. A thread is a path of execution inside a process. Virtual memory is the address space a process sees. A filesystem organizes bytes on disk with permissions. Together they form the architecture of the system, and the mechanism that enforces them lives partly in the kernel and partly in hardware such as the MMU.

This combination matters because it removes arbitrary conflicts. Without it, each engineer would have to carve RAM by hand and avoid every other program. The capability to represent each program separately, and to manage communication between components through a clear structure, is what makes large software possible. Custom operating systems for real-time use still keep the same idea: define a small set of trusted primitives, then build on them.

Worked Example: custom real-time control

Problem: A team wants a custom operating system tuned for strict timing. Should they drop the process idea?

Knows / Needs: Knows processes, threads, virtual memory, filesystem exist. Needs to decide what to keep for timing control.

Steps: Step 1: keep the process as the unit of isolation. Step 2: keep the scheduler for ordering work. Step 3: keep virtual memory for protection. Step 4: tune time slices and priorities for timing.

Result: The custom system still uses processes, only with tighter scheduling rules.

Why this makes sense: The process contract removes manual resource fights, so tuning one mechanism beats rebuilding every program.

Pitfall: the OS is not just a library

Myth: The operating system is a helper library programs call when convenient.

Correction: It is the authority that owns hardware state, switches modes, and can deny access.

Why confusion happens: System calls look like normal function calls, so the mode switch and permission check stay invisible.

02 / HARDWARE
Physical base

CPU, RAM, and disk set the limits

The working set lives in RAM, RAM spills to disk, and history explains why.

JIT — CPU (Central Processing Unit): the chip that executes instructions. A core is one independent execution lane. Modern chips hold 16 or 32 cores, each running its own instruction stream.
JIT — RAM (Random Access Memory): fast byte storage holding the working set, the data and instructions a program touches right now. Contents vanish on power loss.
JIT — working set: the pages and bytes a program actively reads and writes during a phase of execution.

Hardware is simple in shape. The CPU executes instructions on its cores. RAM holds the working set that cores read and write at speed. The disk holds what RAM cannot fit and keeps bytes after power loss. Requests flow from cores to RAM, and RAM spills over to disk when space runs short.

This diagram shows the same path used in every later module. A core asks RAM for bytes, computes, then writes results back. When RAM fills, the system moves cold pages to disk and brings them back on demand. The mechanism is old: 50, 60, and 70 years ago a machine ran one program from a punch card from start to finish, which wasted the fast CPU whenever the program waited on slow storage.

  • Cores execute: each core runs instructions independently and fast.
  • RAM stages: the working set sits in RAM for quick core access.
  • Disk backs: RAM spills cold data to disk for capacity and survival.
  • Speed gap drives design: waiting on disk or network while cores idle is the waste multiprogramming fixes.

Worked Example: from punch card to shared machine

Problem: An early machine runs one punch-card program at a time. Why is that wasteful once CPUs get fast?

Knows / Needs: Knows cores execute in nanoseconds while disk and network take far longer. Needs a reason to share one machine.

Steps: Step 1: run one program and watch the CPU stall on every disk read. Step 2: admit a second program whose working set already sits in RAM. Step 3: let the second program use the cores during the stall.

Result: Total idle time falls because fast execution overlaps slow waiting.

Why this makes sense: The speed gap is physical, so overlapping work is the only way to keep cores busy.

Pitfall: more cores do not remove sharing

Myth: With 32 cores, each program gets its own core, so no sharing logic is needed.

Correction: Systems run hundreds of processes, so cores, RAM, and disk are still shared and scheduled.

Why confusion happens: Small demos show four programs on four cores, which hides the crowded real case.

03 / MULTIPROGRAMMING
Sharing time

Context switching lets one machine run everything

Time slices, the scheduler, and overlap of fast compute with slow IO.

JIT — context switching: saving one process state off the CPU and loading the next, so many programs take turns. Time-sharing is the policy of splitting CPU time into small slices.
JIT — scheduler: the kernel component that decides which ready process runs next, on which core, and for how long. It tracks state and complexity of hundreds of choices.

Oftentimes a program runs very fast on a CPU and then must wait on disk or network IO. Without sharing, the CPU idles. Context switching fixes this: the system gives each program a short slice, saves its registers and pointers, then loads the next program. Even one core can run chat, music, database, and terminal programs together by rotating slices of 1 millisecond or 10 milliseconds, each executing thousands or millions of instructions.

With four cores, the scheduler can place the chat window on one core, music on the next, the database on the third, and the terminal on the fourth. With one core, the same four programs take turns. The scheduler handles the complexity of who waits, who runs, and how to overlap computation with slow IO so no fast cycle is wasted.

Worked Example: one core, four programs

Problem: One core must run chat, music, database, and terminal at once. How?

Knows / Needs: Knows each slice is 1 ms or 10 ms with thousands or millions of instructions. Needs a rotation that keeps music smooth while the database waits on disk.

Steps: Step 1: run chat for one slice. Step 2: save chat state and run music. Step 3: run database until it blocks on disk IO, then skip it. Step 4: run terminal, then repeat.

Result: All four progress because blocked programs yield while ready ones consume slices.

Why this makes sense: Fast CPU cycles would otherwise idle during slow IO, so rotation recovers them.

Pitfall: slices are not parallelism

Myth: Time-sharing means four programs literally execute at the same instant on one core.

Correction: One core executes one instruction stream at a time; fast rotation only creates the illusion.

Why confusion happens: Interaction feels instant, so the save-and-restore work underneath stays hidden.

04 / WHY PROCESSES
Isolation promise

Each process pretends it owns everything

The argument for isolation, with the video editor under attack.

JIT — isolation: the kernel blocks one process from reading or writing another process memory unless sharing was explicitly arranged.

Consider writing a custom video editor. You want to think only about frames and cuts, not about which slice of RAM the music player uses. The process gives you that: your editor acts as if the CPU is yours, the address space is yours, and RAM feels infinite or near infinite. The same promise covers Unix systems such as Mac and Ubuntu, and Windows offers more or less the same abstraction.

Without the promise, every program would need to negotiate arbitrary RAM and disk regions with every other program. Worse, a malicious chat program could read the editor RAM instead of its own. The operating system prevents this conflict by mapping each process to disjoint physical pages and checking permissions on every access. You identify your own bytes by virtual address; the kernel identifies the true physical owner behind the scenes.

Private slices plus one malicious access
The kernel mapping blocks the cross-read the arrow attempts.
  • Private view: each process sees full addresses from zero upward.
  • Separate backing: the kernel maps views to disjoint RAM pages.
  • Checked access: reads outside your map are denied.
  • Simple engineering: programs ignore each other by construction.
Worked Example: malicious chat versus editor

Problem: The chat program tries to access video editor RAM instead of its own slice.

Knows / Needs: Knows each process owns a private virtual space. Needs to see why the read fails.

Steps: Step 1: chat issues a load from an editor virtual address. Step 2: the MMU consults the chat page map, not the editor map. Step 3: no valid physical owner exists for chat at that entry, so the kernel denies the access.

Result: The editor bytes stay intact; the chat program receives a fault.

Why this makes sense: Ownership lives in per-process maps, so a virtual address only has meaning inside its own process.

Pitfall: infinite memory is an illusion

Myth: A process really owns all RAM from zero to billions of addresses.

Correction: It owns a virtual range; physical pages are granted on demand and shared hardware stays protected.

Why confusion happens: Code can name any virtual address, which feels like ownership until a miss reveals the mapping.

05 / CREATION
Birth of processes

Fork clones, exec becomes someone new

How boot, fork, exec, and ELF load turn bytes into running programs.

JIT — fork: a call that clones the calling process into an almost identical child. The underlying mechanism on Linux is the clone path. PID (Process Identifier) is the number that tells parent and child apart.
JIT — exec and execve: calls that replace the current program text with a new executable file and start it. execve is the precise variant that takes path, argument list, and environment. ELF (Executable and Linkable Format) is the compiled binary layout produced by tools like GCC: a header plus pages of initial program data, or data for an interpreter.

When a machine boots on a Unix system, an initial process starts and every later process is forked from it, whether kernel or user work. Calling fork makes an identical copy of the video editor process except for a unique PID, a different parent, its own copy of the parent descriptors, and zeroed resource usage. You can recognize this contract in the man pages: man fork states the child is an exact copy apart from those listed differences.

A forked copy running the same code is rarely the goal. The child then calls execve with a path to an executable object file. The call transforms the process by reloading the text area of memory with the new program and executing it instead. Man exec describes the new process as constructed from an ordinary file, either an executable object file with an identifying header followed by pages, or interpreter data. That is how one running image becomes a different program without creating a third process.

Problem: The running video editor must start a database helper program.

Knows / Needs: Knows fork clones and execve replaces. Needs a new program without disturbing the editor.

Result: Two processes exist: the original editor and the new database program.

Why this makes sense: Clone-then-replace reuses identity setup and swaps only the code being executed.

Pitfall: fork alone does not start new code

Myth: Calling fork directly loads a different program.

Correction: Fork only duplicates; execve is what loads the new ELF text.

Why confusion happens: Tutorials say fork plus exec creates processes, which blurs the two halves.

06 / INSIDE
Process anatomy

User space runs code, kernel context guards truth

Modes, memory halves, and file descriptors via open.

JIT — user space versus kernel context: user space holds the program, libraries, heap, and user stack. Kernel context holds the kernel stack plus per-process metadata the kernel trusts.
JIT — user mode versus kernel mode: user mode has limited hardware rights. Kernel mode has full rights but only runs kernel code, entered for disk IO, network sends, and similar privileged work. The systems programming course idea is exactly this split: normal functions stay in user mode; requests that touch hardware switch modes.
JIT — file descriptor: a small identifier number returned by open (fopen wraps it in C) that names one open file for a process, with permissions checked by the kernel.

In user mode the process executes its executable code and libraries. When it needs disk IO or a network send, it switches into kernel mode and uses a separate kernel stack because a different function sequence runs there. The kernel also stores metadata: PID, UID (User Identifier), time accounting, and the table of file descriptors. Man open documents the deal: give a path plus read or write argument, receive a descriptor number back.

A single-threaded process has one user stack and one kernel stack. A multithreaded process keeps multiple user stacks and multiple kernel stacks inside one shared address space, which the next modules use. To identify an open file, user code presents the descriptor; the kernel maps it to the true file object and checks whether the requested read or write is allowed.

Correction: Each process has its own table, so numbers only match by copied inheritance.

Why confusion happens: Small examples always show 0, 1, 2, which look universal.

07 / MEMORY LAYOUT
Stack and heap

Stack grows one way, heap fragments the other

Addresses 0 to 0x200 in hexadecimal, and why opposites help.

JIT — hexadecimal: base-16 numbering using 0-9 plus a-f. Addresses such as 0x200 or 0x2C8 are hexadecimal values, compact for byte offsets.
JIT — stack frame: one function call record holding locals and return state. Heap object is any separately allocated value such as an array, graph node, hashmap entry, or JS-style object.

Take a tiny virtual space from address 0 to address 0x200 in hexadecimal. Near the bottom sit program text, constants, and fixed data: the adds, moves, and jumps the CPU executes. Above that, two regions grow toward each other. The program stack grows and shrinks as functions call and return. The heap holds objects that outlive one call and are passed around.

A deep recursion can stack hundreds or even thousands of frames, then release them as calls return. Heap use also rises and falls, but by a different technique: allocations and frees leave fragments, so used and free chunks interleave instead of forming one clean pile. The opposite growth keeps fixed code stable while both flexible regions share the middle without a preset split.

Worked Example: recursion versus object churn

Problem: One task recurses deeply; another builds many short-lived objects. Where does pressure land?

Knows / Needs: Knows the space spans 0 to 0x200 with text at the bottom. Needs to place both growth patterns.

Steps: Step 1: run recursion and watch frames pile into hundreds or thousands. Step 2: return and watch the stack release. Step 3: allocate arrays and hashmaps and free every other one. Step 4: observe heap fragments rather than one clean block.

Result: Stack pressure is tall but temporary; heap pressure is scattered and needs reuse of holes.

Why this makes sense: Order of freeing decides fragmentation: strict order compacts, arbitrary order scatters.

Pitfall: heap is not a tidy pile

Myth: Freed heap bytes instantly rejoin one free block.

Correction: Live neighbors pin holes in place, so free space fragments.

Why confusion happens: Stack behavior teaches clean push and pop, which heap does not follow.

08 / THREADS
Parallel selves

Processes isolate, threads share and sprint

Multiprocess versus multithreaded work, and Linux tasks.

JIT — thread: an execution path inside a process with its own stack but shared address space and heap. Task is the Linux name covering both processes and threads in one scheduler structure.

A process can hold exactly one thread: one user stack plus one kernel stack. It can also hold 2, 5, 10, or 100 threads, each with its own user and kernel stacks but sharing the same virtual addresses and heap. Because threads share, switching between them is lighter and cheaper than switching whole processes, yet coordination grows since one bad write can affect all siblings. Threads on different CPU cores can execute simultaneously inside one process.

Two designs use this differently. A multiprocess design forks itself and links the pieces with message passing communication on the system or with shared memory. A multithreaded design stays in one process and spins up threads that read and write the same heap directly. On Linux both are represented as tasks; the main difference is how much address state they share.

Problem: One process must handle chat IO and music decode at the same instant.

Knows / Needs: Knows each thread owns a stack and shares the heap. Needs true simultaneity.

Steps: Step 1: create thread A for chat and thread B for music. Step 2: scheduler places A on core 0 and B on core 1. Step 3: both step through their own stacks while reading shared tables. Step 4: join results through the shared heap.

Why this makes sense: Separate stacks allow separate positions; shared memory allows instant handoff.

Pitfall: sharing is not free safety

Myth: Threads are always better because switches cost less.

Correction: Shared heap means one thread bug can corrupt all threads in the process.

Why confusion happens: Lower switch cost is visible in benchmarks; coordination cost appears later under load.

09 / LIFECYCLE
States of work

Ready, running, waiting, zombie

How the scheduler tracks 100 processes on 4 or 8 cores.

JIT — process state: the scheduler label for what a process needs next. Ready wants CPU. Running holds CPU. Waiting sleeps on network or disk IO. Zombie is killed but awaits kernel cleanup.

One system may try to run 100 processes at once with only 4 cores, or 8 cores on a larger box. It cannot actively run them all together, so the scheduler tracks each state. A ready process wants more CPU time and nothing blocks it. A running process currently executes. A waiting process sleeps until its network request or disk IO completes, then moves back to ready. A killed process becomes a zombie until the operating system reclaims its entry.

Transitions are constant. Running code that blocks goes to waiting. IO completion moves it to ready. The scheduler picks the next ready entry for each free core. Termination moves it to zombie, and cleanup removes it. This staged dance is why interactive programs stay smooth while background work waits its turn.

Worked Example: 100 processes on 4 cores

Problem: 100 processes compete for 4 cores while several wait on disk.

Knows / Needs: Knows ready, running, waiting, and zombie meanings. Needs an order that avoids idle cores.

Steps: Step 1: mark 4 running and the rest ready or waiting. Step 2: when a runner blocks on disk, move it to waiting. Step 3: promote the next ready process to running. Step 4: reap finished ones from zombie.

Result: Cores stay busy while waiters sleep without polling.

Why this makes sense: State labels let the scheduler skip sleepers and pick only runnable work.

Pitfall: zombie is not running

Myth: A zombie still consumes CPU time.

Correction: It is dead code awaiting table cleanup; it holds no core.

Why confusion happens: It still appears in listings, so it looks alive.

10 / VIRTUAL MEMORY
Translation machinery

MMU turns virtual wishes into physical pages

Pages, the 0x2C8 walkthrough, miss path, and tiered trees for 48-bit spaces.

JIT — MMU (Memory Management Unit): the hardware-plus-kernel proxy that translates each virtual address into a physical address using the per-process page map.
JIT — page and page table: a page is the transfer unit, 4 KB to 16 KB, with some systems using 2 MB large pages. The page table maps virtual page numbers to physical page slots plus flag bits. The offset inside the page passes through unchanged.

The CPU speaks virtual addresses such as 0x12345 and asks to store the number 10 there. The request does not reach RAM directly. It goes to the MMU proxy, much like a database proxy that routes app queries to the right connection. The MMU looks up the program page map and may transform the address to a very different physical slot such as 83145, then completes the store. Individual instructions may ask for one byte or an 8-byte range, but mapping, disk transfer, and protection all happen per page.

Follow 0x2C8 exactly. The high hexadecimal digit selects page table index 2; the low part 0xC8 is the page offset. At index 2 the entry holds a D (dirty) bit and an R (resident) bit plus a physical slot. D tells whether the page changed since load from disk, so eviction knows if a writeback is needed. R tells whether the page is actually resident in memory. Here R is 1, so the page is present, and the slot reads 9. The MMU goes to physical page 9, adds offset 0xC8, grabs the requested bytes, and loads them into register 1. A later example stores the contents of register 4 into address 1352 by the same index-plus-offset translation.

If R were 0 instead of 1, the kernel would fetch the backing chunk from disk, move the process into a waiting and sleeping state, run other work, then deliver a trap when the bytes are ready, flip R to 1, and finish the lookup. Wall-clock time grows for that access, but overlap hides the stall. The system keeps one page map per executing process and never lets two processes own the same RAM region at once, which is the protection half of the design. Modern 64-bit x86 uses 48-bit addresses, far too large for one flat 16-entry style array per process, and 99.9 percent of that sparse space sits unused. The fix is a tiered tree: large chunks split into smaller chunks across levels, so only used branches consume entries. MAPAP, the chat spelling of mmap, names the related file-backed mapping idea: map file contents into memory so reads and writes act on addresses; it is deferred here except as vocabulary.

Myth: Virtual page 2 and page 3 sit next to each other in RAM.

Correction: Slot numbers are assigned where free space exists, so 2 can map to 9 while 3 maps elsewhere.

Why confusion happens: Virtual numbers look sequential, which suggests physical order that mapping deliberately breaks.

Key Answers

  • Process — a running program with private CPU view, memory view, and files, enforced by the kernel.
  • Context switching — saving one program and loading the next so many share few cores in slices.
  • Scheduler — the kernel chooser that orders ready work across cores and tracks waiting.
  • Fork — the clone call that duplicates a process except identity and accounting.
  • Exec — the replace call, precise form execve, that loads a new ELF program over the old text.
  • File descriptor — the small number open returns to identify one open file for later reads.
  • Stack — ordered call frames that grow and shrink as functions enter and return.
  • Heap — shared objects like arrays and hashmaps that fragment with arbitrary free order.
  • Thread — a stack plus position inside shared addresses and heap, lighter to switch.
  • Process state — ready, running, waiting on IO, or zombie awaiting cleanup.
  • Virtual memory — private addresses translated to physical pages on every access.
  • Page — the 4 KB to 16 KB unit of mapping and disk transfer, sometimes 2 MB large.
  • MMU — the proxy hardware and kernel logic that maps virtual pages to physical slots.
  • Page table — the per-process map from index to slot plus D dirty and R resident flags.

FAQ — Still Confused?

What is the difference between fork and exec?
Fork clones the calling process into an identical child apart from PID, parent, descriptor copies, and zeroed usage. Exec, precise form execve, replaces the text area with a new ELF executable and starts it. Remember: fork duplicates who runs; exec changes what runs.
Why not run one program per computer?
Early punch-card machines did exactly that and idled fast CPUs during slow disk waits. Oftentimes one program blocks while another could compute, so sharing one system across thousands of processes is cheaper and faster. Remember: sharing recovers idle cycles.
What do threads share exactly?
Threads in one process share virtual addresses and the heap, including arrays, graphs, and hashmaps, but each keeps its own user and kernel stacks and register position. That is why two threads can run on different cores simultaneously yet corrupt each other with one bad write. Remember: share the heap, privatize the stack.
Why do stack and heap grow in opposite directions?
Fixed code sits low near address zero in hexadecimal layout 0 to 0x200. Letting the stack grow down and the heap grow up shares the middle flexibly: deep recursion with hundreds or thousands of frames borrows space without starving objects, and reverse. Remember: opposites delay collision.
What happens on a page miss when R is 0?
The kernel fetches the backing bytes from disk, parks the process in waiting and sleeping state, runs other ready work, then sends a trap when the page is resident, sets R to 1, and retries the instruction that loads register 1 or stores register 4 to 1352. Wall-clock time grows for that access but overlap hides it. Remember: miss means sleep, then retry.
Why do 48-bit address spaces need tiered trees?
A flat array with one entry per page over 48-bit on 64-bit x86 would need billions of slots per process, while 99.9 percent of the sparse space sits unused. A tree stores only live branches: top levels name large chunks, lower levels name pages like index 2 with offset 0xC8, slot 9, D and R bits. Remember: trees pay only for used branches.
What is mmap or MAPAP versus regular reads?
MAPAP is the chat spelling of mmap, the file-backed mapping call. Regular reads copy bytes through explicit open, read, and write calls with descriptor numbers. Mmap maps file contents into the address space so loads and stores act on memory while the kernel pages file data in 4 KB to 16 KB units behind the scenes. Remember: mapping turns file offsets into addresses.
