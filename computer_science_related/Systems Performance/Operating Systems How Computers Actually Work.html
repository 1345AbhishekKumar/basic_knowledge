01 / FOUNDATION
Why this matters

The OS Dictates Performance

Hardware cannot run itself. The operating system (OS) is the interface between raw devices and every program, and its choices set the ceiling for speed.

A CPU (Central Processing Unit) executes instructions. RAM (Random Access Memory) holds live data. Disks, networks, and input devices move bytes in and out. None of these know about Postgres, Node, or your editor. The kernel, the always-running core of the OS, boots first, takes over the CPU, and lends these resources out safely.

That is why performance tuning is OS tuning. A database read is a disk request through the kernel. An app stall is often a scheduling or memory-mapping decision. Learn the interface and you can predict cost.

Hardware belongs to the kernel; apps borrow it
Every app path crosses the OS before touching a device.
  • Hardware provides raw ability: compute, store, move bytes.
  • The kernel owns those devices from boot onward.
  • Apps borrow through gated requests, never by direct wiring.
  • Each borrowing choice adds latency, copies, or queueing.

Worked example: why a Postgres read is an OS story

Problem: A query feels slow. Is it the query or the machine?

What we know / need: Know Postgres runs on top of the OS. Need the path a read takes.

Approach: Follow the bytes across the boundary.

Steps: 1) Postgres asks for rows. 2) The kernel maps the request to disk blocks. 3) Disk latency plus cache state plus CPU turns decide arrival time.

Result: Most wall time lives in OS-mediated steps, not SQL parsing.

Why this makes sense: The OS owns the disk and the scheduler, so its abstractions dominate cost.

Pitfall

Treating the OS as free plumbing. Every abstraction — files, memory, turns on CPU — has a measurable price.

Misconception

Myth: Only OS implementers need OS internals.
Correction: Anyone tuning databases or fine-grained app speed uses them daily.
Why confusion happens: Frameworks hide the kernel until a latency spike forces you to look down the stack.

02 / MAP
See the stack

Layers of Execution

Five concentric layers separate your keystrokes from silicon. Name each layer and you always know where a request is.

From the center out: hardware at the core, then the kernel touching it directly, then system calls as the gated doorway, then system libraries (often C or C++ helpers with the OS), then user space where Rust, TypeScript, Go, Python, and JavaScript programs live. Applications is another name for that outer ring.

System libraries are convenience wrappers. In some cases they call down into system calls; in some cases they do purely local work and never enter the kernel. Applications may call libraries only, or call system calls directly, because both live in user mode.

Five rings from silicon to program
Step outward with the buttons to cross each boundary.
Hardware: bare CPU, RAM, disk, network. Everything else borrows from here.
  • Hardware is the innermost truth: it only runs instructions and moves bytes.
  • The kernel is the first program at boot and the only direct device driver.
  • System calls expose small gated functions that switch into the kernel.
  • Libraries wrap calls for comfort; user space holds your processes and threads.

Worked example: camera bytes reach OBS

Problem: A camera is plugged in over mini-HDMI in and USB-C in. How do its bytes appear in OBS?

What we know / need: Know user code cannot touch the port. Need the crossing path.

Approach: Walk the rings outward.

Steps: 1) OBS in user space calls a library. 2) The library issues a system call. 3) The kernel streams bytes into a buffer in RAM, then pipes them up.

Result: OBS projects a virtual camera without ever driving hardware directly.

Why this makes sense: Each ring adds safety and portability; only the kernel speaks the device protocol.

Pitfall

Calling a library and assuming you avoided the kernel. Many wrappers still cross; check whether the path needs hardware.

Misconception

Myth: User space talks to disks and cameras directly.
Correction: It always crosses system calls into the kernel for device work.
Why confusion happens: Calls look like normal functions, hiding the mode switch inside.

03 / MACHINE
What CPUs run

From Code to CPU Instructions

CPUs speak tiny timed steps. Languages, compilers, and runtimes exist so you never hand-place those steps yourself.

A CPU runs one instruction after another: add register 1 and 2 into 3, subtract, move value 100 into memory location 4. Vendors differ — Intel versus AMD define different exact sets — and families range from about 50 to hundreds of operations. This family choice is called CISC (Complex Instruction Set Computer) versus RISC (Reduced Instruction Set Computer), and each instruction takes a different amount of time.

Low-level C or C++ compiles to assembly, then an assembler turns it into executable bytes. High-level JavaScript, Python, or TypeScript runs inside a virtual machine or runtime environment, but that runtime is itself just CPU instructions. Systems programming lives here: close to assembly, timings, and the hardware perspective. Pretend a single-core CPU here to keep reasoning simple; this deliberately simplistic view keeps complexity low before multi-core chips that run several things at once return in module 9.

Human code narrows to timed steps
Each stage removes freedom and adds machine truth.
  • Write control flow: functions, classes, ifs, whiles, recursion, threads.
  • Compile or interpret down to a small timed instruction language.
  • Execute sequentially on one core; timings differ per operation and vendor.
  • Trust runtimes, but remember they are CPU instructions underneath.

Worked example: move 100 into memory

Problem: Store value 100 at memory location 4.

What we know / need: Know high-level assignment; need the machine form.

Approach: Lower one level at a time.

Steps: 1) Write x = 100. 2) Compile to mov 100 -> [4]. 3) CPU executes the move in its allotted cycles.

Result: One line becomes one timed hardware act.

Why this makes sense: Abstractions compile away; only timed steps remain.

Pitfall

Memorizing gate layouts for adders instead of learning instruction costs. Good engineers know timings and effects; few recite logic gates.

Misconception

Myth: Interpreted code escapes the CPU.
Correction: Virtual machines and runtimes are compiled programs executing instructions too.
Why confusion happens: The extra layer hides the final lowering step.

04 / PERMISSION
Two modes

Kernel Mode vs User Mode

Same processor, two permission levels. Your code lives in the restricted one and borrows power through gates.

User mode (also called user space execution) is where Rust, TypeScript, or Python processes start by default, single or multi-process, single or multi-threaded. There you can run classes, function calls, loops, and iterations using CPU plus RAM. Kernel mode is the privileged level where the OS manages input-output (IO), virtual memory, and devices, with its own program stack just like user mode has.

The split is about permissions plus layers of abstraction. Pure computation stays local. The moment you need disk, network, or device bytes, you must cross into the kernel. That crossing is a system call.

  • Do CPU-plus-RAM work locally with no crossing.
  • Issue a system call when hardware is needed.
  • Resume in user mode when the kernel returns bytes or status.

Worked example: loop versus download

Problem: Which of these two needs the kernel: summing an array or fetching a file?

What we know / need: Know both run in user space. Need the hardware test.

Approach: Ask whether a device is involved.

Steps: 1) Sum touches CPU and RAM only, so it stays local. 2) Fetch needs disk or network, so it crosses the gate.

Result: Same process, two paths: local versus gated.

Why this makes sense: Permissions follow hardware, not code size.

Pitfall

Assuming slow code means slow CPU. Often the cost is crossings plus device waits, not arithmetic.

Misconception

Myth: Kernel mode is a different computer.
Correction: It is the same process and CPU at a higher privilege with a separate stack.
Why confusion happens: Diagrams draw two boxes, suggesting two machines.

05 / GATEWAY
The OS API

System Calls: Small Gates, Huge Power

About one hundred tiny functions guard all hardware. Learn the famous six and the rule that keeps the set small.

A system call looks like a normal function but switches into kernel mode. The famous set: read and write move bytes to and from disk, open and close bracket file use, fork clones a process, exec replaces its binary, mmap (memory map) maps files from disk into memory for direct access, and stat gathers statistics. Systems typically hold around one hundred, not thousands, because designers refuse endless growth.

Where it is needed: consider saving a photo in an editor. Without a shared gate every app would reimplement drive protocols. Resource constraint: hundreds of SSD (Solid-State Drive) and HDD (Hard Disk Drive) models speak different protocols, latencies, and quirks; no app team can track them all. What breaks without it: every program ships its own buggy driver, disks corrupt, and modern systems of millions of lines collapse into chaos. Unix keeps order with do-one-thing-well: one call opens, one closes, one reads, one writes; libraries then combine them.

App or library, same gated doorway
Both callers live in user mode; the kernel serves.

  • Name the hardware need: read, write, new process, mapping, stats.
  • Pick the single-purpose call; never expect one call to do everything.
  • Call directly or through a wrapper, knowing both start in user mode.
  • Handle the return and errors; the kernel reports, you decide.

Worked example: fork then exec launches an app

Problem: Start a new and different program from a running one such as a browser.

What we know / need: Know fork copies the caller wholesale except PID (Process Identifier) and small details. Need a different binary running.

Approach: Clone, then replace.

Steps: 1) Call fork with no arguments; two processes now exist. 2) In the child, call exec with the new binary. 3) The child image becomes the new program; the parent continues.

Result: One pattern launches anything while reusing process setup.

Why this makes sense: Copy is cheap and uniform; replacement gives variety. The PID return value tells parent from child.

Pitfall

Forgetting fork copies whoever called it. Call from the wrong process and you clone the wrong world.

Misconception

Myth: More system calls would be better.
Correction: A small stable set prevents driver sprawl and keeps behavior learnable.
Why confusion happens: Libraries look like endless calls, but most never enter the kernel.

06 / BYTES
Files are an illusion

Files, Descriptors, Buffers and IO Errors

A disk holds a trillion ones and zeros. The file system turns that desert into named files, and read turns files into bytes you own.

A file descriptor is a small integer ticket. Call open and the kernel hands one back; present it on every later call. read attempts to read nbytes of data from the object referenced by the descriptor into the buffer pointed to by buff. You must allocate that buffer first: a big array on the stack for small reads, or heap memory via malloc or calloc for large ones.

Errors are integers with names. EIO means an IO error hit the file system, including an orphaned process group case. EAGAIN means a file marked non-blocking had no data ready — the async path that refuses to wait — so try again later. Blocking waits; non-blocking returns immediately.

Open, then read into memory you own
No buffer, no place to put bytes.

Non-blocking IOStay responsiveReturns EAGAIN if emptyServers, async loopsCaller retries later
  • Open first; keep the returned descriptor.
  • Allocate buff for exactly the nbytes you will ask for.
  • Call read with fd plus buff plus nbytes.
  • Branch on success versus EIO versus EAGAIN.

Worked example: read 4096 bytes safely

Problem: Fetch one 4-KB page from disk.

What we know / need: Know the signature needs fd, buff, nbytes. Need owned memory.

Approach: Reserve, then request.

Steps: 1) fd = open(path). 2) Stack char buff[4096] or heap malloc(4096). 3) read(fd, buff, 4096); on EAGAIN retry, on EIO report.

Result: Bytes land in memory you control, or a named error explains why not.

Why this makes sense: The kernel never guesses where to write; you supply the destination.

Pitfall

Reading before opening, or passing a tiny buffer for a large nbytes. Both corrupt results or fail the call.

Misconception

Myth: EAGAIN means the disk broke.
Correction: It means no data was ready on a non-blocking object — try again.
Why confusion happens: All errors look alike until you read the manual entry.

Recall check (retrieval): Recite the open, descriptor, buffer, nbytes order from memory. Reading the manual documentation until you understand each argument is the sophisticated habit; don't guess the order.

07 / OBSERVE
See it live

top, btop and Manual Pages

Two live monitors plus the built-in manual turn abstract calls into numbers you can watch and verify.

top is simple, rudimentary, and usually preinstalled. It lists every running process with PID (Process Identifier), CPU percent, run time, and memory use. Brave looked heavy here because streaming plus chat burns cycles. btop (like htop) is installed with a package manager such as brew install btop; it adds sorting by metrics, per-core histories, GPU percent, and a calmer layout. On the M4 Max box with many cores and 36 GB of RAM, about 15 GB were in use and 20 GB sat available, with part of the rest held as cache.

CPU percents can disagree. One tool may scale to a single core while the other scales to all cores, so the same Brave process shows two numbers. The sophisticated man documentation resolves the rest: man read alone shows the shell builtin (section 1, user commands); man 2 read, man 2 open, and man 2 fork show true system calls; section 3 holds library functions such as scanf; section 6 holds games and demos such as banner. Use apropos when you forget the section. When speed matters, this manual is the source of truth for arguments and errors. Don't trust a percent until you understand its denominator; that perspective removes a complicated-looking discrepancy.

08 / ISOLATION
One program, many lives

Processes and Virtual Memory

A program is static ink on disk. A process is that program alive, with private memory and turns on the CPU.

Engineers say source is C, Ruby, or JavaScript, but the program is really the compiled bytes — or for interpreted languages, the interpreter that will run your code. A process is a program under execution: loaded live and granted CPU cycles. OBS may hold several processes for mics and cameras; Brave plus Helium plus Spotify plus QuickTime plus Postgres show five, while the box may carry one hundred.

Every process receives its own virtual memory space. The OS tells OBS, Brave, and Helium that each owns all RAM, plus a near-infinite range — 2^64 or 2^48 depending on address width — far larger than fitted memory. On the 64-bit chips in modern laptops this gives simplicity for coders plus security through isolation. Don't mistake the illusion for fitted RAM: behind the scenes the OS maps slices to real RAM, a distinct memory-management component whose full complexity, documentation, and sophisticated edge cases get a later stream. The companion detail that Postgres starts a new process per connection while MySQL starts a new thread per connection already hints at performance costs. From the programming perspective this looks complicated, but the contract is simple to understand.

09 / TIME
Who runs next

CPU Scheduler: Slices, States and Priorities

One core runs one thing at a time. The scheduler fakes simultaneity with millisecond turns, tracked states, and priorities.

The CPU scheduler (also called process scheduler) is the kernel part that decides what runs, for how long, and when. Pretend one core: OBS gets a turn, then Brave, then a new Postgres query for half a millisecond, then Spotify fetching the next song chunk, then Helium background work. Each turn is a very short time slice — 1 ms, sometimes 0.5 ms or 5 ms — yet at billions of cycles per second that still holds millions of instructions, or a couple thousand in the smallest windows.

Every switch is a context switch with real overhead: reset CPU registers, disturb caches (thrash), and change which virtual memory view is active. Where it is needed: consider music playing while a query lands during a stream. Resource constraint: one core cannot do both at once, and naive equal sharing ignores urgency. What breaks without it: audio stutters, queries stall, and interactive apps freeze because the wrong process holds the core.

Worked example: who runs in the next 3 ms

Pitfall

Believing round-robin equal shares suffice. Ignoring priority and waiting states wastes turns on processes that cannot proceed.

Misconception

Correction: Waiting processes cost no CPU; only readyplus-switch costs matter.
Why confusion happens: Task lists count sleepers alongside runners.

Key Answers

  • Kernel — the always-running core that owns the CPU, memory, disk, and devices and serves requests.
  • User mode — restricted execution for your code; it can use CPU and RAM but must ask for hardware.
  • System call — the gated function doorway from user mode into kernel mode for hardware work.
  • System library — helpful wrapper layer; some functions call the kernel, some never leave user space.
  • Process — a program under execution: code loaded live plus memory plus scheduled CPU turns.
  • Program — static code on disk (or its interpreter) before it is loaded and run.
  • fork — clone-yourself call with no arguments; parent and child differ only by returned PID.
  • exec — replace the current process image with a different binary; paired with fork to launch apps.
  • File descriptor — integer ticket from open that later read and write calls must present.
  • Buffer — caller-owned memory sized for nbytes; too small means truncated or failed reads.
  • Virtual memory — each process sees private, near-infinite memory while the OS maps real RAM behind the scenes.
  • Scheduler — kernel decider that hands short CPU turns to ready processes by priority and state.
  • Time slice — a millisecond-scale turn; at billions of cycles per second it still runs millions of instructions.
  • Context switch — the costly swap between processes that clears registers and disturbs caches.
  • Ready state — queued and able to run, only waiting for the scheduler to pick it.
  • Waiting state — blocked on disk, network, or user input until an interrupt wakes it to ready.
  • Zombie — the book name for a killed, dead process awaiting cleanup; sleep matches waiting.
  • Priority and nice — scheduler hints about importance; Windows has 32 levels, macOS 128, Linux uses nice.
  • man page — the source-of-truth manual; read section 2 for calls like read, open, and fork.
  • top and btop — live monitors showing PID, CPU percent, time, and memory; btop adds per-core and GPU views.

Still Confused? Frequently Asked Questions

Do I need transistor-level architecture before learning the OS?

No. Know that CPUs run timed instructions and that layouts differ by vendor. That is enough to grasp permissions, calls, and scheduling. Deeper gate-level detail helps later but never blocks this lesson. Remember: implications flow down the stack.

Why only about one hundred system calls?

Long-lived systems stay small on purpose. One call opens, one closes, one reads, one writes, following the do-one-thing-well rule. Libraries then combine those few primitives into richer behavior. Fewer gates means fewer bugs and faster learning.

Why does read need a file descriptor and a buffer?

The descriptor proves you opened the object; the buffer proves you reserved space. Without the ticket the kernel cannot find the file, and without nbytes of memory it has nowhere to put results. Allocate on the stack for small reads or the heap with malloc or calloc for large ones.

Why do top and btop disagree on CPU percent?

One may scale to a single core while the other scales to all cores on a many-core machine such as the M4 Max. Both read the same processes but normalize differently. Check per-core views before concluding an app is overloaded. Remember: percent needs a denominator.

Is a process just a running program?

Almost. A program is static code on disk; a process is that code loaded live and given CPU turns plus private virtual memory. Postgres shows the split clearly by starting one process per connection. Remember: static versus live.

Why does every process think it owns all memory?

Simplicity plus security. Programmers write as if memory were huge (2^48 or 2^64 on 64-bit chips) while the OS maps pieces to real RAM behind the scenes. Isolation stops one app from reading another. Remember: illusion outside, mapping inside.

Why is scheduling harder than round-robin sharing?

Processes differ in urgency and state. Some wait on disk or network, some need priority, and every switch costs registers, caches, and memory views. The scheduler weighs all three signals every turn. Remember: fair is not the same as fast.
