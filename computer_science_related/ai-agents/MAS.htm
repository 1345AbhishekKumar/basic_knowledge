01 · Foundations

What is a Multi-Agent System?

A Multi-Agent System is a system composed of multiple interacting autonomous agents situated in an environment. Each agent may have its own information, goals, capabilities, constraints, and decision process.

Property
Autonomy

An agent selects actions without requiring every action to be explicitly commanded by a central controller.

Property
Social ability

Agents communicate, coordinate, cooperate, compete, negotiate, or delegate.

Property
Reactivity

Agents perceive environmental changes and can respond to events.

Property
Proactivity

Agents can initiate actions to pursue goals instead of waiting for external commands.

Good fit

Problems that naturally want multiple agents

  • Different actors control different resources.
  • Decision-making is geographically or organizationally distributed.
  • Participants have incomplete or private information.
  • Multiple goals or incentives must be reconciled.
  • Local autonomy improves resilience or scalability.
Bad fit

When a MAS is just architecture cosplay

  • A normal deterministic function already solves the task.
  • Every agent needs every other agent's state all the time.
  • There is no meaningful autonomy boundary.
  • Communication costs exceed useful computation.
  • The “agents” are merely renamed service functions.
Design test: every agent boundary should be justified by something concrete: authority, capability, information, trust, geography, ownership, latency, incentives, or organizational responsibility.

03 · Agents

Agents and agent types

An agent is best understood by what it can perceive, what it can decide, what it can do, and what objective it is pursuing.

Agent type Internal mechanism Strength Weakness Example
Reactive Perception → rules/behaviors → action Fast and simple Limited long-term reasoning Collision avoidance
Deliberative World model + reasoning/planning Long-horizon reasoning Model and computation cost Route planner
Hybrid Reactive + deliberative layers Fast response + planning Architectural complexity Autonomous robot
BDI Beliefs + desires + intentions Explicit goal-oriented reasoning Requires meaningful mental-state model Negotiating service agent
Agent boundary

What belongs inside an agent?

  • Private beliefs/state.
  • Goals and priorities.
  • Decision policy or planner.
  • Available capabilities/tools.
  • Permissions and constraints.
  • Communication interface.
  • Failure and recovery logic.
Developer rule

“Agent” does not mean “LLM”

An agent can be rule-based, symbolic, optimization-based, reactive, learned, or hybrid. A language model can implement part of an agent's reasoning process, but the agent itself also includes state, actions, goals, tools, interaction, and execution constraints.

Model ≠ agent ≠ system. Keeping these abstractions separate prevents a large class of architecture mistakes.
04 · Environment

Environment, observability, and uncertainty

Agent design changes dramatically depending on what the agents can observe and how predictable the environment is.

A fully observable environment exposes the information required to determine relevant state. In a partially observable environment, agents must infer hidden state from observations, memory, models, or communication.
In a deterministic setting, the same state and action have a predictable result. In a stochastic setting, uncertainty affects outcomes, requiring probability, robustness, expected utility, or learning.
A static environment remains stable while an agent thinks. In a dynamic environment, another agent, user, process, or physical system may change the state before the decision executes.
Episodic decisions are relatively independent. Sequential problems have stateful consequences, so actions affect future opportunities, resources, and goals.
Discrete environments use countable states or actions. Continuous environments involve quantities such as position, velocity, physical control, time, or continuous resource levels.
Hidden state

Belief state

When reality cannot be observed directly, maintain an estimate rather than pretending uncertainty does not exist.

Timing

Stale information

A value observed at t₀ can be invalid at t₁. Every distributed design should define freshness.

Interaction

Other agents are part of the environment

Another agent can change state independently, compete for resources, or provide unreliable information.

Architecture determines how an agent turns observations and goals into actions.

06 · BDI

Belief–Desire–Intention architecture

BDI gives the agent an explicit practical-reasoning model. It distinguishes what the agent believes from what it wants and what it has committed itself to doing.

flowchart TB PERCEPT["Percepts / Messages"] --> UPDATE["Belief Revision"] UPDATE --> BELIEF["Beliefs"] BELIEF --> DESIREGEN["Goal / Desire Generation"] DESIREGEN --> DESIRES["Desires"] BELIEF --> DELIB["Deliberation"] DESIRES --> DELIB DELIB --> INTENT["Intentions"] INTENT --> PLAN["Plan Selection"] PLAN --> ACT["Execute"] ACT --> ENV["Environment"] ENV --> PERCEPT ACT --> EVENT["Failure / New Event"] EVENT --> UPDATE style BELIEF fill:#1b2140,stroke:#8d9cff,color:#f1f3f5 style DESIRES fill:#17372f,stroke:#58d9af,color:#f1f3f5 style INTENT fill:#3b3020,stroke:#efbf72,color:#f1f3f5 style ACT fill:#241e36,stroke:#a99cff,color:#f1f3f5
Beliefs What the agent currently believes about itself, other agents, the environment, and system state.
Desires Goals or desired states that the agent would like to achieve.
Intentions The subset of goals the agent has committed to pursuing.
Why this distinction matters

An agent can want ten things and intentionally pursue only two. Resources, priorities, deadlines, commitments, and beliefs determine which desires become intentions.

Practical implementation: treat belief updates, goal generation, deliberation, intention commitment, plan execution, and failure handling as separate state transitions.
07 · Communication

Communication, speech acts & ACL

A message is not merely data. It can represent a communicative act: informing, requesting, proposing, accepting, rejecting, querying, subscribing, cancelling, and more.

Communicative act Intent Example
inform Tell another agent a proposition. inventory = 42
request Ask another agent to perform an action. reserve_dock(3)
query-if / query-ref Ask whether something is true or ask for an object/value. available(truck_8)?
propose Offer an agreement or action. deliver by 14:00 for $8
accept-proposal Accept a proposal. commit(route_17)
reject-proposal Reject a proposal. reject(route_17)
FIPA ACL

Message structure

FIPA ACL specifies a message structure containing a communicative act and parameters describing participants, content, content interpretation, and conversation control. 

performative: request
sender: planner-01
receiver: carrier-08
content: deliver(order-417)
language: SL
ontology: supply-chain-v2
protocol: fipa-request
conversation-id: conv-417
reply-by: 2026-09-07T10:00:00Z
Design principle

Content and protocol are different things

The content says what is being communicated. The protocol says what the message means in the conversation and what messages may legally follow.

“request(deliver(order_417))” is a request. The business meaning of delivery, response deadlines, rejection rules, retries, and completion behavior belongs to the surrounding protocol.

08 · Protocols

Interaction protocols

Protocols turn arbitrary message exchange into a predictable state machine. They define legal transitions and expected outcomes.

One agent asks another to perform an action. The participant can agree, refuse, or produce a result/failure.

Proposal

FIPA Propose

One agent proposes an action or commitment that becomes relevant if the receiver accepts.

PROPOSE → ACCEPT / REJECT
Subscription

09 · Coordination

Coordination mechanisms

Coordination answers a simple question: how can autonomous agents avoid interfering with each other while still achieving useful system-level behavior?

Blackboard

Shared workspace

Agents post observations or partial solutions to a common workspace. 

board.publish(
  "route_candidate",
  route17
);
Tuple space

Structured shared tuples

Agents write and retrieve tuples without requiring direct producer–consumer coupling. 

space.put({
  type: "task",
  id: 417
});
Pub/Sub

Event-based coordination

Agents subscribe to relevant events instead of synchronously querying everything. 

subscribe(
  "inventory.updated"
);
Direct coordination

Agent-to-agent

Good when the relationship is known and interaction is naturally pairwise.

  • Simple request/reply.
  • Negotiation.
  • Delegation.
Indirect coordination

Environment-mediated

Agents influence the shared environment and observe changes rather than communicating directly. This is often called stigmergic coordination in agent-based systems.

  • Shared workspace.
  • Physical traces.
  • Event streams.
10 · Negotiation

Negotiation, auctions, and markets

Coordination assumes compatible interests. Negotiation is needed when agents have different preferences, constraints, or incentives.

Mechanism Basic idea Useful when Core risk
Contract Net Agents propose ways to perform a task. Distributed task allocation. Communication overhead.
English auction Price increases as participants bid. Competitive allocation. Strategic bidding.
Dutch auction Price decreases until a participant accepts. Fast allocation. Timing sensitivity.
Bargaining Agents exchange offers and counteroffers. Bilateral tradeoffs. Long interactions / deadlock.
Argumentation Agents exchange reasons supporting or attacking proposals. Decisions needing explanations or justification. Complex semantics.
Game-theoretic warning: optimizing each agent independently does not guarantee a good system outcome. Incentive design is part of MAS design.
11 · Organisations

Teamwork, joint intentions, and organisation

A team is more than a set of agents with related goals. Reliable teamwork requires explicit commitments, roles, dependencies, and failure behavior.

Joint goal

Shared objective

Team members know what system-level outcome they are jointly responsible for producing.

Roles

Responsibility boundaries

Each agent knows which subtasks it owns, supports, depends on, or delegates.

Commitment

Intention to remain engaged

Agents know when they may abandon a task, renegotiate it, or require help.

Organisation models
Structure Description Advantage Risk
Hierarchical Higher-level agents direct lower-level agents. Clear authority. Central bottlenecks.
Federated Local groups retain autonomy and coordinate with peers. Local autonomy. Cross-group negotiation.
Peer-to-peer Agents coordinate directly without permanent hierarchy. Resilience and autonomy. Discovery and coordination cost.
Coalition Agents dynamically form groups around temporary goals. Flexible resource aggregation. Membership and trust management.
12 · Planning

Planning and decision making

Use explicit planning when actions have predictable structure, meaningful preconditions/effects, and longer-horizon consequences.

STRIPS

State-space planning

Actions specify preconditions and effects. A planner searches for a sequence that transforms the initial state into the goal state. 

ACTION move(truck,A,B)

PRECONDITION
at(truck,A)
clear(B)

EFFECT
not at(truck,A)
at(truck,B)
HTN

Hierarchical Task Networks

Decompose abstract tasks into smaller executable tasks. Useful when domain expertise naturally describes workflows hierarchically. 

DELIVER_ORDER
  ↓
prepare_order
schedule_transport
load_vehicle
execute_route
Rule-based

Fast and deterministic

Ideal where domain rules are stable and easy to enumerate.

Optimization

Choose the best feasible solution

Useful when cost, capacity, time, or constraints dominate the problem.

Learned policy

Adapt from experience

Useful when explicit models are incomplete and feedback can improve decisions.

Decision hierarchy: prefer explicit rules when sufficient → optimisation when constraints dominate → planning when action sequences matter → learning when adaptation is genuinely required.
13 · Learning

Multi-Agent Reinforcement Learning

In multi-agent learning, the environment itself changes because other agents are making decisions. That creates non-stationarity, coordination challenges, and credit-assignment problems.

Independent

Independent learners

Each learner treats other agents as part of its environment. Easy to define, difficult to reason about theoretically.

Cooperative

Shared objectives

Agents optimize aligned outcomes. Credit assignment becomes difficult when rewards are shared.

Competitive

Opposing objectives

Agents learn against one another. Strategy, robustness, exploitability, and equilibrium matter.

State Information used for decision making.
Action Available intervention.
Reward Feedback about outcomes.
Policy Strategy for selecting actions.
Important: multiple agents does not automatically mean multi-agent RL. Many MAS problems are better solved with deterministic protocols, planning, optimisation, or explicit coordination mechanisms.

15 · Semantics

Ontology, schemas, and shared state

Agents cannot coordinate reliably if they disagree about what an order, event, status, deadline, capacity value, or completion signal means.

Entity

Order

ID, destination, priority, state, deadline, customer, constraints.

Event

OrderDelayed

Defines exactly when an order is considered delayed and what information accompanies the event.

Constraint

TemperatureRange

Defines eligibility for vehicles, warehouses, and routes.

Versioning

Treat message schemas as APIs 

{
  "schema_version": "2",
  "event": "order.delayed",
  "order_id": "417",
  "observed_at": "2026-09-07T11:40:00Z",
  "eta": "2026-09-07T14:18:00Z",
  "confidence": 0.91
}
Never rely on “everyone knows what this means.” Formalize critical semantics, version them, and define compatibility rules.
16 · Security

Security, identity, trust, and permissions

Autonomy without boundaries is not sophistication. It is an incident waiting for a convenient Tuesday.

Identity

Who is this agent?

Use authenticated identities and stable identifiers. Do not trust the claimed sender field by itself.

Authorization

What may it do?

Enforce least privilege at the capability/action boundary.

Trust

Should its information be believed?

Consider provenance, freshness, confidence, historical reliability, and independent verification.

Integrity

Was the message modified?

Transport and application-level integrity controls should protect critical commands and data.

Audit

Can the decision be reconstructed?

Store enough metadata to trace perception, message, decision, action, and outcome.

Sandboxing

What happens if the agent is wrong?

Restrict dangerous tools, sensitive resources, external side effects, and irreversible actions.

18 · Failure modes

Challenges and common mistakes

Most MAS failures are not caused by agents being insufficiently “intelligent.” They are caused by bad boundaries, bad protocols, stale state, uncontrolled autonomy, and distributed-systems problems.

Scale

Communication explosion

A naive all-to-all communication model can create rapidly increasing coordination overhead.

State

Stale information

Agents may act on facts that were correct when observed but invalid when used.

Emergence

Unexpected behavior

Local policies can combine into system-level oscillation, starvation, deadlock, or resource thrashing.

Trust

Unreliable agents

A participant may be wrong, compromised, unavailable, or operating with incomplete information.

Real time

Coordination latency

Multiple network round trips can violate deadlines even when every individual agent is fast.

Autonomy

Too much authority

Agents should not be allowed to perform irreversible actions without appropriate controls.

Anti-patterns
Mistake Why it fails Better approach
Every service becomes an agent. Complexity is added without autonomy. Require a real decision boundary.
Agents share everything. Boundaries disappear. Share only information required by the protocol.
No explicit protocol. Conversation semantics become implicit. Model interactions as state machines.
Communication is assumed free. Network cost becomes dominant. Measure message count, bytes, and round trips.
No failure model. One failed agent can block the entire system. Design timeouts, retries, fallbacks, escalation.
Agents optimize only local reward. Local optimization can harm global objectives. Design incentives and system-level metrics together.

20 · Operations

Deployment and operations

A MAS becomes a distributed production system once the agents leave your laptop. At that point networking, discovery, observability, state, and failure recovery become first-class concerns.

Lifecycle

Spawn → register → operate → retire

Define how agents start, discover services, restore state, become healthy, and terminate.

Discovery

How does an agent find another?

Use registries, directories, capability discovery, service discovery, or explicit routing.

Observability

Trace + metrics + logs

Record conversation IDs, agent IDs, decisions, outcomes, latency, retries, and failures.

State

Durable recovery

Decide what state is ephemeral, replicated, checkpointed, or reconstructable.

Scaling

Add agents without chaos

Define partitioning, load balancing, capacity limits, and admission control.

Rollouts

Change safely

Version protocols, roll out gradually, and preserve compatibility during migration.

Production rule: every autonomous action that can damage data, spend money, affect users, or trigger external side effects should have bounded authority and observable evidence.
