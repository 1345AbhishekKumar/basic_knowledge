Detailed Architectural Explanations

Core Concept 01 · Query Routing

Why Dual-Tier Memory is Necessary

Dumping raw chat history directly into an LLM context window causes catastrophic token bloat, high API bills, and the "Lost-in-the-Middle" problem where the model misses key details. Production systems separate memory into two distinct tiers: Episodic DB for raw chronological auditing, and Semantic DB for distilled, instant conceptual recall.

Core Concept 02 · Distillation

The Consolidation ("Dreaming") Daemon

Similar to biological sleep where the brain replays daily experiences and converts short-term memories into long-term knowledge, an Offline Consolidation Daemon runs asynchronously. It sweeps thousands of raw turns, strips chitchat ("Hi", "Thanks"), and writes permanent facts directly into Semantic Memory.

1. Core Component Definitions (Labels in Figure 2.0)

Panel 1 · Left

Query Routing & Retrieval Gate

Retrieval Gate: The routing logic that inspects incoming queries to decide whether to trigger exact SQL, vector similarity, or a hybrid combination.
Case A (Exact Relational Lookup): Queries with specific entity IDs or time ranges (e.g., "Last 10 messages from user #441"). Handled purely by indexed SQL B-Trees in sub-milliseconds with $0 embedding cost.
Case B (Semantic & Hybrid Query): Queries about concepts or sentiments (e.g., "Past 20 complaints regarding shipping delays"). Requires SQL metadata filtering followed by vector embedding distance calculations.

Panel 2 · Center

Dual-Tier Database Repository

Episodic DB (Raw Turn History): Relational SQL tables (SQLite / PostgreSQL) storing raw transcripts with strict schema columns: [id, user_id, turn_text, timestamp, status]. It preserves the exact historical record.
Semantic DB (Distilled Facts): Vector stores (pgvector, Qdrant) or structured markdown files (MEMORY.md) containing high-dimensional embeddings (e.g. 1536-d) representing immutable truths, user preferences, and business policies.

Panel 3 · Right

Batch Consolidation Engine

Consolidation Engine: An asynchronous worker process triggered on schedule or after every 2,000 conversations.
Auxiliary Cheap LLM: A low-cost model (e.g. Llama-3-8B or GPT-4o-mini) that reads bulk episodic logs, extracts durable entity facts, and summarizes key insights.
Cost Optimization: Shrinks context injection payloads by up to 90%, preventing the need to re-feed thousands of historical turns.

Data Mechanics

Vector Embeddings & Cosine Distance

Text is transformed into numerical vectors where semantic meaning corresponds to geometric direction. Using cosine distance (<=> operator in pgvector), the retrieval gate measures semantic similarity between the user's intent and stored historical complaints, returning only top-K matching records.

2. Step-by-Step Flow: How Retrieval & Consolidation Work

Follow the arrows in Figure 2.0 to trace both online retrieval paths and the offline background consolidation loop:

Flow A • Fast Exact Relational Lookup (Top Arrow)

The user requests "Fetch last 10 messages for user #441". The Retrieval Gate identifies user ID and timestamp constraints and executes an indexed SQL query directly on the Episodic DB: SELECT * FROM conversation_turns WHERE user_id = 441 ORDER BY timestamp DESC LIMIT 10. Results return in <5ms without running vector embeddings.

Flow B • Hybrid Semantic Retrieval (Bottom Orange Arrow)

The user requests "Find 20 past complaints about shipping delays". The Retrieval Gate performs a two-stage hybrid search: (1) Pre-filters the Episodic DB using SQL for category = 'support', then (2) calculates cosine vector similarity against the query embedding in the Semantic DB, returning the 20 most conceptually relevant complaints out of thousands of records.

Flow C • Offline Batch Consolidation Loop (Dashed Orange Arrows)

Every 2,000 turns, the Consolidation Engine awakens in the background. It queries un-distilled turns from the Episodic DB (dashed arrow rightward), runs them through the Auxiliary Cheap LLM to strip conversational pleasantries and synthesize actionable rules (e.g. "Warehouse B has recurring 48-hour dispatch delays"), and commits these distilled facts into the Semantic DB (dashed arrow downward and back into center).
