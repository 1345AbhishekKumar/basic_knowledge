AI Agents in LangGraph

An agent (= a helper program that plans, presses tools, and checks its own work) beats a plain chatbot that answers in one shot. You will trace the full build, from a hand-written loop to a writer crew, using small pictures and plain words.

01 / START
One idea - loop beats one shot

One-shot answers lose, loops that fix win

A plain chat writes from the first word to the last with no backspace. An agentic workflow (= a job done in small rounds with checking) writes, reads, and fixes.

One line versus rounds
One pass has no repair step, the loop adds outline, draft, critique, fix.

Think of a student told to write an essay with no eraser. That is one-shot prompting (= asking once and taking the first answer). Small slips stay forever.

An agent works more like cooking with tasting. It makes an outline, drafts, tastes by reading its draft, and seasons again. Each round uses fresh facts from tools such as web search.

Tests across many tasks show the tasting loop beats the single pass, because errors get caught early and facts get checked.

Bench steps
  1. 1Ask for an outline before any full text.
  2. 2Fetch outside facts and place them near the draft.
  3. 3Write a draft, then critique it in plain points.
  4. 4Fix with the critique and repeat until good.
Story 1 - Maya and the cake

Maya must bake for a school fair. She tastes the batter, adds sugar, and bakes again. The second cake wins because tasting caught the bland mix.

Story 2 - Sam and the letter

Sam writes a note to his coach in one rush and sends a wrong date. Next time he drafts, rereads, and fixes the date. The slow loop saves him.

Analogy
Like cooking with tasting instead of serving the first mix.
Common mistake
Many people think a longer single prompt equals a smarter answer.
Why this matters
Every later module reuses this loop shape, so learn it cold.

02 / SPARK
One idea - surprise saves teach

The demo that saved itself

On a live stage the web search broke. The helper switched to a backup search and still finished the essay.

Plan B switch
When the first tool fails the helper picks the backup and carries on.

The speaker asked the helper to research online and write. The main search tool (= a button that fetches web pages) failed in front of a crowd. The helper did not freeze.

It had a second button for an encyclopedia search. It pressed that one, gathered facts, and wrote the essay. The builder had even forgotten that backup existed.

The same trick helps train new models. Simple copies of old text teach little. Careful loop-made text, with checks and fixes, teaches a lot more.

Bench steps
  1. 1Give the helper two ways to find facts, not one.
  2. 2Let failure trigger a switch, not a full stop.
  3. 3Keep loop-made drafts as rich training material.

03 / PATTERNS
One idea - five reusable moves

Five patterns every agent reuses

Planning, tool use, reflection, team talk, and memory appear in almost every helper. Learn the five and you can read any agent.

Five moves on one bench
Each move has one job, together they form full behavior.

Planning (= choosing steps before acting) is the outline. Tool use (= pressing outside buttons like search or math) gathers fresh facts. Reflection (= reading your own draft and listing flaws) drives fixes.

Team talk (= two or more helpers passing work) splits hard jobs. Memory (= a shared notebook of what happened) keeps the thread across rounds.

Some of this lives inside the text predictor (= the LLM, a next-word guesser). Much lives outside in the frame (= the surrounding code that loops, stores, and routes).

Bench steps
  1. 1Write steps before touching any tool.
  2. 2Pick the right tool and read what returns.
  3. 3Critique, share roles, and log all in memory.
Story 1 - Ana and the play

Ana plans scenes, borrows props, rehearses, and asks friends to play parts. Each pattern maps to one theater job, and the show lands.

Story 2 - Ben and the shed

Ben sketches the shed, borrows a drill, checks his cuts, and notes measures on the wall. The wall notes are memory that saves rework.

Analogy
Like a kitchen team with planner, cook, taster, and order board.
Common mistake
Many people think the model alone does planning and memory.
Why this matters
Spotting the five lets you debug any agent fast.

05 / GRAPH
One idea - loops drawn as maps

A graph that is allowed to loop

A graph (= a map of boxes and arrows) can cycle back. That cycle is the whole secret behind agents that retry.

Boxes plus choice arrows
Nodes do work, plain arrows move on, choice arrows branch.

A node (= one box of work) can be a model call or a tool run. An edge (= an arrow) moves work to the next box. A conditional edge (= a choice arrow) reads the last output and picks the next box.

Plain chains move one way. Agent maps add a back arrow from action to agent, so the loop can repeat until done.

Clear arrows give control. Builders see each path and can fix one branch without breaking the rest.

Bench steps
  1. 1Draw one box per job the helper does.
  2. 2Join boxes with plain arrows for fixed order.
  3. 3Add a choice arrow where the path must branch.
  4. 4Close the retry loop back to the model box.
Story 1 - Nina and the laundry

Nina map has wash, dry, and fold boxes. If shirts feel damp she loops back to dry. The back arrow saves wearable clothes.

Story 2 - Tom and the quiz

Tom draws study, test, and done boxes. A low score sends him back to study. The choice arrow routes him by score.

Analogy
Like a board game where some squares send you back.
Common mistake
Many people think more boxes always means smarter behavior.
Why this matters
Controlled loops are what make agents steady and testable.
Link forward
These boxes run live in 09 graph rebuild.
Try it - pick a path

A straight line ends after one try. Failures have nowhere to go.
Choice plus back arrow retries only when needed. That is control.

06 / MEMORY
One idea - notebook that grows

A memory list that only grows

Agent state (= the shared notebook every box can read) holds messages. New notes get added, old notes stay.

Add, do not erase
Each round appends, so the full trail stays readable.

The simple state is just a message list. Each turn appends new notes with an add rule (= combine, never erase). The full trail stays in view.

Rich states add slots like task, plan, draft, and counts. Plain slots get overwritten. Step trails still append, so retries stack neatly.

Saved states let work pause and resume later. That pause power also lets humans step in, which later modules use.

Bench steps
  1. 1Start state as an empty message list.
  2. 2Mark message lists as add-only.
  3. 3Save each snapshot so any point can resume.
Story 1 - Zoe and the log

Zoe keeps a trip log and never tears pages. When the group argues about a turn, the log settles it fast.

Story 2 - Max and the scorecard

Max writes each golf stroke on one card. Old strokes stay, so trends show. Erasing would hide the pattern.

Analogy
Like a receipt roll that keeps every line printed.
Common mistake
Many people think memory means one giant prompt.
Why this matters
Full trails make repeats, audits, and resumes simple.
Link forward
Snapshots power 12 human control time travel.

07 / REACT
One idea - think, act, look

The ReAct recipe in plain words

ReAct (= think plus act) repeats three lines. Thought says the plan, Action presses a tool, Observation reads what came back.

Press play to step through the three stages.

The prompt teaches the shape with one full example. It lists two toy tools (= practice buttons with fixed answers). Calculate (= do small math) solves sums. Average dog weight (= look up breed pounds) returns fixed numbers for three breeds.

A run looks like this. Question about a toy poodle leads to thought, then action with the breed name, then pause. The frame runs the tool and pastes the observation back.

Harder questions chain rounds. Two breeds need two lookups, then a sum, then the final answer. Each observation feeds the next thought.

08 / AUTO
One idea - hands-free loop

A loop that runs itself safely

A small query function (= a runner that repeats the three lines) parses each reply, runs tools, and stops at Answer or a turn cap.

Runner with guard rails
Parse, check, run or return, with a max-turn brake.

Hand-running every round is slow. The runner uses a pattern (= a text finder for the word Action) to split tool calls from final answers.

If an action exists, the code checks the name, runs the matching tool, and builds the next prompt with the observation. If no action exists, the text holds Answer and the runner returns.

A max-turns cap (= a hard stop after N rounds) prevents endless loops. Unknown tool names raise a clear error instead of silent drift.

Bench steps
  1. 1Match the Action pattern in each model reply.
  2. 2Check the name, run the tool, paste the reply.
  3. 3Stop on Answer or when the turn cap hits.
Story 1 - Kim and the washer

Kim sets her washer to stop after two rinses. The cap prevents floods. Auto loops need the same brake.

Story 2 - Dan and the list

Dan scans notes for the star mark. Stars mean tasks, plain lines mean done. Pattern finds split work from finished work.

Analogy
Like a washing cycle with a timer plus an end chime.
Common mistake
Many people think the loop can run with no stop rule.
Why this matters
Guards turn a demo into something safe to ship.
Link forward
Guards reappear as graph edges in 09 rebuild.

09 / REBUILD
One idea - same loop, real parts

The same agent rebuilt from graph parts

Three small methods replace the hand runner. One calls the model, one checks for tool calls, one runs them.

Press play to step through the three stages.

Bind tools (= tell the model which buttons exist) once at setup. The call step sends system plus messages and appends the model reply to state.

The check step looks at the last message. Tool calls present means go to action, absent means go to end. The action step loops over calls, runs each tool, and appends tool replies.

Entry starts at the model box. Action links back to the model box. The compiled graph (= the runnable map) can even draw itself for review.

Bench steps
  1. 1Bind the tool list to the chosen model.
  2. 2Add model and action boxes plus a choice arrow.
  3. 3Compile, draw the map, and run with messages.
Story 1 - Jo and the food truck

Jo posts the menu, checks orders, and cooks in rounds. Binding the menu first stops strange requests later.

Story 2 - Al and the print shop

Al routes jobs to printer or binder by ticket marks. Clear routing keeps both machines busy without mix-ups.

11 / SEARCH
One idea - search plus threads

Search built for helpers, threads that recall

Helper search splits hard asks, picks sources, keeps short notes, and remembers threads across visits with live updates.

Split, pick, keep, recall
Four small jobs turn web noise into usable notes.

Inside, helper search splits a hard ask into small queries. It picks the best source per piece, keeps short chunks, and scores out weak notes. A weather ask routes to weather data, not random blogs.

Regular search returns links to open and scrape. Helper search returns neat records with answers and sources. The demo showed messy page soup versus one clean record.

Threads (= saved chats under one id) keep recall. Same id continues the talk, new id starts blank. Streams (= live updates as work runs) show each message, and token streams show words as they form.

12 / PEOPLE
One idea - people plus crews

People approve, crews write, teams grow

Pauses let people check tool calls. Edits rewrite history. The same controls steer a writer crew from plan to polished essay.

Pause, edit, crew loop
Human gates plus plan, research, write, and critique rounds.

A pause before action (= a stop that waits for a yes) lets a person approve each tool press. State views show messages plus next box. A yes resumes, a fix rewrites the call first.

Edits can retarget a call, mock a tool reply, or jump back to an old snapshot (= a saved point you can resume). Branching keeps both the old path and the new try.

The writer crew chains plan, research, write, critique, and more research. Counters track rounds and stop at a max. Bigger maps grow this into teams, leads, and search trees.

Bench steps
  1. 1Pause before risky tools and ask for a yes.
  2. 2Fix calls or mock replies, then resume the thread.
  3. 3Loop plan, study, write, and critique to a cap.

FAQ

Is an agent just a chatbot with tools ▾

Tools help, but the loop matters more. A chatbot answers once, while an agent plans, presses, reads, critiques, and retries. Remember the tasting cook, not the single-serve machine.

Why not always run tools in parallel ▾

Parallel fits only free parts like two cities. Chained asks need order because later inputs come from earlier replies. Check sharing first, then pick timing.

Where does memory actually live ▾

Mostly outside the model in saved state. Messages append each turn, and snapshots let threads pause and resume. The model reads the notebook, it is not the notebook.

When should a human step in ▾

Before risky or costly tools like deletes, sends, or buys. A short pause with a clear preview keeps speed while blocking harm. Low-risk reads can flow freely.

What if a tool fails mid-run ▾

Offer a backup path like the stage save. Let the choice arrow switch sources instead of halting. Log the failure so later critique can route better.

How does the writer crew know when to stop ▾

Counters track rounds against a max, and the critique checks quality. When rounds run out or the draft passes, the graph ends. Caps turn open loops into shippable jobs.

Do I need LangGraph for a tiny helper ▾

A tiny loop can start as plain code with a runner. Move to graphs when you need branches, saved threads, pauses, or teams. Start small, grow the map only when pain shows.

What comes after single agents ▾

Crews that share state, leads that route jobs, and search trees that test many paths. Each adds control for harder work. The same five patterns still apply at larger scale.
