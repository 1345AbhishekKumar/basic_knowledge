Module 01

What is an AI Agent?

The fundamental shift from single-shot generation to iterative, multi-step work — and the ReAct loop that powers it.

A · Core Explanation

From One-Shot to Iterative Intelligence

An AI agent is not simply a language model that generates text in one pass. The fundamental shift from a traditional LLM call to an agentic system is the move from single-shot generation to iterative, multi-step work. When you ask a standard LLM to "write an essay about gym beginners," it produces the entire output in one linear pass — no planning, no research, no revision. An agent, by contrast, works the way a human would: it outlines first, identifies what information it needs, gathers that information through tools like web search or database queries, drafts a response, and then critically reflects on its own output to tighten arguments, fill gaps, and improve flow.

This iterative cycle is called the ReAct loop — Reason, Act, Observe. The model reasons about what to do next, takes an action (often calling an external tool), observes the result, and then either provides an answer or loops back to reason again. Each pass adds depth: reasoning becomes stronger, hallucinations decrease, and organization improves — all qualities that suffer when everything is attempted in a single shot.

Agents shine in domains requiring careful, accurate, sourced work: legal research with specific case citations, healthcare documentation, customer support that must look up account details before responding. However, this capability comes with increased complexity, latency, and cost. The key insight is knowing when the iterative approach is worth the overhead. Tasks with clear, repeatable processes (invoice field extraction) are perfect starting points, while tasks demanding both high complexity and high precision (tax forms) require the most engineering effort. A helpful framework is the complexity-precision matrix: the biggest early wins come from high-complexity, low-precision tasks — you get leverage from automating something tricky without being blocked by needing perfect output.

B · Real-World Examples

Three Use Cases Across the Complexity Spectrum

● Obvious

Essay Writing Agent

An agent outlines the essay structure, generates search terms, calls a search API, fetches relevant pages, writes a draft, self-critiques for gaps and weak arguments, and revises — each pass adding depth that a one-shot prompt would miss entirely.

◈ Counter-Intuitive

Invoice Field Extraction

Seems too simple for an agent — until you realize invoice formats vary wildly across vendors. The agent's ability to adapt (trying OCR, checking against vendor templates, validating line-item totals against subtotals) outperforms a rigid single-pass approach that breaks on format variation.

▲ Edge Case

Customer Service for Returns

The agent must verify the purchase, check the return policy, confirm eligibility, and walk through the return process — steps that vary per case and can't be scripted as a fixed flow. A one-shot LLM would hallucinate policy details; an agent looks them up.

Visual Analogy

Think about how you actually write an essay. You don't produce a perfect first draft in one go. You plan, outline, do some research, write a messy draft, read it over, and revise again and again. It's a process. That iterative process IS what agentic AI does. Instead of asking the AI to do everything in one linear pass, you let it work the way a human would — step by step, with reflection and revision built in.

Common Misconception: "Agents are just ChatGPT with a fancy UI"

Many people think an "AI agent" is simply a chatbot with a nicer interface. The truth: the key difference is iteration. An agent works through the ReAct loop: it reasons about what to do, takes actions (like calling web search or database APIs), observes results, and loops back to refine. This iterative process is what produces stronger reasoning, fewer hallucinations, and better organization. The UI is irrelevant; the architecture is everything.

Module 02

Building Blocks — Autonomy, Context & Decomposition

How much control to give your agent, what information to feed it, and how to break tasks into LLM-doable steps.

A · Core Explanation

The Three Foundations of Agent Design

The first major decision in building an agent is determining how much autonomy it should have. This exists on a spectrum. At one end, scripted agents hardcode every step — generate search terms, call web search, fetch pages, write the essay — making the model's only job text generation within a deterministic, predictable pipeline. At the other end, highly autonomous agents decide for themselves whether to search Google, read research papers, convert PDFs, or even write and execute new functions. This is powerful but unpredictable and difficult to control. In practice, most production agents are semi-autonomous: they pick from tools you've defined and make decisions within guardrails you've set.

What steers a non-deterministic model toward consistent, high-quality output is context engineering — the deliberate design of what information the agent has access to. This includes the task background, the agent's role, memory of past actions, and the available tools. The model alone isn't the source of intelligence; the engineered context around it is. Think of context engineering as setting up a new employee: you give them a job description, background on the project, access to the tools they need, and notes from previous work. Without this context, even the smartest employee (or model) will flounder.

Once context is established, the most critical skill is task decomposition. Start with how you would do the task manually. For each step, ask: "Can an LLM do this?" If the answer is no, split it smaller until it can. The essay example decomposes into outline (LLM), generate search terms (LLM), call search API (tool), fetch pages (tool), write draft (LLM), self-critique (LLM), and revise (LLM). Each step is small, checkable, and clear — so when output isn't good enough, you know exactly which step to improve. This granularity is what makes agent systems debuggable. When something breaks, you don't have to guess; you look at the trace of each step and find the failure point.

B · Real-World Examples

Decomposition in Action

● Obvious

Essay Writing Decomposition

Outline (LLM) → Generate search terms (LLM) → Fetch pages (Tool) → Write draft (LLM) → Self-critique (LLM) → Revise (LLM). Each step is clear, small, and independently testable.

◈ Counter-Intuitive

Calendar Scheduling

Seems simple — "schedule a meeting" — but requires multiple LLM calls: check calendar for availability, find open slots, make the appointment, confirm back. What looks like one task is actually four, each requiring tool access.

▲ Edge Case

Steps That Need NO LLM

Fetching a URL is pure code, not an LLM call. Some steps in your decomposition should be tools only, with zero model involvement. Recognizing these prevents unnecessary token costs and latency.

Visual Analogy

Think of task decomposition like writing a recipe. You don't just say "make dinner." You break it into chop vegetables, sauté onions, season to taste, plate the dish. Each step is small, checkable, and clear. If the dish tastes wrong, you know exactly which step to fix — was it the seasoning? The cooking time? The same principle applies to agents: decomposed tasks are debuggable tasks.

Common Misconception: "More autonomy is always better"

It's tempting to give agents maximum freedom — let them decide everything. The reality: fully autonomous agents are powerful but unpredictable, harder to debug, and riskier in production. They might decide to fetch 50 web pages when 3 would suffice, write and execute arbitrary code, or take paths you never anticipated. Semi-autonomous agents with well-engineered guardrails are usually the sweet spot. You define the toolkit and the boundaries; the agent makes decisions within them. This gives you the flexibility of autonomy with the control of scripting.

Module 03

Memory, Knowledge, Guardrails & Evaluation

The three elements that separate toy agents from reliable ones — and how to measure if they're working.

A · Core Explanation

What Makes an Agent Reliable?

Three foundational elements separate a toy agent from a reliable one: memory, knowledge, and guardrails. Memory is dynamic — it updates on every run. Short-term memory lets agents write down their work as they go, and in multi-agent systems, other agents can read those notes. Long-term memory stores lessons learned: after finishing a task, the agent reflects on what went well and what failed, compares results to expectations, and stores those lessons for future runs. This creates a feedback loop similar to supervised learning, where each run improves quality.

Knowledge, by contrast, is static. This is reference material loaded upfront — PDFs, CSVs, documentation, or database access. The agent doesn't modify it; it pulls from this library whenever it needs to cite something accurately. The distinction matters: without memory, an agent repeats mistakes; without knowledge, it hallucinates facts. Together, they give the agent both a foundation of truth (knowledge) and a mechanism for improvement (memory).

Guardrails are the quality gates between what the agent produces and what ships. Because LLMs are non-deterministic, they can produce factually wrong or misformatted output. Three guardrail approaches exist, and production systems typically use at least two. Deterministic checks (code snippets) validate format and length — fast, cheap, preferred whenever possible. LLM judges evaluate nuanced qualities like factual consistency or tone, sending revision feedback back to the agent. Human-in-the-loop review stops the agent before shipping, allowing a person to approve, reject, or request changes. Evaluation runs parallel: measure component-level quality (is each step working?) and end-to-end quality (is the final output good?), using traces — the intermediate steps of search queries, drafts, and reasoning — to diagnose failures. Start evaluating right away, but don't worry about having a perfect evaluation system from the get-go.

B · Real-World Examples

Memory, Knowledge & Guardrails in Practice

● Obvious

Essay Agent Long-Term Memory

After writing several essays, the agent stores that APA citation format was preferred and that introductions should be under 150 words. On the next run, it loads these lessons and consistently applies them — no reminders needed.

◈ Counter-Intuitive

Static Knowledge Can't Handle Recency

A PDF loaded as knowledge can't tell the agent today's news or current inventory levels — that requires a tool (web search, database query), not more knowledge. Knowing the difference prevents over-reliance on static docs for dynamic information.

▲ Edge Case

Memory Can Encode Mistakes

If feedback is wrong or biased — a reviewer who always marks good work as "needs improvement" — the agent "learns" the wrong lesson. Memory quality depends on feedback quality. Bad feedback compounds over runs.

Visual Analogy

Think of an agent like a new employee on their first day vs. their hundredth day. On day one, they have access to the company wiki and documentation (knowledge) but no experience. After a hundred days, they've learned what works and what doesn't through feedback and reflection (memory). Knowledge is the reference library; memory is the personal notebook that grows with experience. Guardrails are the approval process — a manager reviews their work before it ships.

Your customer service agent occasionally gives wrong return policies.

Module 04

Four Core Design Patterns

Reflection, tool use, planning, and multi-agent collaboration — the building blocks that reliably boost agent quality and capability.

A · Core Explanation

The Four Patterns That Make Agents Powerful

Four design patterns reliably boost agent quality and capability: reflection, tool use, planning, and multi-agent collaboration. Reflection means the model produces output, critiques it, and rewrites if needed. That second pass, guided by a prompt asking it to fix problems, almost always improves quality. Reflection is especially powerful with code, where external feedback — running the code, capturing errors, feeding test results back — gives the model concrete information to produce a better version. It works best for structured outputs like JSON, procedural instructions, creative work, and long-form writing. The trade-off is added latency and cost from multiple passes, so always test with and without reflection to confirm it's actually helping.

Tool use gives the LLM a menu of functions it can call — web search, database queries, code execution, calendar access. The model decides when and which tools to use. Critically, the LLM never executes code; it requests a function call, your code executes it, and you feed the result back as new context. Tools have two parts: an interface (name, description, typed input schema) visible to the agent, and implementation code hidden from it. Good tools include error handling, caching, async support, and versioning — they should be built like products.

Planning replaces hardcoded step sequences with LLM-driven decision-making. You give the agent a toolkit and prompt it to create a plan, then execute step by step. The strongest use case today is agentic coding, where models break programming tasks into sub-tasks and work through them. Planning increases autonomy but also unpredictability — it requires guardrails on permissions, tool call validation, and output passing between steps. Multi-agent collaboration applies the principle of specialization: each agent has a clear role and focuses on what it's good at. This avoids context bloat in any single agent, allows mixing cheaper and expensive models, and enables parallel work — but adds coordination complexity that must be managed with clear interfaces and robust orchestration.

B · Real-World Examples

The Four Patterns in Action

● Obvious

Email Reflection

First draft is wordy and vague. The critic identifies generic language and missing specifics. The rewrite is cleaner, more concrete, and more professional — a noticeable quality jump from a single pass.

◈ Counter-Intuitive

Reflection Can Hurt

For simple tasks — generating a single keyword or extracting one field — the extra reflection pass adds latency and cost without measurable improvement. Always benchmark with and without; sometimes the first draft is already good enough.

▲ Edge Case

Code Reflection with Execution

Write code → critic reviews → actually run the code → capture errors and test results → feed back to model → produce V2. The external execution feedback is what makes this dramatically better — the model isn't guessing, it has real error messages to fix.

Visual Analogy

Reflection is like having an editor review your draft before you publish — they catch what you missed. Tool use is like giving a chef access to the pantry, stove, and knives instead of just asking them to describe a recipe. Planning is like a general figuring out the battle strategy before deploying troops, rather than charging in blindly. Multi-agent collaboration is like a restaurant kitchen: the sous chef, line cook, and pastry chef each specialize, and the expeditor coordinates.

Common Misconception: "LLMs execute tools directly"

It's natural to assume that when an LLM "calls a tool," it runs the code itself. The truth: LLMs only generate text — they request function calls. Here's the actual loop: the LLM looks at available tools and outputs a special request like "I want to call get_current_time with timezone Pacific." Your code sees that request, executes the function, gets the result, and feeds it back to the LLM as new context. The LLM then uses that result to finish its answer or requests another tool. The model never runs code; it only asks for it. This separation is what makes tool use safe and controllable.

Practical Application

Your code-generation agent produces code that sometimes fails to run.

Decision 1: What external feedback can you use? Run the code, capture errors, run tests — feed concrete results back to the model.

Module 05

Multi-Agent System Design

How agents communicate, coordinate, and collaborate — from simple assembly lines to complex hierarchical teams.

A · Core Explanation

Building Agent Teams That Work

Multi-agent systems borrow from how human teams work: you don't hire one generalist to do everything; you build a team of specialists who hand off work. Each agent gets a clear role, a specific set of tools, and a defined interface for inputs and outputs. The marketing brochure example illustrates this: a researcher agent finds market trends using web search and retrieval tools, a graphic designer agent creates visual assets with image generation and code execution tools, and a writer agent turns findings into copy — potentially just an LLM with no external tools. The output is better because of specialization at each step.

Four communication patterns govern how agents interact, ordered from simplest to most complex. Sequential is an assembly line — each agent finishes, then passes output to the next. It's easy to debug with predictable timing and cost, and it's where you should start. Parallel runs independent agents simultaneously, reducing latency but adding coordination complexity. Hierarchical introduces a manager agent that plans and coordinates; specialists report to the manager, not to each other. This is the most common pattern in production today because it balances adaptability with control. All-to-all, where any agent can message any other at any time, is rare in production — outputs vary wildly run to run, making it suitable only for brainstorming or low-stakes creative tasks.

Two pitfalls dominate multi-agent failures: redundant work (multiple agents redoing the same searches or calling the same tools) and unnecessary serialization (chaining steps that could run concurrently). Four best practices mitigate these: define clear input/output schemas (interfaces, not vibes), scope tools per agent with least privilege, log complete traces for debugging, and evaluate both component-level and end-to-end quality. If your end-to-end eval shows problems but components look fine, you know it's a handoff or integration issue. If a specific component eval fails, you know which agent needs improvement.

B · Real-World Examples

Communication Patterns in Practice

● Obvious

Sequential Brochure Pipeline

Researcher → Designer → Writer, like an assembly line. Each agent finishes completely before the next starts. Easy to debug, predictable timing and cost. This is where you should start.

◈ Counter-Intuitive

Parallel Isn't Always Faster

If coordination overhead (managing shared state, merging outputs, handling conflicts) exceeds the time saved by running concurrently, sequential is actually better. Measure before assuming parallelism helps.

▲ Edge Case

All-to-All for Ad Copy

Generating 10 variations of ad copy where some will be garbage is fine — you just regenerate. Low stakes make the chaos of all-to-all communication acceptable. But don't use this for anything that ships to customers.

Visual Analogy

Think about how you'd tackle a complex project in real life. You don't hire one super-generalist to do everything. You build a team: specialists who are really good at their specific thing and hand work off to each other. The researcher gathers intelligence, the designer creates visuals, the writer crafts the message. Each agent is a specialist; the orchestration pattern is your project management style — linear (waterfall), parallel (concurrent sprints), hierarchical (manager coordinates), or chaotic (open brainstorming).

Common Misconception: "More agents means better results"

If one agent is good, five must be better, right? Wrong. For simple tasks, multi-agent systems add unnecessary complexity, slow things down, and make debugging significantly harder. You get communication overhead between agents, potential resource conflicts if two agents try to modify the same file, and complex task dependencies. Start with the simplest coordination method you can and only add complexity as needed. A single agent with good tools and reflection will outperform a poorly coordinated team of five agents. Multi-agent is for when specialization and parallelism provide clear value — not as a default.

Module 06

Production Systems — Scale, Optimize & Secure

The techniques that take you from prototype to production: decomposition patterns, optimization, observability, and security.

A · Core Explanation

From Prototype to Production

Moving from prototype to production requires fundamentally different tools, mindsets, and discipline. The techniques that got you from zero to prototype won't take you from prototype to production. Four decomposition patterns guide how to split complex work across agents. Functional decomposition splits by technical domain — front-end, backend, database — creating specialists for each. Spatial decomposition splits by file or directory structure, powerful for large-scale refactoring across many independent files. Temporal decomposition splits by sequential stages where later phases depend on earlier ones, like a product launch flowing from research to planning to assets to execution. Data-driven decomposition partitions by data chunks, useful for processing large datasets like log files by time or service.

When performance needs improvement, first distinguish between non-LLM components (web search, RAG retrieval, code execution, PDF parsers) and LLM components (generation, extraction, reasoning). Non-LLM components improve by tuning parameters — chunk sizes, similarity thresholds, top-K results — or swapping providers. LLM components improve through better prompts, few-shot examples, trying different models, or decomposing hard tasks further. Fine-tuning is a last resort: costly, reserved for mature systems needing final percentage-point gains.

Latency optimization starts with baselining each step's duration, then parallelizing independent tasks, right-sizing models (small for simple work, large for synthesis), trying faster providers, and trimming context. Cost optimization follows the same pattern: measure per-step costs (LLM tokens, API calls, infrastructure), attack the biggest buckets first, tier models, cache aggressively, constrain outputs to reduce tokens, and batch operations. Observability for AI differs from traditional software because systems are non-deterministic. You need zoom-in metrics (full traces with prompts, tool calls, decisions) for debugging individual runs, and zoom-out metrics (quality scores, hallucination rates, trends) for system health. Security concerns are unique: prompt injection, unsafe code generation, data leakage, and resource exhaustion all require proactive defenses including sandboxing, resource limits, library whitelisting, and input/output sanitation.

B · Real-World Examples

Decomposition Patterns in Practice

● Obvious

Functional: Full-Stack Feature

Front-end agent, backend agent, database agent — each specialized in its domain. This is what we've been using in examples throughout: split by the kind of work that needs to be done.

◈ Counter-Intuitive

Spatial: Refactoring by Directory

Instead of splitting by function, split by file directory. Agents work on separate parts of the codebase in parallel, minimizing conflicts. This breaks down if files have complex dependencies on each other.

▲ Edge Case

Mixing Patterns

A full-stack feature uses functional decomposition at the top level (front-end, backend, database), but the backend agent internally uses temporal decomposition (first schema, then API, then tests). Patterns can nest.

Visual Analogy

Going from prototype to production is like going from a home kitchen to a restaurant kitchen. Same dishes, totally different discipline. At home, you can taste as you go, adjust freely, and serve when ready. In a restaurant, you need health codes, inventory management, consistency under volume, cost controls, and safety protocols. The techniques that make a great home cook won't make a great restaurant. Similarly, the hack that got your prototype working won't make it reliable at scale.

Common Misconception: "If the prototype works, it's production-ready"

A working prototype feels like 90% of the job done. The reality: it's maybe 20%. The techniques that get you from zero to prototype — quick prompts, no guardrails, no observability — won't take you from prototype to production. You need observability (traces, quality sampling, hallucination tracking), security (prompt injection defense, sandboxed code execution, data leakage prevention), cost optimization (model tiering, caching, output constraints), and evaluation infrastructure (component-level and end-to-end). Without these, your agent will fail silently, cost unpredictably, and be vulnerable to manipulation. Production is a different discipline entirely.

Step 2: Where's the latency? LLM generation: 25s, web search: 12s, tool execution: 8s. Baseline each step.
Step 3: What can you parallelize? Multiple web searches can run concurrently — saves ~8s.
Step 4: Can you tier models? Use a small model for keyword generation, large model for synthesis — saves 40% on LLM cost.
Step 5: What can you cache? Search results for identical queries — saves 30% on API costs.
Outcome: Combined optimizations can cut cost by 50% and latency by 40% without sacrificing quality. Measure first, optimize second.

Still Confused?

Frequently Asked Questions

What's the actual difference between an agent and a regular ChatGPT call?
A regular LLM call generates everything in one linear pass — you ask for an essay, it writes the whole thing start to finish. An agent works iteratively: it plans, researches using tools (web search, databases), drafts, reflects on its own work, and revises. This ReAct loop (Reason, Act, Observe) produces stronger reasoning, fewer hallucinations, and better organization. The agent can also call external functions — something a plain LLM cannot do. Think of it as the difference between asking someone to write an essay from memory in one sitting versus giving them time to research, outline, draft, and revise.
When should I NOT use an agent?
Don't use an agent when a task is simple, low-complexity, and can be done in a single pass. If you just need a keyword extracted, a single sentence translated, or a straightforward factual answer, a standard LLM call is faster, cheaper, and sufficient. Agents add latency, cost, and complexity — they're worth it only when tasks need iteration, research, multi-step processes, or tool use. The complexity-precision matrix helps: low complexity / low precision tasks (simple Q&A) don't need agents. Start with high complexity / low precision tasks for the best early wins.
Do I need a framework like LangChain or CrewAI to build agents?
No, but they help you start faster. Frameworks like CrewAI (used in this lesson's demo), LangGraph, and others provide pre-built components for agent orchestration, tool management, and evaluation. For prototyping and personal projects, they're excellent. For production systems, some teams prefer building directly with provider SDKs for maximum control and fewer dependencies. The principles you've learned — context engineering, task decomposition, guardrails, evaluation — apply regardless of framework. Start with a framework to learn, then decide based on your production needs.
How many agents should my system have?
Start with one. Add more only when the task demands specialization or parallelism that a single agent can't provide. A common mistake is over-engineering with five agents when one with good tools and reflection would suffice. For the marketing brochure example, three agents (researcher, designer, writer) make sense because each needs different tools and expertise. For summarizing customer feedback, one agent is plenty. The rule: if you can't articulate why each additional agent exists and what unique tools/role it has, you don't need it.
What's the difference between memory and knowledge — they seem similar?
They serve fundamentally different purposes. Knowledge is static reference material loaded once — PDFs, documentation, database access. It doesn't change between runs. The agent consults it for facts but never modifies it. Memory is dynamic and updates every run. Short-term memory is notes the agent takes during the current task (other agents can read these in multi-agent systems). Long-term memory stores lessons learned — what worked, what failed, what to do differently next time. Without knowledge, the agent hallucinates facts. Without memory, it repeats mistakes. You need both, but they're not interchangeable.
How do I evaluate my agent if the output is subjective (like essay quality)?
Use a second LLM as a judge. Give it a consistent grading rubric (e.g., rate 1-5 on clarity, argument strength, citation accuracy) and have it evaluate the output. This isn't perfect — LLM judges have their own biases — but it's scalable and gives you a baseline. Also evaluate at two levels: component-level (is each step working? are search queries relevant? is the draft coherent?) and end-to-end (is the final output good?). For subjective outputs, combine LLM judging with periodic human review of a sample. Start evaluating early with a simple rubric and iterate — don't wait for a perfect evaluation system.
Is fine-tuning necessary for production agent systems?
Almost never, at least initially. Fine-tuning is costly, requires curated training data, and is hard to reverse. Before considering it, exhaust other options: improve prompts (explicit instructions, constraints, schemas), add few-shot examples, try different models (some follow instructions better), decompose hard tasks into smaller pieces, and ensure your tools and context are well-engineered. Fine-tuning is a last resort for mature systems where you've squeezed out every other optimization and need those last few percentage points of quality. Most production agents never need it.
How do I prevent prompt injection attacks?
Prompt injection — malicious content in user input or external data that hijacks your agent's instructions — is one of the most serious security threats. Defenses include: (1) Separate system instructions from user/external content with clear delimiters. (2) Validate and sanitize all inputs before they reach the agent. (3) Use guardrails to detect unusual requests (e.g., "ignore previous instructions"). (4) Scope tools per agent with least privilege — don't give an agent more access than it needs. (5) For code execution, sandbox everything in Docker with resource limits, library whitelists, and no network access unless explicitly needed. (6) Scan outputs for sensitive data (PII, API keys) before returning them to users. No single defense is sufficient — layer them.
