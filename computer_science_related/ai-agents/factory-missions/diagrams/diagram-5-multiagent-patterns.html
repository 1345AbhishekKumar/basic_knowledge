Core Taxonomy · Multi-Agent Theory

Why Single-Agent Scaling Hits a Wall

A single agent tasked with an entire complex project (architecting, coding, debugging, and testing) quickly degrades due to context poisoning and cognitive overload. To coordinate multi-day autonomous missions, systems adopt explicit interaction topologies. Factory categorizes these into 5 foundational patterns.

Pattern 02 · The Essential Standard

Creator-Verifier & Sunk-Cost Bias

When an agent writes code, it develops an inherent cognitive bias toward believing its implementation is correct. If the same agent is asked to test its own code, it writes tests that merely confirm its previous assumptions. Creator-Verifier separates implementation and testing into two distinct agents with fresh context windows.

1. The 5 Interaction Patterns Defined (Labels in Figure 1.0)

Pattern 01 · Column 1

01 · Delegation (Hierarchical 1-to-1)

Definition: A parent supervisor agent identifies a bounded subtask (e.g., "Inspect database schema for user table") and spawns an ephemeral worker agent. The parent pauses or continues working, then ingests the worker's returned answer. Strict single-hierarchy control.

Pattern 02 · Column 2

02 · Creator-Verifier (Separation of Concerns)

Definition: A strict dual-agent protocol where the Creator generates code or plans, and a completely separate Verifier (with a fresh context window that never saw code generation) validates the output against independent assertions. Eliminates confirmation bias.

Pattern 03 · Column 3

03 · Direct Peer-to-Peer (Mesh Network)

Definition: Uncoordinated direct messaging between peers (Agent A chats with Agent B).
High Risk (State Fragmentation): Without a central orchestrator or shared blackboard, agents frequently disagree on state, create contradictory file edits, or drift out of alignment.

Pattern 04 · Column 4

04 · Negotiation (Conflict Resolution)

Definition: A structured protocol where two agents with conflicting requirements (e.g., Backend Droid changing an API signature vs. Frontend Droid expecting the old schema) exchange trade proposals and converge on a mutually compatible contract boundary.

Pattern 05 · Column 5

05 · Broadcast (1-to-Many Coherence)

Definition: A publish-subscribe mechanism where an Orchestrator publishes global state updates, schema locks, or milestone completions to all active worker droids simultaneously, maintaining system-wide coherence across 16-day runs.

Architecture Rule

When to Use Which Pattern

Use Delegation for quick utility lookups; use Creator-Verifier for all code generation; avoid uncoordinated Direct P2P; use Negotiation at milestone boundaries; and use Broadcast for shared mission constraints.

2. Step-by-Step Flow: Tracing Each Pattern's Communication

Follow how information travels across the 5 architectural columns in Figure 1.0:

Flow 1 • Delegation (Column 1)

Parent receives user goal → Emits spawn_subagent(task="schema_check") → Child initializes in fresh sandbox → Child executes tool and extracts columns → Child returns 3-line response to Parent → Child terminates.

Flow 2 • Creator-Verifier (Column 2, Focal)

Creator Agent writes implementation code → Passes Git commit hash to Verifier → Verifier starts with Zero Context of Creator's thought process → Verifier independently runs the Pre-Code Validation Suite → Verifier returns binary verdict: Pass (merge) or Fail (actionable bug report).

Flow 3 • Negotiation (Column 4)

Backend Droid proposes API change: /users/v2 → Frontend Droid rejects: breaks UI modal → Backend Droid counters: add backward-compatible alias → Frontend Droid accepts → Agreement committed to contract log.

Flow 4 • Broadcast (Column 5)

Orchestrator finishes Milestone 1 → Publishes message to shared mission bus: MILESTONE_1_MERGED, DB_SCHEMA_V3_LOCKED → All active droids immediately update their local context configs, preventing contradictory assumptions across 16-day lifespans.
