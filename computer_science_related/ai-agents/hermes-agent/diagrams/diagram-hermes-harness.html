Hermes Agent Harness Architecture

Complete system design of Nous Research's Hermes Agent: local-first execution, multi-channel gateways, autonomous tool loops, and 3 persistent local memory tiers.

Detailed Architectural Explanations

1. Core Component Definitions (From Diagram Elements)

Every gateway, runtime engine, tool, and storage tier illustrated in Figure 1.0 is formally defined below:

DESKTOP APP & CLI

The native local operating system interface. Enables direct interactive shell commands, live streaming output, and graphical configuration panels on macOS, Linux, and Windows.

WHATSAPP BRIDGE

A local gateway bridge that exposes the agent over mobile messaging. It allows users to query their local machine, trigger scheduled jobs, and receive completion notifications on WhatsApp.

TELEGRAM / DISCORD WEBHOOKS

Secondary messaging gateways connecting team chat channels to the local agent harness via standard incoming and outgoing webhook listeners.

GATEWAY LOGS (hermes/logs/)

Disk-persisted raw telemetry containing end-to-end trajectory exports, error dumps, and timestamped session records for debugging and performance analysis.

ACTIVE WORKING MEMORY

The dynamic context composition constructed for each LLM turn: combining the system identity (`SOUL.md`), high-priority procedural rules (`skills/*.md`), distilled facts (`MEMORY.md`), and recent chat turns within token budget.

AUTONOMOUS TOOL LOOP ENGINE

The heart of the harness. Orchestrates the iterative loop of Reasoning → Structured Tool Dispatch → Environment Evaluation until a task is completely resolved.

TERMINAL / SHELL

Local execution sandbox providing direct bash command execution, file inspection, process management, and local environment scripting.

BROWSER CONTROL

Headless browser automation for navigating web applications, scraping dynamic DOM content, submitting forms, and performing web searches.

DELEGATE_TASK (PARALLEL SUBAGENTS)

A tool that forks execution by launching isolated subagents to handle sub-problems concurrently, returning clean summarized outcomes to prevent context pollution in the main agent.

CLAUDE CODE CLI

Headless invocation of specialized external coding assistants (like Claude Code CLI or Aider) to generate multi-file scripts and execute local automated test suites.

CRON_JOB SCHEDULER

Time-based trigger mechanism enabling the agent to schedule future autonomous workflows, recurring maintenance, and scheduled alerts.

SKILL MANAGER

An autonomous routine that monitors tool usage. When a task requires more than 5 tool calls to succeed, it synthesizes the solution into a new procedural markdown skill in `hermes/skills/`.

USER REPLY DISPATCH

The outbound formatting layer that adopts the designated persona (e.g., Pikachu persona defined in `SOUL.md`) and routes the final verified response back to the originating entry gateway.

PROCEDURAL MEMORY (hermes/skills/*.md)

Stores executable guidelines and procedural knowledge (e.g., `SOUL.md`, `video-prep.md`, `claude-cli.md`) that teach the agent how to execute recurring domain workflows.

SEMANTIC MEMORY (hermes/memories/MEMORY.md)

A single, human-readable markdown knowledge base storing verified durable truths, user preferences (e.g., pytest vs unittest), and environment quirks.

EPISODIC MEMORY (hermes/state.db)

An embedded SQLite database with FTS5 full-text indexing storing chronological chat turns, tool parameters, and exact timestamps across all historic interactions.

CONSOLIDATION ENGINE

An auxiliary background Nous model that periodically sweeps `state.db` during idle periods, distill high-signal facts, and updates `MEMORY.md` while pruning redundant noise.

2. Step-by-Step Diagram Flow Walkthrough

Tracing the execution lifecycle from inbound trigger through the runtime loop to three-tier storage:

  1. 1

    Inbound Ingestion from Gateways (Left Column)

    A prompt arrives via the Desktop App CLI, WhatsApp Bridge, or Telegram/Discord. The gateway parses the payload, assigns a session ID, and appends the raw event to hermes/logs/.

  2. 2

    Active Working Memory Assembly (Arrow to Middle Column)

    The harness reads SOUL.md for persona guidelines, loads relevant SOPs from hermes/skills/, and injects durable user preferences from MEMORY.md, creating a context window grounded in local truth.

  3. 3

    Autonomous Tool Loop Execution (Center Box)

    The runtime enters the autonomous loop:
    • The model emits a tool call (e.g. Terminal, Browser, or delegate_task).
    • The harness executes the tool locally and captures stdout/stderr.
    • The result is fed back into the context buffer for the next reasoning step.

  4. 4

    Guardrail Check & User Reply Dispatch (Bottom of Middle Column)

    When the task is solved (or if max error limits are hit), the loop breaks. The User Reply Dispatch formats the final text using the active persona and transmits it back to the originating gateway.

  5. 5

    Multi-Tier Local Disk Storage Persistence (Arrows to Right Column)

    The harness writes the session to disk across three dedicated memory channels:
    • Top Arrow: Procedural skills are saved if the Skill Manager generated a new SOP.
    • Middle Coral Arrow: Immediate quirks or explicit user facts are appended to MEMORY.md.
    • Bottom Arrow: Complete timestamped turns are saved into SQLite state.db with FTS5 search.

  6. 6

    Background Distillation by Auxiliary Model (Dashed Box)

    During idle periods, the Consolidation Engine queries unprocessed rows in state.db, identifies durable patterns (e.g. preferred coding idioms), and writes refined entries into MEMORY.md.

3. Concrete Implementation Blueprint: Complete Harness Architecture

The Python code below demonstrates the full three-tier architecture: Gateway Ingestion, Active Working Context Assembly, Autonomous Tool Loop, and SQLite FTS5 persistence: 

import sqlite3
import subprocess
from pathlib import Path
from dataclasses import dataclass
from typing import Dict, Any, List

@dataclass
class GatewayMessage:
    channel: str  # desktop_cli, whatsapp, telegram
    user_id: str
    text: str

class HermesHarnessArchitecture:
    def __init__(self, root_dir="./hermes"):
        self.root = Path(root_dir)
        self.skills_dir = self.root / "skills"
        self.memories_dir = self.root / "memories"
        self.logs_dir = self.root / "logs"
        self.db_path = self.root / "state.db"
        
        for d in [self.skills_dir, self.memories_dir, self.logs_dir]:
            d.mkdir(parents=True, exist_ok=True)
        self._init_sqlite()

    def _init_sqlite(self):
        with sqlite3.connect(self.db_path) as conn:
            conn.execute("""
                CREATE VIRTUAL TABLE IF NOT EXISTS conversation_history 
                USING fts5(session_id, channel, role, content, timestamp);
            """)

    def compose_active_working_memory(self, user_prompt: str) -> str:
        """Composes Column 2 Active Context: SOUL + Skills + MEMORY.md."""
        soul = (self.root / "SOUL.md").read_text() if (self.root / "SOUL.md").exists() else "Identity: Hermes Agent"
        memory = (self.memories_dir / "MEMORY.md").read_text() if (self.memories_dir / "MEMORY.md").exists() else ""
        skills = [f.stem for f in self.skills_dir.glob("*.md")]
        
        return (
            f"=== SYSTEM PERSONA ===\n{soul}\n\n"
            f"=== SEMANTIC MEMORY (MEMORY.md) ===\n{memory}\n\n"
            f"=== PROCEDURAL SKILLS ===\n{', '.join(skills)}\n\n"
            f"=== USER QUERY ===\n{user_prompt}"
        )

    def autonomous_tool_loop(self, context: str, max_turns: int = 5) -> str:
        """Simulates ReAct tool loop engine with guardrail."""
        turns = 0
        tool_results = []
        
        while turns < max_turns:
            turns += 1
            # Mock decision: turn 1 executes terminal, turn 2 finishes
            if turns == 1:
                cmd = "echo 'Listing local workspace files...'"
                res = subprocess.run(cmd, shell=True, capture_output=True, text=True)
                tool_results.append(f"terminal output: {res.stdout.strip()}")
            else:
                # Guardrail: task completed
                break
                
        return f"Completed in {turns} turns. Actions taken: {tool_results}"

    def persist_three_tiers(self, session_id: str, channel: str, query: str, answer: str, new_quirk: str = None):
        """Persists state across the 3 Local Disk Storage columns."""
        # Tier 1: Procedural - Handled by skill creator if >5 calls
        # Tier 2: Semantic Memory (MEMORY.md)
        if new_quirk:
            with open(self.memories_dir / "MEMORY.md", "a") as f:
                f.write(f"\n- [Quirk] {new_quirk}")
                
        # Tier 3: Episodic Memory (state.db SQLite FTS5)
        with sqlite3.connect(self.db_path) as conn:
            conn.execute(
                "INSERT INTO conversation_history VALUES (?, ?, 'user', ?, datetime('now'))",
                (session_id, channel, query)
            )
            conn.execute(
                "INSERT INTO conversation_history VALUES (?, ?, 'assistant', ?, datetime('now'))",
                (session_id, channel, answer)
            )
        print(f"[✓] Persisted session {session_id} to 3-tier local storage.")

if __name__ == "__main__":
    harness = HermesHarnessArchitecture()
    msg = GatewayMessage("whatsapp", "user_101", "Analyze system load")
    
    # 1. Gateway Ingestion & Working Memory Composition
    ctx = harness.compose_active_working_memory(msg.text)
    
    # 2. Autonomous Tool Loop Engine
    result = harness.autonomous_tool_loop(ctx)
    
    # 3. Dispatch & Persistence
    harness.persist_three_tiers("sess_101", msg.channel, msg.text, result, new_quirk="Server responds slowly on Mondays")
