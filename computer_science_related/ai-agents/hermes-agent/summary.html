Executive Summary & Core Philosophy

Hermes Agent Harness & Loop Engineering

How Nous Research's 200k+ star open-source Hermes Agent achieves autonomous self-improvement on local machines using multi-channel gateways, autonomous tool loops, and local three-pillar persistence.

1. The "Horse vs. Harness" Reality

In AI agent systems, the LLM is the Horse—a raw, powerful, high-velocity cognitive engine (such as Gemini 3.1, Claude 3.5 Sonnet, or Nous Hermes). However, without gear, the horse is wild, stateless, and unable to interact with the physical operating system.

The Harness is the entire operating framework surrounding the model: the multi-channel gateway (Desktop CLI, WhatsApp), the active working memory context budget, the autonomous tool loop (terminal, browser, cron, Claude CLI), and the local three-pillar persistent memory system.

"Don't overcomplicate the buzzword: The harness is simply the saddle, bridle, and toolbelt that allows you to ride and steer the raw power of the LLM toward durable, real-world goals."

— Core Engineering Tenet

2. Complete Local-First Architecture

Unlike cloud-locked agent frameworks, Hermes executes 100% locally on your machine (macOS, Linux, Windows, Docker, or VPS). No sensitive enterprise memories or execution traces leave your local disk.

3. The Self-Improving Learning Loop

What truly sets Hermes apart is its **autonomous self-refinement cycle**:

Phase 01

Observation & Quirk Learning

When a web scraper or Python script encounters an error, Hermes updates MEMORY.md immediately with the quirk (e.g. YouTube URL formatting) to avoid repeating the mistake.

Phase 02 · Core

Autonomous Skill Creation

After complex, iterative tasks requiring five or more tool calls, Hermes synthesizes a reusable SOP and saves it into hermes/skills/<skill-name>.md for zero-shot future runs.

Phase 03

Idle-Time Distillation

Auxiliary background LLMs periodically sweep state.db conversation history, extract high-signal user preferences (e.g. favorite testing framework = pytest), and prune conversational noise.

Key Architectural Takeaways

  • Zero Cloud Lock-In: Complete local disk autonomy across `SOUL.md`, `MEMORY.md`, and `state.db`.
  • Headless Tool Delegation: Hermes can spawn headless Claude Code CLI sessions to autonomously write, verify, and execute Python scripts (`fetch_hackernews.py`).
  • Compounding User Value: As you interact across desktop and WhatsApp, the agent becomes increasingly personalized without manual prompt restructuring.

4. Comprehensive Concept Definitions (Diagram Elements)

Every component, gateway, tool, and storage layer shown in Figure 1.0 is formally defined below:

THE HORSE (FOUNDATION LLM)

The underlying autoregressive neural network (e.g., Nous Hermes 3, Claude 3.5 Sonnet, Gemini Pro). It provides cognitive horsepower, pattern recognition, and language generation, but is fundamentally stateless, lacks direct system access, and cannot act without scaffolding.

THE HARNESS (OPERATING SYSTEM SCAFFOLDING)

The entire local runtime wrapping the LLM. It manages inbound gateways, context assembly, iterative tool dispatch, execution sandboxes, error recovery, and persistent disk storage.

DESKTOP APP & CLI GATEWAY

The primary interactive interface running on the user's local operating system. It accepts direct keyboard inputs, renders rich terminal output, and facilitates interactive human-in-the-loop approvals.

WHATSAPP BRIDGE

A decoupled remote chat gateway using local webhooks/baileys. It allows the user to trigger agent workflows, receive status alerts, and delegate tasks asynchronously from a mobile device while the agent executes on the local host.

CRON DAEMON

A local recurring scheduler that periodically awakens the agent runtime to execute background duties (e.g., morning news summaries, health checks, disk maintenance) without active user intervention.

EXECUTION LOGS (hermes/logs/)

Disk-persisted JSON/text trajectories recording every input prompt, model thinking trace, tool invocation parameters, and environment output for full post-hoc auditing.

ACTIVE WORKING CONTEXT

The live RAM budget assembled for each turn. It dynamically concats the system prompt (`SOUL.md`), high-relevance procedural skills (`skills/*.md`), and long-term user facts (`MEMORY.md`) within token safety limits.

SOUL.md (PERSONA & CONSTRAINTS)

A local Markdown document defining the agent's enduring identity (e.g., Pikachu persona), voice tone, ethical boundaries, execution rules, and core behavioral invariants.

TOOL EXECUTION LOOP

The autonomous ReAct cycle: the model emits structured JSON tool calls, the runtime executes them locally, and the resulting stdout/stderr is appended back into context until the goal is achieved.

DELEGATE_TASK (SUBAGENTS)

A specialized harness tool that spins up a sub-agent in a clean, isolated context window. This prevents token bloat and context poisoning in the primary agent when performing lengthy exploratory tasks.

CLAUDE CODE CLI (HEADLESS)

Hermes's capability to invoke external coding sub-processes (like Claude Code CLI or Aider) in non-interactive mode to build scripts, run local test suites, and report back the result.

PROACTIVE SKILL CREATOR

An autonomous routine that monitors tool-call chains. When a task requires 5 or more iterative steps to resolve successfully, the agent extracts the procedural recipe into a reusable Markdown SOP in `hermes/skills/`.

PROCEDURAL MEMORY (hermes/skills/*.md)

The "how-to" memory tier. Contains modular, human-readable markdown files specifying standard operating procedures, command recipes, and tool parameters that the agent can read on demand.

SEMANTIC MEMORY (hermes/memories/MEMORY.md)

The "facts & preferences" tier. A single curated markdown file storing distilled knowledge about the user, project settings, environment quirks, and validated truths across sessions.

EPISODIC MEMORY (hermes/state.db)

The "raw history" tier. A local SQLite database powered by FTS5 full-text search storing past conversational turns, tool outputs, and timestamps, continuously pruned by an auxiliary background distillation job.

5. Step-by-Step Runtime Execution Flow

Tracing how a request moves visually across Figure 1.0 from entry gateways, through the autonomous runtime, into local storage:

  1. 1

    Gateway Ingestion (Left Column)

    An inbound trigger enters via the Desktop App & CLI (interactive prompt), the WhatsApp Bridge (remote message), or the Cron Daemon (time-based schedule). The gateway packages the input payload and records an initial entry in hermes/logs/.

  2. 2

    Context Assembly & Loading (Arrow to Runtime)

    The harness assembles the Active Working Context: reading identity from SOUL.md, relevant SOPs from hermes/skills/, and recent user preferences from MEMORY.md. The combined prompt is dispatched to the foundation LLM.

  3. 3

    Autonomous Tool Loop Execution (Center Column)

    The model inspects the goal and invokes local tools: executing terminal bash scripts, navigating headless browsers, delegating complex research to isolated subagents via delegate_task, or triggering headless Claude Code CLI. Each tool outcome is fed back to the model in an autonomous loop.

  4. 4

    Three-Tier Local Persistence & Learning (Arrow to Storage)

    Upon task completion, the harness synchronizes results to local disk:
    • Episodic: Saves raw conversation transcript to state.db (SQLite FTS5).
    • Semantic: If novel user facts or environment quirks were discovered, appends them to MEMORY.md.
    • Procedural: If the task required ≥ 5 tool steps, the Proactive Skill Creator synthesizes a new SOP in skills/*.md.

6. Concrete Implementation Blueprint: Hermes Local Harness Loop

The Python code below illustrates the complete local harness cycle: gateway dispatch, active context loading, tool execution, and local 3-tier memory persistence. 

import sqlite3
import subprocess
from pathlib import Path
from typing import List, Dict, Any

class HermesLocalHarness:
    def __init__(self, root_dir: str = "./hermes"):
        self.root = Path(root_dir)
        self.skills_dir = self.root / "skills"
        self.memories_dir = self.root / "memories"
        self.logs_dir = self.root / "logs"
        self.db_path = self.root / "state.db"
        
        # Ensure directory structure exists
        self.skills_dir.mkdir(parents=True, exist_ok=True)
        self.memories_dir.mkdir(parents=True, exist_ok=True)
        self.logs_dir.mkdir(parents=True, exist_ok=True)
        self._init_sqlite()

    def _init_sqlite(self):
        """Tier 3: Episodic Memory using SQLite FTS5."""
        with sqlite3.connect(self.db_path) as conn:
            conn.execute("""
                CREATE VIRTUAL TABLE IF NOT EXISTS episodic_logs 
                USING fts5(session_id, role, content, timestamp);
            """)

    def load_active_context(self) -> str:
        """Assembles working context: SOUL.md + MEMORY.md + Skills catalog."""
        soul = (self.root / "SOUL.md").read_text() if (self.root / "SOUL.md").exists() else "Identity: Hermes Agent"
        memory = (self.memories_dir / "MEMORY.md").read_text() if (self.memories_dir / "MEMORY.md").exists() else ""
        skills = [f.stem for f in self.skills_dir.glob("*.md")]
        
        return f"{soul}\n\n=== SEMANTIC MEMORY ===\n{memory}\n\n=== AVAILABLE SKILLS ===\n{', '.join(skills)}"

    def execute_tool(self, tool_name: str, **kwargs) -> str:
        """Local tool execution dispatcher."""
        if tool_name == "terminal":
            cmd = kwargs.get("command", "")
            res = subprocess.run(cmd, shell=True, capture_output=True, text=True, timeout=30)
            return res.stdout or res.stderr
        elif tool_name == "delegate_task":
            # Headless subagent dispatch in isolated process
            subgoal = kwargs.get("subgoal", "")
            return f"Subagent completed task: {subgoal}"
        return f"Unknown tool: {tool_name}"

    def auto_persist_memory(self, session_id: str, tool_call_count: int, key_learnings: str, new_skill_code: str = None):
        """Three-tier memory update upon task resolution."""
        # 1. Update Semantic Memory (MEMORY.md)
        if key_learnings:
            mem_file = self.memories_dir / "MEMORY.md"
            with open(mem_file, "a") as f:
                f.write(f"\n- {key_learnings}")
            print("[+] Updated Semantic Memory (MEMORY.md)")

        # 2. Update Procedural Memory if complex task (>= 5 calls)
        if tool_call_count >= 5 and new_skill_code:
            skill_name = "auto_synthesized_workflow.md"
            (self.skills_dir / skill_name).write_text(new_skill_code)
            print(f"[+] Proactive Skill Creator saved: {skill_name}")

        # 3. Update Episodic Database (state.db)
        with sqlite3.connect(self.db_path) as conn:
            conn.execute(
                "INSERT INTO episodic_logs (session_id, role, content, timestamp) VALUES (?, ?, ?, datetime('now'))",
                (session_id, "summary", key_learnings)
            )
        print("[+] Episodic session indexed in state.db")

# Example execution
if __name__ == "__main__":
    harness = HermesLocalHarness()
    context = harness.load_active_context()
    print("[*] Active Working Context Assembled:\n", context[:120], "...\n")
    
    # Simulate autonomous tool execution
    out = harness.execute_tool("terminal", command="echo 'Hermes Local Test'")
    print("[*] Tool Result:", out.strip())
    
    # Autonomous learning persistence
    harness.auto_persist_memory("sess-001", tool_call_count=6, key_learnings="User prefers uv over pip", new_skill_code="# UV Setup SOP\nRun uv venv")
