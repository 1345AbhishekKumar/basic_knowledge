01 / FOUNDATION

Understand the problem before multiplying agents.

Multi-agent architecture is not “put several LLMs in a graph.” The correct abstraction is a set of independently meaningful decision-making components that coordinate toward a system goal.

The first architectural rule

Do not introduce multiple agents until you can identify a concrete reason one agent cannot reliably perform the task. More agents increase coordination, latency, failure modes, state complexity, and observability requirements.

What is an agent?

An agent is a software component that observes context, reasons over it, chooses actions, executes those actions through tools or APIs, maintains state where necessary, and evaluates the resulting state. An LLM can provide the reasoning engine, but the agent is the complete control loop — not merely the model.

When should you use MAS?

Prefer one agent when

  • The task has one coherent objective.
  • The context fits within a manageable working memory.
  • One policy can safely control all tools.
  • Coordination would cost more than specialization provides.
  • The workflow is mostly deterministic.

Consider multiple agents when

  • Different domains require genuinely different expertise.
  • Independent subtasks can run concurrently.
  • Different security boundaries are required.
  • Independent evaluation improves reliability.
  • The environment naturally contains multiple decision makers.

MAS success criteria

Autonomy

Agents can select actions within explicitly defined boundaries rather than requiring a human to specify every step.

Decentralization

Decision authority can be distributed when centralization becomes a bottleneck or creates a single point of failure.

Adaptability

The system can respond to changing tasks, information, resources, and environmental conditions.

Scalability

Independent work can scale horizontally without proportionally increasing coordination cost.

Robustness

Individual agent failures do not automatically become system-wide failures.

Observability

You can reconstruct why the system acted, which agent acted, which tools were called, and where latency or errors originated.

Common application domains

Domain Potential agents Why multiple agents?
Customer service Billing, technical, returns, escalation Domain specialization
Supply chain Supplier, warehouse, logistics, retailer Distributed decisions
Finance Research, risk, execution, compliance Separation of responsibilities
Software engineering Planner, coder, tester, reviewer Independent verification
Robotics Perception, navigation, manipulation Real-time specialization
Smart grids Generation, storage, load, market Distributed optimization
Games NPCs, strategist, planner, environment Emergent interaction

MAS-specific risks

Coordination explosion

If every agent can communicate with every other agent, the interaction graph can become difficult to reason about. Prefer explicit communication paths.

Emergent behavior

Individual agents can behave correctly while their interaction produces undesirable system-level behavior.

Debugging complexity

A failure may originate from the model, prompt, tool, state, routing decision, stale message, or another agent's output.

Cost multiplication

Five agents do not merely mean five prompts. Retries, reflection, context transfer, evaluation, and tool calls can multiply cost.

Knowledge Check
Which is the strongest reason to split one agent into multiple agents?
Correct. Agent boundaries should solve a concrete architectural problem. Complexity is a cost, not a feature.
02 / PROGRESSION

Build the ladder, not the monster.

The safest way to learn and engineer MAS is incremental: establish a reliable single-agent control loop first, then introduce specialization and coordination one architectural dimension at a time.

Mental model

Think of MAS as a progression of control structures. Each new pattern adds coordination power — and coordination cost.

Level 1 — Single Agent

Start with one agent that owns one objective and a bounded collection of tools. This establishes your basic runtime abstraction.

Single-agent architecture One decision maker
flowchart LR U["User"] --> A["Agent"] A --> M["LLM / Reasoner"] A --> T1["Search"] A --> T2["Database"] A --> T3["API"] A --> S["State / Memory"] A --> R["Response"]
single-agent.ts 
type AgentContext = {
  userId: string;
  messages: Message[];
};

const supportAgent = {
  name: "support-agent",

  systemPrompt: `
    You are a customer support agent.
    Diagnose the request, use tools when necessary,
    and never invent account information.
  `,

  tools: [
    getCustomer,
    searchKnowledgeBase,
    createTicket
  ],

  async run(ctx: AgentContext) {
    return llm.generate({
      system: this.systemPrompt,
      messages: ctx.messages,
      tools: this.tools
    });
  }
};
Do this first

Measure the single agent. Record success rate, tool accuracy, latency, token usage, cost, and failure categories. Otherwise you will have no baseline for deciding whether multi-agent complexity actually helped.

Level 2 — Agent + Tools + Memory

An agent becomes useful when it can affect the world. Tools are its action interface; memory provides continuity beyond the current context window.

Agent with capabilities Reasoning + action + state
flowchart TB U["User"] --> A["Agent"] A --> B["Reasoning"] B --> P["Planning"] P --> TS["Tool Selection"] TS --> T["Tool Runtime"] T --> E["External Systems"] A <--> W["Working Memory"] A <--> L["Long-Term Memory"] E --> O["Observation"] O --> A

Separate these concepts

Context

Information currently available to the model during a run.

State

Structured information required to continue or reconstruct execution.

Memory

Information intentionally retained across interactions or tasks.

Level 3 — Sequential Agents

The simplest true multi-agent pattern is a pipeline. Each agent transforms the output of the previous stage.

Sequential agent architecture Assembly line
flowchart LR I["Input"] --> A["Research Agent"] A --> B["Analysis Agent"] B --> C["Writer Agent"] C --> D["Reviewer Agent"] D --> O["Output"]

Example: research → analysis → writing → review. The important point is that the boundary exists because each stage has a distinct responsibility, not because four prompts look impressive on a diagram.

sequential-workflow.ts 
const research = await researchAgent.run(input);

const analysis = await analysisAgent.run({
  research
});

const draft = await writerAgent.run({
  research,
  analysis
});

const final = await reviewerAgent.run({
  draft,
  criteria
});
When sequential wins

Use it when dependencies are explicit: stage B genuinely needs stage A's output. Do not parallelize dependent work merely because parallel execution sounds faster.

Level 4 — Parallel Agents

Parallel execution is appropriate when multiple agents can solve independent views of the same problem without depending on one another's intermediate state.

Parallel agent architecture Fan-out → fan-in
flowchart TB I["Input"] --> F["Fan-out"] F --> A["Research A"] F --> B["Research B"] F --> C["Research C"] F --> D["Research D"] A --> J["Join / Aggregator"] B --> J C --> J D --> J J --> O["Combined Result"]
parallel-workflow.ts 
const results = await Promise.all([
  technicalAgent.run(task),
  financialAgent.run(task),
  marketAgent.run(task),
  riskAgent.run(task)
]);

const answer = await synthesizer.run({
  results
});

Benefit

Wall-clock latency can approach the slowest branch instead of the sum of all branch latencies.

Cost

Four branches may quadruple model calls and introduce conflicting outputs that the aggregator must resolve.

Level 5 — Router / Specialist Selection

A router decides which specialist should handle the task. Unlike a fan-out system, routing intentionally avoids invoking irrelevant agents.

Router architecture One request → selected specialist
flowchart LR U["User"] --> R["Router"] R -->|Billing| B["Billing Agent"] R -->|Technical| T["Technical Agent"] R -->|Returns| C["Returns Agent"] R -->|Unknown| H["Human Escalation"]

Routing can be deterministic, classifier-based, embedding-based, rule-based, LLM-based, or hybrid. For high-risk domains, deterministic constraints should dominate unconstrained model routing.

Level 6 — Orchestrator / Supervisor

An orchestrator owns the global workflow and delegates subtasks to specialized agents. This is one of the most common LLM-based MAS patterns.

Orchestrator architecture Central planning + delegation
flowchart TB U["User Goal"] --> O["Orchestrator / Supervisor"] O --> P["Planner"] P --> O O --> R["Research Agent"] O --> C["Coding Agent"] O --> T["Testing Agent"] O --> W["Writing Agent"] R --> O C --> O T --> O W --> O O --> V["Validator"] V --> O O --> F["Final Result"]
Critical distinction

An orchestrator is not necessarily an “agent manager.” It is a policy component responsible for deciding what work should happen, who should perform it, what information they receive, and whether the resulting state satisfies the goal.

Level 7 — Hierarchical Multi-Agent System

Hierarchical MAS Manager → teams → specialists
flowchart TB G["Global Coordinator"] --> M1["Research Manager"] G --> M2["Engineering Manager"] G --> M3["Operations Manager"] M1 --> R1["Web Researcher"] M1 --> R2["Data Researcher"] M2 --> E1["Coder"] M2 --> E2["Tester"] M2 --> E3["Reviewer"] M3 --> O1["Deployment"] M3 --> O2["Monitoring"]

Hierarchy becomes useful when a flat set of specialists becomes too large for one coordinator to manage directly. The price is additional delegation layers, state propagation, and potential information loss.

Level 8 — Peer-to-Peer / Choreography

Decentralized peer architecture Agents coordinate directly
graph LR A["Agent A"] <--> B["Agent B"] B <--> C["Agent C"] C <--> D["Agent D"] D <--> A A <--> C B <--> D

In choreography, there is no central component controlling every interaction. Agents respond to messages, events, contracts, or environmental changes according to local policies.

Use carefully

Peer-to-peer systems are powerful when autonomy and resilience matter, but they are substantially harder to debug. Introduce them only after centralized coordination has become a demonstrated bottleneck.

Knowledge Check
You have three independent research tasks. Which architecture is the natural first choice?
Correct. Independent tasks map naturally to fan-out/fan-in. Do not introduce negotiation or hierarchy without a reason.
03 / ARCHITECTURE

Choose the topology that matches the problem.

Architecture determines who makes decisions, where state lives, how messages travel, and what happens when a component fails.

Centralized architecture

Centralized supervisor
flowchart TB O["Supervisor"] --> A["Agent A"] O --> B["Agent B"] O --> C["Agent C"] O --> D["Agent D"] A --> O B --> O C --> O D --> O
  • Easy to understand.
  • Easy to observe.
  • Good fit for business workflows.
  • Can become a bottleneck.
  • Supervisor failure can become system failure.

Decentralized architecture

Peer-to-peer system
graph TD A["Supplier Agent"] <--> B["Warehouse Agent"] B <--> C["Logistics Agent"] C <--> D["Retailer Agent"] D <--> A A <--> C
  • High local autonomy.
  • No single coordinator bottleneck.
  • Natural for distributed environments.
  • Harder global reasoning.
  • Harder debugging and governance.

Hybrid / federated architecture

Federated hierarchy
flowchart TB G["Global Coordinator"] G --> R["Research Federation"] G --> E["Engineering Federation"] R --> R1["Research Agent A"] R --> R2["Research Agent B"] R1 <--> R2 E --> E1["Coding Agent"] E --> E2["Testing Agent"] E1 <--> E2

Agent-centric vs workflow-centric

Agent-centric

The agent is the primary abstraction. It owns goals, policies, memory, tools, and autonomous behavior.

Strong fit for open-ended environments and autonomous actors.

Workflow-centric

The workflow is the primary abstraction. Agents perform explicit nodes inside a controlled state machine or graph.

Strong fit for predictable business processes and production reliability.

Architecture decision matrix

Requirement Prefer Avoid
Deterministic business process Workflow / sequential graph Free-form autonomous agents
Independent research Parallel fan-out Sequential chain
Multiple domains Router / specialists One giant prompt
Complex dynamic goal Supervisor / planner Hard-coded sequence only
Distributed actors Choreography / events Central bottleneck
Strict auditability Explicit workflow + state machine Opaque agent-to-agent loops
High error cost Verification + deterministic gates Unvalidated autonomous execution

Core design principles

Single responsibility

One agent should have one coherent job.

Loose coupling

Agents should communicate through stable contracts.

High cohesion

Related capabilities should remain together.

Explicit state

Do not hide critical state inside prompts.

Fault isolation

One failed agent should fail locally whenever possible.

Observability

Every meaningful decision should be reconstructable.

04 / AGENT DESIGN

Design the agent before designing the team.

Every multi-agent system is composed of individual agents. Poor agent boundaries create poor system boundaries.

Agent internal architecture

Agent internals Goal-directed control loop
flowchart TB G["Goal / Objective"] G --> B["Beliefs / Context"] B --> D["Deliberation"] D --> I["Intention / Plan"] I --> A["Action Selection"] A --> T["Tools / Environment"] T --> O["Observations"] O --> B D <--> M["Memory"] D <--> P["Policy / Constraints"]

Agent types

Reactive agent

Maps observations directly to actions. Excellent for low-latency, well-defined rules.

Deliberative agent

Builds internal representations and reasons about future actions before acting.

Hybrid agent

Combines fast reactive behavior with slower deliberative planning.

BDI agent

Models beliefs, desires, and intentions explicitly. Useful for goal-directed autonomous systems.

Capabilities

Reasoning

Interpret evidence and determine plausible actions.

Planning

Decompose goals into ordered or conditional actions.

Memory

Retrieve relevant information from previous interactions.

Tool use

Invoke APIs, databases, search, code, and external systems.

Perception

Interpret text, images, telemetry, events, or environment state.

Evaluation

Determine whether an action produced an acceptable result.

How to define an agent

agent-contract.ts 
interface Agent {
  id: string;

  purpose: string;

Agent boundary test

If you cannot write a concise sentence describing what the agent owns, what it does not own, what inputs it accepts, and what output contract it guarantees, the agent boundary is probably premature.

05 / COMMUNICATION

Agents coordinate through contracts, not vibes.

Communication is an architectural boundary. Treat messages as APIs: version them, validate them, observe them, and define failure semantics.

Message anatomy

Agent message structure
flowchart TB M["Message"] M --> P["Performative / Intent"] M --> C["Content"] M --> O["Ontology / Schema"] M --> CID["Conversation ID"] M --> SID["Sender"] M --> R["Recipient"] M --> T["Timestamp"] M --> V["Protocol Version"]

ACL concepts

Traditional agent systems use concepts such as FIPA ACL and KQML. These approaches emphasize explicit communication intent (“performative”), message content, conversation context, and semantic interpretation.

Request

Ask another agent to perform an action.

Inform

Communicate information or a state transition.

Propose

Offer a candidate action or contract.

Accept

Agree to a proposal or contract.

Reject

Decline an offered action or contract.

Failure

Explicitly report unsuccessful execution.

Contract Net Protocol

Contract Net is a classic coordination mechanism: a manager announces a task, participants submit bids, the manager awards the task, and the winner executes it.

Contract Net interaction
sequenceDiagram participant M as Manager participant A as Agent A participant B as Agent B participant C as Agent C M->>A: Task announcement M->>B: Task announcement M->>C: Task announcement A->>M: Proposal B->>M: Proposal C->>M: Proposal M->>B: Award task M->>A: Reject M->>C: Reject B->>M: Result

Synchronous vs asynchronous communication

Synchronous

Caller waits for the response. Simple and useful for direct request-response interactions.

Risk: one slow dependency can block the entire workflow.

Asynchronous

Sender emits a message and execution continues. Useful for events, long-running tasks, retries, and distributed systems.

Risk: eventual consistency and message ordering become design concerns.

Message transport patterns

Direct messaging

Agent A directly addresses Agent B.

Message bus

Agents communicate through a broker or queue.

Publish / subscribe

Agents subscribe to event categories rather than direct recipients.

Blackboard

Agents read and write shared problem state rather than exchanging every detail directly.

MCP and A2A

Modern agent systems also use protocol-oriented interfaces. MCP (Model Context Protocol) focuses on standardized access to tools, resources, and context. Agent-to-Agent protocols such as A2A focus on interoperability and communication between agents or agentic services.

Architecture rule

Do not confuse a tool protocol with a coordination protocol. “How do I call this capability?” and “How do two autonomous actors negotiate work?” are different architectural questions.

06 / COORDINATION

Coordination is where MAS becomes a systems problem.

Once multiple agents exist, the central question changes from “Can this agent solve the task?” to “How does the system decide who does what, when, with which information, and under what failure conditions?”

Pattern 01
Sequential Pipeline

A fixed chain of transformations.

Best when dependencies are explicit and the process is stable. Example: extract → classify → analyze → write → review.
Pattern 02
Fan-out / Fan-in

Parallel specialists followed by aggregation.

Best for independent evidence collection. Requires a synthesis strategy to resolve contradictions.
Pattern 03
Map-Reduce

Partition work, process partitions, reduce results.

Useful for large collections where each partition can be processed independently.
Pattern 04
Delegation

A supervisor assigns work to specialists.

Useful for dynamic task decomposition where the exact workflow is not known in advance.
Pattern 05
Peer Collaboration

Agents coordinate without a central supervisor.

Appropriate when the environment is inherently distributed or local autonomy is important.
Pattern 06
Competition

Agents compete for tasks or resources.

Auctions and contract mechanisms can allocate scarce resources based on cost, capability, urgency, or expected utility.
Pattern 07
Human-in-the-loop

Humans approve critical decisions.

Use explicit approval gates for high-impact actions rather than hoping the model understands which decisions are irreversible.
Pattern 08
Recursive Delegation

Agents can create and coordinate sub-work.

Powerful but dangerous. Always enforce depth, budget, timeout, and recursion limits.

Workflow definition

workflow.ts 
const workflow = graph({
  version: "2.1",

  nodes: {
    research: researchAgent,
    analyze: analysisAgent,
    review: reviewerAgent,
    publish: publisherAgent
  },

  edges: [
    ["research", "analyze"],
    ["analyze", "review"],
    ["review", "publish"]
  ],

  retries: {
    review: 2
  },

  timeoutMs: 120000
});
Never allow uncontrolled loops

An autonomous multi-agent loop should have explicit limits: maximum steps, maximum depth, maximum wall-clock time, maximum budget, maximum tool calls, and termination criteria.

07 / DECISION

Planning, reasoning, learning, and self-correction.

Agent intelligence is not synonymous with chain-of-thought. Production systems require explicit planning interfaces, constrained tool execution, evaluation, and recovery.

Classical planning

STRIPS

Represents states, actions, preconditions, and effects. Useful for deterministic planning environments.

HTN

Hierarchical Task Networks decompose high-level tasks into increasingly concrete subtasks.

LLM planning

A language model proposes plans using natural language or structured intermediate representations.

LLM agent reasoning loop

Plan → execute → observe → revise
flowchart LR G["Goal"] --> P["Plan"] P --> A["Action"] A --> O["Observation"] O --> C{"Correct?"} C -->|Yes| N["Next Step"] C -->|No| R["Revise Plan"] R --> A N --> D{"Done?"} D -->|No| P D -->|Yes| F["Finish"]

Reflection

Reflection introduces a separate evaluation step that critiques an agent's work and can trigger revision. It should be treated as an engineering mechanism with measurable benefit, not as a ritual where the model simply asks itself whether it did well.

reflection.ts 
const draft = await worker.run(task);

const review = await evaluator.run({
  task,
  output: draft,
  rubric
});

if (review.score < threshold) {
  return worker.run({
    task,
    previous: draft,
    feedback: review.feedback
  });
}

return draft;

Independent learners

Cooperative learning

Agents optimize a shared objective.

Competitive learning

08 / STATE

State is the backbone of reliable agent systems.

If an execution cannot be paused, resumed, inspected, retried, or reconstructed, it is not yet a robust distributed workflow.

Memory architecture

Agent memory layers
flowchart TB A["Agent"] A --> W["Working Memory"] W --> C["Current Task / Context"] A --> E["Episodic Memory"] E --> H["Previous Interactions"] A --> S["Semantic Memory"] S --> V["Vector DB"] S --> K["Knowledge Graph"] A --> P["Persistent State"] P --> D["SQL / Document DB"]

Short-term vs long-term memory

Working memory

  • Current task
  • Current observations
  • Intermediate results
  • Active plan

Long-term memory

  • User preferences
  • Past outcomes
  • Knowledge
  • Historical events

Event sourcing

Instead of storing only the latest state, an event-sourced system records state transitions. The current state can then be reconstructed from the event history.

Event-sourced agent execution
flowchart LR A["Agent Action"] --> E["Event"] E --> S["Event Store"] S --> R["Reducer"] R --> C["Current State"] S --> T["Audit / Replay"]

Partial observability

Agents rarely observe the complete environment. The system therefore needs to distinguish between facts, assumptions, stale information, and unknown information.

Never silently convert unknown into false

If an agent does not know whether an order was shipped, its state should be “unknown,” not “not shipped.” This distinction becomes critical when agents make decisions from incomplete observations.

09 / DEVELOPMENT

Build the system in controlled increments.

The development process should move from requirements to agent boundaries to protocols to implementation, evaluation, and production hardening.

01

Problem analysis

Define the objective, users, constraints, unacceptable outcomes, success metrics, and error tolerance.

02

Agent modeling

Identify responsibilities, capabilities, boundaries, goals, permissions, inputs, outputs, and dependencies.

03

Architecture design

Select centralized, hierarchical, parallel, event-driven, decentralized, or hybrid topology.

04

Protocol design

Define message schemas, API contracts, timeouts, retries, idempotency, correlation IDs, and error semantics.

05

Implementation

Build agents, tools, state management, routing, orchestration, and deterministic guardrails.

06

Testing

Test agents independently, then test communication, workflows, failures, and emergent system behavior.

07

Deployment

Containerize services, configure secrets, queues, databases, service discovery, scaling, and rollback.

08

Observability

Track traces, messages, model calls, tool calls, latency, failures, cost, and business outcomes.

09

Continuous improvement

Evaluate production failures, update prompts and policies, improve tools, retrain where applicable, and evolve protocols carefully.

Framework selection criteria

Language

Does it fit your team's runtime and deployment stack?

State model

Observability

Scalability

Can independent workloads scale horizontally?

Community

Are bugs, integrations, and examples actively maintained?

Escape hatch

Practical advice

For LLM-heavy production applications, favor frameworks that expose state, structured outputs, tool execution, retries, checkpoints, and tracing rather than frameworks that merely make multiple prompts easy to write.

Trustworthy AI

Guardrails

Constrain tools, inputs, outputs, permissions, and high-risk actions with deterministic checks.

Fact verification

Require evidence or independent validation for claims where hallucination has material consequences.

Objective alignment

Ensure local agent objectives do not create incentives that conflict with the global system objective.

Human approval

Insert explicit human authorization before irreversible or high-impact operations.

Zero-error systems and MAKER

Some tasks have extremely low tolerance for error. In those systems, reliability may require decomposing work into tiny steps, executing independent attempts, checking results, and aggressively eliminating incorrect trajectories. Patterns such as MAKER are relevant to this class of reliability engineering.

Important

“Use more agents” is not itself a reliability strategy. Independent agents can independently make the same mistake. Reliability comes from decomposition, diversity where useful, verification, bounded execution, and deterministic constraints.

Containerization

Package independently scalable agents as services when their workload, dependencies, permissions, or deployment lifecycle differs materially. Docker is a common packaging layer; Kubernetes can provide scheduling, service discovery, autoscaling, and deployment orchestration.

Scaling

Horizontal scaling

Run multiple replicas of stateless or checkpointed agents.

Load balancing

Distribute requests across available workers.

Queue-based scaling

Scale workers according to backlog rather than incoming HTTP traffic.

Reliability patterns

Timeout

Every remote operation needs a maximum execution duration.

Retry

Retry transient failures with bounded exponential backoff.

Circuit breaker

Stop repeatedly calling a failing dependency.

Idempotency

Repeated delivery should not duplicate irreversible effects.

Dead-letter queue

Capture messages that repeatedly fail processing.

Checkpointing

Persist execution state so long-running tasks can resume.

Versioning

  • Version agent prompts and policies.
  • Version tool schemas.
  • Version inter-agent message contracts.
  • Keep backward compatibility during migrations.
  • Record the exact model and configuration used for each run.

Cost management

Token budgets

Set per-agent and per-workflow limits.

Model routing

Use cheaper models for simple classification and deterministic work.

Context control

Do not pass the entire history to every agent.

Caching

Cache stable retrievals and deterministic intermediate results.

Early termination

Stop workflows when the objective is already satisfied.

Cost telemetry

Attribute spend to users, agents, tools, and workflows.

support-system.ts 
async function handleSupport(request) {
  const intent =
    await router.classify(request);

  const specialist =
    specialists[intent.type];

  const result =
    await specialist.run({
      request,
      customerId: request.customerId
    });

  const validation =
    await validator.check({
      request,
      result
    });

  if (!validation.safe) {
    return escalationAgent.run({
      request,
      result,
      reason: validation.reason
    });
  }

  return result;
}

Final principle

Build the smallest architecture that reliably solves the problem. Start with one agent. Add tools. Add deterministic workflows. Introduce parallelism where independence exists. Add specialists where responsibilities diverge. Add an orchestrator when dynamic delegation becomes necessary. Introduce decentralization only when the problem itself demands it.
