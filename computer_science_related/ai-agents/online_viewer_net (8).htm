01 / Foundation

Understand the problem before multiplying the agents.

Multi-agent architecture is not “put several LLMs in a loop.” It is a distributed-systems problem in which autonomous decision-makers share goals, resources, context, and constraints.

The first architectural rule If a deterministic workflow, a single well-designed agent, or ordinary microservices can solve the problem with less coordination overhead, use them. Multiple agents are a complexity multiplier.

When should you use MAS?

1

Specialization

Different tasks require genuinely different tools, prompts, policies, knowledge domains, or reasoning strategies.

2

Parallelism

Independent subproblems can execute concurrently, reducing wall-clock latency or increasing throughput.

3

Organizational boundaries

Different teams, vendors, or security domains own separate capabilities that should remain independently deployable.

4

Dynamic delegation

The system cannot reliably know in advance which specialist will be required for every request.

5

Independent scaling

Some capabilities have dramatically different traffic, latency, compute, or availability requirements.

6

Negotiation

Agents must propose, bid, critique, negotiate, or compete under explicit constraints.

MAS vs. alternatives

Approach Use when Main advantage Main failure mode
Single agent One reasoning loop and modest tool set are sufficient. Lowest coordination complexity. Context/tool overload and weak specialization.
Deterministic workflow Steps and transitions are known ahead of time. Predictability and testability. Rigid behavior when the problem changes.
Microservices Capabilities are stable software services with clear contracts. Strong operational isolation. Services do not autonomously reason or adapt.
Multi-agent system Autonomous specialization and dynamic coordination create measurable value. Composability and adaptive delegation. Coordination, nondeterminism, cost, and emergent behavior.

Success criteria

Autonomy

Agents can select actions within bounded permissions.

Decoupling

Agents communicate through contracts rather than hidden state.

Adaptability

The system handles changing inputs without rewriting every branch.

Scalability

Agents can scale independently where workload demands it.

Where MAS appears

Supply chain

Supplier, warehouse, transport, inventory, and retail agents negotiate plans under constraints.

Customer operations

Routing, billing, technical support, returns, compliance, and escalation specialists.

Finance

Research, risk, portfolio, execution, monitoring, and compliance agents.

Smart grids

Distributed producers and consumers coordinate energy allocation.

Robotics

Perception, navigation, task allocation, and fleet coordination.

Game AI

Independent actors pursue goals while responding to other actors and the environment.

MAS-specific risks

Coordination explosion

With N agents, potential interactions can grow approximately with N² if every agent can communicate with every other agent. Avoid unrestricted peer-to-peer graphs unless the problem genuinely requires them.

Emergent behavior

Local policies can interact to create global behavior that nobody explicitly programmed. Test the system as a population, not merely as isolated agents.

Debugging opacity

A final answer may depend on routing, tool calls, memory retrieval, delegation, retries, and intermediate messages. You need distributed traces.

Cost multiplication

Five agents do not merely cost five times one agent: retries, context forwarding, critics, planning loops, and parallel branches can multiply token and compute usage.

Checkpoint 01 Architecture judgment
A deterministic 6-step approval workflow is stable and fully specified. Should you immediately replace it with six autonomous agents?
Correct. Autonomy is an architectural capability, not a badge of sophistication.

Three fundamental topologies

Centralized

Supervisor Orchestrator

One coordinator owns routing and often shared workflow state.

Best for: predictable governance, observability, bounded workflows.

Risk: supervisor bottleneck and single coordination failure.

Decentralized

Peer-to-peer Choreography

Agents coordinate without a permanent central authority.

Best for: distributed ownership and dynamic negotiation.

Risk: hard-to-debug interaction graphs.

Hybrid

Federated Hierarchical

Local supervisors coordinate domains while a higher-level layer handles global policy.

Best for: large organizations and independently owned domains.

Risk: cross-domain consistency and protocol complexity.

Flat vs hierarchical vs network topology

Topology Control Scalability Debugging Use case
Flat Peer Low–medium Difficult Small cooperative groups
Hierarchical Parent → child High Good Enterprise workflows
Network Dynamic Potentially high Difficult Negotiation and ecosystems

Agent-centric vs workflow-centric

Agent-centric

The agent owns decision-making and dynamically determines what to do next.

Prefer when: the next action depends on information discovered during execution.

Workflow-centric

The workflow owns transitions while agents perform bounded tasks.

Prefer when: reliability, compliance, and predictable execution dominate.

Architectural dimensions

Function encapsulation

What capability belongs inside an agent and what should remain a deterministic service?

Orchestration

Who decides the next action, and how can that decision be constrained?

API contracts

What structured input/output does every capability expose?

Auto-correction

Which failures trigger retries, critique, repair, fallback, or human review?

Data communication

What data crosses boundaries, and how is context minimized?

Observability

Can you reconstruct exactly why an agent made a decision?

Architecture decision matrix

Constraint Lean toward Reason
High error cost Centralized + deterministic gates Explicit policy and approval boundaries.
Complex task decomposition Supervisor / hierarchical Specialists can remain focused.
Massive parallel workload Fan-out + queue Independent workers scale horizontally.
Dynamic negotiation Peer / contract-net Agents can propose and evaluate alternatives.
Regulated actions Workflow-centric hybrid Agent reasoning stays behind deterministic policy gates.
Anti-pattern: “Everything is an agent.” A database lookup is not an agent. A calculator is not an agent. A deterministic API is not an agent. Making every function autonomous creates latency and uncertainty without creating intelligence.
03 / Agent Design

Design agents as bounded decision-makers.

An agent needs a purpose, observations, actions, constraints, memory, and a termination condition. “You are a helpful agent” is not an architecture.

Agent types

Reactive

Maps observations directly to actions. Fast and predictable; weak for long-horizon planning.

Deliberative

Maintains an internal model and plans before acting. More capable, but slower.

Hybrid

Fast reactive layer handles routine behavior; planner handles complex cases.

BDI

Explicit beliefs, desires, and intentions provide a useful conceptual model for autonomous behavior.

Capability model

Capability Question Implementation
Reasoning How does it transform evidence into decisions? LLM, rules, solver, classifier

LLM agent loop

agent.py — conceptual implementation 
class Agent:
    def run(self, task):
        state = self.memory.load(task.id)

        for step in range(MAX_STEPS):
            observation = self.observe(task, state)

            decision = self.model.decide(
                system=self.system_prompt,
                tools=self.tools,
                state=observation
            )

            if decision.is_final:
                return self.verify(decision, state)

            result = self.execute_tool(decision.tool_call)

            state = self.update_state(state, result)

            self.memory.save(task.id, state)

        return Escalation("max_steps_exceeded")
Practical rule Give every agent an explicit scope boundary: what it owns, what it may read, what it may mutate, which other agents it may call, and when it must stop.

Communication is an API problem, not a prompt problem.

Agents become reliable when their interactions have explicit schemas, identifiers, delivery semantics, authorization, and versioning.

Agent Communication Languages

FIPA ACL

A classic agent communication model built around communicative acts such as request, inform, propose, accept-proposal, and reject-proposal.

Useful lesson: messages should express intent, not merely dump text.

KQML

An influential knowledge-query and agent communication language that separates the communication performative from the content.

Useful lesson: protocol semantics should remain distinct from payload data.

Interaction protocols

Request / response

Caller asks a known specialist for a bounded operation.

Contract Net

Manager announces a task; eligible agents submit proposals; manager awards work.

Auction

Agents bid according to cost, capability, utility, or resource availability.

Pub/Sub

Publishers emit events; subscribers independently react.

Blackboard

Agents read and write to a shared problem workspace.

Human approval

A protocol explicitly pauses execution until a human supplies a decision.

Synchronous vs asynchronous

Mode Use when Engineering implications
Synchronous Fast bounded calls. Simple request lifecycle; caller waits.
Asynchronous Long-running tasks or independent work. Queues, task IDs, retries, idempotency, persistence.
Streaming Progressive output matters. Backpressure, reconnects, partial results.
Event-driven Many consumers react to state changes. Loose coupling; eventual consistency.

MCP vs A2A

Capability boundary

MCP — tools, resources, context

Use MCP-style interfaces when an agent needs standardized access to tools, APIs, resources, or contextual capabilities.

Mental model: “How does my agent use a capability?”

Agent boundary

A2A — agent collaboration

A2A is designed for interoperability between independent agent applications, including capability discovery and collaborative tasks.

Mental model: “How does this independent agent collaborate with another agent?”

Protocol design principle Do not pass entire conversation histories between agents by default. Send the minimum task context, explicit artifacts, and references needed for the next agent to perform its job.
Checkpoint 02 Protocol design
A billing agent needs to query an invoice API and a CRM. Which boundary is most naturally represented by a tool/resource protocol?
Correct. MCP and A2A solve complementary problems: capability access versus agent-to-agent collaboration.
05 / Coordination

Coordination patterns are the real MAS toolbox.

Most production systems are compositions of a small number of coordination primitives. Pick the simplest pattern that satisfies the task.

Sequential pipeline

Shape: A → B → C.

Each stage transforms the artifact from the previous stage. This is excellent for research → draft → review → publish workflows.

Use when: ordering matters and each stage has a clear input/output contract.

Failure strategy: checkpoint after each stage; retry only failed stages; make outputs immutable where possible.

Routing / fan-out

A router chooses one specialist, or fans a task into independent branches.

Use when: branches are independent and can run concurrently.

Critical concern: define the join semantics. What happens if 2 of 5 agents succeed? What is the timeout?

Map-reduce

Map partitions a large problem into homogeneous subproblems. Workers execute independently. Reduce combines results.

Examples: summarize 10,000 documents, evaluate many transactions, classify thousands of tickets.

Engineering rule: keep workers stateless where possible and make the reduce function deterministic.

Supervisor delegation

A supervisor maintains global context and delegates bounded work to specialists.

Strength: simple mental model and centralized governance.

Risk: the supervisor becomes a bottleneck or receives too much context.

Better design: expose delegation as typed tools with narrow descriptions and structured results.

Peer collaboration

Agents communicate directly, potentially changing roles dynamically.

Use when: no single coordinator has enough information to optimize the system.

Cost: observability and termination become harder. Put explicit TTLs, message budgets, and loop detectors around peer interactions.

Competitive coordination

Multiple agents propose solutions and a selector chooses according to a utility function.

Useful for: planning alternatives, supplier selection, portfolio strategies, or adversarial evaluation.

Competition should be evaluated by objective metrics, not merely by asking another LLM which answer “sounds better.”

Human-in-the-loop

Execution pauses at a defined policy boundary and asks a human for approval, correction, or missing information.

Use for: financial transactions, destructive operations, high-impact decisions, ambiguous authorization, or low-confidence outcomes.

The human step must be modeled as a state transition—not an ad-hoc UI popup.

Recursive delegation and hierarchies

A supervisor delegates to a domain supervisor, which delegates to specialists.

Use when: the organization naturally has multiple levels of responsibility.

Guardrails: maximum depth, maximum delegation count, allowed parent-child relationships, and bounded context propagation.

Blackboard, queues, tuples, and events

Blackboard

Shared evolving workspace. Good for cooperative problem solving.

Queue

Durable work distribution. Good for asynchronous worker pools.

Tuple space

Agents publish and consume structured facts without direct coupling.

Pub/Sub

Event distribution. Good for monitoring and domain reactions.

Orchestration vs choreography

Dimension Orchestration Choreography
Control Central coordinator Distributed reactions
Visibility High Lower
Evolution Coordinator can become coupling point Local changes can be easier
Failure analysis Usually simpler More distributed
Best fit Bounded workflows Event-driven ecosystems

06 / Planning & Learning

Separate “thinking” from “acting.”

A robust agent should distinguish planning, execution, observation, and verification. Otherwise an incorrect assumption can silently propagate through the entire system.

Planning spectrum

STRIPS

Classical planning with explicit states, actions, preconditions, and effects.

HTN

Hierarchical Task Networks decompose abstract tasks into executable subtasks.

Search / optimization

Choose sequences based on cost, utility, constraints, or objective functions.

LLM planning

Generate or revise plans using language-model reasoning, often with validators.

Plan → Execute → Verify

flowchart LR

    R[Request] --> P[Plan]
    P --> G[Guardrails]
    G --> X[Execute]
    X --> O[Observe Result]
    O --> V{Verified?}

    V -->|Yes| DONE[Commit]
    V -->|No| C[Critique / Repair]

    C --> P
    C -->|Unrecoverable| H[Human / Failure]

Tool design

Typed inputs

Never rely on free-form strings when the action has a finite schema.

Explicit side effects

Mark whether a tool reads, writes, sends, deletes, or charges.

Idempotency

Repeated execution should not create duplicate side effects.

Authorization

The tool, not only the prompt, must enforce permissions.

Evidence

Return structured evidence so downstream agents can verify decisions.

Timeouts

Every external call needs explicit timeout and retry semantics.

Reflection and self-correction

Reflection is useful only when it has an evaluation target. “Think again” is not a verification strategy. Give the critic a rubric, constraints, evidence requirements, and a maximum number of repair cycles.

verification loop 
for attempt in range(3):

    answer = agent.solve(task)

    report = verifier.evaluate(
        answer=answer,
        criteria=[
            "all_required_fields_present",
            "evidence_supports_claims",
            "policy_constraints_satisfied"
        ]
    )

    if report.pass:
        return answer

    agent.apply_feedback(report.feedback)

return escalate("verification_failed")

Multi-agent reinforcement learning

Independent learners

Each agent optimizes its own policy. Non-stationarity is the major difficulty.

Cooperative

Agents optimize a shared objective, often requiring credit assignment.

Competitive

Agents optimize opposing or partially opposing objectives.

Do not confuse LLM agents with MARL. An LLM-based MAS can coordinate through prompts and tools without reinforcement learning. Multi-agent reinforcement learning is a separate learning paradigm with policies, rewards, environments, and training dynamics.
07 / State

Treat memory as infrastructure.

Agents should not be trusted to “remember” arbitrary information in context windows. Decide explicitly what state exists, who owns it, how long it lives, and how it is reconstructed.

State hierarchy

Working memory

Current task context, recent observations, active plan.

Session state

Conversation and workflow state across requests.

Long-term memory

Durable facts, preferences, summaries, embeddings.

Domain state

Authoritative business data in transactional systems.

Do not put everything in vector search

Data Preferred storage Reason
Customer balance Transactional database Strong consistency and authoritative value.
Current workflow state Checkpoint / database Must be reconstructable.
Document chunks Vector + document store Semantic retrieval.
Entity relationships Relational / graph Explicit relationships outperform fuzzy retrieval for many queries.
Recent event stream Event bus / log Replay and asynchronous consumers.

Event sourcing

flowchart LR

    C[Command] --> A[Agent]

    A --> E1[TaskCreated]
    A --> E2[AgentDelegated]
    A --> E3[ToolExecuted]
    A --> E4[VerificationCompleted]

    E1 --> LOG[(Event Log)]
    E2 --> LOG
    E3 --> LOG
    E4 --> LOG

    LOG --> R[State Reconstruction]

Event sourcing is valuable when you need auditability, replay, debugging, or recovery. It also makes agent behavior easier to investigate because the sequence of state transitions is explicit.

Partial observability

Agents rarely see the entire environment. They operate on observations. Therefore distinguish: what is true from what the agent currently believes.

belief_state = f(observations, prior_state, retrieved_evidence, uncertainty)

When an action depends on uncertain information, make uncertainty explicit and define whether the agent should retrieve more evidence, ask another agent, or escalate.

08 / Build Workflow

Build in stages. Do not start with ten agents.

The fastest route to a production MAS is usually: prove the task with one capability, establish contracts, then introduce specialization only where the metrics justify it.

Problem analysis

Define the business outcome, inputs, constraints, error cost, latency target, throughput, budget, and success metrics. Establish the baseline single-agent or deterministic solution.

Agent modeling

Identify domains that have distinct responsibilities, tools, data, policies, or optimization objectives. Write an explicit responsibility matrix.

Architecture design

Choose centralized, decentralized, or hybrid topology. Select orchestration, queues, storage, failure boundaries, and scaling units.

Protocol design

Define message envelopes, schemas, IDs, correlation, timeouts, authorization, idempotency, retries, error codes, and versioning.

Implementation

Implement one agent end-to-end. Add typed tools. Add structured outputs. Add checkpointing. Only then compose multiple agents.

Testing

Unit-test tools and agent policies. Integration-test contracts. Simulation-test coordination. Load-test queues and external dependencies.

Deployment

Containerize services, externalize configuration, establish health checks, secrets management, autoscaling, queues, and persistent state.

Observability

Capture trace IDs, agent IDs, model calls, tool calls, latency, tokens, routing decisions, retries, failures, and final outcomes.

Continuous improvement

Build an evaluation dataset from real failures. Improve prompts, tools, routing, policies, models, and workflows based on measured outcomes.

09 / Frameworks

Frameworks are implementation choices, not architecture.

Pick a framework after defining your system. Otherwise the framework's abstractions will quietly become your architecture.

Framework Primary ecosystem Strength Best fit Watch for
JADE Java Classic agent-oriented infrastructure and FIPA concepts. Traditional agent research and Java systems. Less aligned with modern LLM-first development.
Jason AgentSpeak / Java ecosystem BDI-oriented agent programming. Symbolic BDI research and explicit agent reasoning. Different mental model from LLM orchestration.
SPADE Python / XMPP Python-based distributed agents and messaging. Message-oriented agent systems. Infrastructure decisions around messaging and deployment remain yours.

Observability

Can you inspect every transition and tool call?

10 / Evaluation

If you cannot measure the system, you do not control it.

Evaluation must cover individual agents, coordination behavior, final outcomes, cost, latency, safety, robustness, and failure recovery.

Testing pyramid

Unit

Tools, parsers, validators, routing rules, schemas.

Integration

Agent-to-agent contracts, tool access, state transitions.

Simulation

Many agents interacting under controlled environments.

Production eval

Real traffic sampled into an evaluation pipeline.

Core metrics

Metric Definition Why it matters
Task success rate Successful outcomes / total tasks Primary product quality.
First-pass success Tasks solved without repair/retry Reveals hidden orchestration cost.
Latency p50 / p95 / p99 completion time User experience and SLA.
Cost per task Model + compute + tool + infrastructure cost Unit economics.
Tool failure rate Failed tool calls / calls Dependency reliability.
Delegation efficiency Useful delegations / total delegations Measures coordination quality.
Escalation rate Human escalations / total tasks Shows automation boundary.
Policy violation rate Violations / tasks Safety and governance.

MAS evaluation dimensions

Correctness

Did the system produce the correct outcome?

Robustness

Does it recover from bad tools, missing data, and malformed messages?

Coordination

Do agents delegate appropriately instead of duplicating work?

Fairness

Are resource allocation and decisions consistent with policy?

Security

Can an agent cross an authorization boundary?

Cost efficiency

Is the additional coordination worth the outcome improvement?

Zero-error environments

When “almost correct” means failure In systems where every output must be correct, ordinary sampling-based redundancy may not be sufficient. Architect for verification, deterministic checks, independent validation, constrained execution, and explicit escalation. If you use a named pattern such as MAKER, treat it as an architectural pattern requiring empirical validation—not a magic guarantee of zero errors.

Adversarial simulation

Checkpoint 04 Evaluation
Your system's final accuracy is 92%, but it requires four model calls and two retries on average. What should you investigate?
Correct. A good final metric can conceal an inefficient and fragile execution path.
11 / Production

Production MAS is distributed systems engineering with probabilistic components.

Docker and Kubernetes do not make an agent system production-ready. You still need failure isolation, durable state, identity, authorization, observability, versioning, and cost controls.

Timeout

Every network/model/tool call.

Only transient, safe failures.

Circuit breaker

Stop hammering unhealthy dependencies.

Capture messages that repeatedly fail.

Idempotency

Prevent duplicate side effects.

Security model

Layer Control
Identity Every agent/service gets a machine identity.
Authentication Verify callers before accepting agent requests.
Authorization Enforce tool-level permissions outside the model.
Data Encrypt in transit and at rest; minimize context sharing.
Prompt injection Treat retrieved content as untrusted data, never as policy.
Secrets Never expose credentials through prompts or agent context.
Audit Record sensitive actions with actor, policy, timestamp and outcome.

Versioning

Agent version

Prompt, tools, model, policy and code version.

Protocol version

Message and API schema compatibility.

Workflow version

State machine and transition semantics.

Cost control

cost_per_task = model_tokens + tool_calls + compute_time + storage + network + human_review_cost

Record cost at the task and agent level. Measure cost per successful outcome—not merely tokens. A cheaper model that creates more retries can be more expensive.

Production rule Never allow an autonomous agent to have unrestricted write access merely because its prompt says “be careful.” Authorization belongs in infrastructure and application code.
12 / Case Study

Case study: production customer support MAS.

We will build a support platform that classifies incoming requests, delegates to specialists, verifies responses, and escalates sensitive cases.

Problem

A company receives customer requests involving billing, technical issues, subscriptions, returns, account access, and general questions. A single general-purpose support agent has too many tools and inconsistent policy behavior.

Requirements: high first-response quality, low latency for routine questions, strict authorization for financial operations, human escalation for sensitive cases, complete auditability, and independent specialist evolution.

Supervisor pseudo-code

supervisor.py 
def handle_support_request(request):

    task = workflow.start(request)

    intent = router.classify(
        text=request.text,
        allowed_intents=[
            "billing",
            "technical",
            "returns",
            "general"
        ]
    )

    specialist = registry.get(intent)

    result = specialist.run(
        task_id=task.id,
        customer_id=request.customer_id,
        normalized_request=request.text
    )

    verification = verifier.check(
        task=task,
        result=result
    )

    if verification.requires_human:
        return human_review.create(task, result)

    if not verification.passed:
        return retry_or_escalate(task, verification)

    return finalizer.respond(
        result,
        verification
    )

def propose_refund(
    customer_id: str,
    amount: Decimal,
    reason: str,
    actor: AgentIdentity
):

    authorize(
        actor,
        action="refund:propose",
        resource=customer_id
    )

    if amount > Decimal("500"):
        return ApprovalRequired(
            reason="amount_exceeds_automated_limit"
        )

    return billing_service.create_refund_proposal(
        customer_id=customer_id,
        amount=amount,
        reason=reason,
        idempotency_key=generate_idempotency_key()
    )

The mental model to keep

Agents are decision-makers.
Tools are capabilities. Messages are contracts. Workflows are control logic. Memory is state. Verification is reliability. Observability is how you know what happened.

Final architecture heuristic

Start

Minimize autonomy

Use deterministic code wherever requirements are deterministic.

Add

Specialize deliberately

Create an agent when domain ownership, tools, policies, or parallelism justify it.

Operate

Bound everything

Bound steps, time, tokens, cost, delegation, permissions and side effects.

The uncomfortable truth The hardest part of multi-agent engineering is not making agents talk to one another. It is deciding when they should not talk, what they are allowed to know, what they are allowed to change, how failures become state transitions, and how you prove the system improved over a simpler design.
