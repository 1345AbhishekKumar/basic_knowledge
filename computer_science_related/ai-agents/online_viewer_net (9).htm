00 / BUILD PROGRESSION

Build from one agent to a real multi-agent system.

Multi-agent engineering is not a binary switch. It is an architectural progression. Each new stage introduces a capability and a corresponding class of distributed-systems problems.

The safest learning path is to evolve the same application through increasingly capable architectures rather than jumping directly into a swarm of autonomous agents.

Why this progression matters

Every stage answers a real engineering need. Do not introduce another agent merely because a prompt became large. Use a function when a function is enough, a workflow when a workflow is enough, and agents when genuine autonomy or specialization creates measurable value.

01

Single agent

learn the core loop

Begin with one agent that owns the full reasoning loop: receive input, inspect context, reason, act, and return an answer.

Architecture

flowchart LR
    U["User"] --> A["Agent"]
    A --> M["Model"]
    M --> A
    A --> O["Answer"]
What changed?

You have introduced autonomy, but there is no distributed coordination problem yet.

Do not split yet.

A long prompt, long context, or multiple reasoning steps does not automatically justify multiple agents.

Minimal TypeScript model
type AgentInput = {
  task: string;
  context?: string;
};

type AgentOutput = {
  answer: string;
};

async function runAgent(
  input: AgentInput
): Promise<AgentOutput> {
  const response = await model.generate({
    system: `
      You are a focused assistant.
      Solve the task carefully.
    `,
    user: input.task,
    context: input.context
  });

  return {
    answer: response.text
  };
}
1 reasoning owner 1 state boundary 1 failure domain simple debugging
02

Agent + tools

give autonomy capabilities

An agent becomes useful when it can act on the world. Tools should expose capabilities through explicit schemas rather than allowing the model to directly manipulate infrastructure.

Architecture

flowchart LR
    U["User"] --> A["Agent"]
    A --> M["Model"]
    M --> A
    A --> TG["Tool Gateway"]
    TG --> DB["Database"]
    TG --> API["External API"]
    DB --> TG
    API --> TG
    TG --> A
    A --> O["Answer"]
What changed?

The model is now making action decisions. Tools become your enforcement boundary for authentication, validation, side effects, idempotency and observability.

Typed tool boundary
const tools = {
  getOrder: async (
    input: { orderId: string }
  ) => {
    authorize("orders:read");

    return db.orders.findUnique({
      where: { id: input.orderId }
    });
  },

  createRefund: async (
    input: {
      orderId: string;
      amount: number;
    }
  ) => {
    authorize("refunds:create");

    return refunds.create({
      orderId: input.orderId,
      amount: input.amount,
      idempotencyKey: `refund:${input.orderId}`
    });
  }
};
Tool ≠ agent

A tool performs a well-bounded capability. An agent decides what to do next. Keeping those responsibilities separate makes systems easier to secure and test.

03

Sequential agents / workflow

decompose fixed stages

When the work naturally has stages, move from a single reasoning loop to a deterministic pipeline. Each node receives an explicit artifact from the previous node.

Example

Researcher → Writer → Reviewer is a classic sequential architecture. The same idea works for classify → retrieve → resolve → verify. 

flowchart LR
    I["Input"] --> A["Research Agent"]
    A --> B["Writing Agent"]
    B --> C["Review Agent"]
    C --> O["Final Output"]
What changed?

You now have explicit state transitions and an opportunity to checkpoint intermediate artifacts.

Sequential TypeScript
const research = await researchAgent.run({
  task
});

const draft = await writerAgent.run({
  task,
  research
});

const review = await reviewerAgent.run({
  task,
  draft
});

return {
  research,
  draft,
  review
};
Production checkpoint

Persist meaningful artifacts between stages so a failed review does not force a complete re-run of expensive research.

04

Parallel agents

fan-out + join

Parallelism becomes useful when branches are independent. The architecture changes from a chain into fan-out followed by an explicit synchronization or aggregation step. 

flowchart TB
    P["Planner / Router"]
    P --> A["Research Agent"]
    P --> B["Market Agent"]
    P --> C["Risk Agent"]
    A --> J["Join / Synthesizer"]
    B --> J
    C --> J
    J --> O["Final Result"]
What changed?

Concurrency has introduced join semantics, partial failure handling, concurrency limits, cancellation and result aggregation.

Parallel TypeScript
const [
  research,
  market,
  risk
] = await Promise.all([
  researchAgent.run(task),
  marketAgent.run(task),
  riskAgent.run(task)
]);

const final = await synthesizer.run({
  task,
  research,
  market,
  risk
});
Only parallelize independent work.

If branch B depends on branch A, parallel execution only creates race conditions and more complexity.

05

Router

choose the right specialist

A router is appropriate when the application needs to choose among specialized paths. It is not an orchestrator; it normally selects one route rather than managing a long-lived plan. 

flowchart LR
    U["User Request"] --> R["Router"]
    R --> B["Billing Agent"]
    R --> T["Technical Agent"]
    R --> C["Returns Agent"]
What changed?

Classification became part of the architecture. Routing errors become a first-class failure mode.

Structured routing
const route = await router.classify({
  message: userMessage
});

const handlers = {
  billing: billingAgent,
  technical: technicalAgent,
  returns: returnsAgent
} as const;

const agent = handlers[route.intent];

return agent.run({
  message: userMessage
});
Deterministic routing is often better.

A normal classifier, rules engine, or structured model output can be easier to validate than an unconstrained autonomous handoff.

06

Orchestrator / supervisor

plan + delegate + verify

An orchestrator owns a stateful process and delegates work to specialists. It can call multiple agents, inspect intermediate results, retry work, ask for verification, and decide the next step. 

flowchart TB
    U["User"] --> O["Orchestrator / Supervisor"]
    O <--> A["Research Agent"]
    O <--> B["Execution Agent"]
    O <--> C["Verification Agent"]
    O --> H["Human Approval"]
    O --> F["Final Answer"]
Router vs orchestrator

A router answers “which specialist should handle this?” An orchestrator answers “what sequence of actions should the system execute to finish the task?”

Supervisor interface
type WorkerRequest = {
  task: string;
  context: Record<string, unknown>;
};

const workers = {
  research: researchAgent,
  execute: executionAgent,
  verify: verificationAgent
};

async function supervisor(
  state: WorkflowState
) {
  const next = await planner.chooseNext(state);

  if (next.type === "worker") {
    return workers[next.worker].run(
      next.request as WorkerRequest
    );
  }

  if (next.type === "human") {
    return requestHumanApproval(next);
  }

  return finish(state);
}
New complexity

State machines, retries, delegation policies, context propagation, timeouts, partial completion and verification.

07

Hierarchical multi-agent system

supervisors within supervisors

A hierarchy introduces multiple coordination scopes. A top-level supervisor manages domain supervisors, each of which owns a bounded set of specialists. 

flowchart TB
    ROOT["Executive Supervisor"]
    ROOT --> SALES["Sales Supervisor"]
    ROOT --> OPS["Operations Supervisor"]
    ROOT --> FIN["Finance Supervisor"]

    SALES --> LEAD["Lead Agent"]
    SALES --> CRM["CRM Agent"]

    OPS --> FUL["Fulfillment Agent"]
    OPS --> SUPPORT["Support Agent"]

    FIN --> BILL["Billing Agent"]
    FIN --> RISK["Risk Agent"]
Context isolation matters.

Do not blindly pass every conversation, credential, memory object, and tool definition through the entire hierarchy. Each boundary should expose only what the next scope needs.

Hierarchy contract
type SupervisorContract = {
  owns: string[];

  allowedTools: [
    "orders.read",
    "shipments.read"
  ],

    "operations"

08

Peer-to-peer / swarm

distributed negotiation

Peer architectures remove the central coordinator. Agents exchange messages directly and collaborate through negotiation, delegation, bidding, consensus, or shared protocols. 

graph LR
    A["Agent A"] <--> B["Agent B"]
    B <--> C["Agent C"]
    C <--> D["Agent D"]
    D <--> A
    A <--> C
Distributed coordination is expensive.

You now have to reason about loops, duplicated work, deadlocks, conflicting goals, hidden state, message ordering and emergent behavior.

Peer protocol
type Proposal = {
  taskId: string;
  sender: string;
  capability: string;
  cost: number;
  confidence: number;
  expiresAt: number;
};

type Decision = {
  taskId: string;
  winner: string;
  reason: string;
};

async function negotiate(
  proposals: Proposal[]
): Promise<Decision> {
  const winner = [...proposals]
    .sort(
      (a, b) =>
        (b.confidence - a.confidence) ||
        (a.cost - b.cost)
    )[0];

  return {
    taskId: winner.taskId,
    winner: winner.sender,
    reason: "highest confidence / lowest cost"
  };
}

10

Production multi-agent system

operate the system

Production MAS is not “more agents.” It is the addition of operational guarantees around the architecture: observability, security, durable state, bounded retries, policy enforcement, human escalation and cost control.

    U["Users / Clients"]
    U --> G["API Gateway"]

    G --> O["Orchestrator"]
    O --> Q["Queue / Event Bus"]

    Q --> W2["Agent Worker B"]
    Q --> W3["Agent Worker C"]

    W1 --> T["Tools / APIs"]
    W2 --> T
    W3 --> T

    W1 --> OBS
    W2 --> OBS
    W3 --> OBS

Production concerns
  • Authentication and authorization
  • Per-agent and per-tool permissions
  • Durable workflow state
  • Idempotency for side-effecting tools
  • Timeouts and bounded retries
  • Rate limiting and concurrency control
  • Trace IDs across every handoff
  • Prompt, model and workflow versioning
  • Human approval for high-impact actions
  • Cost budgets per task
ARCHITECTURE DECISION

Should this become multi-agent?

Use architecture to solve a real constraint, not to make the system look sophisticated.

Agent-boundary test

A new agent should provide several concrete boundaries that are valuable enough to justify its runtime and coordination cost.

  • Distinct responsibility
  • Distinct tools or data permissions
  • Independent scaling requirements
  • Independent evaluation criteria
  • Independent failure domain
  • Reusable capability
Practical rule

When a proposed “agent” does not have a meaningful boundary, keep it as a function, tool, workflow node, or library module.

Architecture choice flow

01
Can one agent solve it reliably? Stay single-agent when the answer is yes.
02
Does the task have fixed stages? Use a deterministic workflow.
03
Are branches independent? Use parallel workers and an explicit join.
04
Do different domains need different specialists? Add a router or bounded specialist agents.
05
Does one component need to plan and delegate? Introduce an orchestrator or supervisor.
06
Does autonomy truly need to be distributed? Only then move toward peer or event-driven architectures.

Complexity ladder

Single agents add reasoning complexity. Workflows add state-transition complexity. Parallel systems add synchronization complexity. Routers add classification complexity. Orchestrators add dynamic planning complexity. Peer architectures add distributed coordination complexity. Event-driven systems add temporal and consistency complexity. Production adds operational complexity on top of all of it.

Hands-on learning sequence

  • Build a single customer-support agent.
  • Add a typed order lookup tool.
  • Split classify → resolve → verify.
  • Parallelize independent research.
  • Add specialist routing.
  • Introduce a supervisor with durable state.
  • Move long tasks onto an asynchronous queue.
  • Add observability and evaluation.
01 / FOUNDATION

What is a Multi-Agent System?

A MAS is a system composed of multiple autonomous or semi-autonomous agents that interact within an environment to achieve individual or shared objectives.

Agent

An agent perceives context, maintains some state or beliefs, selects actions, invokes capabilities, and works toward goals.

Multi-agent system

A MAS adds multiple decision-making entities whose behavior must be coordinated through shared state, messages, workflows, protocols, or environmental signals.

Environment

The world in which agents operate: users, services, APIs, databases, physical environments, documents, queues, markets, or other agents.

Coordination

The mechanisms agents use to avoid conflicting actions and combine their work: routing, delegation, negotiation, auctions, blackboards, events, contracts, or supervision.

Use MAS

When decomposition is real

Different subproblems require materially different reasoning, tools, context, permissions, or scaling characteristics.

Stay single-agent

When one loop is enough

The task is mostly one reasoning process with a handful of tools and no strong specialization boundary.

Use workflow

When logic is deterministic

You know the stages ahead of time and do not need multiple autonomous decision-makers.

Success criteria

A useful MAS improves autonomy, decoupling, adaptability, specialization, parallelism, resilience, or scalability enough to justify its coordination overhead.

Supply chain

Forecasting, procurement, fulfillment, routing, exception handling, supplier communication.

Customer operations

Classification, billing, account analysis, technical troubleshooting, refunds, escalation.

Finance

Research, financial analysis, risk review, compliance, reconciliation, approval workflows.

Smart grids

Multiple local control agents coordinating energy demand, generation, storage and pricing.

Robotics

Teams of robots coordinating sensing, movement, task allocation and shared objectives.

Game AI

Multiple autonomous entities with local observations, goals, policies and strategic interactions.

What makes MAS hard?

  • Coordination explosion
  • Emergent behavior
  • Debugging opacity
  • Context propagation
  • Message ordering
  • Conflicting goals
  • State consistency
  • Cost multiplication

What good MAS design looks like

  • Explicit agent boundaries
  • Typed contracts
  • Minimal shared state
  • Observable interactions
  • Bounded autonomy
  • Verifiable outputs
  • Human escalation paths
  • Controlled failure domains

Architectural patterns.

Architecture determines where decisions live, where state lives, how agents communicate, and how failure is contained.

Centralized

One coordinator owns the global plan and delegates work. Easy to reason about, but can become a bottleneck.

Decentralized

Agents coordinate peer-to-peer. More autonomous, but much harder to reason about and debug.

Hybrid

A central boundary controls high-level policy while domains retain local autonomy.

Flat

Agents operate at approximately the same level with shared protocols.

Hierarchical

Managers coordinate sub-managers and workers with bounded scopes.

Networked

Agents connect according to capability or interaction topology rather than one rigid tree.

Agent-centric architecture

The architecture is primarily modeled around autonomous entities and their policies. This fits environments where independent behavior is itself the core requirement.

autonomy beliefs goals negotiation

Workflow-centric architecture

The architecture is primarily modeled around state transitions and deterministic control flow, even when individual nodes use LLM agents.

state machine checkpointing joins retries
Dimension Option A Option B Engineering implication
Control Centralized Distributed Distributed control increases coordination complexity.
Structure Flat Hierarchical Hierarchy improves scoping but creates supervisor dependencies.
Execution Synchronous Asynchronous Async improves decoupling but requires durable event semantics.
State Local Shared Shared state increases consistency and permission concerns.

Anti-pattern: “Everything is an agent.”

An email validator does not need to be an autonomous agent. A database operation does not need an LLM. A fixed transformation does not need negotiation. Keep deterministic logic deterministic.

03 / AGENT DESIGN

Design the agent before designing the swarm.

Strong multi-agent systems are built from well-defined agents. Weak agents create weak coordination no matter how sophisticated the orchestration layer is.

    PER --> BEL["Beliefs / State"]
    BEL --> PLAN["Planner"]
    PLAN --> INT["Intentions"]
    INT --> ACT["Action"]
    ACT --> TOOLS["Tools"]
    TOOLS --> ENV

    BEL --> MEM["Memory"]
    MEM --> BEL

    PLAN --> VER["Verifier"]

Reactive

Responds directly to observations. Simple and fast, but weak for long-horizon planning.

Deliberative

Builds plans and reasons over future consequences before acting.

Hybrid

Uses reactive policies for immediate behavior and deliberation for complex decisions.

BDI

Beliefs, desires and intentions explicitly model an agent’s internal decision state.

Agent contract

agent:
  name: verification_agent

  purpose:
    - verify completed work
    - detect unsupported claims
    - emit structured findings

  inputs:
    task: string
    artifact: object

  outputs:
    verdict:
      enum:
        - pass
        - fail
        - needs_human
    findings:
      type: array

  allowed_tools:
    - database.read
    - evidence.search

  forbidden_tools:
    - payment.execute

  limits:
    max_steps: 8
    timeout_ms: 30000
async function agentLoop(state) {
  while (!state.done) {
    const observation = await observe(state);

    const decision = await model.decide({
      goals: state.goals,
      state,
      observation,
      tools: availableTools
    });

    const result = await execute(decision);

    state = await updateState({
      state,
      decision,
      result
    });

    state = await verify(state);
  }

  return state;
}
Scope boundary

Define what the agent owns, not just what it can do. A useful agent can have dozens of tools while still owning one sharply defined outcome.

An older knowledge-query and messaging approach that influenced agent communication research.

Simple and easy to reason about. Useful when latency can be synchronous.

05 / COORDINATION

Coordination is the actual MAS problem.

Having multiple agents is easy. Getting them to cooperate predictably is the engineering challenge. 

flowchart TB
    START["Coordination Patterns"]

    START --> P["Pipeline"]
    START --> F["Fan-out / Fan-in"]
    START --> MR["Map-Reduce"]
    START --> D["Delegation"]
    START --> PC["Peer Collaboration"]
    START --> C["Competition"]
    START --> H["Human-in-loop"]
Sequential pipeline
Use when stage B requires the output of stage A. Keep the contract between nodes explicit and persist meaningful intermediate artifacts.
Routing / fan-out
Use when a task can take multiple specialist paths or several independent branches can execute at once.
Map-reduce
Map many independent chunks to worker agents, then reduce their results through deterministic aggregation or synthesis.
Supervisor delegation
A coordinator owns global state and assigns bounded tasks to specialists. Useful for dynamic workflows.
Peer collaboration
Agents communicate directly without one central owner. Useful when local autonomy and negotiation are part of the problem.
Competitive coordination
Multiple agents propose solutions, bid for tasks, or compete according to explicit utility functions.
Human-in-the-loop
A human becomes a first-class coordination participant, particularly for financial, legal, operational or irreversible actions.
Recursive delegation
Agents can delegate subtasks to additional specialists, but always apply maximum depth, timeout, budget and capability constraints.

Blackboard

Shared workspace where agents contribute observations and hypotheses.

Queue

Durable task handoff with consumer scaling and retry semantics.

Tuple space

Shared structured space where components publish and retrieve data patterns.

Pub/Sub

Broadcast events to independent subscribers that can react independently.

06 / PLANNING & LEARNING

Planning determines what the agents do next.

Planning ranges from fixed workflows to search, optimization, hierarchical decomposition and language-model-driven planning.

STRIPS-style

Formal planning over states, actions, preconditions and effects.

HTN

Hierarchical task networks decompose high-level tasks into subtasks.

Search / optimization

Select actions by exploring possible state trajectories and utility.

LLM planning

Generate and revise plans using language-model reasoning plus constraints and verification.

Typed inputs

Tools should have strict schemas rather than unconstrained argument blobs.

Side effects

Make irreversible effects explicit, observable and permissioned.

Idempotency

Retries must not accidentally duplicate financial or operational actions.

Authorization

The agent deciding an action does not automatically grant permission.

Evidence

High-impact decisions should be accompanied by inspectable support.

Timeouts

Every external capability should have bounded execution behavior. 

async function reflectAndRetry(state) {
  let attempt = 0;

  while (attempt < 3) {
    attempt += 1;

    const action = await planner.plan(state);
    const result = await execute(action);
    const check = await verifier.evaluate({
      state,
      action,
      result
    });

    if (check.pass) {
      return result;
    }

    state = {
      ...state,
      observations: [
        ...state.observations,
        {
          action,
          result,
          failure: check.findings
        }
      ]
    };
  }

  throw new Error(
    "Verification failed after bounded retries"
  );
}

Independent MARL

Each learner optimizes its own policy with limited coordination.

Cooperative MARL

Multiple learning agents optimize a shared or aligned objective.

Competitive MARL

Agents learn against or in competition with other agents.

LLM agents are not automatically MARL.

A system with multiple LLM-based agents is a multi-agent application, but multi-agent reinforcement learning is specifically about agents learning policies through interaction with an environment and reward structure.

07 / STATE & MEMORY

State is where architectures become real.

Agent memory is not one thing. Separate temporary reasoning state from durable business state and long-term knowledge.

Working memory

Immediate context needed for the current decision.

Session state

State associated with the current user interaction or workflow execution.

Long-term memory

Durable information used across multiple tasks or sessions.

Domain state

Source-of-truth business data such as orders, accounts, inventory or financial records.

08 / BUILD WORKFLOW

How to actually build one.

Develop the control plane before optimizing the intelligence layer.

  1. Define the problem and measurable success criteria.
  2. Build the smallest single-agent prototype.
  3. Add deterministic tools and validation.
  4. Convert fixed multi-step logic into an explicit workflow.
  5. Identify genuine specialist boundaries.
  6. Introduce routing, parallelism or supervisor control.
  7. Move long-running work to durable asynchronous execution.
  8. Add evaluation, tracing, security and human approval.
  9. Load-test failure behavior before increasing autonomy.

def supervisor(state):
    decision = planner.invoke({
        "goal": state["goal"],
        "completed": state["completed"],
        "failed": state["failed"]
    })

    if decision["next"] == "research":
        return "research"

    if decision["next"] == "execute":
        return "execute"

    if decision["next"] == "verify":
        return "verify"

    return "finish"

10 / EVALUATION

Evaluate the system, not just the final answer.

A MAS can fail even when the final response looks good. Measure routing, coordination, tool use, state transitions, safety and cost.

Task success Did the system actually achieve the goal? Resolution accuracy

Component evaluation

Evaluate each agent independently against its actual responsibility.

Interaction evaluation

Evaluate handoffs, routing, protocol compliance and coordination behavior.

System evaluation

Evaluate end-to-end task completion, reliability, safety and cost.

Zero-error environments

In high-stakes settings, approximate answer quality may be insufficient. Systems may need bounded action spaces, deterministic checks, redundancy, formal constraints, or evaluation approaches designed around very low tolerance for error.

A research worker may need different compute and concurrency than a verification worker.

Trace every boundary

Every request, message, tool call and state transition should be tied to a common task or trace identifier.

Fail closed

High-impact actions should prefer safe failure and explicit escalation over silent autonomous completion.

Production rule

Never let “the model usually behaves correctly” become a substitute for authorization, validation, idempotency, monitoring or deterministic checks.

async def supervisor(case):
    while not case.done:
        decision = await planner.decide({
            "goal": case.goal,
            "history": case.history,
            "state": case.state
        })

        if decision["agent"] == "billing":
            result = await billing_agent.run(
                decision["task"]
            )

        elif decision["agent"] == "technical":
            result = await technical_agent.run(
                decision["task"]
            )

        elif decision["agent"] == "returns":
            result = await returns_agent.run(
                decision["task"]
            )

        elif decision["agent"] == "verify":
            result = await verifier.run(
                decision["task"]
            )

        elif decision["agent"] == "human":
            return await request_human_review(case)

        else:
            return case.finalize()

        case = case.apply(result)

    return case.result
async def create_refund(order_id, amount):
    authorize("refund:create")

        return existing

Supervisor as the workflow control plane, specialist agents as scalable workers, durable state in a transactional store.

Why it works

Each agent owns a clear domain while the supervisor owns global process state and verification.

Why this architecture works

Customer support is decomposable by domain, individual specialists can operate with narrower permissions and context, and the supervisor provides a single place for task state, escalation and final coordination.

Final architecture heuristic

1

Start simple

One agent plus typed tools is the default starting point.

2

Make decomposition explicit

Split by responsibility, data, tools, permissions, scale or evaluation.

3

Control the edges

Message schemas, state boundaries and authorization should be explicit.

4

Verify important work

Do not ask the same model to blindly judge its own critical actions.

5

Observe the system

Trace decisions, tool calls, agent handoffs and failure paths.

6

Earn more autonomy

Increase autonomy only after the system is measurable and bounded.

The uncomfortable truth

Most teams do not have a “multi-agent problem.” They have a decomposition, state-management, validation, tooling or workflow problem. A more autonomous architecture can amplify those weaknesses rather than fix them.

Final takeaway

Learn MAS by building the smallest useful system first: one agent, then tools, then a workflow, then parallelism, then routing, then orchestration, and only afterward distributed multi-agent autonomy. The architecture should become more sophisticated because the problem requires it—not because the technology makes it possible.
