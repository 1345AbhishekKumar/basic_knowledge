Overview & Philosophy

Why this course exists, and the 'feel the problem first' method
Mark understood

Source: a system-design walkthrough for architecting an "AI PR Review Agent." This is not a tutorial on calling an LLM API with a diff. It's a full methodology for designing agentic systems in general, using the PR-review agent as the running example.

Why this course exists

The naive version of this project takes 20 minutes:

diff = git_diff(pr)
prompt = f"Tell me what's wrong with this code:\n{diff}"
response = call_llm(prompt)
post_comment(pr, response)

This works as a demo. It is not production-ready, and it will not behave like a good senior engineer. The entire point of this course is to show how to get from "demo" to "production agentic system" — not by adding more prompt engineering, but by doing real system design first.

The core insight (read this twice)

The problem is not "build an agent that reviews PRs automatically." The problem is selectivity: which findings does the agent act on, and which ones get deferred to a human's judgment?

A senior engineer reviewing their 20th PR of the day is not as sharp as on their 1st — fatigue, inconsistency, and missed details creep in. The system we're designing exists to solve exactly one problem:

Reclaim senior-reviewer attention by automating the mechanical part of review, while keeping human judgment for what genuinely needs it.

This single sentence — selectivity — is called L0 in this course, and it drives every architectural decision downstream. The system should optimize for surfacing findings worth a senior's attention, not for maximal coverage of every possible comment.

The design philosophy: "Feel the problem before you solve it"

The author's method, used repeatedly throughout, is:

  1. Remove the system and observe the pain. Before writing any code, ask: "What happens today if this AI agent doesn't exist?" Watch (mentally or literally) how a human currently solves the problem. Write down every micro-decision they make — even unconscious ones.
  2. Only then design the fix. Once you've felt why something is needed (retrieval, observability, human-in-the-loop, etc.), the design "writes itself" instead of being copied from a template.
  3. Necessity is manufactured on purpose. "We'll create that necessity intentionally" — i.e., deliberately strip the system down to find where it hurts, rather than pre-emptively bolting on every best practice you've read about (rate limiting, observability, security) without knowing why you need them for this system specifically.

This is contrasted with the common (bad) approach: "let's use LangGraph, let's use Postgres, let's add rate limiting and observability" — chosen because they're popular, not because a specific failure mode demanded them.

The five-move design template

Applied to every component of the system, not just the system as a whole:

Move Question
1. Map the mess What does a human do today, step by step, without this agent?
2. Name trigger & output What precisely starts the work, and what precisely comes out?
3. Assign components Which step is a trigger, a tool/API, an LLM, deterministic ML, or a human checkpoint?
4. Decide autonomy How much does the system do alone vs. defer to a human? (depends on cost-of-error)
5. Assume everything breaks For every component: what fails, and what's the fallback?

This loop is run once per component — orchestrator, retriever, event spine, confidence gate, specialist agents — five separate times, not once for the whole system.

The two-column failure analysis

For every component, failures are split into two directions:

  • Engineering failures — timeouts, retries, malformed payloads, replay attacks, GitHub's 10-second webhook ack window, etc.
  • LLM failures — hallucination, bad retrieval, prompt drift, low confidence, disagreement between parallel agents, etc.

These get placed into a 2×2 known/unknown matrix (what you know, what you'll recognize when you see it, what you've never considered) — and the component design emerges from filling that matrix in, not from a checklist.

What you'll actually build

By the end of this course's methodology (not necessarily by the end of this repo, since the author intentionally leaves later milestones as an exercise):

  • A GitHub-webhook-triggered, queue-backed ingestion service
  • A LangGraph orchestrator that fans out to 4 parallel specialist agents (security, quality, testing, docs)
  • A retrieval layer grounding every specialist in the actual codebase (vector search + hybrid full-text search)
  • An aggregator that merges, deduplicates, and scores findings
  • A confidence-gated human-in-the-loop escalation path
  • A single unified Postgres-compatible database (Tiger Cloud / TimescaleDB) holding three data shapes: semantic memory (vectors), truth (relational findings), and time (observability event spine)
  • A full reliability layer: retries, circuit breakers, idempotency, deduplication, timeouts on every node
  • A harness-driven build workflow ("Genesis Kit") for actually writing the code with an AI coding agent without losing context or vibe-coding

01 · First Principles: Mapping the Mess
01

First Principles: Mapping the Mess

L0 selectivity, the structured finding schema, trust & autonomy
Mark understood

Step 0: Why does this system exist at all?

Before any architecture, ask what happens without the agent.

Without automated review, on a team of any size:

  • Every PR waits for a senior engineer's attention — junior/mid-level review isn't sufficient trust.
  • Senior attention is a scarce resource. PRs queue for hours or days (the author cites real experience: "at least a week" for review comments at past jobs).
  • Quality is inconsistent: the 10th review of the day is not the same quality as the 1st, because of human fatigue.
  • The cost of no review is enormous: people burn huge amounts of time either waiting or reviewing badly.

Conclusion (L0 — the single sentence the whole architecture is built on):

An automated reviewer exists to solve exactly one problem: reclaiming senior-reviewer attention by automating the mechanical part of review. The system optimizes for surfacing findings worth a senior's attention and deferring the rest — not for maximal output/coverage.

This reframes the project. It is not "build a PR review bot." It is "build a triage system that protects human judgment as a scarce resource." Every subsequent design decision (confidence gates, escalation, selective posting) traces back to this one sentence.

Step 1: Watch how a human already does this ("map the mess")

Before touching any tooling, write down every micro-decision a human reviewer makes, including unconscious ones. This is manual, non-technical work — the point is to surface the mess so you know what to organize.

The observed human flow:

  1. A developer pushes a commit and opens a PR.
  2. It waits — pure queueing cost.
  3. A reviewer eventually notices (Slack ping, GitHub notification, or a colleague directly asking "can you review this?").
  4. The reviewer context-switches into the change (a real cost — this is why "the queue" itself is a design concern later).
  5. They read the diff, sometimes pull the branch to actually run it.
  6. They bring in codebase context: past architecture decisions, conventions, documentation, prior related discussions.
  7. They reason across separate concerns (see below), each from a different mindset.
  8. They stay skeptical and cite evidence — "this can NPE because x is nullable on line 40," never a vague "this looks off."
  9. They leave a comment. The author reads it, clarifies, or fixes and re-submits. Sometimes they escalate to someone even more senior.
  10. Sensitive findings are not posted publicly. If a reviewer at a big org finds a serious security vulnerability in an open-source PR, they do not comment it publicly — they escalate privately (e.g., Slack DM) to avoid tipping off anyone who could exploit it before a fix ships.

The four things a human reviewer actually does

Distilled from the above, every senior reviewer does four things, and this becomes the direct blueprint for the agentic system:

Human behavior Engineering translation
Brings codebase context (conventions, ADRs, related code) Retrieval (RAG)
Reasons across separate concerns (security / quality / testing / docs), each a different mindset Multi-agent architecture — not one big prompt
Stays skeptical, cites evidence for every claim Every finding must carry confidence + rationale
Escalates instead of self-certifying on high-stakes issues Human-in-the-loop (HITL) gate

Key rule: the four specialist agents in this system (Security, Quality, Testing, Docs) were not invented by asking "how many agents should we have?" — they were derived directly from observing what a human reviewer actually does. Agent design should come from the human system you mapped, not from an abstract "let's design 4 agents" brainstorm.

Step 2: Name the precise trigger and precise output

A vague trigger is a design smell. Example of a bad trigger: "any email that comes in" for an insurance-claims agent. A precise trigger: "an email arriving at this specific address, containing the word 'claim'."

For the PR agent:

  • Trigger: GitHub emits a pull_request webhook when a PR is opened. This is precise — GitHub explicitly fires this event type, so there's no ambiguity about what starts the workflow.
  • Output: A single structured review posted back to the PR via GitHub's API, with findings attached to specific files and lines.

The word structured is doing a lot of work here. The output is not prose. It is a list of typed findings, each carrying:

finding:
  agent_type: security | quality | testing | docs
  severity: critical | warning | info
  category: <e.g. "sql-injection", "missing-test-coverage">
  file: path/to/file.py
  line: 142
  confidence: 0.0-1.0
  rationale: "why this was flagged, in the agent's own words"

Why every field matters:

  • agent_type / category — traceability: which "mindset" raised this?
  • severity — drives urgency and whether it must be escalated regardless of confidence (a critical finding is always escalated).
  • file / line — exact location, not "somewhere in this file."
  • confidence — drives the human-review gate: below a threshold, don't auto-post, route to a human instead.
  • rationale — makes the finding auditable and disputable. If a developer disputes a finding, you can trace back exactly why the agent said what it said, and use that to debug/improve the system later.

This finding object is the unit that flows through the entire system — from specialist agent → aggregator → confidence gate → GitHub post or human queue → (optionally) dispute → feedback loop.

Step 3: Survey the industry-standard approaches — and why each fails

Before picking an architecture, four common approaches were evaluated and rejected (or accepted with caveats):

  1. Linters — pattern/syntax/style rules only. Cannot reason about intent or logic. No semantic understanding at all.
  2. Static analysis — real data-flow and type analysis, finds genuine bugs, but: high false-positive rate, no codebase-wide judgment, can't read documentation or understand intent.
  3. Single LLM review (one prompt, whole diff) — the "naive tutorial" version. Fails because: - One agent trying to hold 4 different mindsets (security, quality, testing, docs) at once performs worse than 4 focused agents. - No grounding in the actual repo → hallucinates with false confidence. - No auditability, no observability, no way to know why it said what it said.
  4. Agentic fan-out / fan-in (the chosen pattern) — roll out specialist agents in parallel (security, docs, tests, quality), then an aggregator combines ("fans in") their outputs. This is the correct pattern for this problem because the four concerns are genuinely independent of each other (no agent needs another agent's output to do its job).

Step 4: The grounding problem

A senior human reviewer doesn't hallucinate about the codebase because they already know it. An LLM given only a diff has no such knowledge.

  • You cannot stuff the entire repository into the prompt — it exhausts the context window and degrades quality.
  • The fix: retrieval. For every diff, fetch only the most relevant slices of the codebase and inject those into the prompt. This is "context engineering," and it's what "turns the stranger into the colleague" — i.e., what gives the agent the equivalent of a senior's tacit repo knowledge.

Step 5: What kind of memory does a reviewer actually need?

Borrowing directly from how humans hold different kinds of knowledge, three memory types are identified, each needing a different storage shape:

Memory type Human analogy What it holds Storage shape needed
Semantic "I know this codebase" Functions, classes, current code Vector embeddings + similarity search
Episodic "I remember what happened last time" Past reviews, what was flagged, what was disputed Time-ordered relational rows
Procedural "This is how our team likes things done" Conventions, architectural decisions, team preferences Small structured facts/rules

This three-way split becomes the direct basis for the data-layer design in 03-data-engineering-three-shapes.md.

Step 6: Trust requires more than reasoning + grounding — it requires proof

Imagine the agent posts: "This endpoint is vulnerable to SQL injection, confidence 60%," and a developer disputes it. Without a record of:

  • why the finding was raised,
  • which context was retrieved,
  • which prompt version ran,
  • what the model actually returned,
  • what it cost,

...you cannot defend the finding, debug it, or improve the system. The saying used here: "If something can be measured, it can be improved."

This is why an event spine (durable, time-ordered log of every LLM call, tool call, and decision) is required — it's not a "nice to have observability feature," it's a prerequisite for trust. It powers three downstream capabilities:

  1. Trace viewer — reconstruct any review end-to-end.
  2. Audit trail — defend or dispute any finding.
  3. Cost economics — know what the system is spending, in near real time.

Step 7: When not to trust the agent — the confidence gate

Given L0 (selectivity) and the confidence field on every finding, the system defines explicit trust rules:

  • No critical findings + confidence above threshold → auto-post to GitHub.
  • Confidence below threshold → route to a human approval queue.
  • Any critical finding, regardless of confidence → always escalate to a human. Severity overrides confidence.
  • Developer disputes a posted finding → record it as feedback (this is the reversibility / learning loop, discussed more in file 05).

Maturity owns the autonomy. The threshold isn't fixed forever — a brand new, unproven system should start with a conservative threshold (e.g. 0.6) and route more to humans. As the system proves itself over time, the threshold can be relaxed and more autonomy earned. This mirrors general advice for any AI system: new systems need more human override, proven ones earn less.

Step 8: The full first-principles synthesis (one paragraph to memorize)

A pull request triggers the work. It's queued because the trigger must be acknowledged fast. An orchestrator fans work out to four parallel specialists. Each specialist is grounded by retrieval over the codebase (three memory shapes: code, past reviews, conventions). Each specialist returns structured findings with confidence and rationale. An aggregator merges, deduplicates, and computes overall confidence. It routes: post automatically when confident, route to a human when not. Every action along the way is written to an event spine so the whole thing can be traced, audited, and priced. A reliability layer keeps every component degrading gracefully instead of failing hard.

Everything in files 02–07 is just expanding this one paragraph.

Three factors that decide how much autonomy any component gets

Used repeatedly as a general rule, not just for this project:

  1. Consequence of error — a wrong style comment is annoying; a missed SQL-injection finding is dangerous. Match autonomy to blast radius.
  2. Reversibility — an auto-posted review comment can be disputed and removed; a merged database migration cannot be un-run. Give less autonomy to irreversible actions.
  3. System maturity — new, unproven systems earn less autonomy; systems that have proven themselves over time earn more.

A cautionary real story (why "how fast can this go wrong" matters)

The author recounts a real incident at a previous company (SPL): an autonomous LinkedIn outreach agent, expected to take 2–3 days to schedule anything, actually scheduled and completed an in-person dinner with a major prospect in under 9 hours — faster than anyone anticipated, catching the team completely off guard. The lesson: the system failed because an assumption failed ("this can't happen that fast"). Design your autonomy boundaries assuming your worst-case timing assumption is wrong, not just your worst-case output-quality assumption.

Architecture & Design Patterns

Fan-out/fan-in, queueing, LangGraph vs Temporal

The end-to-end flow (prose diagram)

Why a queue sits between ingress and orchestration

This is not an arbitrary architectural flourish — it's forced by a hard constraint: GitHub expects webhook acknowledgment within roughly 10–12 seconds. An LLM-based review can easily take 30–40+ seconds. If you make GitHub wait for the LLM to finish, GitHub will time out and consider the delivery failed (and retry it, creating duplicate-processing risk).

The fix, explained with an analogy: think of a restaurant. The receptionist (ingress service) takes your order and immediately says "got it, we'll have it ready" — they don't disappear into the kitchen to cook it themselves. The chef (orchestrator worker) picks up the order from a ticket queue and cooks on their own timeline. One receptionist, one kitchen, decoupled by a queue.

Concretely:

  1. Ingress verifies the signature + idempotency key.
  2. Ingress enqueues the job into Redis via ARQ and returns 200 to GitHub immediately.
  3. A separate worker pool picks jobs off the queue one at a time and runs the actual LangGraph orchestration.

Where this breaks, and the fix

At high throughput (e.g., 10,000 PRs/minute), a single ARQ worker becomes the bottleneck — queue depth outgrows the worker drain rate. The fix (applying the modular monolith philosophy) is to extract:

  • the webhook receiver as a stateless ingress service, and
  • the orchestrator as a separate, independently scalable worker pool.

You scale the two independently instead of scaling one monolithic process.

Security at the ingress boundary

Two checks happen before any processing, and their order matters:

  1. HMAC signature verification — confirms the payload genuinely came from GitHub (using a shared webhook secret) and rejects forgeries.
  2. Idempotency key check (a.k.a. "unaltered key" in the transcript, really meaning idempotency) — GitHub may retry the same delivery; this check acknowledges and drops duplicates so the same PR isn't processed twice.

Worked example: why verification must happen before parsing

A concrete design decision, presented as a mini case study:

  • Question 1: Should signature verification happen before or after any payload processing? Answer: Always before. If you don't yet know the request is from GitHub, you must not do any real work on it — you return a fixed rejection response regardless of what's inside, so you leak nothing useful to an attacker probing your endpoint.

  • Question 2: A signature-valid but malformed JSON body previously caused a raw 500. Should it be 400 instead? Answer: Yes, 400. Once HMAC verification succeeds, the request is authenticated (it came from someone holding the shared secret). If the authenticated body is malformed, that's a client error (400), not a server fault (500). Correct ordering: verify signature → parse JSON → 400 if malformed → continue processing if valid. Practical benefits: prevents false alarms in server monitoring (a 500 spike looks like your system broke; a 400 correctly signals "bad input"), and it aligns with standard HTTP semantics.

The orchestration pattern: fan-out / fan-in

Because the four specialist concerns (security, quality, testing, docs) are genuinely independent — none needs another's output to do its job — the correct agentic design pattern is fan-out/fan-in, not a sequential pipeline:

  • Fan-out: the orchestrator dispatches the PR diff + retrieved context to all four specialists in parallel.
  • Fan-in: a single aggregator node waits for all four, merges their structured findings, deduplicates overlapping ones, and computes an overall confidence.

This is chosen specifically because sequential review (security → quality → testing → docs, one after another) would be strictly slower with no correctness benefit, since the four concerns don't depend on each other.

Choosing an orchestration engine: LangGraph vs. Temporal

Both were seriously considered. Comparison:

Dimension LangGraph Temporal
Runtime Runs inside your own Python process — no extra infra Separate server infrastructure required
Parallel fan-out First-class via the Send API Supported, but heavier to express
Checkpointing Manual — you checkpoint to the same Redis you already use for the queue Strong, built-in guarantees; resume-from-failure is native
LLM tooling Built specifically for LLM workflows, has rich integrations Generic — not LLM-specific at all
Maturity Newer, less proven at large scale Enterprise-grade, proven at scale
Operational cost None beyond your app You must run and understand your own Temporal server

Decision for the MVP: LangGraph. Reasoning: no extra infrastructure to stand up, first-class support for the exact fan-out pattern needed, and the checkpoint mechanism can reuse the Redis instance already required for the job queue. Temporal is not rejected as "wrong" — it's explicitly flagged as the right choice if/when scale demands it.

The critical follow-on decision: don't marry the framework

To make a future LangGraph → Temporal migration painless, the code defines a single abstract interface:

class WorkflowEngine(ABC):
    @abstractmethod
    def run(self, workflow_input): ...

    @abstractmethod
    def resume(self, workflow_id): ...

    @abstractmethod
    def get_state(self, workflow_id): ...

The LangGraph implementation is just one concrete class implementing this interface. If Temporal is needed later, you add a new class implementing the same three methods — zero changes to the rest of the codebase. General principle worth remembering: make your code framework-agnostic by coding to an interface you own, not to the framework's own API surface directly throughout your business logic.

The retrieval layer (grounding, concretely)

For every incoming PR:

  1. Take the PR diff (the +/- lines).
  2. Compute its embedding.
  3. Query the vector store (code chunks previously embedded from the main branch) using hybrid search: ANN vector similarity + full-text search (FTS), filtered by things like repo and freshness.
  4. Merge and take the top-K most relevant code chunks.
  5. Inject those chunks into each specialist's prompt.

This is standard RAG, applied specifically to source code rather than documents — and it's what prevents specialists from hallucinating about code they've never actually seen.

Observability as an architectural component, not an afterthought

Every specialist's LLM call, every retrieval, every routing decision is recorded as a timestamped event ("agent event") — see file 03 for the storage shape. This isn't bolted on after the fact; it's treated as a first-class component of the orchestrator design because file 01 already established that trust requires proof, not just good reasoning.

Summary: the five architectural decisions and their one-line justification

Decision One-line justification
Webhook → Queue → Worker (not direct call) GitHub's ack window is too short for synchronous LLM calls
Fan-out/fan-in over sequential The four concerns are independent — no benefit to serializing them
LangGraph over Temporal (for MVP) No extra infra, first-class parallel fan-out, reuses existing Redis for checkpoints
Abstract WorkflowEngine interface Keeps the option to migrate to Temporal open without a rewrite
Retrieval before every specialist call Prevents hallucination — grounds the agent the way a senior's repo knowledge grounds them

03

Data Engineering: Three Shapes

Memory, Truth, Time — and why one unified DB wins
Mark understood

Why data engineering gets its own design phase

Once the cognitive design (file 01) is settled, the next question is purely mechanical but critically important: where does everything actually get stored, and in what shape? This is treated as one of the most important layers of the whole system — get it wrong and every other layer inherits the pain.

The three data shapes, restated precisely

Shape What it is Source
Memory Chunks of the codebase + past reviews + conventions — what the agent needs to understand a new diff Semantic + episodic + procedural memory (from file 01)
Truth The findings themselves — GitHub review ID, HITL escalation status, findings, human decisions The output of a completed review
Time Every span of work: LLM calls, tool calls, cost, latency, decisions The observability event spine

Concretely, per shape:

  • Memory → needs similarity search over embeddings → a vector store.
  • Truth → needs timestamped, queryable relational rows → standard Postgres tables.
  • Time → needs high-volume time-series writes with fast rollups → a time-series-optimized table (hypertables).

The naive (and wrong) instinct: three separate databases

The obvious-seeming plan is: a vector DB (e.g. Qdrant) for memory, Postgres for truth, and a time-series DB for observability. This is explicitly called out as over-engineering.

Why three databases is the wrong call

Consider a simple diagnostic question: "For this PR, what code did we retrieve, what review did we produce, and which model call was expensive?" Answering that single question across three separate databases means:

  • Three separate queries against three separate systems.
  • Stitching the results together manually in application code.
  • Three times the operational surface area: connection pools, backup strategies, failure modes, and "what happens if store #2 is down but #1 and #3 are fine?" scenarios.

The actual goal is not "avoid a popular database," it's "avoid unnecessary failure surface for a single logical question." The three data shapes are not compromised on — but they don't need three separate physical databases to exist.

The chosen solution: one unified Postgres-compatible database (Tiger Cloud)

Tiger Cloud = a managed, Postgres-compatible database with the following extensions layered on top, each one solving exactly one of the three shapes:

1. Memory → pgvector + pgvectorscale

  • pgvector lets a normal Postgres column store an embedding (a list of floats) — e.g. a code_chunks table with an embedding vector(1536) column.
  • At scale (millions of code-chunk embeddings), naive pgvector search gets slow. pgvectorscale adds a faster index so Postgres can find nearby vectors far more efficiently — described as "a fast librarian" that knows where things are instead of scanning everything.
  • DiskANN — an indexing algorithm that builds the nearest-neighbor search structure on disk/SSD rather than requiring everything to live in RAM. Necessary once code-chunk counts get into the millions, since you can't keep an unbounded index resident in memory forever.

2. Truth → plain Postgres tables

Standard relational tables for reviews, findings, HITL rows, and GitHub IDs — nothing exotic needed here; Postgres was already going to be the right tool for this shape on its own.

3. Time → hypertables + continuous aggregates

  • A hypertable (from TimescaleDB, which Tiger Cloud is built on) stores time-series rows (e.g. agent_events) but internally partitions them into time-based chunks behind the scenes (e.g. "Monday's rows," "Tuesday's rows") — you interact with it as one logical table, but storage and queries are chunk-aware for efficiency.
  • Why this matters: a dashboard asking "what happened in the last hour" doesn't need to scan the entire history — it only touches the relevant recent chunk(s).
  • Continuous aggregates are pre-computed, automatically-kept-updated summary tables. Instead of scanning 10 million raw agent_events rows every time a dashboard refreshes to answer "what did we spend today?", you read a small, continuously maintained rollup table (cost/minute, P95 latency, token totals, etc.).
  • Practical payoff: a budget guard can check the rollup ("has today's spend already crossed the limit?") cheaply and block further LLM calls if so — without ever touching the raw event table.

Why Tiger Cloud over a pure vector DB (e.g. Qdrant)

The reasoning given: vector similarity is not the only question this agent asks. A real PR review needs, together, in one query:

  • vector similarity (which code is related to this diff),
  • repo filters,
  • freshness filters,
  • exact identifier matching,
  • plus joining against review records, cost records, and audit history.

A pure vector database is excellent at the first bullet but weak at combining it with the rest. Keeping everything in one Postgres-compatible store means retrieval results can live beside metadata, review trails, and hypertables in the same query surface — no cross-database joins in application code.

The invariant that shapes the schema: agent_events is append-only

A hard rule baked into the database itself (not just convention): the agent_events hypertable is immutable — append-only. You can insert, but UPDATE and DELETE are hard-rejected. This matters because:

  • Observability data must be trustworthy for auditing and disputing findings — if rows could be silently edited or deleted, the trace viewer's story could be tampered with.
  • Enforcing this at the database level (not just "we promise not to update rows in application code") is a stronger guarantee — it survives bugs, bad migrations, and rogue scripts.

Implementation detail worth knowing: PostgreSQL rules don't work on hypertables

While building this, an actual schema-design gotcha surfaced (documented here because it's a genuinely useful, non-obvious PostgreSQL fact):

  • Attempted approach: a Postgres RULE intercepting UPDATE/DELETE and rejecting them.
  • Why it failed: Postgres RULEs operate at the query-rewrite stage. TimescaleDB hypertables internally distribute data across many underlying chunk tables and never rewrite rules against that distributed structure — attempting to create such a rule throws an error.
  • The fix: use a trigger (BEFORE UPDATE / BEFORE DELETE) instead of a rule. Triggers operate at the row level and work correctly against hypertables.
  • A related edge case caught by verification: if a caller runs TRUNCATE agent_events instead of DELETE, does the delete trigger fire? No — TRUNCATE is a distinct SQL command with its own execution path; row-level BEFORE DELETE / AFTER DELETE triggers do not fire on it. You need a separate BEFORE TRUNCATE / AFTER TRUNCATE trigger if you want to guard against that too.

This is a good general lesson: an invariant stated in English ("this table is append-only") is not actually enforced until you've checked every SQL code path that could violate it — including the ones nobody thinks about, like TRUNCATE.

Another real gotcha caught during build: embedding dimension mismatch

A configuration inconsistency was flagged during verification: the schema declared vector(1536) (matching, e.g., OpenAI's text-embedding-3-large default), but the .env file specified EMBEDDING_DIMENSION=256. If these don't match:

  • pgvector stores the dimension as part of the column type.
  • Insert time will mismatch and fail (or silently misbehave, depending on the client) — it will not pad or truncate the vector to fit.

Lesson: the embedding model's actual output dimension and the schema's declared vector dimension must be kept in lockstep, and this should be checked explicitly rather than assumed — it's an easy one-line misconfiguration with a confusing downstream failure.

Redis: the fourth store that's allowed to exist separately

Redis (with ARQ) is kept as a separate store from Tiger Cloud, on purpose — it's a job queue / scratchpad, not one of the three "shapes." It's ephemeral by nature (webhook job queue), so it doesn't need the durability guarantees or query flexibility of the unified Postgres store. Splitting this out doesn't reintroduce the "three databases" problem, because its failure mode and access pattern are fundamentally different from Memory/Truth/Time.

Summary table

Concern Store Extension/Mechanism
Code embeddings, semantic search Tiger Cloud (Postgres) pgvector + pgvectorscale + DiskANN
Reviews, findings, HITL rows Tiger Cloud (Postgres) Plain relational tables
Every LLM/tool call, cost, latency Tiger Cloud (Postgres) Hypertables + continuous aggregates
Job queue for incoming webhooks Redis ARQ (Automatic Repeat reQuest-style job queue)

One durable database. One backup story. One place to query. One identity connecting memory, truth, and time.

05

Failure Modes & Reliability

Every named failure mode and its mitigation
Mark understood

The core mindset: "everything will break"

The design methodology treats reliability as a first-class design input, not a checklist added at the end. For every component (file 01's five-move loop, move 5), you ask explicitly: "what happens when this breaks, and what's the fallback?"

This file catalogs every named failure mode from the transcript, the mechanism behind it, and its designed mitigation.

1. Hallucination

  • What it is: the model states something confidently that is simply false. Framed here as "a feature, not a bug" of LLMs in general — the point isn't to eliminate it, it's to contain the consequence.
  • Mitigation:
  • Grounding via retrieval (file 02) — reduces the rate.
  • Citation requirement — every finding must reference actual evidence (file/line), not vague assertions.
  • Confidence field — low confidence routes to human review instead of auto-posting.
  • Rationale field — makes hallucinated findings auditable/disputable after the fact, which feeds back into system improvement.

2. Model / prompt drift

  • What it is: a system performs great at build time on your eval dataset, but degrades in the real world because the distribution of inputs changes — the classic MLOps concept of drift, applied to LLM prompts. Example given: a spam classifier that was great when trained, but spammers adapt their strategy and the model's accuracy silently decays.
  • Mitigation:
  • Monitoring dashboard with alert thresholds.
  • Periodic re-training / periodic prompt updates.
  • Rule-based fallbacks for common cases that don't need an LLM call at all.

3. Tool / API timeout

  • What it is: an external dependency (OpenAI, GitHub API, embedding provider) is slow or down.
  • Mitigation:
  • Timeout + retry on every outbound call.
  • Graceful degradation on partial data (don't fail the whole review because one specialist's tool call timed out — degrade that one finding, not the whole pipeline).
  • Circuit breaker — stop hammering a dead service; fail fast instead of queuing up retries against something that's clearly down.

4. Feedback-loop poisoning

  • What it is: two related but distinct risks: 1. The agent doesn't actually learn from disputes/feedback at all (feedback given, never used). 2. Bad feedback gets incorporated — e.g. a junior engineer disputes a finding in an unhelpful or low-quality way, and the agent "learns" the wrong lesson from it.
  • Mitigation:
  • Minimum evidence threshold before acting on any single piece of feedback — don't let one disputed finding retrain behavior; require a pattern.
  • Decay old feedback over time — stale feedback that's no longer representative shouldn't keep influencing behavior (and shouldn't keep bloating your embedding storage indefinitely).

5. Orchestration deadlock

  • What it is: in a fan-out/fan-in pattern, the aggregator waits for all N parallel specialists to respond. If one specialist hangs (crashes, never returns), the aggregator can wait forever.
  • Mitigation:
  • Timeout on every node in the graph, not just the overall workflow. If a specialist doesn't respond in time, treat it as a partial failure and proceed with what you have rather than blocking indefinitely.

6. The human bottleneck (escalation queue overload)

  • What it is: you cannot have one human clear thousands of escalations per day. If everything below the confidence threshold gets dumped into one undifferentiated queue, the queue grows faster than any human can clear it.
  • Mitigation:
  • Priority queueing — not all escalations are equal; surface higher-priority PRs first.
  • Capacity planning — explicitly model how many escalations per day a human reviewer can realistically absorb, and design the confidence threshold and escalation logic around that number, not an arbitrary default.

7. The "almost-right" problem

  • What it is: the most dangerous failure mode, arguably — a finding that's ~90% correct but subtly wrong in a way that's easy to miss (misattributed line, wrong root cause, etc.). This is worse than an obviously-wrong finding because it's more likely to be trusted.
  • Mitigation:
  • Confidence threshold + HITL gate as the primary defense (same mechanism reused from file 01).
  • Random audits — periodically (e.g. every 2–3 days) manually spot-check auto-posted findings even when confidence was high.
  • Rotate reviewers/models — vary which model reviews what, to avoid a single model's blind spots compounding silently over time.
  • Test with new/adversarial inputs periodically to check the system hasn't quietly degraded.

8. Idempotency / duplicate posting

  • What it is: GitHub may retry a webhook delivery (network hiccup, timeout, etc.). Without protection, the same PR could be reviewed and posted twice.
  • Mitigation:
  • Deduplicate before posting — check whether this exact review/delivery has already been processed before writing anything back to GitHub.
  • This ties directly back to the idempotency key check at ingress (file 02) — the reliability layer isn't a separate afterthought, it's the same invariant enforced at multiple points in the pipeline.

The reliability layer as a named architectural component

All of the above mitigations collectively form what's called the reliability layer: retries, circuit breakers, idempotency, dedup, and per-node timeouts, each one explicitly mapped to the specific failure mode it defends against — not added generically "because best practice says so."

Important teaching point repeated in the transcript: reliability mechanisms were never introduced by saying "let's add retries and circuit breakers because that's standard." They were introduced only after a specific failure mode was named and felt. This keeps the system from being over-engineered with defenses against problems that don't actually apply to it.

Autonomy calibration recap (see also file 01)

Three factors decide how much autonomy any given action gets:

  1. Consequence of error (a wrong style nit vs. a missed SQL injection).
  2. Reversibility (a disputed PR comment vs. an already-merged migration).
  3. System maturity (new system → less autonomy; proven system → more).

The five human-involvement patterns (a general framework)

Not every system needs the same level of human involvement. Five patterns, in increasing order of human control:

  1. Full automation — appropriate only for routine, reversible, low-stakes tasks; humans review periodically, not per-instance.
  2. Human reviews output — the system drafts, a human verifies before it goes out (used for reputational-stakes content).
  3. Human handles the exception — system handles easy/high-confidence cases automatically; humans see only the hard/low-confidence/anomalous ones. This is the pattern chosen for the PR review agent.
  4. Human decides, system prepares — system gathers all context and presents it, but a human makes the actual call (example given: loan approval — system scores and gathers, human approves).
  5. Full human with AI assist — highest-stakes domains (financial, legal, health) where full autonomy is never appropriate regardless of system maturity.

Golden rule stated explicitly: if your system touches financial, legal, or health decisions, you cannot default to full autonomy — this is a hard constraint, not a tuning knob.

06 · Genesis Kit: Harness Engineering
06

Genesis Kit: Harness Engineering

done.html, G0 gates, the L4 verifier, quiz-me
Mark understood

The distinction this whole section rests on

"This is not vibe coding. You spend a lot of time in system design first, then create steps, and only then go to the coding agent."

Vibe coding = typing a vague request at a coding agent and hoping the output is right. Harness engineering / "loop engineering" = giving an AI coding agent a persistent, structured state so that:

  • it doesn't re-derive the whole design from scratch every session,
  • it can't quietly drift the goal to whatever's convenient to implement,
  • someone else (or future-you) can pick up exactly where it left off,
  • every claim of "this works" is checked by an independent process, not self-reported.

"Genesis Kit" is the author's own open-sourced framework for this. It is not specific to this PR-review project — it's a general-purpose methodology for working with any AI coding agent (Claude Code, Codex, Hermes, etc.) on any project.

Core artifacts Genesis Kit creates in your project

File/Artifact Purpose
done.html The locked spec. Defines the cognitive job, inputs, autonomy level, failure tolerance. The agent is never allowed to edit this file. It's the fixed target.
implementation-notes.html Live state. What's currently in flight, current milestone, current phase, any blockers. Read at the start of every session so a new session doesn't duplicate or contradict existing work.
context-graph (.md) The invariants — non-negotiable rules (e.g. "every GitHub webhook payload passes through signature verification," "every specialist finding carries confidence and rationale") — plus a dependency graph: change one thing, see what else must be re-verified.
index.md Project documentation: sources, concepts, how things work — explicitly modeled on Andrej Karpathy's approach to project indexing.
plan.md Detailed milestone plan: chosen approach vs. rejected alternatives, build order, files touched per milestone, demo command, success criteria, loops/skills used, external dependencies, token budget per milestone.
loops.md The actual execution procedure the agent follows — described in detail below.
current.md (per milestone, e.g. M1.md, M2.md) The live checkpoint log for that specific milestone: what's been read, what gate it's at, what iteration it's on.

Why done.html cannot be touched by the agent

A repeatedly-observed failure mode of AI coding agents: over a long session, the agent quietly redefines "done" to match whatever it managed to build, rather than what was actually asked for. Locking the definition of done in a file the agent is forbidden to edit removes that failure mode structurally — it's not a "please don't do this" instruction, it's a hard boundary.

The Gate-0 (G0) procedure — "orient before acting"

Before doing any work on a milestone, the agent must run through this checklist:

  1. Pick candidate existing pages/files matching the milestone by name.
  2. Drill into those existing pages (if the milestone was already started or exists from a prior session).
  3. Search implementation-notes for a "rolling source of truth" — what's already live right now?
  4. Confirm the system doesn't already exist before building it again.
  5. Write a G0 checkpoint into current.md.
  6. Emit a verdict: "unbuilt" (proceed to build) or "already exists" (skip, or refine).

This exists specifically to prevent an agent from re-implementing something that already exists because it lost context between sessions — a very common and wasteful failure mode when working with AI coding agents across multiple sessions.

The five gates that govern every loop iteration

For each iteration inside a milestone's build loop, five gates must pass:

  1. Skill gate — did we load the right domain-knowledge skills for this task (e.g. security engineering skill for the webhook signature work)?
  2. Router gate — did we correctly determine which loop type this task needs (build / debug / research)?
  3. Logging gate — did we log the skills used into the checkpoint (so it's auditable later)?
  4. Progress gate — did this iteration measurably move the milestone forward (not just "produce output")?
  5. Budget gate — are we still within the token budget allocated to this milestone?

Only after all five pass does the loop consider running an independent verifier.

The three loop types

Loop When it's used
Build loop Standard implementation work
Debug loop Triggered when a test fails or the verifier rejects the work
Research loop Triggered when a phase requires investigation before it can be implemented (e.g. "how does TimescaleDB handle rules on hypertables?")

The build loop, step by step

while not milestone_done and iterations < 10:
    create_micro_plan()
    load_skills()
    read_wiki_pages()
    checkpoint_initialization()

    while not phase_done:
        load_next_phase()
        if phase_needs_research:
            run_research_loop()
        else:
            edit_files()
            run_tests()
            if tests_fail:
                run_debug_loop()

    spawn_independent_verifier()   # <-- L4, see below
    if verifier_approves:
        mark_milestone_done()
    else:
        run_debug_loop(retry_once=True)
        update_checkpoint_and_plan()

The independent verifier (L4) — the single most important mechanism

After the build loop believes it's finished, a separate agent instance, spawned fresh, with a deliberately restricted context, is asked to verify the work:

"You are an independent code reviewer for this project. You did not write this code. Verify the goal and success criteria. Do not assume the build agent's claims are true."

Crucially, this verifier is given:

  • the milestone's goal,
  • the success criteria,
  • the invariants (non-negotiables),

but is explicitly not given the builder's own reasoning trail. This mirrors a real engineering practice: the person who wrote the code is not the best-positioned person to catch their own blind spots, because they already believe their own reasoning. A fresh, skeptical reader with no investment in the prior work catches errors the builder can't see in itself.

Why this matters: "writing your own exam paper"

The author's framing: if a model writes its own tests, it's like a student writing their own exam questions — they'll only test what they already know they got right. Genesis Kit deliberately separates the "exam writer" from the "student" — a fresh verifier agent, working only from goal + success criteria + invariants (not the builder's internal reasoning), is the one who "writes the exam" and grades it.

Real example from the transcript: what the verifier actually caught

During M1 (webhook ingress), the build agent claimed the milestone was done. The independent verifier found a real bug: malformed-but-validly-signed JSON was returning a raw 500 instead of a 400. This kicked off a debug loop: fix applied → re-verified → a regression test added (to make sure this specific class of bug can't silently reappear later) → milestone approved.

During M2 (Tiger Cloud infra), the verifier caught the pgvector schema gotcha (Postgres rules vs. hypertables — detailed in file 03) before it became a production bug.

The "quiz me" mechanism — forcing genuine understanding

After a milestone is verified, Genesis Kit can quiz the human on the decisions the agent made, e.g.:

  • "Why does the receive-check happen before HMAC verification rather than giving the principle that verification should get all processing?"
  • "Before the fix, malformed-but-validly-signed JSON caused a raw 500. Is 400 the right response, or should it be something else?"
  • "The idempotency-key router is currently in-memory only — it won't survive a process restart, and a later milestone (M4) will replace it with Redis-backed dedup. Is that acceptable for M1?"
  • "code_chunks has a hardcoded embedding dimension. If a later milestone changes the embedding model without reconciling this, what breaks, and where?"

Purpose: you cannot claim "the agent built this for me and I don't know why it works." The quiz forces you to actually reason through the design decisions the agent made, using multiple-choice-style questions where you have to justify the correct answer, before the milestone is considered genuinely closed on the human side too.

Explicit token-economy discipline

A recurring, deliberately-enforced instruction given to the coding agent:

"Always spawn Haiku or Sonnet [cheaper/faster models] to do this particular task — never spend a lot of tokens on this. Use Opus [the most expensive/highest-capability tier] only as an orchestrator or planner, spawning cheaper sub-agents for the actual mechanical work."

Personal rule stated by the author: "If you've generated one token, tell me what the output of that was. If you can't justify the output, you're out." This is a general discipline for working with AI coding agents at scale: route by task difficulty, don't default to the most expensive model for everything.

The kickoff interview

Before a milestone's plan is even written, Genesis Kit can run a kickoff interview — a short structured Q&A with the human to pin down scope before any code gets touched (e.g., "is this a new build or modifying existing code?", "is this a distributed/multi-service runtime or a single process?"). This exists to prevent the agent from making unstated assumptions about scope.

The named "skills" Genesis Kit draws on

Referred to as an "agentic SW kit" — a library of domain-knowledge skills (security engineering, reliability engineering, distributed systems, etc.) plus a set of named cognitive-process skills used throughout the loop:

Skill name Purpose
Detective Helps debug — root-cause investigation
Verify Checks output against goal/success criteria
Blueprint Design before you build
Scout Explore multiple options before committing to one
Council / Mirror Adversarial self-review — argue against your own plan
Ghost "Shadow and carry" — track parallel/background context
Forecast Predict likely failure points before they happen

The right skill is loaded per milestone based on what that milestone actually needs (e.g. security-engineering + distributed-systems skills for the webhook ingress milestone), not loaded indiscriminately for every task.

Exit protocol (what happens at the end of every milestone)

On milestone approval, three files are updated together, atomically as a practice (even if not a literal DB transaction):

  • current.md (the checkpoint log),
  • plan.md (progress log),
  • implementation-notes.html (the live "what's built right now" summary, including explicitly listed known gaps — e.g. "job queue is currently an in-process stub; M4 will replace it with Redis").

This means a brand-new session, or a completely different person, can read exactly three files and know precisely what exists, what's missing, and what to do next — without re-reading the whole codebase or asking the previous session's author.

Practical starting workflow (how a session actually begins)

  1. Open a fresh AI coding agent session (any agent — Claude Code, Codex, etc. — this framework is explicitly tool-agnostic).
  2. Paste the kickoff prompt (from the project's onboarding doc).
  3. The agent runs Gate-0 automatically: checks for an existing Genesis state, and either initializes a new one or picks up the existing one.
  4. From there, just say "kickoff" and the agent will look up the next unbuilt milestone from plan.md and begin the build loop for it.

Key takeaway

"If you have the harnesses set up right, you'll produce the best code of your life. If you don't have the harnesses, you'll produce the worst code of your life — because you'll have no way to catch the agent quietly drifting away from what you actually wanted."

The technical stack (LangGraph, Tiger Cloud, etc.) is secondary to this methodology — the author explicitly states that if you've already done the system design (files 01–05), the harness makes actually writing the code "damn easy," because the hard thinking already happened before any code was written.

Implementation Milestones

M1 through M9, demo commands, real bugs caught
Mark understood

Build ordering philosophy

Milestones are sequenced to prioritize non-dependent pieces first — specifically, infrastructure that everything else needs (webhook ingress, then the unified database) is built before anything that depends on it (orchestration, retrieval, posting). This avoids building orchestration logic against a database or ingress layer that might still change shape.

Each milestone in Genesis Kit is defined with: an outcome, a demo command that objectively proves it works, success criteria, which loops/skills it uses, its external dependencies, and a token budget. Below is the reconstructed milestone list as built in the walkthrough.

M1 — Webhook Ingress

Outcome: A FastAPI service that authenticates, validates, and routes incoming GitHub PR webhooks — nothing downstream yet.

What it does: - Verifies HMAC signature against the shared webhook secret. - Rejects anything that isn't a pull_request event. - Checks idempotency key to prevent duplicate processing (in-memory for this milestone — explicitly a temporary stub, to be replaced by Redis-backed dedup in M4). - Parses the payload into the required internal format. - Pushes it into a (stubbed, in-process) job router.

Demo command: curl a correctly-signed request vs. an incorrectly-signed request — confirm HMAC rejects the bad one and idempotency correctly drops duplicate deliveries.

Real bug caught by the L4 verifier: malformed-but-validly-signed JSON was returning a raw 500 instead of the correct 400. Fixed, then a regression test was added so this class of bug can't silently reappear.

Explicitly accepted known gap: the idempotency router is in-memory only and won't survive a process restart. This is fine for this milestone because M1's actual goal is just establishing the ingress contract (authenticate → validate → route → prevent duplicates within a single process lifetime) — full durability is scoped to M4.

M2 — Tiger Cloud Infrastructure

Outcome: The unified database is provisioned and schema-migrated against a live Tiger Cloud service (not a local mock).

What it does: - Provisions a Tiger Cloud service via the Tiger MCP/CLI. - Enables required extensions: TimescaleDB, pgvector, pgvectorscale. - Creates the agent_events hypertable + continuous aggregates. - Creates relational tables for reviews/findings/HITL. - Enforces the append-only invariant on agent_events at the database level (trigger-based, not rule-based — see file 03 for why).

Demo command: send a test webhook-equivalent event, then query agent_events and confirm the span row landed correctly.

Real bugs caught during this milestone (see file 03 for full technical detail): - Postgres RULEs don't work on hypertables (query-rewrite stage conflicts with hypertable chunking) — switched to a trigger-based approach instead. - TRUNCATE doesn't fire row-level DELETE triggers — needed a separate guard. - Embedding dimension mismatch between schema (vector(1536)) and .env config (256) — flagged before it caused a silent insert failure.

M3 — Observability / Event Spine

Outcome: Every action in the pipeline (starting with webhook ingress) writes a row to agent_events.

What it does: - Appends a row for every delivery/action (start, end, cost, latency, decision made). - Builds the foundation the trace viewer, audit trail, and cost dashboards will all read from later.

Demo command: trigger a webhook, then query agent_events and confirm every step of the ingress flow produced a corresponding row.

Note on sequencing: the transcript explicitly shows the agent re-checking whether this already exists (per the G0 gate) before building, since record_event-style functionality may have been partially stubbed during M1/M2 already — avoiding duplicate implementation.

M4 — Orchestration (LangGraph fan-out/fan-in)

Outcome: A LangGraph-based orchestrator that fans a PR out to (at this stage, possibly stubbed) parallel nodes, checkpoints to Redis, and can resume after a worker is killed mid-run.

What it does: - Replaces M1's in-memory idempotency stub with Redis-backed dedup (closing the gap explicitly flagged in M1). - Implements the actual fan-out to N parallel graph nodes. - Checkpoints workflow state to Redis so a killed worker can resume rather than restart from scratch.

Demo command: trigger a run, kill the worker process mid-execution, restart it, and confirm it resumes from the checkpoint rather than re-running everything or losing the job.

M5 — Specialist Agents

Outcome: The four specialist nodes (Security, Quality, Testing, Docs) are implemented as real LLM-calling nodes, each producing a structured finding object (see file 01 for the exact schema).

What it does: - Each specialist receives the PR diff + retrieved context (from M6, or a temporary simplified context source until M6 lands). - Each returns findings with agent_type, severity, category, file, line, confidence, rationale. - Model routing per agent is applied here (cheaper model for Docs, stronger model for Security — see file 04).

Demo command: submit a test PR diff with a known issue planted in it (e.g. a deliberate SQL-injection-shaped snippet) and confirm the security specialist flags it with a non-trivial confidence and a correct file/line.

M6 — RAG Retrieval

Outcome: A retrieval layer that embeds the PR diff, performs hybrid search (vector similarity + full-text search) over code_chunks, and merges results before handing them to the specialists.

What it does: - Computes an embedding for the incoming diff. - Runs ANN search (via pgvectorscale + DiskANN) plus FTS over the code_chunks table. - Merges/ranks the top-K chunks and injects them into each specialist's prompt.

Demo command: a hybrid query against known code chunks — confirm the top-K results are actually relevant to a given diff, not arbitrary.

M7 — HITL Gate + Post to GitHub

Outcome: The aggregator merges specialist findings, deduplicates, computes overall confidence, and either auto-posts to GitHub or routes to the human approval queue — closing the loop back to the actual PR.

What it does: - Merge + dedup findings across the four specialists. - Apply the confidence gate rules from file 01 (critical → always escalate; below threshold → human queue; otherwise → auto-post). - Post the structured review back to the GitHub PR via the GitHub API, using the credentials from M4/deployment setup.

Demo command: run against a real (test) PR and confirm a review comment actually lands on GitHub, correctly attached to the right file/line — or correctly routes to the human queue when confidence is low.

M8 — Reliability, Economics, and Minimal Dashboard

Outcome: The reliability layer (file 05) is wired in throughout, cost rollups are queryable, and a minimal Next.js dashboard exists to view the HITL queue and trace history.

What it does: - Retries, circuit breakers, per-node timeouts applied across the pipeline (mapped to the specific failure modes in file 05, not applied generically). - Continuous-aggregate-backed cost dashboard (cost/minute, P95 latency, token totals) — explicitly told to stay tiny; front-end investment is deliberately minimized in favor of the backend/data correctness. - A minimal UI to view escalated reviews and approve/reject them.

Demo command: inject a simulated fault (e.g. force a specialist timeout) and confirm the system degrades gracefully rather than hanging or crashing the whole review.

(Implied) M9 — Evaluation

Referenced in the plan but explicitly left for the reader/community to build out: a golden dataset of known-good PR reviews, used as a regression gate — any new prompt or model swap must perform at least as well as the currently deployed version on this dataset before being promoted. This closes the loop on the "model drift" failure mode from file 05.

What the author explicitly leaves as an exercise

The transcript is explicit that only M1 and part of M2 were built live on camera; the rest (M3–M9) are left for the viewer to complete using the same Genesis Kit harness, with the reasoning that once the system design is done (files 01–05) and the harness is set up (file 06), completing the remaining milestones is comparatively straightforward mechanical work — "if you've designed already, the rest is easy; if you haven't, the harness will expose exactly where your design was incomplete."

Suggested self-check before starting each milestone

For every milestone, before writing code, answer:

  1. What human behavior (file 01) does this milestone encode?
  2. What is the exact trigger and exact output of this component?
  3. What existing invariant (from context-graph) must this component not violate?
  4. What's the demo command that will prove, not just claim, this works?
  5. Which failure modes (file 05) apply to this specific component, and which mitigation is actually wired in — not just planned?

Glossary & Key Quotes

Every term in one place, plus load-bearing quotes
Mark understood

Glossary

Selectivity (L0) — The core design principle: the system should surface only findings worth a senior engineer's attention, deferring the rest, rather than maximizing output coverage.

Mapping the mess — The first step of the design template: documenting, in granular detail, what a human does today without the AI system, before designing anything.

Fan-out / fan-in — An agentic design pattern where independent sub-tasks are dispatched in parallel ("fan-out") and their results are later merged by a single aggregator ("fan-in").

Grounding — Supplying an LLM with actual, relevant context (via retrieval) so it reasons about real information instead of hallucinating.

Context engineering — The practice of deliberately selecting and shaping what goes into a prompt (e.g. via retrieval) rather than dumping everything available into the context window.

Semantic memory — Knowledge of the codebase itself (functions, classes, structure) — stored as vector embeddings for similarity search.

Episodic memory — Knowledge of past events (past reviews, disputes) — stored as timestamped relational rows.

Procedural memory — Knowledge of team conventions and rules — stored as small structured facts.

Event spine — A durable, time-ordered, append-only log of every action the system takes (LLM calls, tool calls, decisions), used for tracing, auditing, and cost tracking.

Hypertable — A TimescaleDB table type that looks like a normal table but is internally partitioned into time-based chunks for efficient time-series storage and querying.

Continuous aggregate — An automatically-maintained summary/rollup table over a hypertable, used so dashboards don't need to scan raw event data on every query.

Idempotency key — A unique identifier used to detect and drop duplicate/retried deliveries of the same event.

Confidence gate — The routing logic that decides whether a finding is auto-posted, escalated to a human, or (if critical) always escalated regardless of confidence.

HITL (Human-In-The-Loop) — Any point in the pipeline where a human reviews/approves before an action is finalized.

Reliability layer — The collection of retries, circuit breakers, timeouts, and deduplication logic, each mapped to a specific named failure mode.

Workflow engine abstraction — An interface (run/resume/get_state) that decouples business logic from a specific orchestration framework (e.g. LangGraph), enabling a future swap to another engine (e.g. Temporal) without rewriting application code.

Genesis Kit — The author's own harness-engineering framework for working with AI coding agents: locked spec (done.html), live state (implementation-notes.html), invariants (context-graph), milestone plan (plan.md), and a gated build/debug/research loop system (loops.md).

G0 (Gate Zero) — The orientation procedure run before any milestone work begins: check for existing work, confirm nothing is being duplicated, write a checkpoint, emit a built/unbuilt verdict.

L4 Verifier — An independently spawned agent, given only the goal, success criteria, and invariants (not the builder's reasoning trail), tasked with skeptically verifying completed work rather than trusting the builder's self-report.

Quiz me — A Genesis Kit mechanism where the human is quizzed on the design decisions the agent made, to force genuine understanding rather than passive acceptance of AI-generated code.

Almost-right problem — A failure mode where a finding is mostly correct but subtly wrong in a way that's easy to miss and dangerous to trust.

Model / prompt drift — Performance degradation over time as the real-world input distribution shifts away from what the system was built/evaluated against.

Key quotes worth remembering

"The problem is not to have an agent that can review your code automatically. The problem is the selectivity — which findings does the agent take, and which ones does human judgment get spent on."

"If you remove a component and you can feel the pain, that's the problem your system needs to solve. Necessity is the mother of invention — so we'll create that necessity intentionally."

"Retrieval is what turns the stranger into the colleague."

"If something can be measured, it can be improved. But if you don't have which context was used, what prompt version ran, what the model returned — you can't defend the system, debug it, or improve it."

"New systems need more override. Proven ones earn less."

"A wrong style comment is annoying. A missed SQL injection is dangerous. Consequence of error decides how much autonomy you give."

"This is not vibe coding. You'll spend a lot of time in system design itself, create a few steps, and only then go to the coding agent."

"If you have the harnesses set up right, you'll produce the best code of your life. If you don't, you'll produce the worst code of your life."

"If you've generated one token, tell me what the output of that was. If you can't justify the output, you're out."

"Having the right assumptions about your system is one of the most important design problems — a system fails because an assumption failed."

Quick-reference: the whole methodology in 10 lines

  1. Remove the system, watch what a human does, write down every micro-decision.
  2. Name a precise trigger and a precise, structured output.
  3. Derive your agent roles from what the human's mindsets actually were — don't invent agent counts abstractly.
  4. Design retrieval so the agent is grounded, not guessing.
  5. Split memory into semantic / episodic / procedural, and store them in the minimum number of physical databases that still preserves the shapes.
  6. Require confidence + rationale on every output; gate autonomy by confidence and severity.
  7. Log everything to an immutable event spine — trust requires proof, not just good reasoning.
  8. For every component, ask "what breaks?" from both an engineering angle and an LLM angle, and map each named failure to a specific mitigation.
  9. Calibrate autonomy by consequence of error, reversibility, and system maturity — never default to full autonomy in financial/legal/health domains.
  10. Build with a harness: locked spec, live state, independent verification, and forced human understanding — not vibe coding.
