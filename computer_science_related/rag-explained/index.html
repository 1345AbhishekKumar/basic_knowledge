RAG: how a chatbot answers questions about your documents

Ask a general-purpose model about your own company policy and it can't know the answer — your policy was never in its training data, and it will cheerfully invent one anyway. Retrieval-augmented generation (RAG) fixes that without retraining: before the model answers, a separate retrieval step finds the right passages in an index of your documents and hands them to the model as context. This lesson lets you watch every step — chunking, embedding, similarity search, and the augmented prompt — inside a miniature knowledge base you control.

No install, no server — opens in your browser. Sources: sources.md.

Part 1 · The problem

The model only knows what it was trained on

Large language models learn from a fixed snapshot of public text. Everything they "know" lives in their weights (researchers call this parametric memory), and that memory has a hard date: the knowledge cutoff of the training data. Ask about anything newer, private, or niche — your company's return policy, a product manual, this week's prices — and the model has no way to know it. It doesn't stay silent; it answers anyway, fluently and confidently, from patterns in its training data. That confident wrongness is what people call hallucination.

The expensive fix would be retraining or fine-tuning the model on every new fact. RAG takes the cheap route: leave the model alone and attach an external, updateable index of documents — non-parametric memory. At answer time the system first looks the facts up in the index, then hands them to the model inside the prompt. The model never "learns" your documents; it reads the relevant page, the way you would.

The name and the architecture come from a 2020 research paper by Patrick Lewis and colleagues at Meta (then Facebook AI Research), which combined a pretrained text generator with a neural retriever over a large passage index. Today the same pattern powers "chat with your docs" support bots, internal knowledge assistants, and research tools — grounded answers with citations, no retraining.

Key idea to hold onto: RAG does not put knowledge into the model. The knowledge sits in an index you can edit at any time. To change what the bot knows, you update the index — never the weights.

Part 2 · The two phases

Index first, then retrieve

Every RAG system runs two separate phases. The first happens before anyone asks a question; the second happens for every question.

Phase 1 · Index (offline, once)

Documents→ Chunks→ Embeddings→ Vector store

Phase 2 · Query (online, per question)

Question→ Embed query→ Top-k similar chunks→ Prompt with context→ Grounded answer

1 Chunk: cut the documents into pieces

A model can only read a limited amount of text at once (its context window), so you can't paste an entire manual into every prompt — and you usually don't want to, because a passage about refunds buried in a 200-page handbook would drown in noise. Indexers first cut each document into smaller units called chunks. Production systems commonly use a few hundred tokens per chunk with a small overlap between neighbours, so that a fact straddling a cut doesn't fall in the crack.

Chunking is a quiet superpower of RAG quality. Too big: one chunk holds several ideas and its meaning gets mushy. Too small: a chunk may not carry enough context to be useful. You'll feel both in the playground.

2 Embed: turn each chunk into a vector of numbers

Text isn't searchable by computer the way humans search it, so an embedding model converts each chunk into a long list of numbers — a vector (a few hundred to a few thousand dimensions; e.g. 768 for BERT-base, 1536 for OpenAI's text-embedding-3-small). The trick is that the numbers are arranged so that similar meaning lands near similar numbers: a sentence about refunds sits closer to another refund sentence than to a sentence about shipping, even if they share no words.

Embedding: text → vector, arranged so meaning is near meaning
"Refunds take 5 days" → [0.21, −0.87, 0.44, …]  ≈  "Money back within a week" → [0.19, −0.90, 0.41, …]

The exact numbers are learned during the embedding model's training. What matters: the two refund-ish sentences end up closer to each other than to a shipping sentence, so later "near" can mean "about the same thing".

Every chunk's vector is stored in a vector database, alongside the chunk's original text and its metadata (which document, which page). For millions of chunks, the store can't compare the query against every vector on each question, so it uses an approximate-nearest-neighbour index to return good matches fast.

3 Retrieve: embed the question, find the nearest chunks

When a user asks something, the same embedding model converts the question into a vector. The retriever then scores every chunk vector against the query vector with a similarity measure — commonly cosine similarity, which measures the angle between two vectors (ignoring their length) and lands between −1 and 1, with 1 meaning "pointing the same way". The top k most similar chunks become the context — k is a tuned parameter you choose: small keeps the prompt focused, large gives the model more to work with.

cosine(q, c) = (q · c) ÷ (|q| × |c|)

This is why RAG finds answers keyword search can't. Ask "how long do I have to change my mind?" and the semantic match is the chunk that says "returns are accepted within 30 days" — no word in common, but the meaning lines up.

4 Augment & generate: give the model the receipts

The retrieved chunks are pasted into the prompt as context, followed by the user's question, often with an instruction to answer only from that context and to cite which chunk each claim came from. Now the generator does its one job: turn the context into a readable answer. The facts come from your documents — the model contributes the language.

"Context: [c3] … [c7] …\nQuestion: …\nAnswer only from the context, citing chunks."

RAG sharply reduces hallucination — the model is answering from passages you chose — but it does not make a model error-proof. If retrieval returns the wrong chunk, the model will confidently answer from the wrong context. In RAG, garbage retrieval in means garbage answer out: the retriever, not the model, is usually where quality is won or lost.

Part 5 · Summary

Summary

  • A general LLM only knows its training snapshot. RAG attaches an external index of your documents so answers can be grounded without retraining.
  • Two phases: index (chunk → embed → store) runs offline once; query (embed the question → similarity search → top-k → augment the prompt → generate) runs for every question.
  • Embeddings put meaning near meaning: "change my mind" can land next to "returns within 30 days" with zero shared words.
  • Retrieval quality decides answer quality. Chunk size, overlap, the similarity measure, and top-k all move the needle — too-large chunks blur into the middle of the map; exact-word search gets lured by decoy words.
  • RAG reduces hallucination but doesn't eliminate it: the model is only as good as the context you retrieved for it.

Go back to the playground and break it on purpose: ask "how long do I have to change my mind…" with keyword search, or set the chunk size to the whole document and watch every dot collapse. Then flip to semantic search with top-k 2–3 and see the same questions answer cleanly.
