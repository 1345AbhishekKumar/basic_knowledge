FIELD BRIEF — READ BEFORE BUILDING

Everything to settle before you write a line of RAG code.

RAG looks like glue code between a vector database and an LLM. It fails like a system with eleven independent decision points. Short version, all eleven, in order.

11 sections ~12 min read 5 interactive demos
01

Why RAG exists

An LLM only knows what was frozen into it at training time. RAG hands it relevant documents at answer-time instead of retraining it.

It buys you three things fine-tuning doesn't: freshness (data changes, weights don't), groundedness (answers can cite a real passage), and privacy (documents stay in your own store, never enter the model's weights).

DECIDE FIRST Is this a knowledge gap or a reasoning gap? RAG only fixes the first. If the model has the facts and still reasons badly, more retrieval won't help.

03

Chunking

Documents get split into chunks before they can be embedded. Size and overlap decide what's even findable later.

Fixed-size

Split every N tokens with a fixed overlap. Trivial, model-agnostic, predictable cost.

Fast to shipSplits mid-idea

Semantic

Split where embedding similarity between adjacent sentences drops — where topic actually changes.

Coherent chunksSlower to index

Recursive

Try paragraph breaks first, then sentences, then words, falling back to a hard cut only if needed. Sane default.

Good defaultIgnores structure

Structural

Split along the doc's own structure — headers, tables, code boundaries. Needed when hierarchy matters.

Preserves meaningNeeds per-format parsers
EXAMPLErecursive chunking, Python
# splits on paragraphs first, then sentences, then words
from langchain.text_splitter import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,      # chars per chunk
    chunk_overlap=50,    # shared context between chunks
    separators=["\n\n", "\n", ". ", " "]
)
chunks = splitter.split_text(document_text)
# chunks[0] -> "Retrieval-Augmented Generation grounds a model's..."
Real case: a 40-page PDF policy manual → ~85 chunks at 500 chars. A user asking about "refund windows" only needs the 2–3 chunks mentioning refunds, not all 85.
PITFALL Too small loses context; too large drowns the relevant sentence in noise. No universal right size — test against your own data.
04

Embeddings

A vector puts each chunk at a point in space, so similar meaning lands nearby. Retrieval = "find the nearest points."

ConsiderationWhat to check
DimensionalityHigher isn't free — it raises storage/search cost. 384–1536 covers most cases.
Domain fitGeneral models struggle on legal, medical, code text. Domain-tuned models can beat them clearly.
Max input lengthChunk size must fit the embedder's context window, or it's silently truncated.
Symmetric vs asymmetricSome models embed short queries and long passages differently — wrong mode hurts retrieval.
ConsistencyNever mix embeddings from two different models in one index.

Try it: click a query below to see which of three stored chunks it lands nearest to.

STORED CHUNKS (fixed)
NEAREST-NEIGHBOR RESULT
EXAMPLEgenerating an embedding, Python
from openai import OpenAI
client = OpenAI()

response = client.embeddings.create(
    model="text-embedding-3-small",
    input="Refund requests must be filed within 30 days."
)
vector = response.data[0].embedding
# vector -> [0.0023, -0.0187, 0.0412, ...]  (1536 numbers)
Real case: "How do I get my money back?" and "refund requests" produce vectors close together in space even though they share almost no words — that's the whole point of embedding over keyword matching.
DECIDE FIRST Switching embedding models later means re-embedding every chunk — no partial migration.
05

Vector stores

Indexes embeddings for fast approximate nearest-neighbor search, usually alongside the original text and metadata.

Embedded / in-process
Runs inside your app, no separate server. Fine under ~100k chunks. Doesn't scale horizontally, weak metadata filtering.
Managed vector databases
Horizontal scaling, metadata filtering, hybrid search, multi-tenant isolation. Right call past prototype scale.
Vector search on an existing database
Adds a vector index to a database you already run. Minimal new infra, moderate scale.

Confirm whichever you pick supports metadata filtering and a tunable ANN index (commonly HNSW).

EXAMPLEstore + query, Python (Chroma)
import chromadb
db = chromadb.Client().create_collection("policies")

# indexing (offline)
db.add(
    documents=["Refund requests must be filed within 30 days."],
    embeddings=[vector],
    metadatas=[{"source": "handbook.pdf", "page": 12}],
    ids=["chunk-001"]
)

# retrieval (online) — nearest 3 chunks, filtered by source
results = db.query(
    query_embeddings=[query_vector],
    n_results=3,
    where={"source": "handbook.pdf"}
)
Real case: the where filter is what lets a multi-tenant app search only this customer's documents instead of everyone's — metadata filtering, not the embedding itself, enforces that boundary.
06

Retrieval strategy

"Top-5 by similarity" is the starting point, not the finish line. Toggle the query type below.

VECTOR-ONLY
HYBRID (VECTOR + KEYWORD)
  • Hybrid search — vector similarity + keyword (BM25); catches exact names/IDs vector search misses.
  • Reranking — retrieve a wide candidate set cheaply, then rerank with a slower cross-encoder for precision.
  • Metadata filtering — narrow by date/source/user before or during search.
  • Query transformation — rewrite vague queries; decompose multi-part questions.
REAL CASE — RERANKING Retrieve top-50 candidates by vector similarity (cheap), then run a cross-encoder over just those 50 to re-score and keep the top-5 (slower, more accurate). Cuts irrelevant hits without paying reranking cost on the whole corpus.
DECIDE FIRST What happens when nothing retrieved is actually relevant? You need a relevance threshold, not just a fixed k.
07

Augmentation & prompting

How retrieved chunks get assembled into the final prompt decides whether the model uses them right.

Ordering matters
Models over-weight the start/end of long context ("lost in the middle"). Put the best chunk first or last.
Say what to do when context is thin
Instruct the model to admit insufficient context rather than guess.
Attribute sources
Ask the model to cite which chunk supports each claim — makes hallucination visible.
Mind the context budget
Chunks + system prompt + history + answer share one window. Too many chunks starves the answer.
EXAMPLEassembled prompt sent to the LLM
Answer only using the context below. If the answer isn't
in the context, say you don't have enough information.
Cite the source after each claim like [source: doc, p.12].

Context:
[1] (handbook.pdf, p.12) "Refund requests must be filed within 30 days of purchase."
[2] (handbook.pdf, p.13) "Refunds are issued to the original payment method within 5–7 business days."

Question: How long do I have to request a refund, and how will I get paid back?
Real case: a good answer here reads: "You have 30 days [source: handbook.pdf, p.12], refunded to your original payment method within 5–7 business days [source: handbook.pdf, p.13]." — every clause traceable to a retrieved chunk.
08

Evaluation

Retrieval and generation are two separate failure surfaces — measure them separately.

LayerMetricQuestion it answers
RetrievalPrecision@k / Recall@kWere the retrieved chunks relevant — and complete?
RetrievalMRRIs the best chunk ranked near the top?
GenerationFaithfulnessDoes the answer stick to what's in the context?
GenerationAnswer relevanceDoes it address the actual question?
End-to-endHuman / LLM-judge reviewWould a real user accept this?

Build a fixed eval set with known-correct answers before you build — not after.

09

Common pitfalls

1. Trusting retrieval by default
Teams tune the prompt endlessly while retrieval quietly returns the wrong chunks. Debug retrieval first.
2. One chunk size for everything
Prose-sized chunks mangle tables, code, and FAQs. Different content needs different rules.
3. No re-indexing plan
Source docs change; without incremental re-indexing your store drifts or needs full rebuilds.
4. Never testing "no answer exists"
This is exactly when hallucination is most likely and most damaging.
5. Confusing retrieval with reasoning
RAG retrieves facts; it doesn't make the model reason better over them.
