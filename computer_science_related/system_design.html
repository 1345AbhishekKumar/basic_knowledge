MODULE 01 · FOUNDATIONS
01

The single server & the life of a request

PAUSE · THINK FIRST

When you type a URL and press enter, how many separate network conversations happen before the page appears — and with whom?

Count the machines that get spoken to, not the arrows on the wire.

CORE EXPLANATION

Every system that has ever served millions of users began as one machine doing everything — and that is not a shortcut, it is the correct way to start. You cannot scale what you do not understand, and a single-server setup is the only place where you can see the entire request lifecycle with your own eyes.

Here is that lifecycle. A user types app.demo.com into a browser. The device has no idea where that is, so it asks DNS — the phonebook of the internet — which replies with an IP address, say 93.184.216.34. Only then does the browser send an HTTP request to that IP. Your one server — running the web application, the database, and the cache in a single box — processes the request and answers.

Notice the two faces this one server wears. For browsers it handles business logic, data storage, and presentation, replying with HTML, CSS, and JavaScript. For mobile apps it exposes API endpoints and replies with JSON — because JSON is lightweight and easy for a phone to parse. GET /products/123 goes in; a product's id, name, description, and price come back out.

This setup is ideal for a small user base because it lets you visualize every core component before complexity arrives. Its weakness is just as clear: everything shares one machine's CPU, memory, and disk, so heavy traffic has nowhere to go but down. The rest of this course is the story of what to split off first, and why — but every later decision is just an intervention at some point in this exact request flow.

STEP BY STEP
  1. The user types a domain — app.demo.com. The device has a name, not a location.
  2. The browser asks DNS; DNS replies with the server's IP address.
  3. Browser or app sends an HTTP request straight to that IP.
  4. The server runs business logic, reads its database, and builds a response.
  5. Browsers receive rendered HTML; mobile apps receive lightweight JSON.
THREE CASES
TYPICAL

The $5 blog box

A WordPress site on a small VPS: web server, PHP, MySQL, and a file cache all on one machine. For a few hundred readers a day this is the correct architecture — nothing is missing; it is simply all in one place.

COUNTER-INTUITIVE

DNS is not in the request path

Draw this flow and most people put DNS in the middle of every arrow. But after the first lookup, the browser and OS cache the IP — your actual HTTP request never touches DNS again. It is a side quest, not a hop.

EDGE CASE

One server, two contracts

The same box serves HTML to browsers and JSON to apps. Design for only one client and the other breaks silently — a session-cookie flow that works in the browser can fail completely for a mobile app that must send tokens in headers.

VISUAL ANALOGY

A food truck with one person inside. They take the order (web and mobile traffic), cook the food (business logic), and keep the books (database). You learn the entire business in a week — and you feel exactly where it breaks when the lunch rush comes.

❌ WHAT PEOPLE GET WRONG

"Single-server means beginner." Every large service started as one box; the senior skill is knowing when to split, not refusing to start small. Also: "the server resolves the domain." No — DNS does, before the request even exists.

WHY THIS MATTERS

Every scaling tool you will ever meet — load balancers, caches, CDNs, replicas — is just an insertion at some point in this one flow. Master the flow, and everything else is commentary.

MODULE 02 · THE DATA LAYER
02

Choosing a database: SQL vs the four NoSQL shapes

PAUSE · THINK FIRST

A social graph, a shopping cart, and a bank ledger walk into a bar. Would you give them all the same database? What would you ask before deciding?

Ask each one the same question: what does a lost write cost you?

CORE EXPLANATION

The database is the first decision you cannot cheaply reverse, which is exactly why companies pay seniors to make it well. The field splits into two camps. Relational databases — PostgreSQL, MySQL, Oracle, SQLite — organize data into tables of rows and columns, like spreadsheets that grew up. Their superpowers are joins (combining customers, products, and orders into new views on demand) and ACID transactions: sequences of operations that either fully happen or not at all, keep the database valid, stay isolated from one another, and survive crashes. A bank transfer is the classic example — money leaves one account and arrives in another, or the universe rolls back.

Non-relational databases trade some of that structure for speed, flexibility, or scale, in four distinct shapes. Document stores (MongoDB) keep JSON-like documents that can nest an entire order inside a customer. Wide-column stores (Cassandra, Cosmos DB) absorb massive write volumes. Key-value stores (Redis, Memcached) live in RAM and answer lookups in microseconds. Graph databases (Neo4j, Neptune) treat relationships as first-class citizens — which is precisely why Amazon uses one for product recommendations.

The decision rule is not "which is newer." If your data has clear relationships and your correctness bar is "never lose a transaction," go relational. If you need sub-millisecond lookups, semi-structured data, or planet-scale writes, one of the four NoSQL shapes fits. And in real systems, the honest answer is often "several, each where it is strongest."

STEP BY STEP · THE DECISION
  1. Sketch the data: naturally tabular with relationships, nested and JSON-ish, or a web of connections?
  2. Name the consistency bar: can a lost write corrupt money (bank), or just show a stale like (feed)?
  3. Name the access pattern: complex joins, simple key lookups, or a firehose of writes?
  4. Match: SQL for structure + transactions; document for flexible shapes; key-value for speed; wide-column for write scale; graph for relationships.
  5. Plan the seams — most real systems are polyglot: a SQL core, a Redis cache, maybe a graph sidecar.
THREE CASES
TYPICAL

E-commerce orders → PostgreSQL

Customers, products, and orders join cleanly, and checkout is a transaction: decrement inventory and record payment together, or not at all. ACID is the product here.

COUNTER-INTUITIVE

Amazon's recommendations run on a graph

"Customers who bought this also bought…" is not a giant SQL join — it runs on Neptune, a graph database. When the question is "how are these things connected?", relationships stored as edges beat tables every time.

EDGE CASE

Session storage inside a SQL-heavy app

Who is logged in lives in Redis — a RAM key-value store — because a 2 ms lookup beats a 20 ms disk query on every single request. One application, three databases, each where it is strongest.

VISUAL ANALOGY

SQL is a library with a strict card catalog — everything has one shelf, and the catalog cross-references anything. NoSQL is a warehouse with painted zones: drop pallets in the right zone and retrieve them fast, but no master index ties the zones together.

❌ WHAT PEOPLE GET WRONG

"NoSQL is newer, so better." NoSQL did not replace SQL — it specialized. Also: "NoSQL means no consistency." Most offer tunable consistency; the real tradeoff is choosing where on that spectrum to sit, knowingly.

WHY THIS MATTERS

The data layer is the most expensive thing you will ever migrate. Every other decision — caching, scaling, API shape — bends around it. Make this call with rough requirements and you have earned the senior title.

MODULE 03 · SCALE
03

Vertical vs horizontal scaling & the load balancer

PAUSE · THINK FIRST

You add two servers and put a balancer in front. Traffic doubles and… some users get logged out on every request. What assumption did this design make?

Where does user state live — and does it travel with the user?

CORE EXPLANATION

When one server stops being enough, you have exactly two levers. Vertical scaling — "scale up" — means feeding the same machine more RAM and CPU. It is simple and fine for moderate traffic, but it carries two fatal flaws: a hard physical cap on how big one box can get, and zero redundancy — when that box dies, your entire application dies with it. Horizontal scaling — "scale out" — means adding more servers to share the load. It scales essentially without limit and buys fault tolerance: if server three fails, servers one and two keep serving users until it recovers.

But the moment you have three servers, a new question appears: which request goes where? That is the load balancer's job. It sits in front of the pool and distributes traffic by algorithm — round-robin for identical servers taking turns, least-connections for sessions of variable length, least-response-time when servers differ in speed, IP hash when a client must stick to one server, weighted variants that respect that 64 GB of RAM deserves more traffic than 16, geographic routing that sends Europeans to the European box, and consistent hashing, which places servers on a hash ring so adding or losing one reshuffles only a slice of clients instead of all of them.

Load balancers also run health checks — constant "are you alive?" pings that pull dead servers out of rotation — and they can themselves be made redundant, monitored, and self-healing. Because any component whose failure kills the whole system is a single point of failure, and the load balancer is now one of them.

STEP BY STEP · GOING HORIZONTAL
  1. Replicate the web tier: run N identical servers instead of one.
  2. Place a load balancer in front (Nginx, HAProxy, or a cloud ELB).
  3. Pick an algorithm that matches your traffic shape and server specs.
  4. Enable health checks so dead servers leave the rotation quietly.
  5. Make the balancer itself redundant — two LBs watching each other, or a self-healing cloud one.
  6. Scale by adding servers; the balancer absorbs them without any client change.
THREE CASES
TYPICAL

Three identical servers under round-robin

Request 1 → S1, request 2 → S2, request 3 → S3, request 4 → back to S1. Perfectly fair, perfectly predictable — and perfect only because the servers are identical.

COUNTER-INTUITIVE

IP hash is deliberately unfair

It pins each client to one server so that server's local session data works. Fairness is not the goal — stickiness is. Weighted round-robin agrees: a 64 GB machine should take four times the traffic of a 16 GB one, and "equal" distribution would be the bug.

EDGE CASE

A server dies mid-pool

Naive hashing (IP mod 3) remaps nearly every client when the pool shrinks — a cache-warming catastrophe. Consistent hashing arranges servers on a ring so only the dead server's slice of clients moves. That is why Memcached and database shards rely on it. Try it in the lab above.

VISUAL ANALOGY

A restaurant host. Round-robin seats parties in order no matter what. Least-connections seats you with the waiter holding the fewest tables. Weighted gives big parties to the senior waiter. Geographic sends you to the nearest location. And the health check is the host noticing a waiter called in sick before seating anyone with them.

❌ WHAT PEOPLE GET WRONG

"Vertical is cheaper, so start there forever." There is a hard cap and no redundancy — one hardware fault is a full outage. Also: "a load balancer just routes." Its health checks are what turn a pile of servers into a fault-tolerant system.

WHY THIS MATTERS

This is the exact decision pattern senior interviews test and real jobs pay for: tradeoffs under rough requirements, with availability on the line.

MODULE 04 · CONTRACTS
04

API design: REST, GraphQL, gRPC & the protocols beneath

PAUSE · THINK FIRST

Your mobile app's profile page needs the user, their posts, and their followers. In REST that is three requests. What would you change about the contract to make it one — and what would you give up?

Who decides the shape of the response — the server, or the client?

CORE EXPLANATION

An API is a contract between pieces of software: which requests can be made, to which endpoints, with which methods, and what comes back. It is an abstraction — you save a user without knowing anything about the server's internals — and it is a boundary, letting a user service and a post service evolve independently. Three styles dominate. REST models your domain as resources at plural-noun URLs (/products, /orders) and rides standard HTTP methods: GET reads safely and idempotently, POST creates, PUT replaces wholesale, PATCH updates partially, DELETE removes. Responses carry meaningful status codes — 201 for created, 404 for missing, 500 for "our fault" — and real REST APIs support filtering, sorting, pagination, and explicit versioning (/api/v1) so you can evolve without breaking clients.

GraphQL, born at Facebook, collapses everything to one endpoint where the client declares the exact shape it needs — user, their post titles, their followers' names — in a single round trip, with queries for reads and mutations for writes. Beware its quirk: it returns HTTP 200 even on errors, with the failure inside an errors array. gRPC goes the other direction: protobuf contracts over HTTP/2 with streaming, built for fast server-to-server chatter inside microservices, rarely for browsers.

Your transport choice constrains everything beneath this. HTTP/HTTPS handles request-response (HTTPS adds TLS — the non-negotiable standard). WebSocket upgrades one connection to bidirectional push, which is how chat works without wasteful polling. AMQP queues messages between producers and consumers for async work. And underneath, TCP guarantees ordered delivery for payments while UDP shrugs and keeps moving — which is exactly what a live video call needs.

STEP BY STEP · THE DESIGN PROCESS
  1. Gather requirements: core use cases, scope boundaries, performance bottlenecks, security constraints.
  2. Choose top-down (design endpoints from workflows — great for interviews) or bottom-up (design around existing data models — common at work). Prefer contract-first either way.
  3. Model resources as plural nouns; map operations to the correct HTTP methods.
  4. Add filtering, sorting, pagination, versioning, and honest status codes.
  5. Design → develop → deploy & monitor → maintain → eventually deprecate and retire. An API is a lifecycle, not a feature.

THREE CASES
TYPICAL

GET /api/v1/products/123 → 200 + JSON

POST to the same URL → 201 Created. The URL names the resource, the method names the action, the code names the outcome. A stranger can use it without reading the docs — which is the explicit goal.

COUNTER-INTUITIVE

GraphQL returns 200 OK… when it fails

The error lives in the body's errors array with its own status hints. Your frontend's catch block never fires, so if you only check HTTP status, your app happily renders null. REST shouts failures from the status line; GraphQL whispers them in the payload.

EDGE CASE

A live video call over UDP

A dropped packet is gone forever — and that is correct engineering: resending last second's audio would be worse than skipping it. TCP's greatest strength, guaranteed delivery, is a bug here. The protocol's "weakness" is the feature.

VISUAL ANALOGY

REST is a set menu: fixed plates, predictable, easy to cache. GraphQL is hotpot: you specify exactly what goes in your bowl, one trip to the counter, zero waste. gRPC is the kitchen intercom — terse, fast, staff-only.

❌ WHAT PEOPLE GET WRONG

"PUT and PATCH are the same." PUT replaces the whole resource; PATCH touches one field. Also: "GraphQL kills REST." They solve different problems, and many systems run both — REST for the public surface, GraphQL for a hungry frontend.

WHY THIS MATTERS

API shape is developer experience multiplied by every consumer, and protocol mistakes become latency ceilings you cannot refactor away later.

⌁ MEMORY

MODULE 05 · IDENTITY
05

Authentication vs authorization: who enters, and what they may touch

PAUSE · THINK FIRST

A user logs in successfully, then requests someone else's private repo and gets denied. Which of the two systems did its job — and which one would you blame if the request had succeeded?

Separate "inside the building" from "inside this room."

CORE EXPLANATION

Security at the door comes in two steps that people constantly blur. Authentication answers "who are you?" — the system verifies identity and either approves the login or rejects it with a 401. Authorization answers "what can you do?" — once you are in, it decides which resources and actions you may touch. The first without the second is a door with no locks behind it.

Authentication has evolved through five stages. Basic auth base64-encodes username and password — trivially reversible, so it survives only inside HTTPS on internal tools. Bearer tokens replaced passwords with a token sent on every request: fast and stateless, which is why it scales. OAuth2 plus JWT lets users log in through a trusted provider like Google or GitHub; the signed JWT carries user id, email, and an expiry, so your server trusts the signature instead of storing passwords. The access-and-refresh pattern splits the job: a short-lived access token makes the API calls, while a long-lived refresh token — kept server-side — silently renews it, so users stay logged in and a stolen access token dies within minutes. SSO extends one login across many services, over modern OAuth2 or legacy XML-based SAML.

Authorization runs on three models. RBAC assigns roles — admin, editor, viewer — each with fixed permissions; it is the default for GitHub repos and dashboards. ABAC evaluates policies over attributes: user department, resource classification, even time of day — flexible but conflict-prone. ACLs attach a permission list to each resource, which is exactly how Google Docs shares one file with Alice-as-viewer and Bob-as-editor.

STEP BY STEP · A REQUEST GETS PAST THE DOOR
  1. The user logs in — authentication verifies identity (password, or a provider like Google).
  2. The server issues a short-lived access token (JWT) plus a long-lived refresh token.
  3. The client sends the access token with every API call; the server validates signature and expiry.
  4. On expiry, the refresh token quietly fetches a new access token — no logout, no drama.
  5. Each request then hits authorization: an RBAC role, ABAC policy, or ACL entry decides allow or deny.
  6. For third parties (Vercel deploying from GitHub), OAuth2 issues a scoped token instead of ever sharing a password.
THREE CASES
TYPICAL

GitHub repository roles — textbook RBAC

A viewer can read, an editor can push code, an admin can delete the repo and manage collaborators. One role label, a fixed bundle of permissions, trivial to reason about at 2 a.m.

COUNTER-INTUITIVE

"Sign in with Google" never trusts an email

OAuth2 hands your app a signed, expiring JWT — you trust the signature, not the address. And when Vercel deploys from your repo, it never sees your password: it holds a scoped token you can revoke. That is the entire genius of delegated authorization.

EDGE CASE

A Google Doc shared per person is an ACL

"Alice: view, Bob: comment" is a permission list attached to one document. Maintaining a million such lists sounds unmaintainable — yet Google runs it at planetary scale. Model choice is an ergonomics-and-scale tradeoff, not a correctness contest.

VISUAL ANALOGY

Authentication is the bouncer checking your ID at the door. Authorization is the color of your wristband — which rooms you can enter. The JWT is the stamp on your hand; RBAC, ABAC, and ACL are the rules the doormen inside apply.

❌ WHAT PEOPLE GET WRONG

"Authentication is security." It is half of step one — a valid login says nothing about permissions. Also: "the token is the policy." A JWT carries identity and claims; RBAC/ABAC/ACL decide what those claims allow. And refresh tokens belong server-side in httpOnly cookies, not in localStorage.

WHY THIS MATTERS

Every endpoint you designed in Module 04 is an open door until this layer decides who walks through — and modern breaches are usually authorization failures, not encryption failures.

MODULE 06 · THE WALLS
06

API security: seven defenses, stacked like a castle

PAUSE · THINK FIRST

Your API is HTTPS-only, requires login, and sits behind a firewall. An attacker still empties a table through the search box. Which wall did they walk through — and which wall was never built?

Encryption protects the road. What protects the query?

CORE EXPLANATION

APIs are doors into your system, and doors get tested — constantly, by robots. Seven techniques cover the seven ways they get tested. Rate limiting caps how many requests a client, IP, or endpoint can make per window — a hundred a minute, say — with a global ceiling on top to absorb botnets; it makes brute force and exhaustion attacks economically pointless. CORS tells browsers which origins may call you: app.yourdomain.com yes, evil.com no. Injection defense stops user input from rewriting your database queries — the classic ' OR 1=1 -- trick dies the moment you use parameterized statements. A web application firewall filters traffic by attack signature before it ever reaches your code. A VPN removes private APIs from the public internet entirely: the admin dashboard only answers from inside the company network.

CSRF protection guards against a subtle betrayal: a malicious site tricking your logged-in browser into sending a forged request that carries your valid cookie. The counter is a CSRF token your page embeds and the server checks — proof the request was born on your site, not merely sent with your credentials. XSS defense handles scripts smuggled into your pages — say, a comment containing JavaScript — that execute in other users' browsers and steal cookies. The cure is encoding output so browsers treat data as data, never as code.

None of these is an optional decoration; they are load-bearing walls, and they work as a stack — because any single unprotected door leaks the whole house.

STEP BY STEP · HARDENING THE PERIMETER
  1. Inventory your doors: every public endpoint, every private one, every input that touches a query or a page.
  2. Clamp volume: per-endpoint, per-user, and global rate limits.
  3. Draw the perimeter: CORS origins for browsers, VPN for internal APIs, a WAF for signature filtering.
  4. Never build queries from strings — parameterize everything, SQL and NoSQL alike.
  5. Pair cookies with CSRF tokens on any state-changing request.
  6. Encode all output and add a Content-Security-Policy so stored scripts stay inert.
THREE CASES
TYPICAL

Rate limiting the login endpoint

The 101st attempt in a minute gets a 429 and a timeout — brute force dies of boredom. The same mechanism with a global ceiling blunts a DDoS: when total traffic crosses the line, you shed load instead of toppling.

COUNTER-INTUITIVE

CSRF uses your own authentication against you

The forged transfer request carries your valid session cookie — so "we authenticate with cookies" is precisely the vulnerability, not the defense. The CSRF token is the only thing that proves the request came from your page.

EDGE CASE

Stored XSS is a time bomb

The attacker's script arrives as an ordinary comment, gets saved by your perfectly-working server, and detonates in the browsers of everyone who later loads the page. Your backend did everything "right"; the failure is that browsers trusted database contents as code. That is why you encode on output, not just validate on input.

VISUAL ANALOGY

Defense in depth is a castle: the moat slows the army (rate limit), the gatehouse inspects visitors (firewall), drawbridge rules decide who crosses (CORS / VPN), IDs get checked inside (auth), letters arrive sealed (parameterized queries), and guards stand in every room (output encoding). No single wall was ever enough.

❌ WHAT PEOPLE GET WRONG

"HTTPS makes us secure." HTTPS encrypts the road, not the castle — injection and XSS ride over TLS all day long. Also: "we sanitize input, so XSS is impossible." Stored XSS demands output encoding; input checks alone will betray you.

WHY THIS MATTERS

One unprotected endpoint leaks the whole user table. Security is not a feature you add; it is a property of the finished system — and the interviewer's favorite final question.
